# AOP 핵심 개념 쉽게 이해하기

### 🏫 상황 설정: 학교 복도 CCTV

> 학교 복도에 CCTV를 설치한다고 상상해보세요.

---

### 🔹 Joinpoint — "CCTV 설치 *가능한* 자리"

복도에는 CCTV를 달 수 있는 자리가 여러 곳 있어요.
- 1번 교실 앞
- 2번 교실 앞
- 화장실 앞
- 급식실 앞
- ...

이 **"달 수 있는 모든 자리"** 가 Joinpoint예요.

> Spring AOP에서는 **메서드 호출 시점**이 유일한 Joinpoint

---

### 🔹 Pointcut — "실제로 CCTV를 *다는* 자리"

설치 가능한 자리는 많지만, 예산이 부족해서 **일부에만** 달아요.
- ✅ 1번 교실 앞 → 설치
- ❌ 2번 교실 앞 → 패스
- ✅ 급식실 앞 → 설치

이 **"실제로 설치하기로 선택한 자리"** 가 Pointcut이에요.

```java
// "findUser로 시작하는 메서드에만 적용해!"
@Pointcut("execution(* findUser*(..))")
```

---

### 🔹 AOP — "CCTV가 찍으면 자동으로 뭔가 일어남"

CCTV 앞을 지나가면 **자동으로** 녹화가 되죠.
선생님이 일일이 지켜보지 않아도요.

이것처럼 AOP는 **내가 따로 코드를 안 짜도**,
특정 메서드가 실행될 때 **자동으로 부가 기능이 붙는 것**이에요.

> 로그 찍기, 시간 측정, 트랜잭션 처리 등

---

### 정리 한 눈에

```
전체 복도        = 프로그램의 모든 메서드
CCTV 달 수 있는 자리  = Joinpoint
실제 CCTV 단 자리    = Pointcut
CCTV가 자동 녹화     = AOP (Advice가 자동 실행)
```

**한 줄 요약**: Joinpoint는 "가능한 모든 곳", Pointcut은 "그 중 내가 고른 곳", AOP는 "거기서 자동으로 뭔가 실행되는 것"

거의 맞아요! 살짝만 다듬으면 완벽해요 😄

---

### CCTV 비유로 완성하기

| 개념 | CCTV 비유 | 실제 의미 |
|------|-----------|-----------|
| **Joinpoint** | CCTV 달 수 있는 자리 | 메서드 실행 시점 |
| **Pointcut** | 실제 CCTV 단 자리 | 적용할 메서드 선택 |
| **Advice** | CCTV가 하는 **동작** (녹화, 감지, 알림) | 실제 부가 로직 코드 |
| **Aspect** | CCTV **설계도** (어디에 달고 + 뭘 할지) | Pointcut + Advice 묶은 클래스 |

---

### 🔹 Advice = "CCTV가 하는 동작"

CCTV 자체가 아니라, CCTV가 **뭘 하는지**예요.
- 누가 지나가기 **전에** 녹화 시작 → `@Before`
- 누가 지나간 **후에** 저장 → `@After`
- 지나가는 **전후 다** 감시 → `@Around`

---

### 🔹 Aspect = "CCTV 설계도 (명세서)"

> "**급식실 앞**(`Pointcut`)에 달고, **앞뒤로 녹화**(`Advice`)해라"

이 두 가지를 **하나로 묶은 설계도**가 Aspect예요.

```java
@Aspect  // 이게 설계도 선언
@Component
public class LoggingAspect {

    @Pointcut("execution(* findUser*(..))")  // 어디에
    public void userPointcut() {}

    @Before("userPointcut()")  // 뭘 할지 (어드바이스)
    public void logBefore() {
        System.out.println("메서드 실행 전 로그!");
    }
}
```


## 프록시

| 레이어 | 프록시 역할 | 예시 |
|---|---|---|
| 네트워크 레벨 | 요청/응답 대리 전달 | Nginx, VPN |
| 애플리케이션 레벨 | 객체 호출 대리 처리 | AOP 프록시, JDK Dynamic Proxy |

Spring AOP => 대리자 패턴

#### 사용하는 이유

**원본 코드 안 건드리기 위해!**
프록시 없이 aop 구현하려면

```java 
❌ 프록시 없이 → 직접 코드 삽입
public User findUser(Long id) {
    log.info("시작");        // 부가 기능
    checkAuth();             // 부가 기능
    long start = System.currentTimeMillis(); // 부가 기능
    
    User user = userRepository.findById(id); // 핵심 로직 딱 한줄
    
    log.info("끝");          // 부가 기능
    log.info("걸린 시간: " + (System.currentTimeMillis() - start)); // 부가 기능
    return user;
}
```

``` java
// ✅ 원본은 핵심 로직만
public User findUser(Long id) {
    return userRepository.findById(id); // 이것만!
}

// 부가 기능은 프록시가 담당
// 한 곳만 수정하면 100개 메서드 전부 적용
```

[ UserServiceProxy ] 가 하는 일:

1. Advice 실행      (@Before → 로그 찍기)
2. 진짜 객체 호출   (userService.findUser() 위임)
3. Advice 실행      (@After → 시간 측정)

1. Spring 컨테이너가 Bean 등록 시점에
   진짜 UserService 대신 UserServiceProxy를 등록

2. @Service, @Controller 가
   UserService를 생성자 주입 요청

3. Spring 컨테이너가 "UserService요? 저한테 있어요!" 하고
   사실 UserServiceProxy를 주입해줌

4. 서비스, 컨트롤러 객체는 프록시인지 모르고 그냥 호출


### Weaving — Advice를 비즈니스 로직에 엮는 시점

> **"언제 Advice를 끼워넣느냐"** 의 3가지 방식


### 런타임 위빙 (RTW) ← Spring 기본

```
원본 .class (Advice 없음)
        ↓ (Spring 실행 중)
프록시 객체 생성 → 호출 시 Advice 실행
```

> 앞서 배운 **프록시 방식**이 바로 이것!
> `.class`도 안 건드리고, 바이트코드도 안 건드림

### 한 눈에 비교

| | 컴파일 타임 | 로딩 타임 | 런타임 |
|--|------------|----------|--------|
| **시점** | 컴파일할 때 | JVM 로딩할 때 | 실행 중 |
| **원본 .class** | 변경됨 | 변경 안됨 | 변경 안됨 |
| **성능** | 가장 빠름 | 중간 | 상대적으로 느림 |
| **Spring 기본?** | ❌ | ❌ | ✅ |
| **필요한 것** | AspectJ 컴파일러 | Java Agent | 프록시 객체 |
