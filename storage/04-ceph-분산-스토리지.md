# Ceph — 분산 스토리지

## 3-1. Ceph


오픈소스 분산 스토리지 시스템입니다. 서버 여러 대에 꽂힌 디스크들을 묶어서 하나의 거대한 저장소처럼 쓰게 해줍니다.

기존 스토리지 장비와 다른 점이 있습니다. 넷앱 같은 전용 스토리지 장비는 그 장비 자체가 스토리지입니다. 용량이 부족하면 더 큰 장비로 바꾸거나 확장 섀시를 답니다. Ceph는 일반 X86 서버에 디스크를 꽂아서 클러스터에 추가하면 용량과 성능이 같이 늘어납니다. 스케일아웃 구조입니다.

구성 요소가 몇 개 있습니다.

OSD는 실제로 데이터를 저장하는 데몬입니다. 디스크 하나당 OSD 하나가 원칙입니다. 디스크가 100개면 OSD가 100개 뜹니다.

MON은 클러스터 지도를 관리합니다. 어느 OSD가 살아 있고 죽었는지, 데이터가 어디 있는지에 대한 지도를 들고 있습니다. 보통 3대 이상 홀수로 둡니다.

MGR은 모니터링과 관리 인터페이스를 담당합니다.

Ceph의 핵심 원리가 CRUSH 알고리즘입니다. 이게 재미있는데, 보통 분산 시스템은 어느 데이터가 어디 있는지 중앙에서 표로 관리합니다. 그런데 데이터가 수억 개가 되면 그 표 자체가 감당이 안 됩니다.

Ceph는 표를 안 만듭니다. 대신 클라이언트가 계산으로 위치를 알아냅니다. 데이터 이름과 클러스터 지도를 넣고 CRUSH 알고리즘을 돌리면 어느 OSD에 저장해야 하는지가 나옵니다. 중앙에 물어볼 필요가 없습니다. 그래서 클러스터가 커져도 중앙 병목이 안 생깁니다.

복제도 중요합니다. Ceph는 데이터를 한 곳에만 두지 않고 보통 3벌을 서로 다른 서버에 저장합니다. 이 3벌을 맡고 있는 OSD 집합을 acting set이라고 합니다.

여기서 쓰기 성능 특성이 나옵니다. Ceph는 acting set 전체가 기록을 끝냈다고 응답해야 클라이언트에게 쓰기 완료를 알려줍니다. 하나라도 늦으면 그만큼 기다립니다. 일관성을 보장하기 위한 설계인데, 대신 복제본 하나가 멀리 있으면 매 쓰기마다 그 거리만큼 손해를 봅니다.

읽기는 다릅니다. primary-affinity 설정으로 어느 복제본에서 읽을지 유도할 수 있어서 가까운 쪽에서 읽게 만들 수 있습니다. 그래서 읽기는 최적화되는데 쓰기는 안 됩니다. 이 비대칭이 제가 장기 최적화에서 컴퓨팅과 스토리지를 같은 DC에 두자고 한 근거입니다.

풀이라는 개념도 있습니다. 논리적으로 나눈 저장 공간입니다. 풀마다 복제 수나 배치 규칙을 다르게 줄 수 있습니다. 성격이 다른 워크로드가 같은 풀을 쓰면 서로 방해하므로, 풀을 분리하는 것이 기본 조치가 됩니다.

PG라는 것도 있는데, 오브젝트와 OSD 사이의 중간 매핑 단위입니다. 오브젝트를 OSD에 직접 매핑하면 오브젝트가 수억 개일 때 관리가 불가능해서, 오브젝트를 먼저 PG에 넣고 PG를 OSD에 매핑하는 2단계로 나눕니다.


## 3-2. Ceph의 세 가지 접근 방식과 RGW


Ceph는 같은 저장소를 세 가지 방법으로 쓸 수 있게 해줍니다.

RBD는 블록 방식입니다. VM에게 이게 네 하드디스크라고 붙여줍니다. OpenStack에서는 Cinder의 백엔드로 씁니다. 이건 블록 계층을 지나갑니다.

CephFS는 파일시스템 방식입니다. 여러 서버가 같은 디렉터리를 동시에 마운트합니다.

RGW가 오브젝트 방식입니다. RADOS Gateway의 약자입니다.

RADOS는 Ceph의 핵심 저장 엔진 이름입니다. Reliable Autonomic Distributed Object Store의 약자인데, 신뢰성 있는 자율 분산 오브젝트 저장소라는 뜻입니다. Ceph의 모든 접근 방식이 결국 이 RADOS 위에 올라갑니다.

게이트웨이라는 말이 붙은 이유는, RADOS는 자체 프로토콜을 쓰는데 그걸 HTTP로 번역해 주는 관문 역할을 하기 때문입니다. 클라이언트가 S3 방식으로 요청을 보내면 RGW가 받아서 RADOS 명령으로 바꿔 처리합니다.

그래서 RGW는 S3 호환입니다. AWS S3용으로 만든 프로그램이 주소만 바꾸면 그대로 동작합니다. 이게 큰 장점입니다. 온프레미스로 옮기면서 애플리케이션 코드를 안 고쳐도 됩니다.

여기서 중요한 성질이 나옵니다. RGW는 HTTP로 접근하기 때문에 트래픽이 네트워크로 나갑니다. 그래서 cgroup의 io.max로는 제한할 수 없고, tc로 네트워크 대역에서 막아야 합니다.


## 3-3. 워크로드


서버가 처리하는 작업 또는 그 작업 덩어리를 뜻합니다. 특정 기술 용어라기보다 일하는 대상을 부르는 말입니다.

이 단어를 왜 쓰냐면, 작업마다 자원을 쓰는 성격이 다르기 때문입니다. 성격이 다르면 배치와 튜닝 방식도 달라져야 합니다.

과제에 나온 두 워크로드를 비교하면 이렇습니다.

서빙 워크로드는 작은 요청을 짧은 지연으로 자주 처리합니다. 24시간 돌고, 응답 시간이 곧 품질입니다. 처리량보다 지연이 중요합니다.

재학습 워크로드는 큰 데이터를 한꺼번에 읽고 씁니다. 정해진 시간 안에만 끝나면 되고 중간에 좀 느려도 상관없습니다. 지연보다 처리량이 중요합니다.

이 둘의 요구가 정반대라는 점이 중요합니다. 요구사항이 다른 워크로드가 같은 자원을 공유하면 한쪽이 다른 쪽을 방해합니다. 그래서 자원 계층에서 갈라놓는 것이 조치가 됩니다.

워크로드를 구분해서 보는 습관이 인프라 설계의 기본이라고 생각합니다. 어떤 워크로드인지에 따라 필요한 스토리지 종류, 네트워크 요구사항, CPU 할당 방식이 다 달라지기 때문입니다.
