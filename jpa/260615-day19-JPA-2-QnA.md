**Q1. `@ManyToOne`과 `@OneToMany` 중 FK(외래키)를 실제로 가지는 쪽은 어디인가?**

<details>
<summary>답 보기</summary>

**`@ManyToOne`이 붙은 쪽(N쪽, 자식)** 이 FK를 가진다.

| 엔티티 | 어노테이션 | 역할 | FK 위치 |
|---|---|---|---|
| Post | `@OneToMany` | 부모(1) | 없음 |
| PostComment | `@ManyToOne` | 자식(N) | `post_id` (자기 테이블) |

DB 관점에서 FK는 항상 "N(여러 개)" 쪽 테이블에 있어야 한다.  
여러 댓글이 같은 `post_id`를 가져야 하기 때문이다.

**한 줄 요약**: `@ManyToOne` = "나는 N이고 FK를 가진 자식"

</details>

---

**Q2. `FetchType.LAZY`와 `FetchType.EAGER`의 차이를 설명하라.**

<details>
<summary>답 보기</summary>

| 구분 | EAGER | LAZY |
|---|---|---|
| 로딩 시점 | 부모 엔티티 조회 **즉시** | 연관 필드를 **실제 사용할 때** |
| 쿼리 | JOIN 또는 추가 쿼리로 즉시 가져옴 | 프록시 객체만 넣어두고, 실제 접근 시 추가 쿼리 발생 |
| 기본값 | `@ManyToOne`, `@OneToOne` | `@OneToMany`, `@ManyToMany` |

**비유**
- EAGER: "택배 시킬 때 옵션 상품까지 한 박스에 넣어서 보내줘" (한 번에 다 받음)
- LAZY: "일단 본품만 보내. 옵션 상품은 필요하면 따로 시킬게" (나중에 별도로 받음)

</details>

---

**Q3. `@OneToMany`와 `@ManyToMany`의 기본 FetchType이 LAZY인 이유는?**

<details>
<summary>답 보기</summary>

연관 엔티티가 **여러 개(컬렉션)** 이기 때문이다.

- `@ManyToOne`, `@OneToOne` → 연관 엔티티가 **1개** → EAGER로 가져와도 비용이 적음
- `@OneToMany`, `@ManyToMany` → 연관 엔티티가 **N개** → 무조건 같이 가져오면 비용이 커짐

예를 들어 `Post` 하나를 조회할 때 댓글 1000개를 항상 같이 가져온다면 큰 낭비가 된다.

</details>

---

**Q4. `CascadeType`이란 무엇이고, 어떤 종류가 있는가?**

<details>
<summary>답 보기</summary>

부모 엔티티에 대한 **영속성 상태 변화를 자식 엔티티에게 전파**할지 결정하는 옵션이다.

| 종류 | 트리거 | 효과 |
|---|---|---|
| `PERSIST` | `em.persist(부모)` | 자식도 함께 `persist()` |
| `MERGE` | `em.merge(부모)` | 자식도 함께 `merge()` |
| `REMOVE` | `em.remove(부모)` | 자식도 함께 DELETE |
| `REFRESH` | `em.refresh(부모)` | 자식도 DB값으로 다시 로딩 |
| `DETACH` | `em.detach(부모)` | 자식도 준영속 상태로 분리 |
| `ALL` | 위 5가지 모두 | 전부 전파 |

</details>

---

**Q5. `orphanRemoval = true`란 무엇인가?**

<details>
<summary>답 보기</summary>

부모의 **컬렉션에서 자식을 제거(`list.remove()`)했을 때**, 그 자식을 DB에서도 자동으로 DELETE하는 옵션이다.

"고아(orphan)" = 부모와의 연결이 끊겨 더 이상 어떤 부모에게도 속하지 않는 자식 엔티티.

```java
post.getComments().remove(0);
// orphanRemoval = true  → 해당 PostComment가 DB에서 DELETE됨
// orphanRemoval = false → 연관관계만 끊김 (FK가 null이 될 수도 있음)
```

</details>

**Q6. 지연 로딩(LAZY)에서 "프록시 객체"란 무엇이고 어떻게 동작하는가?**

<details>
<summary>답 보기</summary>

LAZY 설정 시 Hibernate가 실제 연관 엔티티 대신 넣어두는 **가짜 객체(빈 껍데기)** 다.  
프록시는 `id`만 알고 있으며, 실제 데이터는 비어있다.

```java
Category proxy = item.getCategory();
// 여기까지는 쿼리 없음. proxy.id = 5 만 들어있는 상태

proxy.getName();
// 이 순간 SELECT 쿼리 발생 → 진짜 데이터로 채워짐 (초기화, initialize)
```

프록시는 엔티티를 **상속**받은 자식 클래스 형태로 동작하기 때문에, 엔티티의 기본 생성자가 `protected` 이상이어야 한다.

</details>

**Q7. 일대다(`@OneToMany`) 단방향에서 `@JoinColumn`을 부모 쪽에 쓰면 FK는 어느 테이블에 생기는가? 이 방식의 단점은?**

<details>
<summary>답 보기</summary>

**자식 테이블**에 생긴다. `Post`에 `@JoinColumn(name = "post_id")`를 선언해도, FK 컬럼은 `post_comments` 테이블에 만들어진다.

```
posts 테이블: id, title            (post_id 컬럼 없음)
post_comments 테이블: id, content, post_id  ← FK가 여기 생김
```

**단점 — 불필요한 UPDATE 쿼리 발생:**  
부모가 자식 테이블의 FK를 관리해야 하는데, JPA가 내부적으로 INSERT 후 자식 테이블을 UPDATE하는 쿼리를 추가로 날린다.

```sql
INSERT INTO post_comments ...;
UPDATE post_comments SET post_id=? WHERE id=?;  -- 불필요한 추가 쿼리
```

**권장 대안**: 자식(`PostComment`) 쪽에 `@ManyToOne`을 두고 `mappedBy`로 **양방향 관계**를 맺는 것이 실무에서 일반적이다.

</details>

**Q8. 양방향 연관관계에서 "연관관계의 주인"이란 무엇이고, 누가 주인이 되어야 하는가?**

<details>
<summary>답 보기</summary>

JPA는 양방향 관계에서 **두 엔티티 중 어느 쪽이 FK를 실제로 관리할지** 결정해야 한다.  
이 FK를 실제로 관리하는 쪽을 **연관관계의 주인**이라고 한다.

- **주인** = `@JoinColumn`을 가진 쪽 (FK가 있는 쪽, 자식/N쪽)
- **주인이 아닌 쪽** = `mappedBy` 속성으로 주인을 지정하는 쪽 (부모/1쪽)

**원칙**: FK가 실제로 존재하는 자식 테이블 쪽이 주인이 되어야 한다.

```java
// 주인 (FK 보유, DB에 실제 반영됨)
@ManyToOne
@JoinColumn(name = "order_id")
private Order order;

// 주인이 아닌 쪽 (읽기 전용, DB에 영향 없음)
@OneToMany(mappedBy = "order")
private List<OrderItem> orderItems = new ArrayList<>();
```

</details>

**Q9. 아래 코드에서 `order_id`가 DB에 제대로 저장되지 않는 이유를 설명하라.**

```java
order.getOrderItems().add(orderItem); // (1)
// orderItem.setOrder(order) 호출 없음    (2)
```

<details>
<summary>답 보기</summary>

`OrderItem`이 연관관계의 주인(`@ManyToOne` 보유)이기 때문에, JPA는 **주인 쪽(`OrderItem.order` 필드) 값**을 기준으로 INSERT/UPDATE SQL을 만든다.

`(1)` `order.getOrderItems().add(orderItem)`은 **주인이 아닌 쪽**(`Order`)의 컬렉션을 수정한 것이라 DB에 영향이 없다. 단순 객체 그래프 표현용이다.

`(2)` 주인 쪽인 `orderItem.setOrder(order)`를 호출하지 않았으므로, `OrderItem.order` 필드가 `null`이다. 커밋 시 `order_id`가 `null`로 INSERT된다.

**올바른 코드:**
```java
orderItem.setOrder(order);           // ✅ DB에 order_id 반영됨
order.getOrderItems().add(orderItem); // 객체 그래프 동기화 (옵션이지만 권장)
```

</details>

**Q10. `CascadeType.REMOVE`와 `orphanRemoval = true`의 차이를 트리거 조건 중심으로 설명하라.**

<details>
<summary>답 보기</summary>

| 옵션 | 트리거 조건 | 효과 |
|---|---|---|
| `CascadeType.REMOVE` | **부모 엔티티 자체**가 `em.remove()` 될 때 | 자식 전체가 함께 삭제 |
| `orphanRemoval = true` | 부모의 **컬렉션에서 자식을 제거**할 때 (`list.remove()`) | 그 자식만 DELETE |

```java
// CascadeType.REMOVE만 있는 경우
em.remove(post);              // ✅ comments 전체 삭제됨
post.getComments().remove(0); // ❌ DB에서 안 지워짐

// orphanRemoval = true만 있는 경우
em.remove(post);              // ❌ comments 안 지워짐 (FK null 업데이트 또는 에러)
post.getComments().remove(0); // ✅ 해당 comment DELETE됨
```

**실무에서는 둘을 함께 사용하는 경우가 많다:**
```java
@OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
private List<PostComment> comments = new ArrayList<>();
```

</details>

**Q11. 컬렉션 필드를 왜 빈 리스트로 초기화하는가?**

```java
private List<PostComment> comments = new ArrayList<>();
```

<details>
<summary>답 보기</summary>

**NPE(NullPointerException) 방지**를 위한 관례다.

`comments`를 초기화하지 않으면:
```java
post.getComments().size(); // NullPointerException!
```

생성자에 넣지 않는 이유는 **댓글은 게시글 작성 이후에 생기는 것**이기 때문이다. 생성 시점에 외부에서 받아야 할 필수 정보(`title`)와 달리, `comments`는 "처음엔 비어있다가 나중에 채워지는 것"이므로 필드 선언과 동시에 빈 리스트로 초기화한다.

</details>

**Q12. 실무에서 `@ManyToOne`도 LAZY로 설정하는 걸 권장하는 이유는? EAGER가 N+1 문제를 어떻게 유발하는가?**

<details>
<summary>답 보기</summary>

`@ManyToOne`의 기본값은 EAGER지만, **JPQL로 직접 조회할 때 EAGER 연관 엔티티가 별도 쿼리로 가져와지는 경우**가 많아서 N+1 문제를 더 쉽게 유발한다.

**N+1 문제 예시:**
```java
// Item 목록 10개 조회 (EAGER 상태)
List<Item> items = em.createQuery("select i from Item i", Item.class).getResultList();
// 1번 쿼리: SELECT * FROM items (10건)
// + 10번 쿼리: 각 Item마다 SELECT * FROM categories WHERE id = ? 실행
// 총 11번 쿼리 발생 = 1 + N
```

**권장 패턴:**
```java
@ManyToOne(fetch = FetchType.LAZY) // 실무 권장
private Category category;
```
기본을 LAZY로 두고, 필요한 곳에서만 **fetch join**으로 명시적으로 가져온다.

```java
// fetch join으로 한 번에 가져오기
em.createQuery("select i from Item i join fetch i.category", Item.class)
  .getResultList();
// 1번의 JOIN 쿼리로 해결
```

</details>

**Q13. 아래 코드에서 SELECT 쿼리가 두 번 발생하는 이유를 설명하라.**

```java
Order findOrder = em.find(Order.class, order.getId());        // (1)
findOrder.getOrderItems().get(0).getItemName();               // (2)
```

<details>
<summary>답 보기</summary>

`@OneToMany`의 기본 FetchType은 **LAZY**이기 때문이다.

- **(1)번**: `orders` 테이블만 SELECT. `OrderItem`은 아직 가져오지 않음. `orderItems` 필드에는 프록시(빈 껍데기 컬렉션)가 들어있음.
- **(2)번**: `getOrderItems()`로 컬렉션에 실제 접근하는 순간, Hibernate가 `order_items` 테이블을 SELECT. 이것이 지연 로딩 초기화(initialization)다.

이것이 N+1 문제의 원인이기도 하다. Order를 N개 조회하면 각각의 `getOrderItems()` 접근마다 추가 쿼리가 발생한다.

</details>

**Q14. 양방향 연관관계에서 "연관관계 편의 메서드"를 만드는 이유와, 아래 코드에서 `contains(this)` 체크가 필요한 이유를 설명하라.**

```java
public void setOrder(Order order) {
    this.order = order;
    if (order != null && !order.getOrderItems().contains(this)) {
        order.getOrderItems().add(this);
    }
}
```

<details>
<summary>답 보기</summary>

**편의 메서드가 필요한 이유:**  
양방향 연관관계에서는 주인 쪽(`orderItem.order`)과 반대쪽(`order.orderItems`) 두 곳을 모두 동기화해야 한다.  
따로 관리하면 실수로 한쪽만 업데이트해 객체 그래프와 DB 상태가 불일치하는 버그가 생긴다.  
편의 메서드로 **한 번만 호출하면 양쪽 동기화가 보장**되도록 캡슐화하는 것이다.

**`contains(this)` 체크가 필요한 이유:**  
`setOrder()`를 여러 번 호출하거나 이미 컬렉션에 추가된 상태에서 다시 호출하면, `order.getOrderItems().add(this)`가 중복으로 실행되어 **같은 OrderItem이 컬렉션에 두 번 들어갈 수 있다.**  
`contains(this)`로 이미 들어있는지 확인한 후 추가하여 중복을 방지한다.

</details>

**Q15. 일대다 단방향(`@OneToMany` + `@JoinColumn`)에서 불필요한 UPDATE 쿼리가 발생하는 이유를 설명하고, 이를 해결하는 구조를 제시하라.**

<details>
<summary>답 보기</summary>

**원인:**  
`Post`는 FK(`post_id`)를 **자기 테이블에 갖지 않는다.** 그런데 `Post`가 연관관계를 "관리"하는 주인이다.  
자식을 `persist()`한 시점에는 FK를 채울 수가 없어서(자식 테이블에 INSERT할 때 `post_id`를 모르는 상태), 일단 FK 없이 INSERT한 뒤 나중에 UPDATE로 FK를 채운다.

```sql
INSERT INTO post_comments (id, content) VALUES (?, ?);  -- FK 없이 삽입
UPDATE post_comments SET post_id=? WHERE id=?;          -- FK 나중에 추가
```

**해결 구조 — 양방향 관계로 전환:**  
FK를 실제로 가진 자식 쪽(`PostComment`)에 `@ManyToOne`을 두고, 부모 쪽에 `mappedBy`를 선언하면 불필요한 UPDATE가 사라진다.

```java
// PostComment (자식, 주인)
@ManyToOne
@JoinColumn(name = "post_id")
private Post post;

// Post (부모, 주인 아님)
@OneToMany(mappedBy = "post")
private List<PostComment> comments = new ArrayList<>();
```

`PostComment.post` 값이 세팅된 상태로 INSERT하면 FK가 처음부터 포함된다.

</details>

**Q16. `cascade = CascadeType.ALL`과 `orphanRemoval = true`를 함께 쓰는 것이 적절한 엔티티 설계 상황은? 반대로 쓰면 안 되는 상황은?**

<details>
<summary>답 보기</summary>

**함께 쓰기 적절한 상황:**  
자식 엔티티가 **부모에게만 종속**되어 독립적으로 존재할 수 없을 때.

```java
// Order와 OrderItem — OrderItem은 Order 없이는 의미 없음
@OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
private List<OrderItem> orderItems = new ArrayList<>();
```
- 주문 삭제 시 주문 항목도 같이 삭제 (REMOVE)
- 주문 항목을 주문에서 빼면 DB에서도 삭제 (orphanRemoval)

**쓰면 안 되는 상황:**  
자식 엔티티가 **여러 부모에서 공유**되는 경우.

```java
// Product(상품)는 여러 OrderItem에서 참조됨
// 주문 항목을 삭제했다고 상품 자체가 삭제되면 안 됨!
@ManyToOne
private Product product; // cascade 적용 금지
```

공유되는 엔티티에 `CascadeType.REMOVE`나 `orphanRemoval`을 쓰면 **다른 곳에서도 참조하는 데이터가 삭제**되는 심각한 버그가 발생한다.

**한 줄 기준**: "이 자식이 이 부모 없이 혼자 존재할 수 있는가?" → 아니오 = cascade + orphanRemoval 가능, 예 = 사용 주의.

</details>

**Q17. `mappedBy`를 설정하지 않은 양방향 관계(`@OneToMany` + `@ManyToOne` 양쪽에 `@JoinColumn` 설정)에서는 어떤 문제가 발생하는가?**

<details>
<summary>답 보기</summary>

JPA가 두 연관관계를 **독립적인 두 개의 단방향 관계**로 인식하여 **중간 테이블**을 생성하거나, 각각 FK를 따로 관리하려다 충돌이 발생한다.

예를 들어 `Post`와 `PostComment`에 모두 `@JoinColumn`이 있으면:
- `post_comments.post_id` (PostComment → Post FK)
- `posts.comment_id` (Post → PostComment FK, 이상한 구조)

가 함께 만들어지거나, 동일한 FK를 두 군데서 각자 업데이트하려다 데이터 불일치가 생긴다.

**올바른 구조:**
```java
// 주인 (FK 보유) — @JoinColumn 사용
@ManyToOne
@JoinColumn(name = "post_id")
private Post post;

// 주인이 아닌 쪽 — mappedBy로 주인 지정 (DB에 영향 없음)
@OneToMany(mappedBy = "post")
private List<PostComment> comments = new ArrayList<>();
```

`mappedBy`는 "이 컬렉션은 실제 FK를 관리하지 않고, 상대방의 `post` 필드가 주인이야"라고 선언하는 것이다.

</details>

**Q18. N+1 문제란 무엇인가? LAZY 로딩이 N+1 문제의 원인이 되는 메커니즘을 설명하라.**

<details>
<summary>답 보기</summary>

**N+1 문제**: 1번의 쿼리로 N개의 엔티티를 가져왔을 때, 각 엔티티의 연관 엔티티를 로딩하기 위해 **추가로 N번의 쿼리가 발생**하는 현상.

```java
// Order 10개 조회 (1번 쿼리)
List<Order> orders = orderRepository.findAll();

// 각 Order의 Member 정보에 접근 (Order마다 1번씩, 총 10번 쿼리)
for (Order order : orders) {
    System.out.println(order.getMember().getName()); // 여기서 쿼리 발생
}
// 총 1 + 10 = 11번 쿼리 실행
```

**메커니즘:**  
LAZY로 설정된 연관 필드는 실제 접근 전까지 프록시로 유지된다. 루프에서 각 엔티티의 연관 필드에 접근할 때마다 프록시가 초기화되며 SELECT가 발생한다.

**해결 방법:**
1. **fetch join**: `select o from Order o join fetch o.member` — 1번의 JOIN 쿼리로 해결
2. **`@EntityGraph`**: Spring Data JPA에서 fetch join을 편리하게 적용
3. **batch size**: `@BatchSize`로 IN 절을 이용한 일괄 로딩

</details>

**Q19. 아래 두 코드의 차이를 설명하라. 어느 쪽이 올바른 양방향 연관관계 설정인가?**

```java
// (A)
order.getOrderItems().add(orderItem);

// (B)
orderItem.setOrder(order);
```

<details>
<summary>답 보기</summary>

**DB 반영 여부가 다르다.**

**(A)** `order.getOrderItems().add(orderItem)`:  
`Order`는 연관관계의 주인이 **아닌** 쪽(`mappedBy` 쪽)이다. 이 컬렉션 조작은 **DB에 영향을 주지 않는다.** 객체 그래프상에서만 연결된 것처럼 보이지만, 실제 `OrderItem.order_id` 컬럼은 변하지 않는다.

**(B)** `orderItem.setOrder(order)`:  
`OrderItem`이 FK(`order_id`)를 가진 연관관계의 **주인**이다. 이 값이 JPA INSERT/UPDATE SQL에 반영되어 DB의 `order_id` 컬럼이 실제로 채워진다.

**올바른 방법**: **(B)를 반드시 호출해야 DB에 반영된다.** 실무에서는 연관관계 편의 메서드를 만들어 (A)와 (B)를 동시에 처리해 객체 그래프와 DB 상태를 항상 일치시킨다.

```java
// 편의 메서드 — 한 번만 호출하면 양쪽 동기화
orderItem.setOrder(order); // (B) + 내부에서 (A)도 실행
```

</details>

**Q20. "쓰기 지연 저장소(write-behind)"와 "지연 로딩(lazy loading)"은 같은 메커니즘인가? 차이를 설명하라.**

<details>
<summary>답 보기</summary>

**아니다. 둘은 완전히 다른 메커니즘이고, 이름만 비슷할 뿐이다.**

| 구분 | 쓰기 지연 저장소 (write-behind) | 지연 로딩 (lazy loading) |
|---|---|---|
| 대상 | **쓰기** SQL (INSERT/UPDATE/DELETE) | **읽기** SQL (SELECT) |
| 목적 | SQL을 모아뒀다가 flush 시점에 한꺼번에 전송 (배치 처리 최적화 + 롤백 용이) | 연관 엔티티를 즉시 조회하지 않고 실제 접근 시점에 SELECT |
| 동작 원리 | 쓰기 SQL을 큐(쓰기 지연 저장소)에 쌓아두다가 `flush()`/`commit()` 시 DB로 전송 | 프록시 객체를 넣어두다가 실제 필드 접근 시 SELECT 쿼리 발생 |
| 제어 위치 | 영속성 컨텍스트 내부 | 연관관계 설정 (`fetch = FetchType.LAZY`) |

```java
// 쓰기 지연 — persist()해도 flush 전까지 INSERT가 DB에 안 나감
em.persist(product1); // INSERT가 쓰기 지연 저장소에 쌓임
em.persist(product2); // 또 쌓임
tx.commit();          // 이때 flush → INSERT 2개가 한꺼번에 나감

// 지연 로딩 — 필드에 접근하기 전까지 SELECT가 안 나감
Item item = em.find(Item.class, 1L);   // items 테이블만 SELECT
item.getCategory().getName();          // 이 순간 categories 테이블 SELECT
```

**공통점**: 둘 다 "어떤 동작을 미룬다"는 컨셉은 같다.  
**핵심 차이**: 쓰기 지연은 "쓰기 SQL을 **언제 보낼지**"의 문제, 지연 로딩은 "읽기 SQL을 **언제 날릴지**"의 문제다.

</details>

**Q21. 아래 클래스 설계의 문제점을 찾고, 올바른 설계로 수정하라.**



```java
@Entity
public class Post {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;

    @OneToMany
    @JoinColumn(name = "post_id")
    private List<PostComment> comments = new ArrayList<>();
}

@Entity
public class PostComment {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String content;
    // Post에 대한 참조 없음
}
```

<details>
<summary>답 보기</summary>

**문제점:**  
일대다 **단방향** 구조로, `Post` 쪽에 `@JoinColumn`이 있어 내부적으로 INSERT 후 UPDATE 쿼리가 추가로 발생한다.

**올바른 설계 — 양방향으로 전환:**

```java
@Entity
public class Post {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;

    // mappedBy: "PostComment의 post 필드가 주인"임을 선언
    @OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<PostComment> comments = new ArrayList<>();

    public Post(String title) {
        this.title = title;
    }

    // 연관관계 편의 메서드
    public void addComment(PostComment comment) {
        comments.add(comment);
        comment.setPost(this);
    }
}

@Entity
public class PostComment {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String content;

    // 주인: FK(post_id)를 실제로 보유
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "post_id")
    private Post post;

    public PostComment(String content) {
        this.content = content;
    }

    public void setPost(Post post) {
        this.post = post;
    }
}
```

**개선 포인트:**
1. FK 주인을 `PostComment` 쪽으로 이동 → 불필요한 UPDATE 제거
2. `@ManyToOne(fetch = FetchType.LAZY)` → N+1 문제 예방
3. `cascade = ALL` + `orphanRemoval = true` → 댓글 생명주기를 게시글에 종속
4. 연관관계 편의 메서드(`addComment`) → 양쪽 동기화 보장

</details>
