# 연관관계 매핑

## 외래키 -> 자식이 부모를 찾아갈 수 있도록!

`@ManyToOne`을 붙이는 쪽이 항상 **자식(N쪽)**이고, FK를 가지는 쪽이에요.

생각해보면 당연해요. "여러 개의 PostComment가 하나의 Post를 가리킨다" = `PostComment` 입장에서 보면 "나(Many)는 하나의 Post(One)에 속한다"가 되죠. 그래서 `PostComment`에 `@ManyToOne`이 붙고, FK 컬럼(`post_id`)도 `PostComment` 테이블(자식 테이블)에 생깁니다.

반대로 `@OneToMany`가 붙는 쪽(`Post`)은 "하나의 내가 여러 개의 자식을 가진다"는 부모(1쪽)이고, 자기 테이블에는 FK가 없어요.

정리:
| | 어노테이션 | 역할 | FK 위치 |
|---|---|---|---|
| Post | `@OneToMany` | 부모(1) | 없음 |
| PostComment | `@ManyToOne` | 자식(N) | `post_id` (자기 테이블) |

DB 관점에서 FK는 항상 "N(여러개)" 쪽 테이블에 있어야 하잖아요 (여러 댓글이 같은 post_id를 가질 수 있어야 하니까). 그래서 `@ManyToOne`이 붙는 쪽 = FK 보유 = 자식, 이라는 매핑은 항상 성립합니다.

한 줄 요약: `@ManyToOne`은 "나는 N이고 FK를 가진 자식"이라는 뜻이라서 항상 자식 쪽에 붙는다.

# 다대일 단방향

## 왜 LAZY는 처음에 Category를 같이 조회하지 않을까?

기술적으로 못 하는 게 아니라, `FetchType.LAZY`로 **설정했기 때문에 Hibernate가 일부러 안 가져오는 거야.**

```java
@ManyToOne(fetch = FetchType.LAZY) // "필요할 때까지 가져오지 마"
private Category category;
```

이건 개발자가 Hibernate한테 이렇게 지시한 것:

> "Item을 조회할 때, category 정보는 일단 가져오지 마. 진짜로 `getCategory().getName()` 같은 걸 호출해서 데이터가 필요해지면 그때 가서 가져와."

**그럼 EAGER였으면?**

```java
@ManyToOne(fetch = FetchType.EAGER)
private Category category;
```

이러면 Hibernate한테:

> "Item 조회할 때 category도 무조건 같이 가져와. (보통 JOIN으로)"

라고 지시한 거야.

**비유**

- **EAGER** = "택배 시킬 때 옵션 상품까지 같이 한 박스에 넣어서 보내줘" (한 번에 다 받음)
- **LAZY** = "일단 본품만 보내. 옵션 상품은 필요하면 따로 시킬게" (나중에 별도로 받음)

둘 다 "할 수 있긴" 한데, **언제 가져올지를 설정으로 미리 정해놓은 것**이고, LAZY는 "지금 안 가져온다"는 전략적 선택이야.

**핵심**

- `em.find(Item.class, id)` 자체는 `items` 테이블만 조회하는 게 정상 동작 (Category는 별도 테이블이니까)
- LAZY는 "이 시점에 category까지 같이 가져올 필요 없다"는 **최적화 설정**
- 정말로 필요해지는 시점(`getName()` 호출)에 가서야 추가 쿼리로 가져옴

**한 줄 요약**: SELECT를 "못하는" 게 아니라, LAZY 설정 때문에 Hibernate가 "지금은 필요 없으니 나중에 가져온다"고 의도적으로 지연시키는 거야.

## 핵심 차이: 연관 엔티티를 "언제" 로딩하느냐

|           | EAGER                             | LAZY                                                       |
| --------- | --------------------------------- | ---------------------------------------------------------- |
| 로딩 시점 | 부모 엔티티 조회 **즉시**         | 연관 필드를 **실제 사용할 때** (`getCategory()` 호출 시점) |
| 쿼리      | JOIN 또는 추가 쿼리로 즉시 가져옴 | 프록시 객체만 채워두고, 실제 접근 시 추가 쿼리 발생        |
| 기본값    | `@ManyToOne`, `@OneToOne`         | `@OneToMany`, `@ManyToMany`                                |

**예시**

```java
@ManyToOne(fetch = FetchType.EAGER) // 기본값
private Category category;
```

```java
Item item = itemRepository.findById(1L).get();
// EAGER: 이 시점에 Category까지 같이 SELECT (또는 JOIN) 됨

// vs LAZY
Item item = itemRepository.findById(1L).get();
// 이 시점엔 category 자리에 프록시(가짜 객체)만 들어있음

item.getCategory().getName();
// LAZY일 때 이 시점에 SELECT * FROM categories WHERE id = ? 실행
```

**LAZY의 동작 원리**

LAZY로 설정하면 Hibernate는 실제 Category 대신 **프록시 객체**를 넣어둠. 이 프록시는 `id`만 알고 있는 빈 껍데기야. `getName()` 같은 메서드를 호출하는 순간 진짜 DB 쿼리를 날려서 데이터를 채움 (이걸 **초기화(initialize)** 라고 함).

```java
Category proxy = item.getCategory();
// 여기까지는 쿼리 없음. proxy.id = 5 만 들어있는 상태

proxy.getName();
// 이 순간 SELECT 쿼리 발생 → 진짜 데이터로 채워짐
```

**왜 기본값이 다른가?**

- `@ManyToOne`, `@OneToOne` → 연관 엔티티가 **1개**이므로 EAGER로 가져와도 비용이 적음 → 기본 EAGER
- `@OneToMany`, `@ManyToMany` → 연관 엔티티가 **여러 개(컬렉션)** 라서 무조건 같이 가져오면 비용이 커짐 → 기본 LAZY

**주의할 점: EAGER의 함정**

EAGER가 항상 JOIN으로 한 번에 가져오는 건 아니야. JPQL로 직접 조회하면 EAGER 연관 엔티티는 **별도 쿼리**로 가져오는 경우가 많아서, 오히려 N+1 문제를 더 쉽게 유발함. 그래서 실무에서는 **`@ManyToOne`도 LAZY로 설정**하고, 필요한 곳에서만 fetch join으로 명시적으로 가져오는 패턴을 권장해.

```java
@ManyToOne(fetch = FetchType.LAZY) // 실무 권장
private Category category;
```

**한 줄 요약**: EAGER는 조회 즉시 연관 엔티티를 가져오고 LAZY는 실제 사용 시점에 프록시를 통해 가져오는데, EAGER가 오히려 N+1을 유발하기 쉬워서 실무에서는 `@ManyToOne`도 LAZY로 설정하는 게 권장돼.

# SELECT가 두 번 일어나는 이유 — 지연 로딩(Lazy Loading)

```
// 83번째 줄: Order만 SELECT (1번째 쿼리)
Order findOrder = em.find(Order.class, order.getId());

// 84번째 줄: getOrderItems()에 실제로 접근하는 순간 OrderItem SELECT (2번째 쿼리)
findOrder.getOrderItems().get(0).getItemName();
```

@OneToMany는 기본값이 FetchType.LAZY 입니다. 즉 Order를 조회할 때 OrderItem을 바로 가져오지 않고, getOrderItems()를 실제로 사용하는 순간에 SQL을 날립니다. 이걸 N+1 문제의 원인이기도 한 지연 로딩이라고 합니다.

즉시 로딩(EAGER)으로 바꾸면 JOIN으로 한 번에 가져오지만, 일반적으로 LAZY가 권장됩니다.

# 일대다 단방향

```
public class Post {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  private String title;

  @OneToMany
  @JoinColumn(name = "post_id") // Post가 아닌 PostComment 자식 테이블에 생성할 외래키 칼럼명을 작성 - manytoone때와 달리 내 테이블이 아니라 자식에 생김
  private List<PostComment> comments = new ArrayList<>(); // 게시글이 만들어지기 전에 댓글이 먼저 달릴 수 없으니 빈값으로만 만들어놓기

  public Post(String title) {
    this.title = title;
  }
```

`@JoinColumn`에 적힌 `post_id`는 **Post 테이블이 아니라 PostComment 테이블에 생기는 외래키 컬럼**이라는 뜻이에요.

`@ManyToOne`일 때는 외래키가 내 엔티티(주인 쪽) 테이블에 생기죠. 예를 들어 `PostComment`에 `@ManyToOne @JoinColumn(name="post_id")`이 있으면, `post_id` 컬럼은 `PostComment` 테이블 자체에 생깁니다.

근데 `@OneToMany`는 반대예요. "1쪽"인 `Post` 입장에서 `@JoinColumn`을 쓰면, Post 테이블에 뭔가 생기는 게 아니라 — JPA가 대신 자식 테이블(`PostComment`)에 `post_id`라는 외래키 컬럼을 만들고, 그걸로 연관관계를 관리합니다.

즉:

```
posts 테이블: id, title  (post_id 컬럼 없음)

post_comments 테이블: id, content, ... , post_id (FK)  ← 여기 생김
```

`Post`는 FK를 갖지 않으면서도, FK를 통해 자식들을 조회/관리하는 구조가 되는 거예요.

**참고**: 이 방식(단방향 `@OneToMany` + `@JoinColumn`)은 사실 비효율적이에요. 내부적으로 INSERT 후 UPDATE 쿼리가 추가로 나가는 문제가 있어서, 실무에서는 `PostComment` 쪽에 `@ManyToOne`을 두고 `mappedBy`로 양방향 관계를 만드는 게 일반적입니다.

### 왜 리스트는 빈값으로 초기화하나?

생성자 매개변수 = "객체를 만들 때 외부에서 반드시 받아야 하는 필수 정보" (title)
빈 컬렉션 초기화 = "객체 생성 시점엔 비어있지만, 나중에 채워질 수 있는 것"을 NPE 없이 안전하게 다루기 위한 관례

한 줄 요약: 댓글은 게시글 작성 이후에 생기는 거라 생성자엔 없고, NPE 방지를 위해 필드에서 빈 리스트로 미리 초기화해두는 것.

### 일대다 단방향의 특징 \*\*

    부모 엔티티가 자식 엔티티의 FK값을 바꾸기 위해 UPDATE 쿼리를 추가로 날림

> update post_comments set post_id=? where id=?
>
> > 불필요한 쿼리가 날라감

# 양방향

> (결론) @JoinColumn은 FK가 실제로 존재하는 곳에 만들자!

> 양방향 연관관계의 주인 = 외래키를 가진 자식 테이블이 조인컬럼을 가지도록 하자!

## setOrder()
단, Lombok `@Getter`만 있고 `@Setter`가 없다면 직접 setter를 만들어줘야 합니다.

여기서 중요한 건 **양방향 연관관계에서 연관관계의 주인(FK를 가진 쪽)만 DB에 실제로 반영된다**는 점이에요.

```java
// OrderItem이 연관관계의 주인
orderItem.setOrder(order); // 이게 실제 order_id 컬럼에 영향을 줌

// Order 쪽에서 컬렉션에 추가하는 건
order.getOrderItems().add(orderItem); // DB에는 영향 없음 (단순 객체 그래프 표현용)
```

`order.getOrderItems().add(orderItem)`만 하고 `orderItem.setOrder(order)`를 안 하면, `OrderItem` 테이블의 `order_id`는 `null`로 들어갑니다. JPA는 주인 쪽(`OrderItem.order` 필드) 값을 기준으로 INSERT/UPDATE SQL을 만들기 때문이에요.

그래서 보통 실무에서는 **연관관계 편의 메서드**를 만들어서 양쪽을 동시에 맞춰줍니다:

```java
public class OrderItem {
    private Order order;

    public void setOrder(Order order) {
        this.order = order;
        if (order != null && !order.getOrderItems().contains(this)) {
            order.getOrderItems().add(this);
        }
    }
}
```

이렇게 하면 `orderItem.setOrder(order)` 한 번만 호출해도 양쪽 객체 그래프와 DB 매핑이 다 일치하게 돼요.

한 줄 요약: `setOrder()`는 사용 가능하고, 오히려 양방향에서는 주인 쪽 setter를 호출해야 DB에 FK가 제대로 저장된다.

# CascadeType 종류와 비교

`CascadeType`은 부모 엔티티에 대한 영속성 상태 변화를 자식 엔티티에게 전파(propagation)할지 결정하는 옵션입니다. `@OneToMany(cascade = ...)` 같은 곳에 설정합니다.

## 1. PERSIST
부모를 `persist()`(저장)할 때, 자식도 함께 `persist()` 됩니다.

```java
em.persist(post);
// post.getComments()에 들어있는 PostComment들도 자동으로 INSERT
```

## 2. MERGE
부모를 `merge()`(준영속 → 영속 병합)할 때, 자식도 함께 `merge()` 됩니다.

## 3. REMOVE
부모를 `remove()`(삭제)할 때, 자식도 함께 DELETE됩니다.

```java
em.remove(post);
// post의 모든 comments도 DELETE됨
```

## 4. REFRESH
부모를 `refresh()`(DB값으로 다시 로딩)할 때, 자식도 함께 refresh됩니다.

## 5. DETACH
부모를 영속성 컨텍스트에서 `detach()`할 때, 자식도 함께 detach됩니다.

## 6. ALL
위 5가지(PERSIST, MERGE, REMOVE, REFRESH, DETACH) 전부를 적용. `CascadeType.ALL`로 한 번에 설정.

# 고아 객체 자동 삭제 (orphanRemoval)

`CascadeType`과는 **별개의 옵션**입니다. 컬렉션에서 자식을 제거(`remove`)했을 때, 그 자식을 DB에서도 자동으로 DELETE할지 결정합니다.

```java
@OneToMany(mappedBy = "post", orphanRemoval = true)
private List<PostComment> comments = new ArrayList<>();
```

```java
post.getComments().remove(0); // 리스트에서 제거
// orphanRemoval = true면 → 해당 PostComment가 DB에서 DELETE됨
// orphanRemoval = false(기본값)면 → 그냥 연관관계만 끊김 (FK가 null이 될 수도)
```

"고아(orphan)" = 부모와의 연결이 끊겨서 더 이상 어떤 부모에게도 속하지 않는 자식 엔티티를 의미합니다.

---

# 비교 표

| 옵션 | 트리거 시점 | 효과 |
|---|---|---|
| `CascadeType.REMOVE` | **부모 엔티티 자체**가 `remove()`될 때 | 자식 전체가 함께 삭제됨 |
| `orphanRemoval = true` | 부모의 **컬렉션에서 자식을 제거**할 때 (`list.remove()`) | 그 자식만 DELETE됨 |

둘 다 자식을 "삭제"한다는 결과는 같지만, **트리거되는 조건이 다릅니다**.

```java
// CascadeType.REMOVE만 있는 경우
em.remove(post); // ✅ comments 다 같이 삭제됨

post.getComments().remove(0); // ❌ DB에서 안 지워짐 (FK만 끊김 시도)

// orphanRemoval = true만 있는 경우
em.remove(post); // ❌ comments는 안 지워짐 (post_id가 null로 업데이트되거나 에러)

post.getComments().remove(0); // ✅ 해당 comment DELETE됨
```

실무에서는 보통 **두 개를 같이 씀**:

```java
@OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
private List<PostComment> comments = new ArrayList<>();
```

이렇게 하면 "부모 삭제 시 자식도 삭제" + "컬렉션에서 자식 빼면 그 자식도 삭제"가 모두 보장됩니다.

한 줄 요약: `CascadeType.REMOVE`는 부모가 삭제될 때 자식도 삭제, `orphanRemoval`은 자식이 부모 컬렉션에서 빠질 때(고아가 될 때) 자식이 삭제 — 둘은 트리거 조건이 다른 별개 옵션.

# o1_0이 뭔지 — Hibernate 6의 자동 생성 테이블 별칭(alias)

```
from orders o1_0        -- o = orders 앞글자, 1_0 = 첫 번째 등장
from order_items oi1_0  -- oi = order_items 앞 두 글자, 1_0 = 첫 번째 등장
```
SQL의 AS 별칭과 같은 개념입니다. Hibernate 6(Spring Boot 3+)부터 쿼리 내에서 테이블을 참조하기 위해 자동 생성하는 별칭이고, 기능적으로는 아무 의미 없습니다. 이전 Hibernate 5에서는 orders orders0_ 같은 형태였는데 6에서 포맷이 바뀌었습니다.

## JPA Cascade 타입 비교

### 핵심 차이 한 줄 요약

| | `CascadeType.PERSIST` | `CascadeType.ALL` |
|---|---|---|
| 범위 | 저장할 때만 전파 | **모든 작업** 전파 |
| 포함 연산 | PERSIST | PERSIST + MERGE + REMOVE + REFRESH + DETACH |

---

### CascadeType 종류

```
ALL = PERSIST + MERGE + REMOVE + REFRESH + DETACH
```

| 타입 | 전파되는 시점 |
|---|---|
| `PERSIST` | `em.persist()` 호출 시 |
| `MERGE` | `em.merge()` 호출 시 |
| `REMOVE` | `em.remove()` 호출 시 → **부모 삭제 시 자식도 삭제** |
| `REFRESH` | `em.refresh()` 호출 시 |
| `DETACH` | `em.detach()` 호출 시 |

### 실전 예시

```java
@Entity
public class Order {

    @OneToMany(mappedBy = "order", cascade = CascadeType.PERSIST)
    private List<OrderItem> items;
}
```

```java
Order order = new Order();
OrderItem item = new OrderItem();
order.getItems().add(item);

em.persist(order);
// ✅ item도 자동으로 persist됨

em.remove(order);
// ❌ item은 삭제 안 됨! (REMOVE가 없으니까)
```

```java
@OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
private List<OrderItem> items;

em.remove(order);
// ✅ item도 같이 삭제됨
```

---

### 언제 뭘 써야 할까?

**`CascadeType.PERSIST`만 쓰는 경우**
- 자식 엔티티를 부모와 함께 저장하고 싶지만,
- 부모 삭제 시 자식은 **남겨두고 싶을 때**
- 예: `User` 삭제해도 `Post`는 남겨야 할 때

**`CascadeType.ALL` 쓰는 경우**
- 자식이 부모 없이 **독립적으로 존재할 이유가 없을 때**
- 예: `Order` 삭제하면 `OrderItem`도 의미 없을 때
- **생명주기가 완전히 종속된 관계**에서만 사용

---

### ⚠️ `ALL` 남용 주의

```java
// 위험한 예시
@ManyToMany(cascade = CascadeType.ALL)  // ❌
private List<Tag> tags;

// Tag는 여러 Post에서 공유되는데
// 한 Post 삭제 시 Tag까지 날아감!
```

> **공유되는 엔티티**에 `ALL` 또는 `REMOVE` 걸면 의도치 않은 데이터 삭제 발생 → 독립적 생명주기를 가진 관계에서는 `PERSIST`나 `MERGE`만 선택적으로 쓸 것

---

**한 줄 요약**: `PERSIST`는 "같이 저장만", `ALL`은 "모든 걸 같이" — 자식이 부모에게 **완전히 종속된 관계**일 때만 `ALL` 사용 🎯
