# 표준에 없는 이상 현상 — Lost Update · Write Skew

ANSI 표준 3종은 불완전하다는 비판이 유명합니다 (Berenson et al., *A Critique of ANSI SQL Isolation Levels*, 1995). 실무에서는 오히려 아래가 더 자주 터집니다.

## 6.1 Lost Update (갱신 손실)

```
T1: SELECT stock FROM item WHERE id=1;      -- 10
T2: SELECT stock FROM item WHERE id=1;      -- 10
T1: UPDATE item SET stock = 9 WHERE id=1; COMMIT;
T2: UPDATE item SET stock = 9 WHERE id=1; COMMIT;   -- 2개 팔렸는데 재고는 1 감소
```

**REPEATABLE READ로도 막히지 않습니다.** 스냅샷은 "읽기"를 보호할 뿐, "읽은 값으로 계산해서 쓰기"라는 **애플리케이션 로직의 논리적 공백**은 보호하지 못하기 때문입니다.

**해결책 3가지**

```sql
-- 1. 비관적 락: 읽을 때부터 잠근다
SELECT stock FROM item WHERE id=1 FOR UPDATE;

-- 2. 원자적 갱신: 읽지 말고 DB에게 계산시킨다
UPDATE item SET stock = stock - 1 WHERE id=1 AND stock > 0;
```

```java
// 3. 낙관적 락 (JPA)
@Version
private Long version;
```

재고, 포인트, 좌석 예약, 쿠폰 발급 도메인에서는 격리 수준과 **별개로** 반드시 다뤄야 합니다.

## 6.2 Write Skew (쓰기 편향)

두 트랜잭션이 **서로 다른 행을 읽고 서로 다른 행을 쓰는데**, 합쳐놓으면 비즈니스 제약이 깨지는 현상입니다.

```
규칙: 당직자는 최소 1명. 현재 A, B 두 명 당직 중.

T1(A): SELECT COUNT(*) WHERE on_call = true;  -- 2명, "나 빠져도 되네"
T2(B): SELECT COUNT(*) WHERE on_call = true;  -- 2명, "나 빠져도 되네"
T1: UPDATE staff SET on_call = false WHERE id = A; COMMIT;
T2: UPDATE staff SET on_call = false WHERE id = B; COMMIT;
→ 당직자 0명
```

각자 다른 행을 수정했으므로 락도 충돌하지 않고 MVCC도 문제를 못 느낍니다. **스냅샷 격리의 근본적 한계**이며, `SERIALIZABLE`이거나 판단 근거가 된 범위 전체를 명시적으로 잠가야 합니다.
