# **PK 조회가 가장 빠른 이유**



PK에는 자동으로 B+Tree 인덱스가 생성됩니다.

&nbsp;                \*\*← Root 노드\*\*

                 \*\*/       \\\\\*\*

           \*\*\\\[ 25 ]        \\\[ 75 ]           ← Branch 노드\*\*

          \*\*/     \\\\        /     \\\\\*\*

       \*\*\\\[10,20] \\\[30,40] \\\[60,70] \\\[80,90]    ← Leaf 노드\*\*






**탐색 방식**



찾으려는 값과 노드의 값을 비교

작으면 왼쪽, 크면 오른쪽으로 이동

반복하면 Leaf 노드 도달 → 데이터 위치 확인



**왜 PK가 특히 더 빠른가?**

일반 인덱스 vs PK 인덱스의 차이가 있습니다.

**일반 인덱스 조회 (2단계)**

① B+Tree로 인덱스 탐색 → 해당 행의 PK값 획득

② PK값으로 실제 데이터 다시 탐색  ← 추가 작업 발생!

---

① emp\_name 인덱스 B+Tree 탐색 → "한지민" 찾음 → PK(emp\_id) 획득

② emp\_id로 실제 테이블(디스크) 다시 접근 → 나머지 데이터 가져옴



**PK 인덱스 조회 (1단계) — 클러스터링 인덱스**

① B+Tree로 탐색 → Leaf 노드에 실제 데이터가 바로 있음! ✅



---



\[ emp\_name 인덱스 Leaf 노드 ]



  "한지민"  →  emp\_id: 1023   ← PK값이 이미 여기 있음!

  "홍길동"  →  emp\_id: 1045

  "김철수"  →  emp\_id: 1067



PK는 클러스터링 인덱스라서 Leaf 노드 자체에 실제 데이터가 저장됩니다.

일반 인덱스처럼 "주소를 찾고 → 다시 찾아가는" 2번의 과정이 없습니다.

## **WHERE VS HAVING 절**

WHERE 절 = 통계함수 이외의 조건 = 그룹화하기 전

HAVING 절 = 통계함수를 이용한 조건= 그룹화 후





SELECT category, COUNT(\*) AS product\_count

FROM tbl\_product

GROUP BY category

HAVING COUNT(\*) <= 2; -- 또는 HAVING product\_count <= 2;



여기서 HAVING 절에서 별명을 원래 못씀

MYSQL에서는 되는데, 표준 SQL에서는 실행 순서상 안됨~



**만약 두 절 모두에서 처리 가능한 조건이라면 어느 절에서 처리하는 것이 성능 향상에 도움이 될까요?**

WHERE절!

WHERE 절이 먼저 실행되기 때문에 **모수를 줄이는게** 좋음~



count(\*)  -- 모든 칼럼 중 어느 한 칼럼이라도 값을 가지고 있으면 count에 포함해줌



```sql

SELECT \\\* FROM tbl\\\_product ORDER BY amount, price DESC;
```

# **안에 있는 SELECT는 서브 쿼리**



**SELECT 절 뒤에 SELECT 오면 = 스칼라 (값)**



**FROM 절 뒤에 SELECT 오면 = 인라인 뷰 (테이블 자리)**



**WHERE 절 뒤에 SELECT 오면 = 중첩 서브쿼리 ( 칼럼 = 값 , 칼럼 IN (값1, 값2) )**

**> 단일행 서브쿼리 = 결과가 하나**

**> 다중행 서브 쿼리 = 결과가 두개**



**---**
