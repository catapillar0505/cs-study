# 1. MySQL 아키텍처와 스토리지 엔진

## 1.1 기초 — MySQL은 2계층 구조다

Oracle이나 PostgreSQL에는 "스토리지 엔진을 고른다"는 개념이 없습니다. 이것은 **MySQL 고유의 아키텍처 특징**입니다.

```
┌─────────────────────────────────────────┐
│  MySQL 엔진 (Server Layer)               │
│  - 커넥션 관리 / 인증                     │
│  - SQL 파서 (문법 검사, 구문 트리 생성)     │
│  - 옵티마이저 (실행 계획 수립)              │
└─────────────────────────────────────────┘
                  ↕  Handler API
┌─────────────────────────────────────────┐
│  스토리지 엔진 (Storage Engine Layer)     │
│  InnoDB │ MyISAM │ MEMORY │ CSV │ ...   │
│  - 실제 디스크 읽기/쓰기                   │
│  - 인덱스 구조 관리                        │
│  - 락, 트랜잭션, 복구                     │
└─────────────────────────────────────────┘
```

**윗층은 "무엇을 할지"를 정하고, 아랫층은 "실제로 어떻게 데이터를 다룰지"를 담당합니다.**

두 층은 `Handler API`라는 규격으로 분리되어 있어, 규격만 지키면 엔진을 갈아 끼울 수 있습니다. 그래서 MySQL을 **플러그인형(pluggable) 스토리지 엔진** 구조라고 부릅니다.

## 1.2 이 구조가 만드는 결과

계층이 분리되어 있다는 것은 **엔진에 따라 지원 기능이 다르다**는 뜻입니다.

| 항목 | 담당 계층 |
|---|---|
| SQL 문법 파싱 | MySQL 엔진 (공통) |
| 옵티마이저 | MySQL 엔진 (공통) |
| **트랜잭션** | **스토리지 엔진** |
| **락 단위** | **스토리지 엔진** |
| **외래 키** | **스토리지 엔진** |
| **인덱스 구조** | **스토리지 엔진** |

여기서 실무적으로 헷갈리는 현상이 발생합니다.

```sql
CREATE TABLE child (
  id INT,
  parent_id INT,
  FOREIGN KEY (parent_id) REFERENCES parent(id)
) ENGINE = MyISAM;
-- 에러 없이 생성됨! 그런데 외래 키는 동작하지 않음
```

**파서(윗층)는 `FOREIGN KEY` 문법을 알기 때문에 통과시키지만, MyISAM(아랫층)은 그 제약을 구현하지 않아 그냥 무시합니다.** 같은 이유로 MyISAM 테이블에 `BEGIN; ... ROLLBACK;`을 실행해도 에러는 안 나지만 **아무것도 되돌아가지 않습니다.**

## 1.3 엔진 확인 방법

```sql
SHOW ENGINES;                      -- 사용 가능한 엔진 목록 + 기본 엔진
SHOW TABLE STATUS LIKE 'users';    -- 특정 테이블의 엔진
SELECT @@default_storage_engine;   -- InnoDB
```

## 1.4 주요 엔진 비교

| 엔진 | 트랜잭션 | 락 단위 | 외래 키 | 저장 위치 | 용도 |
|---|---|---|---|---|---|
| **InnoDB** | O | **행** | O | 디스크 | 사실상 유일한 실무 선택지 |
| **MyISAM** | **X** | **테이블** | **X** | 디스크 | 레거시 |
| **MEMORY** | X | 테이블 | X | **RAM** | 임시 데이터 |
| ARCHIVE | X | 행 | X | 디스크(압축) | 로그 아카이빙 |
| CSV | X | 테이블 | X | 디스크(.csv) | 데이터 교환 |
| BLACKHOLE | - | - | - | 없음 | 복제 중계용 |

## 1.5 락 단위(Lock Granularity) — 기초

**락 단위란 데이터를 수정할 때 "얼마나 넓은 범위를 잠그느냐"입니다.**

```
테이블 락:  [■■■■■■■■■■]  테이블 전체를 잠금
행 락:      [□□■□□□■□□□]  건드리는 행만 잠금
```

**테이블 락의 문제** (MyISAM)

```
100만 행짜리 게시판 테이블

사용자 A: 1번 글 수정   → 테이블 전체 잠금
사용자 B: 500번 글 수정 → 대기 ★ (전혀 다른 행인데도)
사용자 C: 900번 글 수정 → 대기 ★
```

**행 락의 경우** (InnoDB)

```
사용자 A: 1번 글 수정   → 1번 행만 잠금
사용자 B: 500번 글 수정 → 즉시 처리 ✓
사용자 C: 900번 글 수정 → 즉시 처리 ✓
```

> MyISAM에도 `concurrent_insert`로 "테이블 끝에 INSERT하는 경우"에 한해 읽기와 동시 진행이 가능한 제한적 기능이 있습니다. 하지만 **UPDATE/DELETE는 여전히 테이블 전체를 잠급니다.**

## 1.6 MyISAM — 왜 존재했고 왜 사라졌는가

**장점 (과거 기준)**

- 구조가 단순해 가볍고 빠름 (트랜잭션/락/MVCC 오버헤드 없음)
- `SELECT COUNT(*)` 즉시 반환 — 메타데이터에 전체 행 수를 저장해두기 때문. InnoDB는 MVCC 때문에 "누구에게 몇 건인지"가 트랜잭션마다 달라 **매번 세야 합니다.**
- 파일 크기가 작음 (`.MYD` 데이터 + `.MYI` 인덱스)
- 과거엔 FULLTEXT 인덱스를 MyISAM만 지원 (InnoDB는 5.6부터 지원)

**치명적 단점**

- **Redo Log도 Undo Log도 없음** → 비정상 종료 시 자동 복구 불가. `REPAIR TABLE`/`myisamchk` 수동 실행이 필요하고 데이터 유실 가능
- 트랜잭션 없음, 외래 키 없음, 테이블 락

> **MySQL 8.0의 변화:** `mysql` 시스템 스키마(권한 테이블 등)가 전부 InnoDB로 이전되었습니다. MySQL이 MyISAM을 사실상 정리했다는 신호입니다.

## 1.7 MEMORY 엔진

데이터를 **메모리에만** 보관합니다. 디스크 I/O가 없어 매우 빠릅니다.

**중요한 뉘앙스:** 서버 재시작 시 **데이터는 사라지지만 테이블 구조는 남습니다.** 테이블 정의는 데이터 딕셔너리(디스크)에 저장되기 때문입니다. 즉 재시작 후 **테이블은 존재하되 0건**이 됩니다.

**제약**

- 테이블 수준 잠금
- `BLOB`, `TEXT` 타입 사용 불가
- `VARCHAR`도 고정 길이로 저장 → 메모리 사용량이 예상보다 큼
- 기본 인덱스가 **HASH** → 등호 검색은 빠르나 **범위 검색·정렬에는 무용**
- `max_heap_table_size` 초과 시 에러

> 현실적으로 이 용도는 **Redis가 대체**했습니다.  
> 또한 MySQL 내부 임시 테이블은 8.0.16부터 MEMORY가 아닌 **TempTable 엔진**을 사용합니다.

# 2. 트랜잭션과 ACID

## 2.1 기초 — 트랜잭션은 "묶음"이다

```sql
UPDATE account SET balance = balance - 10000 WHERE id = 1;  -- 출금
UPDATE account SET balance = balance + 10000 WHERE id = 2;  -- 입금
```

두 문장 사이에서 서버가 죽으면 10000원이 증발합니다. 그래서 DB는 **"전부 반영되거나, 전부 없던 일이 되거나"** 를 보장하는 단위를 제공합니다.

| ACID | 의미 | InnoDB의 구현 수단 |
|---|---|---|
| **A**tomicity (원자성) | 전부 아니면 전무 | **Undo Log** |
| **C**onsistency (일관성) | 제약 조건을 깨지 않음 | PK, FK, UNIQUE, CHECK 검증 |
| **I**solation (격리성) | 서로 간섭하지 않음 | **MVCC + 락** |
| **D**urability (지속성) | 커밋된 건 장애에도 남음 | **Redo Log + 더블 라이트 버퍼** |

## 2.2 핵심 — "커밋 전 중간 상태가 존재한다"

위 이체 예시에서 첫 UPDATE만 실행되고 아직 커밋되지 않은 순간이 **반드시** 존재합니다. 그 순간의 DB는 **총액이 10000원 모자란, 논리적으로 깨진 상태**입니다.

혼자 쓰는 DB라면 상관없지만, 실제 서비스에서는 커넥션 풀로 수십 개의 트랜잭션이 동시에 돌고 있습니다. **누군가는 그 깨진 중간 상태를 볼 수 있습니다.** 여기서 모든 동시성 문제가 시작됩니다.

## 2.3 가장 확실한 해법과 그 한계

트랜잭션을 한 번에 하나씩만 돌리면(**직렬 실행**) 간섭이 0입니다. 그러나 트랜잭션 하나가 0.1초라면 초당 10건밖에 처리하지 못합니다.

그래서 DB는 **동시에 돌리되 마치 하나씩 돈 것처럼 보이게** 만들려 합니다. 이것이 **직렬화 가능성(Serializability)** 입니다. 100% 보장에는 큰 비용이 들기 때문에,

> **"어느 정도까지 간섭을 허용하고 성능을 얻을 것인가"**

를 고를 수 있게 한 것이 **격리 수준(Isolation Level)** 이고, 다이얼을 낮췄을 때 새어나오는 문제들이 **이상 현상(Anomaly)** 입니다.

# 3. 동시성 문제와 이상 현상

## 3.1 이상 현상이 3가지인 이유

무작정 외우기보다 **겹치는 패턴**으로 나누면 자연스럽게 3가지가 나옵니다.

내가 T1이고 다른 트랜잭션 T2가 끼어든다고 할 때:

| 끼어드는 시점 | T2가 하는 일 | 나에게 보이는 문제 |
|---|---|---|
| T2가 **커밋하기 전** | UPDATE 중 | **Dirty Read** |
| T2가 **커밋한 후** | 기존 행의 값 변경 | **Non-Repeatable Read** |
| T2가 **커밋한 후** | 새 행 추가 | **Phantom Read** |

즉 **"커밋 전이냐 후냐"** 로 한 번, 커밋 후는 **"기존 행이 바뀐 거냐 / 행 개수가 바뀐 거냐"** 로 또 나뉩니다.

## 3.2 Dirty Read — 존재한 적 없는 값을 읽는다

```
T1: BEGIN
T1: UPDATE account SET balance = 5000 WHERE id = 1;   -- 아직 커밋 X
                    T2: SELECT balance WHERE id = 1;  -- 5000 읽음 ★
T1: ROLLBACK;                                          -- 원래대로 1000
```

T2가 읽은 5000은 **DB 역사상 단 한 번도 확정된 적이 없는 값**입니다. 이 값으로 "잔액 충분, 결제 승인"을 내렸다면 그대로 사고입니다.

셋 중 가장 위험합니다. 다른 둘은 "옛날 값"이나 "시점이 섞인 값"을 보는 것이지만, Dirty Read는 **아예 유효하지 않은 값**을 봅니다.

## 3.3 Non-Repeatable Read — 같은 걸 두 번 읽었는데 다르다

```
T1: SELECT balance WHERE id = 1;   -- 1000
                    T2: UPDATE account SET balance = 5000 WHERE id = 1;
                    T2: COMMIT;    -- 이번엔 정상 커밋
T1: SELECT balance WHERE id = 1;   -- 5000  ★ 같은 쿼리, 다른 결과
```

T2는 잘못한 게 없습니다. 문제는 **T1 입장에서 자기 트랜잭션 안의 세계가 도중에 바뀌었다**는 것입니다.

이름 그대로 읽으면 명확합니다 — **Non(불가) + Repeatable(반복) + Read(읽기)**.

> **왜 문제인가:** 한 트랜잭션 안에서 "잔액 확인 → 계산 → 차감"을 하는데 확인 시점과 차감 시점의 값이 다르면 계산이 무의미해집니다. 리포트의 앞부분 합계와 뒷부분 상세가 안 맞는 것도 같은 원인입니다.

**"커밋"이 핵심입니다.** 커밋 전이면 Dirty Read가 됩니다.

## 3.4 Phantom Read — 없던 행이 나타난다

```
T1: SELECT * FROM member WHERE age BETWEEN 20 AND 29;  -- 3건
                    T2: INSERT INTO member(age) VALUES (25);
                    T2: COMMIT;
T1: SELECT * FROM member WHERE age BETWEEN 20 AND 29;  -- 4건 ★ 유령 등장
```

기존 행들의 값은 하나도 안 바뀌었습니다. **결과 집합의 크기**가 바뀐 것입니다.

## 3.5 왜 3.3과 3.4를 굳이 나누는가 — "락을 걸 대상이 있느냐"

학문적 분류 때문이 아니라 **해결 방법이 근본적으로 다르기 때문**입니다.

- **Non-Repeatable Read 방지:** 내가 읽은 행에 "손대지 마" 락을 걸면 됩니다. 그 행은 **실체가 있으니** 락을 걸 수 있습니다.
- **Phantom Read 방지:** 무엇에 락을 걸어야 할까요? **아직 존재하지 않는 행에는 락을 걸 수 없습니다.** `age = 25`인 행이 지금 없는데 어떻게 잠급니까?

그래서 팬텀을 막으려면 **"행과 행 사이의 빈 공간"** 을 잠그는 완전히 다른 메커니즘(**Gap Lock**)이 필요합니다.

| | Non-Repeatable Read | Phantom Read |
|---|---|---|
| 대상 | 특정 **행(row)** 의 값 | 조회 **범위**의 결과 집합 |
| 원인 연산 | `UPDATE`, `DELETE` | `INSERT` |
| 막는 방법 | 행 락 (대상이 존재함) | **범위 락** (대상이 존재하지 않음) |
| 비용 | 상대적으로 저렴 | 비쌈 (INSERT를 광범위하게 차단) |

이 비용 차이 때문에 표준에서도 팬텀 방지를 가장 높은 등급으로 미뤄둔 것입니다.

# 4. 트랜잭션 격리 수준 4단계

## 4.1 표

위 3가지를 **심각한 것부터 하나씩 차단**해 나가는 구조입니다.

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| `READ UNCOMMITTED` | 발생 | 발생 | 발생 |
| `READ COMMITTED` | **차단** | 발생 | 발생 |
| `REPEATABLE READ` | **차단** | **차단** | 발생(표준상) |
| `SERIALIZABLE` | **차단** | **차단** | **차단** |

## 4.2 이름이 곧 정의다 (외울 필요 없음)

- **READ UNCOMMITTED** = "커밋 안 된 것도 읽음" → 당연히 Dirty Read 발생
- **READ COMMITTED** = "커밋된 것만 읽음" → **Dirty Read는 정의상 불가능**
- **REPEATABLE READ** = "반복 읽기가 보장됨" → Non-Repeatable Read 불가능
- **SERIALIZABLE** = "직렬 실행과 동일" → 전부 불가능

> `READ UNCOMMITTED`는 실무에서 거의 쓰이지 않습니다. 정합성을 완전히 포기하는 대가로 얻는 이득이, 현대 DB의 MVCC 덕분에 거의 없기 때문입니다.

## 4.3 DBMS별 기본 격리 수준

| DBMS | 기본 격리 수준 |
|---|---|
| **MySQL (InnoDB)** | `REPEATABLE READ` |
| PostgreSQL | `READ COMMITTED` |
| Oracle | `READ COMMITTED` |
| SQL Server | `READ COMMITTED` |

```sql
SELECT @@transaction_isolation;   -- REPEATABLE-READ
```

**MySQL만 RR인 이유:** 역사적 배경입니다. 초기 MySQL의 복제는 **STATEMENT 기반**이었는데, READ COMMITTED에서는 커밋 순서와 문장 전달 순서가 어긋나 **마스터와 슬레이브 데이터가 달라지는** 문제가 있었습니다. 이를 피하려 RR을 기본값으로 잡았고 지금까지 이어집니다.

> 현재는 ROW 기반 복제가 기본이라, Gap Lock 부담과 언두 로그 유지 부담을 줄이려 **RC로 낮춰 쓰는 회사도 많습니다.**

# 5. InnoDB는 이것을 어떻게 구현하는가

## 5.1 두 갈래의 구현 방식

**방식 A — 락 기반 (전통적)**

읽을 때 공유 락(S), 쓸 때 배타 락(X)을 걸고 트랜잭션 종료까지 유지(2PL).

- READ COMMITTED → 읽기 락을 읽는 순간만 잡고 놓음
- REPEATABLE READ → 읽기 락을 끝까지 유지

**치명적 단점: 읽기와 쓰기가 서로를 막습니다.** 조회가 압도적으로 많은 웹 서비스에서 이는 재앙입니다.

**방식 B — MVCC (현대 DB의 답)**

> **데이터를 덮어쓰지 말고, 옛날 버전을 남겨두자.**  
> 쓰는 사람은 새 버전을 만들고, 읽는 사람은 옛날 버전을 읽는다.  
> → **읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않는다.**

MySQL InnoDB, PostgreSQL, Oracle이 모두 채택했습니다.

## 5.2 MVCC의 구성 요소

**① 언두 로그 (Undo Log)**

`UPDATE` 실행 시 InnoDB는  
1. 변경 **전** 데이터를 언두 로그에 복사하고  
2. 실제 데이터 페이지를 새 값으로 수정합니다.

언두 로그는 원래 **롤백**을 위한 장치였는데, 이 "과거 버전 저장소"를 **MVCC의 읽기 소스로 재활용**한 것입니다.

**② Read View (스냅샷)**

SELECT 시 "그 시점에 어떤 트랜잭션이 활성 상태였는가"를 기록한 Read View를 만듭니다. 데이터를 읽을 때 각 행의 버전을 보고 판단합니다.

- Read View 생성 이전에 커밋된 버전 → 읽어도 됨
- 아직 활성 중이거나 나중에 커밋됨 → **언두 로그를 타고 더 과거 버전으로 이동**

## 5.3 RC와 RR의 진짜 차이는 단 한 줄

| | Read View를 언제 만드는가 |
|---|---|
| `READ COMMITTED` | **SELECT 할 때마다 새로** |
| `REPEATABLE READ` | **트랜잭션의 첫 SELECT 때 한 번만** |

- RC는 매번 새 스냅샷 → 그 사이 커밋된 변경이 보임 → **Non-Repeatable Read 발생**
- RR은 스냅샷 고정 → 트랜잭션 내내 같은 시점의 세계 → **Non-Repeatable Read 차단**

그리고 중요한 결과가 하나 더 나옵니다.

**RR의 고정된 스냅샷은 INSERT된 행도 걸러냅니다.** 즉 **InnoDB는 RR에서 락 없이도 Phantom Read를 상당 부분 막습니다.** (표준 이론과 달라지는 지점)

## 5.4 Consistent Read vs Current Read

MVCC 스냅샷은 **일반 SELECT**에만 적용됩니다.

| 구분 | 대상 | 읽는 데이터 |
|---|---|---|
| **Consistent Read** | 일반 `SELECT` | 스냅샷 (과거 시점) |
| **Current Read** | `SELECT ... FOR UPDATE`, `LOCK IN SHARE MODE`, `UPDATE`, `DELETE` | **최신 데이터 + 락** |

당연합니다. 5초 전 스냅샷을 보고 UPDATE하면 남의 변경을 덮어쓰게 되니까요.

## 5.5 Gap Lock과 Next-Key Lock

Current Read에서는 락으로 팬텀을 막습니다.

```
Record Lock : 실제 존재하는 행 자체를 잠금
Gap Lock    : 행과 행 "사이의 빈 공간"을 잠금 → 여기에 INSERT 불가
Next-Key Lock = Record Lock + Gap Lock
```

인덱스에 `age` 값이 `10, 20, 30`으로 있고 `WHERE age BETWEEN 15 AND 25 FOR UPDATE`를 하면, 20이라는 행뿐 아니라 **10~20 사이, 20~30 사이의 빈 공간까지** 잠급니다. 다른 트랜잭션이 `age = 22`를 INSERT하려 하면 대기합니다.

> **실무 주의:** Gap Lock은 존재하지 않는 데이터까지 잠그므로 **데드락과 락 대기의 주범**입니다. 인덱스가 없는 컬럼으로 조건을 걸면 풀스캔하며 사실상 테이블 전체에 갭 락이 걸립니다. `FOR UPDATE`를 쓸 때 인덱스 설계가 중요한 이유입니다.

## 5.6 그래도 남는 팬텀 케이스

스냅샷 읽기와 잠금 읽기가 **섞일 때** InnoDB RR에서도 팬텀이 보입니다.

```
T1: SELECT * FROM member WHERE age = 25;              -- 0건 (스냅샷 생성)
                T2: INSERT INTO member VALUES (100, 25); COMMIT;
T1: SELECT * FROM member WHERE age = 25;              -- 0건 (스냅샷 유지)
T1: SELECT * FROM member WHERE age = 25 FOR UPDATE;   -- 1건 ★ 팬텀
```

세 번째 쿼리는 Current Read라 최신 데이터를 보기 때문입니다. T1이 그 행을 직접 `UPDATE`해도 그 순간부터 자기 스냅샷에 보이기 시작합니다.

> **정확한 서술:** InnoDB는 RR에서 팬텀을 **대부분 방지**하지만, **잠금 읽기가 섞이면 예외적으로 발생**할 수 있다.

## 5.7 Redo Log와 Undo Log

### 배경 — 왜 로그가 필요한가

InnoDB는 **버퍼 풀(Buffer Pool)** 이라는 메모리에 데이터를 올려놓고 작업합니다.

```
UPDATE 실행 시:
1. 디스크에서 페이지를 버퍼 풀로 읽어옴
2. 버퍼 풀 메모리 상에서 값을 수정   ← 이 시점엔 디스크는 옛날 값
3. 나중에 한가할 때 디스크에 반영 (flush)
```

수정된 채 아직 디스크에 안 내려간 페이지를 **더티 페이지(Dirty Page)** 라고 합니다. 2와 3 사이에 서버가 죽으면 커밋된 변경이 사라집니다(지속성 위반). 그렇다고 커밋마다 데이터 페이지를 쓰자니, 페이지가 디스크 여기저기 흩어져 있어 **랜덤 I/O**라 너무 느립니다.

### Redo Log — WAL (Write-Ahead Logging)

**해법: 무거운 데이터 페이지 대신 가벼운 "변경 기록"만 순차 쓰기로 먼저 저장한다.**

```
커밋 시점:
  데이터 페이지 → 디스크 (X, 랜덤 I/O라 느림, 나중에)
  Redo Log      → 디스크 (O, 순차 I/O라 빠름, 즉시)
```

서버가 죽어도 재시작 시 Redo Log를 읽어 **아직 반영 안 된 커밋된 변경을 다시 실행(REDO)** 하면 복구됩니다.

```sql
innodb_flush_log_at_trx_commit = 1  -- 커밋마다 fsync (기본, 완전 안전)
                               = 2  -- OS 캐시까지, 1초마다 fsync (DB 죽어도 OK)
                               = 0  -- 1초마다 (가장 빠르나 최대 1초 유실)
```

### 비교

| | Redo Log | Undo Log |
|---|---|---|
| 저장 내용 | 변경 **후** 정보 (어떻게 다시 할지) | 변경 **전** 정보 (어떻게 되돌릴지) |
| 방향 | 재실행 (앞으로) | 취소 (뒤로) |
| ACID 담당 | **D**urability | **A**tomicity |
| 부가 용도 | 크래시 복구 | **MVCC 스냅샷 읽기** |
| 정리 시점 | 체크포인트 이후 재사용 | 참조 트랜잭션이 모두 끝난 후 |

### Redo Log ≠ Binary Log (자주 혼동)

| | Redo Log | Binary Log (binlog) |
|---|---|---|
| 소속 계층 | **InnoDB (스토리지 엔진)** | **MySQL 엔진 (서버)** |
| 기록 내용 | 페이지 물리적 변경 | 논리적 변경 (SQL 또는 행 이미지) |
| 목적 | **크래시 복구** | **복제(Replication), 시점 복구(PITR)** |
| 크기 | 고정, 순환 재사용 | 계속 누적 |

둘의 순서를 맞추기 위해 커밋 시 내부적으로 **2단계 커밋(2PC)** 이 수행됩니다.

## 5.8 InnoDB의 다른 핵심 구조

### 클러스터형 인덱스 (Clustered Index)

InnoDB에서 **테이블은 곧 PK 기준으로 정렬된 B+Tree**입니다. 데이터가 인덱스 리프 노드 안에 직접 들어있습니다.

```
InnoDB (클러스터형)              MyISAM (비클러스터형)

PK 인덱스 B+Tree                 인덱스              데이터 파일
  └─ 리프에 실제 행 데이터          └─ 리프에 행 주소 → [.MYD 파일의 행]
```

- PK 조회가 매우 빠름
- **세컨더리 인덱스는 리프에 PK 값을 저장** → 세컨더리로 조회하면 PK를 얻고 **다시 PK 인덱스를 타야** 함
- **PK가 무작위 값(UUID)이면** B+Tree 중간에 끼워 넣게 되어 페이지 분할이 잦음 → **AUTO_INCREMENT나 순차 값 권장**

### 더블 라이트 버퍼 (Doublewrite Buffer)

Redo Log만으로 부족한 케이스가 있습니다. **부분 페이지 쓰기(Torn Page)** 문제입니다.

InnoDB 페이지는 16KB인데 OS/디스크는 보통 4KB 단위로 씁니다. 16KB 중 8KB만 쓰인 상태에서 전원이 나가면 **페이지 자체가 깨집니다.** Redo Log는 "이 페이지에 이 변경을 적용하라"는 내용인데, 페이지가 깨졌으면 적용할 기반이 없습니다.

그래서 InnoDB는 데이터 페이지를 실제 위치에 쓰기 전에 **별도 영역에 통째로 한 번 먼저 씁니다.** 크래시 후엔 이 사본으로 복원한 뒤 Redo를 적용합니다. **MyISAM에는 이런 장치가 전혀 없습니다.**

### 버퍼 풀

- InnoDB: **데이터와 인덱스를 모두** 캐싱
- MyISAM: **인덱스만**(`key_buffer`) 캐싱, 데이터는 OS 캐시에 의존

```sql
innodb_buffer_pool_size = 물리 메모리의 50~70%   -- 가장 중요한 튜닝 파라미터
```

# 6. 표준에 없는 이상 현상

ANSI 표준 3종은 불완전하다는 비판이 유명합니다 (Berenson et al., *A Critique of ANSI SQL Isolation Levels*, 1995). 실무에서는 오히려 아래가 더 자주 터집니다.

## 6.1 Lost Update (갱신 손실)

```
T1: SELECT stock FROM item WHERE id=1;      -- 10
T2: SELECT stock FROM item WHERE id=1;      -- 10
T1: UPDATE item SET stock = 9 WHERE id=1; COMMIT;
T2: UPDATE item SET stock = 9 WHERE id=1; COMMIT;   -- 2개 팔렸는데 재고는 1 감소
```

**REPEATABLE READ로도 막히지 않습니다.** 스냅샷은 "읽기"를 보호할 뿐, "읽은 값으로 계산해서 쓰기"라는 **애플리케이션 로직의 논리적 공백**은 보호하지 못하기 때문입니다.

**해결책 3가지**

```sql
-- 1. 비관적 락: 읽을 때부터 잠근다
SELECT stock FROM item WHERE id=1 FOR UPDATE;

-- 2. 원자적 갱신: 읽지 말고 DB에게 계산시킨다
UPDATE item SET stock = stock - 1 WHERE id=1 AND stock > 0;
```

```java
// 3. 낙관적 락 (JPA)
@Version
private Long version;
```

재고, 포인트, 좌석 예약, 쿠폰 발급 도메인에서는 격리 수준과 **별개로** 반드시 다뤄야 합니다.

## 6.2 Write Skew (쓰기 편향)

두 트랜잭션이 **서로 다른 행을 읽고 서로 다른 행을 쓰는데**, 합쳐놓으면 비즈니스 제약이 깨지는 현상입니다.

```
규칙: 당직자는 최소 1명. 현재 A, B 두 명 당직 중.

T1(A): SELECT COUNT(*) WHERE on_call = true;  -- 2명, "나 빠져도 되네"
T2(B): SELECT COUNT(*) WHERE on_call = true;  -- 2명, "나 빠져도 되네"
T1: UPDATE staff SET on_call = false WHERE id = A; COMMIT;
T2: UPDATE staff SET on_call = false WHERE id = B; COMMIT;
→ 당직자 0명
```

각자 다른 행을 수정했으므로 락도 충돌하지 않고 MVCC도 문제를 못 느낍니다. **스냅샷 격리의 근본적 한계**이며, `SERIALIZABLE`이거나 판단 근거가 된 범위 전체를 명시적으로 잠가야 합니다.

# 7. 인덱스의 원리

## 7.1 기초 — 인덱스는 "정렬된 사본"이다

인덱스를 "책의 색인"에 비유하지만, 더 정확한 표현은 이것입니다.

> **인덱스 = 특정 컬럼 값을 기준으로 정렬해서 따로 만들어 둔 자료구조**

```
                    [2024-04-01]
                   /            \
        [2024-02-01]              [2024-08-01]
        /        \                /          \
   ...리프 노드 (실제 값들이 정렬되어 연결됨)...

리프:  2024-01-03 → 2024-01-07 → 2024-01-15 → 2024-02-01 → ... → 2025-03-20
        ↑ 각 노드는 PK 값을 함께 가지고 있음
```

**핵심 성질 두 가지**

1. 위에서 아래로 내려가며 원하는 값을 빠르게 찾는다 — O(log N)
2. **리프 노드들이 정렬된 순서로 연결 리스트처럼 이어져 있다** (B+Tree의 특징)

## 7.2 2번 성질이 만드는 것 — 범위 스캔

```sql
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
```

```
1. B+Tree를 타고 내려가 '2024-01-01' 위치를 찾는다   ← 몇 번의 탐색
2. 거기서부터 리프 노드를 옆으로 쭉 읽는다             ← 순차 접근
3. '2025-01-01'을 만나면 멈춘다  ★
```

**3번이 결정적입니다.** 정렬되어 있으니 범위를 벗어나는 값을 만나는 순간 **"뒤에는 볼 필요 없다"가 보장됩니다.** 이것이 실행 계획의 **`range` 스캔**입니다.

# 8. SARGable — 인덱스를 살리는 조건 작성법

## 8.1 문제 상황

```sql
-- (A) 인덱스 무력화
SELECT * FROM orders WHERE YEAR(order_date) = 2024;

-- (B) 인덱스 활용
SELECT * FROM orders 
 WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01';
```

**결과는 완전히 동일**한데 성능은 수십~수백 배 차이가 납니다.

## 8.2 이유 — 인덱스에 저장된 것은 "원본 값"이다

```
인덱스에 저장된 값:  2024-01-03, 2024-01-07, 2024-02-01, ...
쿼리가 묻는 값:      YEAR(...) = 2024
```

**인덱스 어디에도 `YEAR(order_date)`의 결과값은 저장되어 있지 않습니다.** 그래서 DB는 이렇게 할 수밖에 없습니다.

```
행 1: order_date = 2024-01-03 → YEAR() 계산 → 2024 → 일치 ✓
행 2: order_date = 2023-11-20 → YEAR() 계산 → 2023 → 불일치 ✗
...
행 1000000: ...
```

**모든 행을 꺼내 함수를 적용해봐야 합니다.** 이것이 풀 테이블 스캔입니다.

## 8.3 더 근본적으로 — 정렬이 깨진다

함수를 통과한 값의 순서는 원본의 순서와 무관해질 수 있습니다.

```
원본 정렬:      1, 2, 3, 4, 5
MOD(x, 3):      1, 2, 0, 1, 2      -- 순서 완전 파괴 ★
```

**옵티마이저는 함수의 수학적 성질을 하나하나 알지 못합니다.** 그래서 **"인덱스 컬럼에 함수가 씌워지면 그 인덱스는 못 쓴다"** 고 보수적으로 판단합니다.

> **원칙 한 줄**  
> **인덱스 컬럼은 비교 연산자의 왼쪽에 홀로, 아무 가공 없이 두어라.  
> 계산이 필요하면 반대편(상수 쪽)에서 하라.**

## 8.4 SARGable — 정식 용어

> **SARGable = Search ARGument able**  
> "검색 인자로 쓸 수 있는", 즉 **인덱스 탐색에 직접 사용 가능한 조건**

인덱스가 있어도 조건은 두 가지 역할로 갈립니다.

| | Access 조건 | Filter 조건 |
|---|---|---|
| 역할 | **읽을 범위를 결정** | 읽어온 행을 **걸러냄** |
| 성능 영향 | 읽는 양 자체를 줄임 ★ | 이미 다 읽은 뒤 버림 |
| EXPLAIN | `type: range/ref` | `Extra: Using where` |

**함수를 씌운 조건은 Access 조건이 되지 못하고 Filter 조건으로 강등됩니다.** 결과는 맞지만 읽는 양이 줄지 않습니다.

## 8.5 Non-SARGable 패턴 모음

### (1) 날짜 함수 — 가장 흔한 케이스

```sql
-- ✗ 인덱스 무력화
WHERE YEAR(order_date) = 2024
WHERE DATE(order_date) = '2024-05-01'
WHERE DATE_FORMAT(order_date, '%Y-%m') = '2024-05'
WHERE order_date + INTERVAL 1 DAY > NOW()

-- ✓ 범위 조건으로 변환
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
WHERE order_date >= '2024-05-01' AND order_date < '2024-05-02'
WHERE order_date >= '2024-05-01' AND order_date < '2024-06-01'
WHERE order_date > NOW() - INTERVAL 1 DAY
```

마지막 예시는 **`+ INTERVAL 1 DAY`를 컬럼 쪽에서 상수 쪽으로 이항**한 것입니다. SARGable 변환의 전형입니다.

> **경계값 주의 — `BETWEEN`**
> ```sql
> -- ✗ 위험 (order_date가 DATETIME인 경우)
> WHERE order_date BETWEEN '2024-05-01' AND '2024-05-31'
> ```
> `'2024-05-31'`은 `'2024-05-31 00:00:00'`으로 해석되어 **5월 31일 00:00:01 이후 데이터가 전부 누락됩니다.**
> ```sql
> -- ✓ 안전: 시작은 이상, 끝은 미만
> WHERE order_date >= '2024-05-01' AND order_date < '2024-06-01'
> ```
> `>= 시작 AND < 다음구간시작` 패턴이면 DATE/DATETIME/TIMESTAMP 어느 타입이든 안전합니다.

### (2) 산술 연산

```sql
-- ✗                          -- ✓
WHERE price * 1.1 > 11000     WHERE price > 10000
WHERE salary / 12 > 5000      WHERE salary > 60000
```

### (3) 문자열 함수와 LIKE

```sql
-- ✗                                        -- ✓
WHERE SUBSTRING(phone, 1, 3) = '010'        WHERE phone LIKE '010%'
WHERE UPPER(email) = 'TEST@EXAMPLE.COM'     WHERE email = 'test@example.com'
```

**`LIKE`는 앞부분이 고정되어야만 인덱스를 씁니다.**

```sql
WHERE name LIKE '김%'     -- ✓ range 스캔 가능
WHERE name LIKE '%김'     -- ✗ 풀스캔
WHERE name LIKE '%김%'    -- ✗ 풀스캔
```

인덱스는 **왼쪽부터** 정렬되어 있습니다. `'김'`으로 시작하는 값은 연속 구간을 이루지만, `'김'`으로 **끝나는** 값은 인덱스 전체에 흩어져 있습니다.

> 뒷부분 검색이 꼭 필요하면 → **FULLTEXT 인덱스**, 또는 문자열을 뒤집어 저장한 컬럼에 인덱스.

### (4) 암묵적 형변환 — 가장 발견하기 어려운 함정

```sql
-- phone 컬럼이 VARCHAR인 경우
WHERE phone = 01012345678     -- ✗ 컬럼이 숫자로 변환됨 → 인덱스 무력화
WHERE phone = '01012345678'   -- ✓
```

> **MySQL의 비교 규칙:** 문자열과 숫자를 비교하면 **문자열을 숫자로** 변환합니다. 즉 컬럼이 문자열이면 **컬럼이 변환당합니다.** 반대로 컬럼이 INT인데 `WHERE id = '123'`이면 상수 쪽이 변환되므로 인덱스가 살아 있습니다.

**JOIN에서도 동일하게 발생합니다.** 조인 키의 타입이 다르거나(`VARCHAR` vs `INT`), **콜레이션이 다르면**(`utf8mb4_general_ci` vs `utf8mb4_unicode_ci`) 형변환으로 인덱스가 무력화됩니다. 조인이 갑자기 느려질 때 반드시 확인할 항목입니다.

### (5) 부정 조건과 OR

```sql
WHERE status != 'DONE'
WHERE status NOT IN ('A', 'B')
WHERE user_id = 1 OR order_no = 'X'   -- 각 컬럼에 인덱스 없으면 풀스캔
```

인덱스는 "여기부터 여기까지"를 좁히는 도구인데, `!=`는 사실상 전체를 가리킵니다.  
`OR`은 index merge로 처리될 수도 있지만 옵티마이저가 풀스캔을 고르는 경우가 많아, `UNION ALL` 분리가 더 빠를 때가 있습니다.

### (6) 복합 인덱스의 후행 컬럼 가공

```sql
INDEX idx_user_date (user_id, order_date)

WHERE user_id = 1 AND YEAR(order_date) = 2024
```

`user_id = 1`까지는 인덱스를 타지만 **`order_date`는 Filter로만 작동**합니다. 그 사용자의 주문이 10만 건이면 10만 건을 다 읽습니다.

> **복합 인덱스는 앞 컬럼부터 등호 조건이 이어질 때 가장 효율적**이고, **범위 조건이 나오는 순간 그 뒤 컬럼은 Access 조건으로 쓰이지 못합니다.**

## 8.6 심화 — 그래도 함수를 써야 한다면

### 함수 기반 인덱스 (MySQL 8.0.13+)

```sql
CREATE INDEX idx_order_year ON orders ((YEAR(order_date)));
--                                     ↑↑ 괄호 두 겹 필수

SELECT * FROM orders WHERE YEAR(order_date) = 2024;   -- 이제 인덱스 사용 ✓
```

**`YEAR()`의 결과값으로 정렬된 별도 인덱스를 만든 것**입니다. 8.2의 문제를 정면으로 해결한 방식이죠.

주의: 쿼리의 표현식이 인덱스 정의와 **정확히 일치**해야 합니다.

### 생성 컬럼 (Generated Column)

```sql
ALTER TABLE orders 
  ADD COLUMN order_year INT AS (YEAR(order_date)) STORED,
  ADD INDEX idx_order_year (order_year);
```

- `STORED`: 디스크에 실제 저장 (공간 소모)
- `VIRTUAL`: 읽을 때 계산 (8.0에서는 이것도 인덱스 가능)

### 그런데 대부분의 경우 함수 인덱스는 불필요합니다

`order_date` 인덱스 하나면 **연도, 월, 일, 임의 기간을 전부 커버**합니다.

```
idx_order_date 하나로:
  2024년 전체 ✓ / 2024년 5월 ✓ / 최근 7일 ✓ / 특정 2주 구간 ✓
```

반면 `YEAR()` 함수 인덱스는 **연도 조회에만** 쓰입니다. **인덱스는 공짜가 아닙니다** — 공간을 차지하고 INSERT/UPDATE/DELETE마다 갱신되어 쓰기 성능을 떨어뜨립니다.

> **원칙: 쿼리를 SARGable하게 고칠 수 있으면 그것이 우선이고, 함수 인덱스는 도저히 쿼리를 바꿀 수 없을 때(레거시, ORM 제약)의 차선책입니다.**

## 8.7 반대 방향의 오해 — "인덱스를 쓰면 항상 빠르다"가 아니다

**옵티마이저는 인덱스를 쓸 수 있어도 일부러 안 쓰기도 합니다.**

```sql
WHERE order_date >= '2020-01-01'   -- 전체의 95%가 해당
```

인덱스를 타면:

```
1. 인덱스에서 PK를 얻고
2. PK로 클러스터형 인덱스를 다시 타서 실제 행을 읽고   ← 랜덤 I/O
3. 이걸 95만 번 반복
```

**차라리 테이블을 순차적으로 쭉 읽는 게 빠릅니다.** 일반적으로 **조회 대상이 전체의 20~25%를 넘으면 옵티마이저는 풀스캔을 선택**합니다.

이 판단은 **통계 정보(카디널리티)** 기반이며, 통계가 낡으면 잘못된 선택을 합니다.

```sql
ANALYZE TABLE orders;   -- 통계 정보 갱신
```

> **커버링 인덱스:** 위 2번의 "테이블 재접근"이 병목입니다. 필요한 컬럼이 인덱스 안에 다 있으면 2번을 통째로 생략할 수 있어 극적으로 빨라집니다. 실행 계획에 `Using index`로 표시되며, **`SELECT *`를 피하라는 조언의 실질적 근거**가 이것입니다.

# 9. EXPLAIN으로 검증하기

이론만 알고 끝내면 안 됩니다. 반드시 확인하는 습관을 들여야 합니다.

```sql
EXPLAIN SELECT * FROM orders WHERE YEAR(order_date) = 2024;
```
```
type: ALL          ← 풀 테이블 스캔
key:  NULL         ← 사용된 인덱스 없음
rows: 998234       ← 읽을 것으로 예상되는 행 수
Extra: Using where ← 다 읽고 나서 걸러냄
```

```sql
EXPLAIN SELECT * FROM orders 
 WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01';
```
```
type: range              ← 범위 스캔 ✓
key:  idx_order_date     ← 인덱스 사용 ✓
rows: 51200              ← 읽을 양 대폭 감소
Extra: Using index condition
```

## `type` 읽는 법 (좋은 순서대로)

| type | 의미 |
|---|---|
| `const` / `eq_ref` | PK/UNIQUE로 단 1행 — 최고 |
| `ref` | 인덱스 등호 조건, 여러 행 |
| `range` | **인덱스 범위 스캔** ← 목표 |
| `index` | 인덱스 전체 스캔 (풀스캔보단 낫지만 나쁨) |
| `ALL` | **풀 테이블 스캔** ← 피해야 할 것 |

## `Extra` 읽는 법

| Extra | 의미 |
|---|---|
| `Using index` | **커버링 인덱스** — 테이블 접근조차 안 함 (최고) |
| `Using index condition` | 인덱스 컨디션 푸시다운(ICP) 작동 |
| `Using where` | 읽은 뒤 필터링 |
| `Using filesort` / `Using temporary` | 정렬/임시테이블 발생 — 튜닝 대상 |

> **더 정확한 확인:** `EXPLAIN ANALYZE`(8.0.18+)는 **예상치가 아닌 실제 실행 시간과 실제 읽은 행 수**를 보여줍니다. 옵티마이저의 추정이 틀린 경우를 잡아낼 수 있습니다.

# 10. Spring / JPA 환경에서의 적용

## 10.1 격리 수준

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void settle() { ... }
```

- 기본값 `Isolation.DEFAULT`는 **DB 설정을 그대로 따른다**는 의미. MySQL이면 RR.
- 실무에서 격리 수준을 코드로 올리는 일은 드뭅니다. 전역적으로 락 경합과 데드락 위험이 커지기 때문입니다.
- 일반적 접근: **격리 수준은 기본값으로 두고, 문제되는 특정 지점에만 비관적/낙관적 락을 국소 적용.**

## 10.2 인덱스 — JPA에서 놓치기 쉬운 지점

```java
// ✗ JPQL의 함수가 그대로 SQL 함수로 번역됨
@Query("SELECT o FROM Order o WHERE FUNCTION('YEAR', o.orderDate) = :year")

// ✓ 서비스 계층에서 범위를 계산해 넘긴다
LocalDateTime start = LocalDate.of(year, 1, 1).atStartOfDay();
LocalDateTime end   = start.plusYears(1);
List<Order> findByOrderDateGreaterThanEqualAndOrderDateLessThan(
        LocalDateTime start, LocalDateTime end);
```

QueryDSL도 마찬가지로 `order.orderDate.year().eq(2024)` 대신  
`order.orderDate.goe(start).and(order.orderDate.lt(end))`를 씁니다.

```yaml
spring:
  jpa:
    properties:
      hibernate:
        format_sql: true
logging:
  level:
    org.hibernate.SQL: debug
```

**실제 생성되는 SQL을 찍어보고 그것을 `EXPLAIN`에 거는 습관**이 중요합니다. ORM이 만든 쿼리라고 최적인 것은 전혀 아닙니다.

## 10.3 외래 키에 대한 실무 관점

외래 키는 정합성을 보장하지만, 부모 테이블에 락이 전파되고 대량 삽입 성능을 떨어뜨립니다. 그래서 대규모 트래픽 서비스나 JPA 프로젝트에서는 **DB 레벨 FK 없이 애플리케이션에서 정합성을 관리**하는 선택도 흔합니다.

```java
@JoinColumn(foreignKey = @ForeignKey(ConstraintMode.NO_CONSTRAINT))
```

다만 이건 트레이드오프이지 "FK를 안 쓰는 게 정답"인 것은 아닙니다.

# 11. 부록: 핵심 요약

## 11.1 전체 흐름

```
[스토리지 엔진]
MySQL은 2계층 구조다
  → 그래서 엔진마다 기능이 다르다
  → InnoDB: 트랜잭션 O, 행 락, FK O, Redo/Undo 있음 → 실무 표준
  → MyISAM: 트랜잭션 X, 테이블 락, FK X, 복구 로그 없음 → 레거시
  → MEMORY: RAM 저장, 재시작 시 데이터 소실(구조는 유지)

[트랜잭션과 격리]
동시성이 필요하다
  → 그런데 커밋 전 중간 상태가 존재한다
  → 남이 그걸 보면 이상 현상 (Dirty / Non-Repeatable / Phantom)
  → 얼마나 막을지 고르게 한 것이 격리 수준 4단계
  → 락으로 막으면 읽기·쓰기가 서로 막는다
  → 그래서 MVCC (언두 로그 + Read View)로 우회
  → Read View를 언제 만드느냐가 RC와 RR의 차이
  → 스냅샷이 안 통하는 잠금 읽기는 Next-Key Lock으로 보완
  → 그래도 Lost Update, Write Skew는 애플리케이션이 책임진다

[인덱스]
인덱스는 "원본 값으로 정렬된 B+Tree"다
  → 정렬되어 있으니 시작점을 찾고 범위 끝에서 멈출 수 있다 (range)
  → 그런데 인덱스에는 함수 결과값이 저장되어 있지 않다
  → 함수를 씌우면 모든 행에 함수를 적용해봐야 한다 → 풀스캔
  → 그래서 컬럼은 가공하지 말고 상수 쪽을 조작한다 (SARGable)
  → 정 안 되면 함수 기반 인덱스 / 생성 컬럼 (차선책)
  → 단, 대상 범위가 너무 넓으면 옵티마이저는 일부러 풀스캔
  → 결론은 항상 EXPLAIN으로 확인
```

## 11.2 한 줄 원칙

| 주제 | 원칙 |
|---|---|
| 스토리지 엔진 | 특별한 이유가 없으면 **InnoDB** |
| 격리 수준 | 기본값 유지 + 필요한 지점에만 국소적 락 |
| Lost Update | 격리 수준으로 안 막힌다 → 락 또는 원자적 UPDATE |
| 인덱스 조건 | **컬럼은 연산자 왼쪽에 홀로, 아무것도 씌우지 않는다** |
| 날짜 조건 | `>= 시작 AND < 다음구간시작` |
| 검증 | 추측하지 말고 `EXPLAIN` / `EXPLAIN ANALYZE` |

## 11.3 자주 나오는 함정 정리

| 함정 | 진실 |
|---|---|
| MySQL 기본 격리 수준은 READ COMMITTED | **REPEATABLE READ** (MySQL만 예외) |
| RR에서 Phantom Read가 빈번하다 | InnoDB는 MVCC+Next-Key Lock으로 **대부분 방지** |
| MyISAM은 행 락을 쓴다 | **테이블 락** |
| MyISAM도 트랜잭션을 지원한다 | **지원하지 않음** (문법만 통과) |
| MyISAM에 FK를 걸면 에러가 난다 | **에러 없이 무시됨** (더 위험) |
| MEMORY 재시작 시 테이블도 사라진다 | **테이블 구조는 남고 데이터만 소실** |
| Redo Log = Binlog | Redo는 엔진 계층/크래시 복구, Binlog는 서버 계층/복제 |
| 인덱스가 있으면 항상 탄다 | 대상이 20~25% 넘으면 **일부러 풀스캔** |
| `phone = 01012345678` 정상 동작 | 암묵적 형변환으로 **인덱스 무력화** |
