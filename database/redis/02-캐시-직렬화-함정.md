# Redis 캐시 직렬화 함정

> 한 줄 요약
> **Redis는 객체를 그대로 담지 못한다. 문자열로 바꿔 저장하고, 되돌릴 때 타입 정보가 온전히 남지 않을 수 있다.**

## 무슨 일이 일어나는가

집계 결과처럼 여러 값이 묶인 객체를 캐시에 넣으면, 클라이언트가 **직렬화해서 문자열로 저장**하고 꺼낼 때 **역직렬화**한다. 이때 **원래 어떤 타입이었는지 정보가 남지 않으면 일반 맵(`LinkedHashMap`)으로 복원**된다.

코드는 원래 타입인 줄 알고 쓰다가 `ClassCastException`으로 터진다.

## 왜 발견이 늦는가

**캐시가 맞았을 때만 터진다.** 캐시가 비어 있으면 DB에서 제대로 된 객체를 받으므로 멀쩡하다.

```
첫 요청  → 캐시 없음 → DB 조회 → 정상 ✓
두 번째  → 캐시 있음 → 역직렬화 → 터짐 ✗
```

로컬에서는 재현이 안 되고, 배포 직후에는 멀쩡하다가 잠시 뒤부터 터지는 식이라 원인을 찾기 어렵다.

## 대응

**① 직렬화 방식을 명시한다.** 타입 정보를 함께 저장하거나, DTO 전용 직렬화기를 지정한다.

```java
// 값 직렬화기를 타입에 맞게 지정
template.setValueSerializer(new Jackson2JsonRedisSerializer<>(StatsDto.class));
```

**② 꺼낸 값을 믿지 않는다.** 기대한 타입이 아니면 캐시가 없는 것으로 치고 원본을 읽는다.

```java
Object cached = cache.get(key);
if (!(cached instanceof StatsDto dto)) {
    return loadFromDb(id);
}
```

**캐시는 없어도 되는 것이다.** 이상하면 붙들고 고치려 하지 말고 버리고 원본을 보는 편이 맞다.

**③ 스키마가 바뀌면 키 버전을 올린다.** 필드를 추가·변경했는데 옛 형식이 남아 있으면 같은 문제가 난다 → [캐시 전략과 무효화](../../performance/03-캐시-전략과-무효화.md)
