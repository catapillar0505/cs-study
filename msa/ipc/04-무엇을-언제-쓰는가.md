# 무엇을 언제 쓰는가

## 한 줄로

**둘 중 하나를 고르는 게 아니라 상황에 따라 섞어 씁니다.** 정확성과 성능이 중요한 핵심 호출은 gRPC, 만들기 쉽고 눈으로 확인해야 하는 부가 호출은 REST.

## 판단표

| 상황 | 선택 | 이유 |
|---|---|---|
| **돈·재고처럼 정확성이 중요하고 호출이 잦음** | **gRPC** | 타입 안전(컴파일 타임 검증) + 빠름 |
| **알림·로그처럼 부가적이고 단순함** | **REST / Feign** | 만들기 쉽고 디버깅 편함 |
| **외부 회사·브라우저에 공개하는 API** | **REST** | gRPC는 브라우저가 직접 못 부름 |
| 팀마다 언어가 다름 | gRPC | `.proto`에서 각 언어 코드가 자동 생성됨 |
| 빠르게 프로토타입을 만들어야 함 | REST | 계약서·코드 생성 단계가 없음 |

## 한 요청 안에서 섞어 쓰는 모습

계좌 이체를 예로 들면, 하나의 요청이 두 가지 일을 합니다.

```
[이체 요청] ──gRPC(빠르고 엄격)──▶ [은행 서비스]   ← 돈이 걸린 핵심 처리
           ──OpenFeign(느슨함)──▶ [알림 서비스]   ← 부가적인 알림 발송
```

코드로는 이렇게 나란히 놓입니다.

```java
// 1. [gRPC] 실제 이체 처리 — 정확성이 중요
TransferResponse res = bankingStub.processTransfer(transferRequest);

// 2. [OpenFeign] 알림 발송 — 부가 기능
notificationClient.sendNotification(notificationRequest);
```

**두 줄 다 그냥 메서드 호출처럼 생겼지만**, 하나는 이진 데이터로 HTTP/2를 타고,
하나는 JSON으로 HTTP/1.1을 탑니다.

## 계약이 강제되는가 — 가장 큰 실무 차이

이 차이는 코드 중복으로 눈에 보입니다.

**gRPC 쪽**: `.proto` 하나를 양쪽이 공유하므로 데이터 클래스가 **한 벌만** 존재합니다.

```
        [ 공용 .proto → 자동 생성 jar ]
              ↙                    ↘
        은행 서비스              이체 서비스
```

**REST 쪽**: 강제 장치가 없으므로 같은 DTO를 **양쪽에 따로 씁니다.**

```java
// 이체 서비스에도
public record NotificationRequest(String transactionId, String message) { }

// 알림 서비스에도 똑같이 (따로 작성)
public record NotificationRequest(String transactionId, String message) { }
```

**이 중복이 "REST는 계약이 문서에만 있다"의 실체입니다.**
한쪽에서 필드 이름을 바꿔도 **컴파일은 잘 됩니다.** 실행해야 깨집니다.

> 완화 방법은 있습니다. **공용 모듈(common-module)을 만들어 DTO를 공유**하면
> 중복이 사라지고 컴파일 타임 안전성도 얼마간 얻습니다.
> 다만 이건 팀의 약속일 뿐, gRPC처럼 **도구가 강제**하는 것은 아닙니다.
> → [msa/09 멀티모듈 프로젝트 구조](../09-멀티모듈-프로젝트-구조.md)

## 꼭 알아야 할 함정 — 부가 기능의 실패가 핵심을 죽이면 안 된다

위 이체 예시에서 **알림 서비스를 꺼놓고** 요청해보면 이런 일이 벌어집니다.

```
① 이체 처리 성공 ✅   (돈은 이미 옮겨졌다)
② 알림 발송 실패 ❌
→ 전체 요청이 500 에러
→ 사용자 화면: "이체 실패"  💀
```

**"돈은 빠졌는데 사용자에게는 실패로 보인다"** — 분산 시스템에서 가장 골치 아픈 상황입니다.

여기서 두 가지 교훈이 나옵니다.

| 교훈 | 대응 |
|---|---|
| **부가 기능의 실패가 핵심 기능을 실패로 만들면 안 된다** | 알림 호출을 `try-catch`로 감싸거나, 아예 **비동기(이벤트)로 분리** → [eda](../eda/README.md) |
| **실패에 대비한 장치가 필요하다** | 재시도·서킷브레이커·폴백 → [msa/06 장애 격리](../06-장애-격리.md) |

> **이 지점이 "동기 통신 → 비동기 통신(EDA)"으로 넘어가는 동기입니다.**
> 알림은 **"주문이 생성되었다"는 이벤트를 던져두면 알림 서비스가 알아서 가져가 처리**하게 바꾸면,
> 알림 서비스가 죽어 있어도 이체는 성공합니다.

## 통신 방식 선택은 "정답"보다 "설명 가능한가"

세 가지 축으로 정리하면 됩니다.

```
     전송 형식        프로토콜         계약이 강제되는 시점
   이진 vs JSON  ×  HTTP/2 vs 1.1  ×  컴파일 vs 런타임
```

gRPC는 세 축 모두에서 "엄격하고 빠른 쪽", REST는 "느슨하고 편한 쪽"입니다.
어느 쪽이든, **왜 그쪽을 골랐는지 설명할 수 있으면 됩니다.**
