# gRPC와 Protobuf

## 한 줄로

**`.proto` 파일 하나를 계약서로 삼아** 서버와 클라이언트의 코드를 자동 생성한다. 데이터는 필드 이름 대신 **번호**로 실려 가므로 작고 빠르며, 규약이 어긋나면 **빌드가 실패**한다.

## 문제부터 — REST의 아쉬운 점 세 가지

| 아쉬운 점 | 설명 |
|---|---|
| **① 느림** | JSON은 사람이 읽는 텍스트입니다. `{"quantity":100}` 처럼 **필드 이름까지 전부 문자열로** 실려 나가고, 받는 쪽도 문자열 파싱을 해야 합니다 |
| **② 규약이 문서에만 있음** | 상대가 `quantity`를 보내는지 `qty`를 보내는지는 문서를 믿거나 코드를 까봐야 합니다. 오타는 **실행해봐야** 드러납니다 |
| **③ 연결 낭비** | HTTP/1.1은 요청 하나가 커넥션 하나를 점유합니다 |

gRPC는 이 셋을 각각 바꿉니다.

| | REST | gRPC |
|---|---|---|
| 데이터 형식 | JSON (텍스트) | **Protobuf (이진)** — 이름 대신 번호 |
| 규약 정의 | 문서 / 코드 | **`.proto` 파일 하나가 원본**, 거기서 코드가 생성됨 |
| 전송 | HTTP/1.1 | **HTTP/2** — 커넥션 하나로 여러 요청 동시 처리 |
| 오류 발견 | 런타임 | **컴파일 타임** |

> **멀티플렉싱(Multiplexing)**: HTTP/2가 커넥션 하나로 여러 요청을 동시에 주고받는 기능입니다.
> 1차선 도로(HTTP/1.1)를 여러 차선(HTTP/2)으로 바꾼 것이라 생각하면 됩니다.

## 핵심 개념 1 — IDL과 `.proto`

**IDL = Interface Definition Language (인터페이스 정의 언어)**

"우리 둘이 주고받을 데이터의 모양과 함수 목록"을 **언어 중립적으로** 적어둔 **계약서**입니다.

**왜 "언어 중립"인가?** 계약서를 자바로 쓰면 파이썬 팀이 못 씁니다.
그래서 자바도 파이썬도 아닌 **제3의 문법**으로 씁니다. gRPC의 IDL이 **Protocol Buffers(`.proto`)** 입니다.

```protobuf
syntax = "proto3";                     // 문법 버전

service StockService {                 // ← 함수 목록 (인터페이스)
  rpc CheckStock (ProductRequest) returns (StockResponse);
}

message ProductRequest {               // ← 데이터 구조 (DTO)
  string productId = 1;
}

message StockResponse {
  string productId = 1;
  int32  quantity  = 2;
  bool   inStock   = 3;
}
```

읽는 법:

- **`service`** = 인터페이스. "이 서버는 `CheckStock`이라는 함수를 제공한다"는 선언
- **`message`** = 데이터 구조체. 자바로 치면 클래스
- **`= 1`, `= 2`는 값이 아닙니다.** 이게 초보자가 가장 많이 오해하는 지점입니다 ↓

## 필드 번호 — Protobuf가 빠른 진짜 이유

JSON은 필드 **이름**을 매번 같이 보냅니다.

```
{"productId":"123","quantity":100,"inStock":true}      → 대략 48 바이트
```

Protobuf는 이름 대신 **번호**만 보냅니다.

```
[1] "123"   [2] 100   [3] true                          → 대략 12 바이트
 ↑            ↑         ↑
 태그 1번     태그 2번   태그 3번  →  받는 쪽은 자기 .proto를 보고
                                     "1번은 productId구나" 하고 해석
```

**양쪽이 같은 `.proto`를 갖고 있으니 번호만 보내도 뜻이 통합니다.**
전화번호부를 둘 다 갖고 있으면 "3번한테 연락해"만 말해도 되는 것과 같습니다.

그래서 작고 빠릅니다. 대신 **규칙이 하나 생깁니다.**

> ⚠️ **한 번 정한 필드 번호는 절대 바꾸지 마세요.**
> 필드 *이름*은 바꿔도 됩니다(번호로 통신하니까). 하지만 *번호*를 바꾸면
> 아직 옛 `.proto`로 빌드된 상대가 데이터를 **엉뚱하게 해석**합니다.
> 필드를 지울 땐 삭제 대신 `reserved 2;` 로 번호를 예약해 재사용을 막는 것이 정석입니다.
>
> 반대로 **새 번호로 필드를 추가하는 것은 안전합니다.** 모르는 번호는 무시되므로
> 서버·클라이언트를 동시에 배포하지 않아도 됩니다. 이걸 **하위 호환(backward compatibility)** 이라 합니다.

## 핵심 개념 2 — 코드 생성

`.proto`는 그 자체로는 아무 일도 못 합니다. **`protoc`(프로토콜 컴파일러)** 가 자바 코드로 번역해야 합니다.

```
                        stock.proto  (계약서 원본)
                              │
                  ┌───────────┴────────────┐
             protoc (기본)          protoc + grpc 플러그인
                  │                        │
                  ▼                        ▼
        ProductRequest.java          StockServiceGrpc.java
        StockResponse.java            ├─ ...ImplBase     (서버가 상속할 추상 클래스)
        (데이터 클래스)                └─ ...BlockingStub (클라이언트가 쓸 호출 대행자)
                  │                        │
                  └───────────┬────────────┘
                              ▼
                   공용 라이브러리(jar) 하나
                  ┌───────────┴────────────┐
                  ▼                        ▼
            재고 서비스               주문 서비스
             (구현한다)                (Stub을 쓴다)
```

**서버와 클라이언트가 똑같은 이 jar를 공유합니다.** 이게 "규약을 한 곳에 둔다"의 실체입니다.

**여기서 "컴파일 타임 검증"이 나옵니다.**

- 서버는 자동 생성된 추상 클래스를 **상속**합니다 → `.proto`에 없는 메서드를 만들면 **컴파일 에러**
- 클라이언트는 자동 생성된 Stub을 **호출**합니다 → 파라미터 타입이 틀리면 **컴파일 에러**

REST에서는 오타가 404로 실행 중에 드러났지만, 여기서는 **빌드가 아예 안 됩니다.**

> **주의**: 생성된 코드는 `build/` 폴더 아래라 Git에 커밋되지 않습니다.
> 그래서 **저장소를 클론한 직후에는 그 클래스들이 없어 IDE가 빨간 줄을 긋습니다.**
> 한 번 빌드하면 사라집니다. 처음 만나면 당황스러운 부분입니다.

## 핵심 개념 3 — Channel과 Stub

자동 생성 코드에서 실제로 쓰는 건 두 가지입니다.

| 용어 | 정체 | 비유 |
|---|---|---|
| **Channel** | 상대 서버로 가는 **HTTP/2 연결 통로**. 재사용되고 여러 스레드가 같이 써도 안전 | **전화선** |
| **Stub** | 그 통로 위에서 특정 함수를 대신 호출해주는 **대행 객체** | **그 전화선을 쓰는 수화기** |

`Stub`은 영어로 "몽당연필, (표의) 남은 조각"이라는 뜻인데, 여기서는 **"진짜 구현 대신 서 있는 껍데기"** 를 가리킵니다.

```java
StockResponse response = stockStub.checkStock(request);
```

이 한 줄이 실제로 하는 일:

```
① request 객체를 Protobuf 이진 데이터로 변환 (직렬화)
② HTTP/2로 상대 서버에 전송
③ 응답 바이트를 받음
④ 다시 StockResponse 객체로 변환 (역직렬화)
```

**전부 Stub이 대신합니다.** 이게 [01](01-서비스-간-통신이란.md)에서 말한 RPC의 목적입니다.

Stub은 세 종류가 생성되는데, 가장 이해하기 쉬운 것은 **BlockingStub**입니다.

| Stub 종류 | 호출 방식 |
|---|---|
| **BlockingStub** | **동기** — 응답 올 때까지 그 자리에서 대기. 평범한 메서드 호출과 같은 감각 |
| FutureStub | 비동기 — 결과를 나중에 꺼내 씀 |
| (Async)Stub | 비동기 — 콜백으로 받음 |

## 핵심 개념 4 — `StreamObserver`와 4가지 통신 방식

서버 코드에서 가장 낯선 부분이 이것입니다.

```java
public void checkStock(ProductRequest request, StreamObserver<StockResponse> responseObserver) {
    ...
    responseObserver.onNext(response);   // 데이터 1건 "보내기"
    responseObserver.onCompleted();      // "더 보낼 거 없음" 종료 신호
}
```

**왜 `return response;` 가 아닌가?**

gRPC는 "응답 1건 주고 끝"이 아닌 경우도 지원해야 하기 때문입니다.
`.proto`에 `stream` 키워드를 붙이면 **네 가지 통신 방식**이 나옵니다.

| 방식 | 예시 | 데이터를 보내는 횟수 |
|---|---|---|
| **Unary** (기본) | 재고 조회 | 서버가 **1번** |
| Server Streaming | 실시간 주식 시세 구독 | 서버가 **N번** |
| Client Streaming | 대용량 파일 업로드 | 클라이언트가 **N번** |
| Bi-directional | 채팅 | **양쪽이 N번** |

네 방식을 **하나의 API 모양으로 통일**하려다 보니,
"값을 return한다"가 아니라 **"콜백 객체에 데이터를 흘려보내고, 다 흘렸으면 끝났다고 알린다"** 가 된 것입니다.

```
onNext(...)     — 데이터를 보낸다 (Unary는 정확히 1번)
onCompleted()   — 정상 종료.  ⚠️ 이걸 안 부르면 클라이언트는 영원히 기다립니다
onError(...)    — 에러 종료
```

## Protobuf 객체는 왜 Builder로만 만드나

```java
StockResponse response = StockResponse.newBuilder()   // new 가 아님
    .setProductId("123")
    .setQuantity(100)
    .build();                                          // ← 여기서 굳어짐
```

Protobuf 메시지는 **불변(immutable) 객체**입니다. 한 번 만들면 값을 바꿀 수 없습니다.
**네트워크로 나갈 데이터가 도중에 바뀌면 안 되기 때문**입니다.
그래서 Builder로 다 채운 뒤 `build()`로 굳히는 방식만 제공합니다.

## 흔한 오해

**"`= 1`, `= 2`는 기본값이다"**
아닙니다. **필드 번호(태그)** 입니다. 값과 아무 관계가 없습니다.

**"브라우저에서 gRPC 서버 주소를 열면 뭔가 보일 것이다"**
브라우저 주소창에 `localhost:9090`을 쳐도 **아무것도 안 나옵니다. 정상입니다.**
gRPC는 HTTP/2 + 이진 프레임이라 브라우저가 직접 말을 걸 수 없습니다.
찔러보려면 `grpcurl` 같은 전용 도구나 Postman의 gRPC 탭을 씁니다.

**"gRPC 포트와 웹 포트가 같다"**
보통 다릅니다. 한 애플리케이션이 **HTTP 포트(예: 8081)와 gRPC 포트(예: 9090)를 따로** 엽니다.
서비스 디스커버리도 원래 HTTP용이라, gRPC 포트는 **부가 정보(메타데이터)로 따로 실어** 등록해야 합니다.
