# JWT

## 한 줄로

**서명이 붙은 JSON 조각**이다. 누구나 열어볼 수 있으므로 비밀을 담으면 안 되고, 대신 **위조할 수는 없으므로** 서버가 아무것도 저장하지 않고도 "누구인지"를 믿을 수 있다.

## 구조 — 점으로 나뉜 세 덩어리

**JWT = JSON Web Token**

```
eyJhbGciOiJSUzI1NiJ9  .  eyJzdWIiOiJob25nIiwiZXhwIjox...  .  SflKxwRJSMeKK...
└──── Header ────┘        └────────── Payload ────────┘     └── Signature ──┘
    "서명 알고리즘"           "실제 내용 (클레임)"              "위조 방지 서명"
```

| 부분 | 내용 |
|---|---|
| **Header** | 어떤 알고리즘으로 서명했는가 |
| **Payload** | 사용자 정보 = **클레임(Claim)** |
| **Signature** | 위조 검증용 서명. **발급자만 만들 수 있음** |

## 클레임(Claim)이란

**클레임**은 "주장, 진술"이라는 뜻입니다. **토큰이 담고 있는 사실 한 줄 한 줄**을 가리킵니다.

```json
{
  "sub": "3f2a1b8c-7d4e-...",                    ← 이 토큰의 주인은 이 사람이다
  "iss": "http://localhost:8080/realms/msa-shop", ← 이 토큰은 여기서 발급했다
  "exp": 1756789012,                              ← 이 시각에 만료된다
  "preferred_username": "hong",                   ← 로그인 아이디는 hong이다
  "realm_access": { "roles": ["admin"] }          ← 이 사람의 역할은 admin이다
}
```

자주 쓰는 표준 클레임 세 개:

| 클레임 | 원래 단어 | 뜻 |
|---|---|---|
| **`sub`** | **sub**ject | **주체 = 사용자 고유 식별자.** 절대 안 바뀜 |
| **`iss`** | **iss**uer | 발급자 (누가 만든 토큰인가) |
| **`exp`** | **exp**iration | 만료 시각 |

> **`sub`가 실무에서 가장 중요합니다.**
> 이 값이 내 DB에서 그 사용자의 프로필을 찾는 **연결 고리**가 됩니다. → [07 회원가입](07-회원가입과-사용자-데이터.md)
> 이메일이나 아이디로 잇지 않는 이유는 **그것들은 바뀔 수 있기 때문**입니다.

## ⚠️ 가장 중요한 오해 — JWT는 암호화가 아닙니다

**Header와 Payload는 암호화가 아니라 Base64 인코딩일 뿐입니다.**

**Base64**는 "아무 데이터나 문자로 표현하는 방식"이지 **암호가 아닙니다.**
비밀번호를 거는 게 아니라, 그냥 **모양을 바꿔 적은 것**입니다.

```
   토큰 문자열을 https://jwt.io 에 붙여넣으면
   → Payload 내용이 그대로 보입니다. 누구나. 열쇠 없이.
```

그래서:

> **JWT에 비밀번호·주민번호 같은 민감정보를 넣으면 안 됩니다.**
>
> JWT가 보장하는 것은 **"비밀"이 아니라 "위조되지 않았음(무결성)"** 입니다.

```
읽기      → 누구나 가능 ✅
고쳐 쓰기 → 불가능 ❌  (서명이 깨져서 바로 들통남)
```

## 서명 방식 두 가지 — 이게 MSA에서 중요합니다

| 방식 | 서명 키 / 검증 키 | 문제 |
|---|---|---|
| **대칭키** (HS256) | 서명과 검증에 **같은 비밀키** | 검증하려면 **모든 서비스가 그 비밀키를 알아야** 함 → 하나만 털려도 끝 |
| **비대칭키** (RS256) | 서명 = **개인키**(발급자만), 검증 = **공개키**(누구나) | ✅ 서비스들은 공개키만 있으면 됨 |

**비유: 도장과 도장 확인표**

```
  대칭키:  "도장을 다 나눠 준다"  → 누구나 도장을 찍을 수 있음 😱
  비대칭키: "도장은 나만, 그 도장 모양표는 다 나눠 준다"
           → 다들 진짜인지 확인은 할 수 있지만, 찍을 수는 없음 ✅
```

**실무의 인증 서버는 비대칭키(RS256)를 씁니다.** 그 덕분에 이런 구조가 가능합니다.

```
   [인증 서버]  ← 개인키로 서명해 토큰 발급
        │
        │ 공개키만 공개 (누구나 받아갈 수 있음)
        ├────────────┬────────────┐
        ▼            ▼            ▼
   [게이트웨이]  [서비스 A]   [서비스 B]
    각자 혼자 검증. 인증 서버에 매번 물어볼 필요 없음
```

## 검증은 실제로 무엇을 확인하나

서비스가 토큰을 받으면 **세 가지**를 확인합니다.

| 검사 | 무엇을 보나 | 실패하면 |
|---|---|---|
| **서명** | 공개키로 서명이 맞는지 | 위조된 토큰 → 401 |
| **만료(`exp`)** | 지금이 만료 시각 전인지 | 만료된 토큰 → 401 |
| **발급자(`iss`)** | 우리가 신뢰하는 곳이 발급했는지 | 남의 토큰 → 401 |

세 번째가 의외로 중요합니다. 서명이 유효하고 만료 전이어도,
**다른 시스템이 발급한 토큰**이면 우리 서비스에 쓰면 안 되기 때문입니다.

> **동작 순서**: 서비스는 기동 후 **최초 1회 공개키를 받아와 캐싱**하고,
> 이후에는 **인증 서버 없이 혼자 검증**합니다.
> 그래서 **인증 서버가 잠깐 죽어도 이미 발급된 토큰의 검증은 계속 동작합니다.**

## 액세스 토큰과 리프레시 토큰

로그인하면 보통 **두 개**를 받습니다.

| | 액세스 토큰 | 리프레시 토큰 |
|---|---|---|
| 용도 | **매 요청에 실려** API 호출에 사용 | 액세스 토큰이 만료됐을 때 **새로 받기 위해** 사용 |
| 수명 | 짧음 (보통 **5분**) | 김 (보통 30분~수일) |
| 노출 위험 | 큼 (매번 네트워크를 탐) | 작음 (갱신할 때만 씀) |

**왜 이렇게 나누나?**
액세스 토큰은 자주 오가므로 유출 위험이 큽니다. **짧게 두어 유출돼도 피해 시간을 줄입니다.**
그렇다고 사용자가 5분마다 다시 로그인할 수는 없으니, 리프레시 토큰으로 **조용히 갱신**합니다.

> 이 조용한 갱신을 **Silent Refresh**라고 합니다. → [06 SPA와 CORS](06-spa와-cors.md)

> **실습 중 갑자기 401이 뜨면 대부분 토큰 만료입니다.** 다시 받으면 됩니다.

## 흔한 오해 정리

| 오해 | 사실 |
|---|---|
| "JWT는 암호화되어 있다" | **인코딩일 뿐입니다.** 누구나 읽습니다 |
| "JWT를 쓰면 무조건 안전하다" | 위조는 못 하지만, **훔친 토큰은 그대로 쓸 수 있습니다.** 그래서 짧게 둡니다 |
| "토큰을 서버에서 지우면 로그아웃된다" | 서버는 토큰을 저장하지 않습니다. **만료 전까지는 유효합니다** |
| "Bearer가 뭔가 특별한 것이다" | `Bearer`는 "소지자"라는 뜻입니다. **"이 토큰을 가진 자에게 권한을 준다"** 는 관례적 표기입니다 |
