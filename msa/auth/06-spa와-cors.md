# SPA와 CORS

## 한 줄로

브라우저 앱이 **직접 토큰을 들고** 다른 출처의 API를 부르면 두 가지가 새로 필요해진다. 비밀을 숨길 수 없으니 **PKCE**, 출처가 다르니 **CORS**.

## SPA란

**SPA = Single Page Application (단일 페이지 애플리케이션)**

```
      [ 옛날 방식: 서버 렌더링 ]              [ SPA ]

  브라우저 ──요청──▶ 서버                브라우저 ──최초 1회──▶ 서버
          ◀─완성된 HTML─                        ◀── JS 묶음 ──
  (페이지마다 새로 받아서 화면 깜빡임)
                                        이후엔 JS가 API만 호출해서
                                        화면을 직접 고쳐 그림 (깜빡임 없음)
                                        브라우저 ──API──▶ 서버
                                                ◀── JSON ──
```

**핵심 차이: 화면을 서버가 그리느냐, 브라우저의 자바스크립트가 그리느냐.**

React·Vue·Angular가 SPA를 만드는 대표 도구입니다.
그리고 **SPA는 서버와 JSON API로만 대화하므로, 인증도 API 방식(토큰)으로 해야 합니다.**

## 문제 ① — SPA는 비밀을 가질 수 없습니다

[03](03-oauth2와-keycloak.md)에서 본 `client-secret`을 SPA는 쓸 수 없습니다.

```
   JS 코드에 secret을 넣으면?
   → 브라우저 개발자도구 → Sources 탭 → 그냥 보입니다 😱
   → 빌드된 파일을 내려받아도 보입니다
```

그래서 SPA는 **public 클라이언트**(비밀 없는 클라이언트)로 등록합니다.
그런데 secret이 없으면 **인가 코드를 훔친 사람이 그냥 토큰으로 바꿔갈 수 있습니다.** 위험합니다.

### 해결 — PKCE

**PKCE = Proof Key for Code Exchange** (읽을 때는 "픽시")

secret 대신 **매번 새로 만드는 일회용 비밀**을 쓰는 방식입니다.

```
① 앱이 무작위 문자열을 만든다              (원본, code_verifier)
② 그것을 해시한 값을 로그인 요청에 함께 보낸다  (지문, code_challenge)
        ▼
③ 인증 서버가 그 지문을 기억해둔다
        ▼
④ 로그인 성공 → 인가 코드 발급
        ▼
⑤ 앱이 코드 + **원본 문자열**을 보내 토큰을 요청
        ▼
⑥ 인증 서버: "원본을 해시하니 아까 그 지문과 같네" → 토큰 발급 ✅
```

**공격자가 ④의 코드를 가로채도 원본 문자열을 모르므로 토큰으로 바꿀 수 없습니다.**
해시는 되돌릴 수 없기 때문입니다.

> **해시(hash)** 란 어떤 값을 고정 길이 문자열로 바꾸는 **일방향 함수**입니다.
> 같은 입력은 항상 같은 결과가 나오지만, **결과에서 입력을 되돌릴 수는 없습니다.**
> 비밀번호를 저장할 때 쓰는 그 해시입니다.

> **SPA와 모바일 앱에서는 PKCE가 필수**라고 생각하면 됩니다.
> 설정에서는 보통 한 줄(`pkceMethod: 'S256'` 등)로 켜집니다. `S256`은 SHA-256을 쓴다는 뜻입니다.

## 문제 ② — 출처가 다릅니다 (CORS)

### 출처(Origin)란

**출처 = 프로토콜 + 호스트 + 포트**, 이 셋의 조합입니다.

```
http://localhost:5173      ← 프론트엔드 개발 서버
http://localhost:8090      ← API 서버
      ↑         ↑
   같은 호스트지만 포트가 다름 → 브라우저는 "다른 출처"로 봅니다
```

**셋 중 하나만 달라도 다른 출처입니다.** `http`와 `https`도 다른 출처입니다.

### 동일 출처 정책 — 브라우저의 기본 보안 규칙

> **"어떤 페이지의 자바스크립트는 다른 출처의 응답을 읽을 수 없다"**

**왜 이런 규칙이 있나?** 없다면 이런 일이 벌어집니다.

```
① 사용자가 은행 사이트에 로그인 (쿠키 보유)
② 악성 사이트 방문
③ 악성 사이트의 JS가 은행 API를 호출
④ 브라우저가 쿠키를 자동으로 실어 보냄 → 잔액 응답이 옴
⑤ 악성 사이트가 그 응답을 읽어감 💀
```

**동일 출처 정책이 ⑤를 막습니다.** 요청은 갈 수 있어도 **응답을 읽지 못하게** 합니다.

### CORS — 그 규칙에 예외를 두는 표준

**CORS = Cross-Origin Resource Sharing (교차 출처 자원 공유)**

> **핵심: 허락하는 주체는 브라우저가 아니라 "서버"입니다.**
> 서버가 응답 헤더로 **"저 출처에서 온 요청은 읽어도 좋다"** 고 말해주면 브라우저가 그때만 허용합니다.

```
   프론트엔드 (5173)               API 서버 (8090)
        │  GET /api/users/me            │
        │  Origin: http://localhost:5173│
        ├──────────────────────────────▶│
        │                               │ "5173은 허용 목록에 있네"
        │  Access-Control-Allow-Origin: http://localhost:5173
        │◀──────────────────────────────┤
        │
   브라우저: "서버가 허락했네" → JS가 응답을 읽게 해줌 ✅
```

### ⚠️ 가장 흔한 오해

**CORS 에러는 서버가 요청을 거부한 게 아닙니다.**

```
서버: 200 OK 를 잘 보냈음
브라우저: "허락 헤더가 없네" → JS에게 안 넘겨줌 → 콘솔에 빨간 에러
```

**그래서 서버 로그에는 아무 문제가 없고, 브라우저 콘솔에만 에러가 뜹니다.**
"서버는 멀쩡한데 왜 안 되지?" 하는 상황의 정체가 이것입니다.

## Preflight — 본 요청 전의 사전 확인

브라우저는 "위험할 수 있는" 요청은 **본 요청을 보내기 전에 미리 물어봅니다.**

```
① OPTIONS /api/users/me           ← Preflight (사전 확인)
   "이 출처에서, 이 메서드로, 이 헤더를 붙여 보내도 되나요?"
        ▼
   서버: "그 출처, 그 메서드, 그 헤더 다 허용합니다"
        ▼
② GET /api/users/me               ← 본 요청
   Authorization: Bearer ...
```

**언제 Preflight가 발생하나?**

- `GET`/`POST`/`HEAD`가 아닌 메서드 (`PUT`, `DELETE`, `PATCH`)
- **표준이 아닌 헤더를 붙일 때** ← **`Authorization` 헤더가 여기 해당합니다**

> **즉, 토큰을 쓰는 SPA는 거의 항상 Preflight가 발생합니다.**
>
> 그래서 CORS 설정에 **`OPTIONS` 메서드와 `Authorization` 헤더를 반드시 허용**해야 합니다.
> 빠뜨리면 **본 요청은 시작도 못 합니다.**
>
> 개발자도구 Network 탭에 요청이 **`OPTIONS`와 `GET` 두 개**로 보이는 것이 정상입니다.

## CORS 설정에서 챙길 네 가지

| 설정 | 뜻 | 빠뜨리면 |
|---|---|---|
| 허용할 **출처** | 어느 출처를 믿을지 | 그 출처의 JS가 응답을 못 읽음 |
| 허용할 **메서드** | GET·POST·… | **`OPTIONS` 누락 시 Preflight 실패** |
| 허용할 **헤더** | 어떤 요청 헤더를 받을지 | **`Authorization` 누락 시 토큰을 못 보냄** |
| **인증정보** 허용 여부 | 쿠키 등을 함께 보낼지 | 쿠키 기반일 때 필요 |

> ⚠️ **"모든 출처 허용(`*`)" + "인증정보 허용"은 함께 쓸 수 없습니다.**
> 아무 출처나 허용하면서 인증정보까지 보내면 위험하기 때문에 표준이 금지하고 있습니다.

> ⚠️ **보안 필터가 CORS보다 먼저 도는 경우**가 있습니다.
> 그러면 **Preflight(`OPTIONS`) 요청이 401로 거부**됩니다. `OPTIONS` 요청에는 토큰이 안 붙으니까요.
> 보안 설정에 CORS를 **명시적으로 연결**해 줘야 합니다. 아주 흔한 함정입니다.

## CORS 설정이 두 군데 필요합니다

브라우저가 **인증 서버와 API 서버 둘 다** 직접 호출하기 때문입니다.

| 어디 | 무엇을 위해 |
|---|---|
| **인증 서버의 허용 출처 설정** | 브라우저 → **인증 서버** 호출 (토큰 교환) |
| **API 서버의 CORS 설정** | 브라우저 → **API 서버** 호출 |

한쪽만 해 두면 다른 쪽에서 막힙니다.

## SPA가 토큰을 다루는 실제 모습

### 토큰을 요청마다 붙이는 일 — 인터셉터

API 호출마다 헤더를 붙이는 코드를 반복하지 않으려면,
**HTTP 클라이언트의 인터셉터(가로채기)** 를 씁니다.

```
   "이 클라이언트로 나가는 모든 요청 직전에 토큰을 붙여라"
        ▼
   화면 코드는 그냥 api.get('/api/users/me') 만 쓰면 됨
```

**게이트웨이 필터([gateway/03](../gateway/03-필터로-요청-가로채기.md))와 발상이 같습니다** — 가로채서 공통 처리를 끼워 넣는 것.

### Silent Refresh — 조용한 갱신

액세스 토큰은 보통 5분이면 만료됩니다. 사용자가 5분마다 다시 로그인할 수는 없습니다.

```
   요청 직전에 확인:
     만료까지 여유가 있으면  → 그대로 사용
     곧 만료될 것 같으면     → 리프레시 토큰으로 조용히 새 토큰을 받아옴 (화면 깜빡임 없음)
     리프레시 토큰도 만료됐으면 → 다시 로그인 필요
```

> ⚠️ **갱신은 비동기입니다.** 기다리지 않고 요청을 보내면 **옛 토큰이 붙어 401**이 날 수 있습니다.

### 토큰은 어디에 저장되나

라이브러리들은 보통 토큰을 **`localStorage`가 아니라 자바스크립트 메모리**에 둡니다.

- 새로고침하면 사라지지만, **인증 서버에 로그인 세션이 남아 있어 조용히 다시 받아옵니다**
- `localStorage`보다 안전한 기본값입니다

> 다만 **XSS가 발생하면 실행 중인 스크립트가 메모리의 토큰에 접근할 수는 있습니다.**
> 그래서 보안만 놓고 보면 [BFF](05-bff-패턴.md)가 여전히 낫습니다.

## 두 방식 비교

| | **SPA 직접** | **BFF** |
|---|---|---|
| 토큰 보관 | **브라우저 JS 메모리** | **서버 세션** |
| 브라우저가 보내는 것 | `Authorization: Bearer ...` | **세션 쿠키만** |
| 인증 서버 Client | **public** (secret 없음) | **confidential** (secret 있음) |
| PKCE | **필수** | 불필요 (secret이 있으므로) |
| CORS | **필요** (출처가 다름) | 불필요 (같은 출처로 프록시) |
| XSS 시 토큰 유출 | **가능** ⚠️ | **불가능** |
| 구현 난이도 | **쉬움** | 조금 복잡 |
| 백엔드 수정 | 불필요 | 불필요 |

**보안만 놓고 보면 BFF가 낫습니다.** 다만 SPA 직접 방식이 **더 단순하고 프론트/백엔드를 완전히
분리**할 수 있어 여전히 널리 쓰입니다. **두 방식의 차이를 아는 것이 중요합니다.**
