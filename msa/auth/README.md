# auth — 인증과 인가

서비스를 여러 개로 쪼갠 뒤 **"이 요청을 보낸 사람이 누구이고, 이걸 해도 되는가"** 를 어떻게 판단할지 정리합니다.

모놀리스에서 쓰던 세션 방식이 왜 무너지는지에서 시작해, **토큰(JWT)** → **표준 규약(OAuth2)** →
**전문 인증 서버(Keycloak)** → **토큰을 누가 들고 있을 것인가(BFF vs SPA)** 순서로 이어집니다.

## 전체 구조 한눈에

```
       사용자
         │ ① 아이디/비밀번호
         ▼
  ┌──────────────────┐
  │   인증 서버       │  개인키로 서명한 JWT 발급
  │  (Keycloak)      │  공개키는 누구에게나 공개
  └────────┬─────────┘
           │ ② 토큰
           ▼
  ┌──────────────────────────────────────────────┐
  │  토큰을 누가 들고 있나?                        │
  │                                              │
  │   브라우저가 직접 [06]      서버 세션에 [05]   │
  │   · PKCE 필요               · secret 필요     │
  │   · CORS 필요               · 쿠키만 오감      │
  │   · XSS에 노출              · XSS에 안전      │
  └────────┬─────────────────────────────────────┘
           │ ③ Authorization: Bearer ...
           ▼
  ┌──────────────────────────────────────────────┐
  │  내 서비스들 (Resource Server)                 │
  │   · 공개키로 서명·만료·발급자 검증 [02]         │
  │   · 토큰 안의 역할로 인가 판단 [04]             │
  │   · 게이트웨이가 검증했어도 다시 검증 (제로 트러스트) │
  └──────────────────────────────────────────────┘
```

## 이 폴더를 관통하는 문장들

> **인증은 "너 누구야", 인가는 "너 이거 해도 돼".** 실패하면 각각 401과 403.

> **JWT는 암호화가 아니라 인코딩이다.** 누구나 읽을 수 있지만 **고쳐 쓸 수는 없다.**

> **인증은 직접 만들지 마라.** 로그인·해싱·토큰 발급·소셜 로그인은 전문 서버에 맡긴다.

> **관문은 1차 방어선, 백엔드는 최후 방어선.** 내부 네트워크도 믿지 않는다.
