# OAuth2와 Keycloak

## 한 줄로

OAuth2는 **"토큰을 주고받는 방식"을 정한 표준 규약**이고, Keycloak은 그 규약을 구현한 **인증 서버 제품**이다. 내가 만든 서비스들은 전부 **토큰을 검증만 하는 쪽**이 된다.

## OAuth2의 등장인물 4명

**OAuth2**는 "인가(권한 위임)"를 위한 **표준 규약**입니다. 네 역할이 등장합니다.

```
┌──────────────────┐                    ┌────────────────────────┐
│ Resource Owner   │                    │ Authorization Server   │
│ (자원 주인 = 사용자)│ ①ID/PW ────────▶ │ (인증 서버 = Keycloak)  │
└──────────────────┘                    └───────────┬────────────┘
         │                                          │ ②토큰 발급
         ▼                                          ▼
┌──────────────────┐   ③토큰 첨부해 요청   ┌────────────────────────┐
│ Client           │ ───────────────────▶ │ Resource Server        │
│ (앱/브라우저/curl) │                     │ (자원 서버 = 내 서비스들)│
└──────────────────┘                      └────────────────────────┘
```

| 역할 | 우리말로 | 실제로는 |
|---|---|---|
| **Resource Owner** | 자원의 주인 | **사용자 본인** |
| **Authorization Server** | 인가 서버 | **Keycloak** — 토큰을 발급하는 곳 |
| **Client** | 클라이언트 | 토큰을 **받아가는** 앱 (브라우저·모바일앱·서버) |
| **Resource Server** | 자원 서버 | 토큰을 **검증하고 데이터를 주는** 서버 = **내가 만든 서비스들** |

**핵심**: 내가 만든 서비스는 대부분 **Resource Server**입니다.

> **로그인 화면도, 비밀번호 검증도, 회원 DB도 만들지 않습니다.**
> 오직 **"이 토큰이 진짜인가"만 확인**합니다.

## Client와 Resource Server의 차이 — 자주 헷갈립니다

| | **Resource Server** | **OAuth2 Client** |
|---|---|---|
| 하는 일 | 토큰을 **검증만** 한다 | 토큰을 **직접 받아온다** |
| 로그인 화면 | 없음 (남이 알아서 받아옴) | **인증 서버로 리다이렉트시킴** |
| 필요한 것 | **공개키** | **client-id + client-secret** |
| 세션 | 없음 (Stateless) | **있음** (받은 토큰을 보관해야 하니까) |

이 구분이 [05 BFF 패턴](05-bff-패턴.md)의 전부입니다.
**같은 게이트웨이라도 Resource Server로 만드느냐 Client로 만드느냐에 따라 구조가 완전히 달라집니다.**

## OIDC — OAuth2 위에 얹은 한 겹

**OAuth2는 원래 "인가"용이라 "이 사람이 누구인가"를 정의하지 않았습니다.**

원래 목적이 이런 것이었습니다: *"이 앱이 내 구글 드라이브 파일을 읽게 허락한다"*
— 여기에는 "그 사람이 누구인가"가 필요 없습니다. 권한만 넘기면 되니까요.

그런데 실무에서는 **로그인(신원 확인)** 에도 쓰고 싶어졌습니다.
그래서 그 위에 한 겹을 표준으로 얹은 것이 **OIDC**입니다.

**OIDC = OpenID Connect**

```
┌────────────────────────────────────┐
│  OIDC   — 인증(신원). "너 누구야"   │
├────────────────────────────────────┤
│  OAuth2 — 인가(권한). "이거 해도 돼"│
└────────────────────────────────────┘
```

Keycloak은 OIDC를 구현합니다. 그래서 **URL에 `openid-connect`가 들어갑니다.**

```
http://localhost:8080/realms/msa-shop/protocol/openid-connect/token
                                      └──────┬──────┘
                                      OIDC 프로토콜이라는 표시
```

## Keycloak의 용어 4개

이것만 알면 관리 콘솔을 쓸 수 있습니다.

```
Keycloak 서버
 └─ Realm  "msa-shop"        ← 완전히 독립된 세계 (사용자·설정이 서로 격리됨)
     ├─ Client  "msa-client" ← 토큰을 받아갈 애플리케이션 등록 정보
     ├─ User    "hong"       ← 실제 사용자 계정
     └─ Role    "admin"      ← 권한 딱지. User에게 부여함
```

| 용어 | 뜻 | 비유 |
|---|---|---|
| **Realm** | 독립된 사용자·설정 공간 | **회사 하나** |
| **Client** | 토큰을 요청할 앱의 등록 정보 | 그 회사의 **출입증 발급 대상** |
| **User** | 사용자 계정 | **직원** |
| **Role** | 권한 이름 | **직급·직책** |

> **Realm이 "영역, 왕국"이라는 뜻**입니다. 서로 완전히 격리됩니다.
> A realm의 사용자는 B realm에서는 존재하지 않습니다.

> ⚠️ **`master` realm은 Keycloak 자체를 관리하는 realm입니다.**
> 여기에 앱 사용자를 만들면 안 됩니다. 반드시 **새 realm을 만들어** 그 안에서 작업하세요.
> (`master`가 필요한 경우는 [07 회원가입](07-회원가입과-사용자-데이터.md)에 나옵니다.)

## Client 설정에서 가장 중요한 두 가지

Keycloak 콘솔에서 Client를 만들 때 **성격을 정하는 설정 두 개**가 있습니다.

### ① public이냐 confidential이냐

**"이 클라이언트가 비밀(secret)을 안전하게 보관할 수 있는가?"** 를 묻는 것입니다.

| | **public** | **confidential** |
|---|---|---|
| secret | 없음 | **있음** |
| 해당하는 것 | 브라우저 SPA, 모바일 앱 | **서버 애플리케이션** |
| 이유 | 코드가 사용자 기기에 내려가므로 **비밀을 숨길 수 없음** | 서버 안에만 있으므로 숨길 수 있음 |

> **SPA에 secret을 넣으면?** 개발자도구 → Sources 탭에서 **그냥 보입니다.**
> 그래서 브라우저 앱은 반드시 public입니다. 그 대신 [PKCE](06-spa와-cors.md)로 구멍을 메웁니다.

### ② 어떤 흐름(flow)을 허용할 것인가

| 흐름 | 어떻게 토큰을 받나 | 언제 |
|---|---|---|
| **Standard flow**<br>(Authorization Code) | **인증 서버 로그인 화면으로 리다이렉트** → 돌아올 때 코드 → 토큰으로 교환 | **실무 표준** |
| **Direct access grants**<br>(password) | 앱이 **ID/PW를 직접 받아** 인증 서버에 보냄 | **학습·테스트용** |

> ⚠️ **Direct access grants(password 방식)는 실무에서 권장되지 않습니다.**
> 앱이 사용자 비밀번호를 직접 만지기 때문입니다. OAuth 2.1에서는 아예 제거되었습니다.
> **`curl`로 토큰을 받아 테스트할 때만** 편의상 켭니다.
>
> **Standard flow에서는 비밀번호를 인증 서버만 봅니다.** 앱은 구경도 못 합니다.
> 앱이 해킹당해도 비밀번호는 새지 않습니다. → [05 BFF](05-bff-패턴.md) · [06 SPA](06-spa와-cors.md)

## 리다이렉트 주소를 미리 등록해야 하는 이유

Standard flow를 쓰면 **로그인 후 돌아올 주소**를 Keycloak에 미리 등록해야 합니다.

**등록되지 않은 주소로는 절대 리다이렉트하지 않습니다.**

왜냐하면, 그러지 않으면 이런 공격이 가능하기 때문입니다.

```
공격자가 만든 링크:
  .../auth?client_id=msa-client&redirect_uri=http://evil.com
                                              ↑ 여기로 토큰이 날아감 💀
```

이걸 **오픈 리다이렉트(Open Redirect) 공격**이라고 하고, 사전 등록이 그 방어책입니다.

> **실습 중 `Invalid parameter: redirect_uri` 에러**를 만나면 대부분 이 등록의 오타입니다.
> 가장 자주 걸리는 함정입니다.

## 개발 모드의 함정 — 설정이 날아갑니다

Keycloak을 `start-dev` 모드로 띄우면 **내장 DB(H2)에 데이터를 저장**합니다.
**컨테이너를 지우면 realm 설정이 전부 사라집니다.**

| 대응 | 방법 |
|---|---|
| 백업 | 콘솔에서 **Realm settings → Action → Partial export** 로 JSON 저장 |
| 영속화 | 외부 DB(MySQL 등)를 붙여 띄우기 → [07](07-회원가입과-사용자-데이터.md) |

> **버전마다 관리자 계정 환경변수 이름이 다릅니다.** 관리자 콘솔 로그인이 안 되면 이걸 의심하세요.
>
> | 버전 | 환경변수 |
> |---|---|
> | ~25 | `KEYCLOAK_ADMIN` / `KEYCLOAK_ADMIN_PASSWORD` |
> | **26+** | **`KC_BOOTSTRAP_ADMIN_USERNAME` / `KC_BOOTSTRAP_ADMIN_PASSWORD`** |
