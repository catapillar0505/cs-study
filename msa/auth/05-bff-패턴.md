# BFF 패턴

## 한 줄로

**토큰을 브라우저에 주지 말고 서버가 대신 들고 있자.** 브라우저는 자바스크립트로 읽을 수 없는 세션 쿠키만 갖고, 게이트웨이가 백엔드로 보낼 때 토큰을 붙여 준다.

## 문제 — 토큰을 브라우저 어디에 둘 것인가

브라우저가 토큰을 직접 들고 있으면 **보관 장소를 정해야 합니다.** 그런데 어디에 둬도 문제가 있습니다.

| 저장 위치 | 문제 |
|---|---|
| **`localStorage`** | **자바스크립트로 읽을 수 있음** → XSS 공격 한 번이면 토큰이 통째로 털림 |
| `sessionStorage` | 같은 문제 + 탭을 닫으면 사라짐 |
| 자바스크립트 변수(메모리) | 새로고침하면 사라짐 (다시 받아오면 되긴 함) |

> **XSS = Cross-Site Scripting.** 공격자가 페이지에 **악성 스크립트를 심는** 공격입니다.
> 내가 짠 코드가 아니어도 됩니다. **광고 스크립트나 npm 패키지 하나만 오염돼도** 벌어집니다.
>
> `localStorage`에 토큰이 있으면 `localStorage.getItem('token')` **한 줄로 탈취**됩니다.
> 그리고 그 토큰이 유효한 동안 **공격자가 완전히 그 사용자 행세**를 할 수 있습니다.

## 해결 — BFF

**BFF = Backend For Frontend (프론트엔드 전용 백엔드)**

프론트엔드를 **대신해서 인증을 처리해 주는 서버 계층**입니다.

```
        [ 브라우저가 토큰을 드는 방식 ]        [ BFF 방식 ]

  브라우저                                 브라우저
   └ 토큰 보관 😰 (XSS 위험)                └ 세션 쿠키만 보관 ✅
        │ Authorization: Bearer ...              │ Cookie: JSESSIONID=...
        ▼                                        ▼
   게이트웨이                                게이트웨이
   └ 토큰 검증만                             └ 토큰을 서버 세션에 보관 🔒
                                             └ 백엔드로 보낼 때 붙여줌
```

**핵심 세 가지**

1. 브라우저는 **토큰을 절대 보지 못한다**
2. 브라우저는 **`HttpOnly` 세션 쿠키**만 갖는다 → **자바스크립트로 읽을 수 없음** → XSS로 못 훔침
3. 게이트웨이가 세션에 토큰을 보관했다가, 백엔드로 보낼 때 **자동으로 붙여준다**

> **`HttpOnly` 쿠키란?** 브라우저가 요청에 **자동으로 실어 보내지만**,
> **자바스크립트(`document.cookie`)로는 읽을 수 없는** 쿠키입니다.
> 이 한 가지 속성이 XSS로부터 토큰을 지켜 줍니다.

## 게이트웨이의 역할이 뒤바뀝니다

[03](03-oauth2와-keycloak.md)에서 본 두 역할이 여기서 갈립니다.

| | **Resource Server 방식** | **BFF (Client) 방식** |
|---|---|---|
| 게이트웨이가 하는 일 | 토큰을 **검증만** | 토큰을 **직접 받아옴** |
| 로그인 화면 | 관여 안 함 | **인증 서버로 리다이렉트시킴** |
| 필요한 것 | 공개키 | **client-id + client-secret** |
| 세션 | 없음 (Stateless) | **있음** (토큰을 여기 보관) |

```
   브라우저 ──▶ [ 게이트웨이 = OAuth2 Client ] ──▶ [ 백엔드 = Resource Server ]
                  로그인을 대신 수행                    토큰 검증만
```

**백엔드는 여전히 Resource Server입니다.** 바뀌는 것은 게이트웨이 하나뿐입니다.

## Authorization Code Flow — 진짜 로그인 흐름

```
① 브라우저: 보호된 페이지에 접속
        ▼
② 게이트웨이: "너 로그인 안 했네" → 인증 서버 로그인 페이지로 리다이렉트
        ▼
③ 브라우저: 인증 서버 로그인 화면 → 사용자가 ID/PW 입력
        │   ★ 비밀번호는 인증 서버만 봅니다. 게이트웨이는 절대 못 봅니다
        ▼
④ 인증 서버: 로그인 성공 → 게이트웨이로 되돌려보냄  (?code=일회용_교환권)
        ▼
⑤ 게이트웨이: 받은 code + client-secret 을 들고 인증 서버에 **직접** 요청
        │   (브라우저를 거치지 않고 서버끼리)  → 토큰 획득 🔒
        ▼
⑥ 게이트웨이: 토큰을 **세션에 저장**하고, 브라우저에는 세션 쿠키만 줌
        ▼
⑦ 브라우저: 이후 요청마다 세션 쿠키만 보냄 (토큰은 구경도 못 함)
```

**⑤번이 핵심입니다.** 토큰이 **브라우저를 거치지 않고 서버끼리** 오갑니다.

### 왜 `code`라는 일회용 교환권을 한 번 거치나?

④에서 브라우저를 통해 오는 값은 누가 훔쳐볼 수도 있습니다.
그래서 **토큰이 아니라 일회용 교환권만** 보냅니다.

```
   코드를 훔쳤다 → 토큰으로 바꾸려면 client-secret 이 필요 → 서버만 갖고 있음
                → 바꿀 수 없음 ✅
```

> 이 구조 덕분에 "브라우저를 지나가는 값"과 "실제 토큰"이 분리됩니다.
> 비밀을 보관할 수 없는 SPA는 secret 대신 다른 방법(**PKCE**)으로 같은 효과를 냅니다. → [06](06-spa와-cors.md)

## 토큰을 백엔드로 어떻게 넘기나 — TokenRelay

브라우저는 토큰을 안 보냅니다. 그럼 백엔드는 어떻게 받을까요?

```
   브라우저                게이트웨이                    백엔드
      │ Cookie: JSESSIONID    │                            │
      ├──────────────────────▶│                            │
      │                       │ ① 쿠키로 세션 찾기          │
      │                       │ ② 세션에서 토큰 꺼냄        │
      │                       │ ③ Authorization: Bearer ... │
      │                       ├───────────────────────────▶│
```

**게이트웨이가 세션에 보관해둔 토큰을 꺼내 헤더로 붙여 줍니다.**
Spring Cloud Gateway에서는 `TokenRelay`라는 내장 필터가 이 일을 합니다.

> **"로그인은 됐는데 API만 401"** 이라면 이 필터를 빠뜨린 것입니다. 가장 흔한 증상입니다.

## BFF의 가장 큰 장점 — 백엔드를 안 고쳐도 된다

**인증 방식을 통째로 바꿨는데, 백엔드 서비스는 한 줄도 안 바뀝니다.**

백엔드 입장에서는 **"`Authorization` 헤더에 유효한 토큰이 오면 된다"** 는 계약만 지켜지면,
그 토큰을 **브라우저가 보냈든 게이트웨이가 붙였든 상관없기 때문**입니다.

## 대가 — 다시 Stateful이 됩니다

[01](01-인증과-인가.md)에서 "세션은 MSA에서 무너진다"고 했는데, BFF는 **세션을 다시 씁니다.**

```
   게이트웨이를 2대로 늘리면?
   → 세션이 공유되지 않아 로그인이 풀림 (01의 그 문제가 그대로 재현)
   → 해결: 세션을 Redis 같은 외부 저장소로 빼기 (Spring Session)
```

> **BFF는 Stateless의 장점을 일부 포기하고 보안을 얻는 선택입니다.**
> 이 트레이드오프를 아는 것이 중요합니다.

## CSRF를 다시 켜야 합니다 — 자주 놓치는 지점

토큰 방식에서는 CSRF 보호를 끄는 것이 관례였습니다. 그 근거는 이랬습니다.

> "우리는 쿠키가 아니라 `Authorization` 헤더를 쓴다.
> 헤더는 브라우저가 자동으로 붙여주지 않으므로 **CSRF 공격이 성립하지 않는다.**"

**하지만 BFF는 세션 쿠키를 씁니다.** 브라우저가 쿠키를 **자동으로** 실어 보내므로
**CSRF 공격이 실제로 성립할 수 있습니다.**

> **CSRF = Cross-Site Request Forgery.**
> 악성 사이트가 몰래 요청을 보내도 브라우저가 쿠키를 자동으로 실어 줘서 서버가 속는 공격입니다.

**정확한 기준은 이렇습니다.**

```
   ❌ "REST API니까 CSRF를 끈다"
   ❌ "토큰 방식이니까 끈다"
   ✅ "쿠키를 안 쓰니까 끈다"     ← BFF는 쿠키를 쓰므로 해당 없음. 켜야 합니다
```

## 두 방식 비교

| | **브라우저가 토큰을 듦** | **BFF** |
|---|---|---|
| 토큰 보관 | 브라우저 | **서버 세션** 🔒 |
| 브라우저가 보내는 것 | `Authorization: Bearer ...` | **세션 쿠키만** |
| 인증 서버 Client | public (secret 없음) | **confidential** (secret 있음) |
| 서버 상태 | 없음 (Stateless) | **있음** (세션) |
| XSS 시 토큰 유출 | **가능** ⚠️ | **불가능** |
| CSRF | 해당 없음 | **대비 필요** |
| 테스트 | curl 편함 | **브라우저 필요** (리다이렉트+쿠키라서) |
| 구현 난이도 | 쉬움 | 조금 복잡 |

**어느 쪽이 맞나?**

| 클라이언트 | 권장 |
|---|---|
| **웹 브라우저 (SPA 포함)** | **BFF** — XSS 위험 때문 |
| 모바일 앱 | Authorization Code + PKCE (앱이 토큰 보관) |
| 서버 간 통신 / CLI | 토큰을 직접 다루는 방식 |

> **브라우저가 클라이언트라면 BFF가 현재 권장되는 방식**입니다.
> 다만 브라우저가 직접 토큰을 다루는 방식도 **더 단순하고 프론트/백엔드를 완전히 분리**할 수 있어
> 여전히 널리 쓰입니다. → [06 SPA와 CORS](06-spa와-cors.md)
