# 회원가입과 사용자 데이터

## 한 줄로

**인증 정보는 인증 서버에, 서비스 고유 정보는 내 DB에** 나눠 저장하고, 인증 서버가 만들어준 **UUID 하나로 둘을 잇는다.**

## 문제 — 사용자 정보를 누가 저장하나

[03](03-oauth2와-keycloak.md)에서 "인증은 직접 만들지 말고 인증 서버에 맡겨라"고 했습니다.
로그인·토큰 발급·비밀번호 해싱을 전부 대신 해주니까요.

그런데 회원가입을 하려니 문제가 생깁니다.

```
   사용자가 입력하는 것
   ┌────────────────────────────────────┐
   │ 아이디      hong        ← 누가 저장? │
   │ 비밀번호    ****        ← 누가 저장? │
   │ 이메일      hong@a.com  ← 누가 저장? │
   ├────────────────────────────────────┤
   │ 닉네임      길동이       ← 누가 저장? │
   │ 전화번호    010-...     ← 누가 저장? │
   │ 주소        서울시...    ← 누가 저장? │
   └────────────────────────────────────┘
```

**인증 서버는 "인증"을 위한 서버이지 "회원 관리" 서버가 아닙니다.**
닉네임·전화번호·주소 같은 **서비스 고유 데이터**를 넣을 자리가 마땅치 않습니다.
(속성(attribute) 기능이 있긴 하지만 **검색·조인·통계에 쓰기엔 부적합**합니다.)

## 해결 — 책임을 둘로 나눈다

```
┌─────────────────────────────┐      ┌──────────────────────────────┐
│ 인증 서버 (인증 담당)         │      │ 내 서비스 DB (프로필 담당)     │
│  · 아이디 / 비밀번호          │      │  · 닉네임                     │
│  · 이메일                    │      │  · 전화번호                    │
│  · 비밀번호 해싱·정책         │      │  · 주소                       │
│  · 토큰 발급                 │      │                              │
│                             │      │                              │
│  UUID: 3f2a-1b8c-...  ──────┼──────┼─▶ PK = 그 UUID               │
└─────────────────────────────┘      └──────────────────────────────┘
              ↑                                    ↑
        "너 누구야"를 책임                "너에 대해 무엇을 아는가"를 책임
```

**연결 고리는 인증 서버가 만들어준 UUID입니다.**

- 인증 서버에 사용자를 만들면 **UUID가 하나 생깁니다**
- 그 UUID를 **내 DB 테이블의 기본키(PK)** 로 씁니다
- 나중에 로그인한 사용자의 토큰에서 **`sub` 클레임(= 그 UUID)** 을 꺼내면 프로필을 찾을 수 있습니다

> **UUID = Universally Unique Identifier.**
> 전 세계에서 겹치지 않도록 만들어진 식별자로, `3f2a1b8c-7d4e-4a1b-9c2d-8e5f0a1b2c3d` 같은
> 하이픈 포함 **36자 문자열**입니다.

### 왜 이메일이나 아이디로 잇지 않나

**바뀔 수 있기 때문입니다.**

```
   이메일로 이었다 → 사용자가 이메일을 바꿈 → 프로필을 못 찾음 💀
   UUID로 이었다  → 이메일이 바뀌어도 UUID는 그대로 ✅
```

**절대 안 바뀌는 값(불변 식별자)으로 잇는 것**이 원칙입니다.
[02 JWT](02-jwt.md)에서 `sub`가 중요하다고 한 이유가 이것입니다.

## 어떻게 계정을 만드나 — Admin API

관리자 콘솔(웹 화면)에서 하는 일은 **전부 REST API로도 할 수 있습니다.**
콘솔 자체가 그 API를 쓰는 웹 앱이기 때문입니다.

**우리 서비스가 사용자 대신 그 API를 호출해 계정을 만들어 주는 것**이 이 방식의 핵심입니다.

```
  회원가입 요청
     │  {아이디, 비밀번호, 이메일, 닉네임, 전화번호, 주소}
     ▼
┌─────────────────────────────────────────────┐
│ 우리 회원 서비스                             │
│                                             │
│  ① 관리자 토큰 받기                          │
│  ② 인증 서버에 계정 생성 요청 ───────────────┼──▶ [ 인증 서버 ]
│     ← 201 Created + Location 헤더           │
│  ③ Location 에서 UUID 추출                   │
│  ④ 내 DB에 프로필 저장 (PK = 그 UUID) ───────┼──▶ [ 내 DB ]
└─────────────────────────────────────────────┘
```

> **왜 인증 서버가 제공하는 회원가입 화면을 안 쓰나?**
> 그러면 **닉네임·주소를 같이 받을 수 없습니다.**
> 우리 화면에서 한 번에 받고 뒤에서 나눠 저장하려면 이 방식이 필요합니다.

## realm이 두 개 나옵니다 — 헷갈리는 지점

Admin API를 호출하려면 **관리자 권한 토큰**이 필요합니다.
그런데 그 관리자는 **다른 realm에 있습니다.**

| | realm | 역할 |
|---|---|---|
| **인증 주체** (누가 요청하나) | **`master`** | Keycloak 자체를 관리하는 realm. **관리자 계정이 사는 곳** |
| **작업 대상** (어디에 만드나) | **`msa-shop`** | 실제 서비스 사용자가 저장될 곳 |

```
   ① master realm 에서 관리자 토큰을 받아
   ② 그 토큰으로 msa-shop realm 에 사용자를 만든다
```

설정에 `realm`과 `target-realm` 같은 값이 **두 개** 있는 이유가 이것입니다.

## `Location` 헤더에서 UUID 꺼내기 — 가장 낯선 부분

**인증 서버는 사용자를 만들고 나서 UUID를 응답 본문(JSON)으로 주지 않습니다.**
**본문은 비어 있습니다.**

대신 **HTTP `Location` 헤더**에 새로 만들어진 자원의 주소를 담아 줍니다.

```
HTTP/1.1 201 Created
Location: http://.../admin/realms/msa-shop/users/3f2a1b8c-7d4e-4a1b-9c2d-8e5f0a1b2c3d
                                                 └──────────── 이게 UUID ────────────┘
```

그래서 **경로의 마지막 조각을 잘라내는** 처리가 필요합니다.

> **이건 특정 제품의 별난 규칙이 아니라 REST의 표준 관례입니다.**
> **"자원을 새로 만들었으면 `201 Created` + `Location` 헤더로 그 주소를 알려준다"** 가 원칙입니다.
> 다른 API에서도 자주 만나게 됩니다.

## 토큰 요청은 JSON이 아니라 form 형식입니다

```
Content-Type: application/x-www-form-urlencoded      ← 이것
Content-Type: application/json                        ← 이게 아님
```

**OAuth2 토큰 엔드포인트는 표준적으로 form 형식을 요구합니다.**
JSON으로 보내면 **415 Unsupported Media Type** 이 납니다. 아주 흔한 실수입니다.

> **form-urlencoded** 란 `a=1&b=2` 형태로 값을 이어 붙이는 방식입니다.
> HTML `<form>`이 데이터를 보내는 기본 형식이라 그런 이름이 붙었습니다.

## ⚠️ 가장 중요한 한계 — 분산 트랜잭션

```java
@Transactional              // ← 이건 "내 DB만" 되돌립니다
public void signUp(...) {
  // ① 인증 서버에 계정 생성  ← 성공
  // ② 내 DB에 프로필 저장    ← 여기서 실패하면?
}
```

**`@Transactional`은 내 DB만 되돌립니다. 인증 서버에 만들어진 계정은 그대로 남습니다.**

```
   인증 서버: hong 계정 존재 ✅
   내 DB:    프로필 없음     ❌
   → 로그인은 되는데 프로필이 없는 "고아 계정" 발생 💀
```

**서로 다른 두 시스템에 걸친 작업은 하나의 트랜잭션으로 묶을 수 없습니다.**
이것이 **분산 트랜잭션 문제**입니다. → [eda/09](../eda/09-분산-트랜잭션-문제.md)

### 실무 해결책

| 방법 | 설명 |
|---|---|
| **보상 트랜잭션 (Saga)** | DB 저장이 실패하면 **방금 만든 계정을 삭제**하는 처리를 직접 넣는다 |
| 순서 바꾸기 | DB를 먼저 저장 → 계정 생성 실패 시 DB 롤백 (다만 UUID를 먼저 못 받음) |
| 배치 정리 | 주기적으로 고아 계정을 찾아 정리 |

**가장 흔한 것은 보상 트랜잭션입니다.**

> "되돌리는 것"이 아니라 **"반대 작업을 새로 하는 것"** 이라는 점이 핵심입니다.
> Saga 패턴 전반은 [eda/10](../eda/10-saga-패턴.md)에 정리되어 있습니다.

## 실무에서 반드시 챙길 것

| # | 문제 | 대응 |
|---|---|---|
| 1 | **관리자 비밀번호가 설정 파일에 평문** | 환경변수로 빼기. 더 나아가 **전용 서비스 계정**을 만들어 "사용자 관리" 권한만 부여 |
| 2 | 요청마다 관리자 토큰을 새로 발급 | 토큰을 캐싱하고 만료 시에만 갱신 |
| 3 | **회원가입 API가 무방비** | 요청 제한(Rate Limiter)이나 CAPTCHA. 없으면 봇이 계정을 무한정 만듭니다 → [gateway/04](../gateway/04-요청-제한-rate-limiter.md) |
| 4 | 입력값 검증 없음 | 필수값·이메일 형식 검증 |

> **①이 특히 중요합니다.** `master` realm의 관리자 계정은 **Keycloak 전체를 제어할 수 있는 최고 권한**입니다.
> 이 값이 Git에 올라가면 인증 시스템 전체가 뚫립니다.

## 회원가입 경로에는 인증을 걸면 안 됩니다

게이트웨이 설정에서 자주 놓치는 부분입니다.

**회원가입은 로그인하기 전에 하는 일**이므로, 아직 토큰이 없는 사용자가 접근해야 합니다.

```
   /api/users/signup   → 누구나 허용
   그 외 전부          → 인증 필요
```

**순서에 주의하세요.** "누구나 허용" 규칙이 **"전부 인증 필요"보다 앞에** 와야 합니다.
