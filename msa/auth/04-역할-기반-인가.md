# 역할 기반 인가

## 한 줄로

토큰 안의 **역할(role)** 을 보고 접근을 허용할지 정한다. 그런데 **인증 서버가 역할을 적어 놓은 모양**과 **프레임워크가 기대하는 모양**이 달라서, 그 사이를 이어주는 **번역기**가 필요하다.

## 인증만으로는 부족한 이유

[01](01-인증과-인가.md)에서 본 두 질문을 다시 떠올려 봅시다.

```
인증 통과 = "당신은 hong이군요"       ← 여기까지가 [02] JWT 검증
       ↓
    그런데 hong이 관리자 페이지에 들어가도 되나?  ← 이게 인가
```

로그인한 사람이라고 아무거나 다 할 수 있으면 안 됩니다.
**"이 사람이 이 일을 해도 되는가"** 를 판단하는 근거가 **역할(Role)** 입니다.

## 역할은 토큰 안에 실려 옵니다

인증 서버는 로그인한 사람의 역할을 **토큰의 클레임에 담아** 보냅니다.

```json
{
  "preferred_username": "boss",
  "realm_access": {
    "roles": ["admin", "user"]      ← 이 사람은 admin 역할을 갖고 있다
  }
}
```

**서버가 DB를 뒤질 필요가 없습니다.** 역할이 토큰 안에 이미 적혀 있고, 서명이 그 내용을 보증합니다.

> 이것이 [01](01-인증과-인가.md)에서 말한 Stateless의 실체입니다.
> "누구인지"뿐 아니라 **"무슨 권한인지"까지 토큰 하나에 들어 있습니다.**

## 문제 — 표기법이 서로 다릅니다

**Keycloak이 토큰에 넣어주는 모양:**

```json
"realm_access": { "roles": ["admin"] }
```

**Spring Security가 찾는 모양:**

```
GrantedAuthority: "ROLE_admin"
```

**두 가지 차이**가 있습니다.

| | Keycloak | Spring Security |
|---|---|---|
| 위치 | `realm_access` 안에 **중첩** | 최상위 권한 목록 |
| 이름 | `admin` | **`ROLE_admin`** (접두사가 붙음) |

기본 설정으로는 Spring이 `realm_access` **안을 들여다보지 않습니다.**
그래서 **아무리 admin 역할을 부여해도 403이 납니다.**

## 해결 — 번역기(Converter)

하는 일은 딱 두 가지입니다.

```
   토큰                          번역기가 하는 일              Spring이 이해하는 형태
{                            ① realm_access 안으로 들어가
  "realm_access": {             roles 배열을 꺼낸다        →   ["ROLE_admin", "ROLE_user"]
    "roles": ["admin","user"] ② 각 이름 앞에 ROLE_ 을 붙인다
  }
}
```

코드로는 이 정도 분량입니다.

```java
List<String> roles = ...realm_access 에서 꺼낸 목록...;

return roles.stream()
    .map(role -> new SimpleGrantedAuthority("ROLE_" + role))   // ← 이 한 줄이 핵심
    .toList();
```

**이 번역기를 연결하지 않으면 역할 검사가 항상 실패합니다.**

> **직접 확인해보기 좋은 실험**: 번역기 연결을 빼고 관리자 계정으로 호출해 보세요.
> 토큰에는 분명 `admin`이 들어 있는데도 **403**이 납니다.
> "표기법이 다르다"는 말을 확실히 체감할 수 있습니다.

## `hasRole`과 `hasAuthority` — 매우 흔한 실수

```java
.hasRole("admin")               // 내부적으로 "ROLE_" 을 자동으로 붙여서 찾음
.hasAuthority("ROLE_admin")     // 접두사 없이 정확히 그 문자열을 찾음
```

**둘은 완전히 같은 뜻입니다.**

> ⚠️ **`hasRole("ROLE_admin")` 이라고 쓰면 `ROLE_ROLE_admin`을 찾게 되어 항상 실패합니다.**
> "역할 부여도 했고 번역기도 붙였는데 계속 403"이라면 이걸 의심하세요.

## 이중 검증 — 제로 트러스트

여기서 중요한 설계 원칙이 하나 나옵니다.

**게이트웨이가 이미 토큰을 검증했는데, 백엔드가 또 검증해야 할까요?**

```
   ❌ 게이트웨이만 검증          ✅ 백엔드도 검증

   공격자 ──────────────┐         공격자 ──────────────┐
       (백엔드에 직접)   ▼             (백엔드에 직접)   ▼
              [product-service]              [product-service]
              인증 없이 통과 💀               토큰 없음 → 401 ✅
```

**게이트웨이만 검증하면, 백엔드에 직접 요청하는 순간 인증이 완전히 우회됩니다.**
→ [gateway/01의 "게이트웨이의 한계"](../gateway/01-게이트웨이란.md)

이렇게 **"내부 네트워크라고 해서 믿지 않는다"** 는 원칙을 **제로 트러스트(Zero Trust)** 라고 합니다.

> **그럼 게이트웨이 검증은 낭비인가?** 아닙니다.
> 잘못된 요청을 **관문에서 미리 걸러** 백엔드의 부담을 줄이고,
> 로깅·요청 제한 같은 공통 정책을 함께 적용하는 자리이기 때문입니다.
>
> **관문은 "1차 방어선", 백엔드는 "최후 방어선"** 입니다.

## 검사를 어디에 걸 것인가

두 가지 층위가 있습니다.

| 방식 | 어디에 | 예 |
|---|---|---|
| **URL 단위** | 보안 설정에서 경로별로 | `/api/admin/**` 은 admin만 |
| **메서드 단위** | 컨트롤러·서비스 메서드에 어노테이션 | 이 메서드는 admin만 |

URL 단위가 한눈에 보여서 좋고, 메서드 단위는 **같은 경로 안에서도 조건이 갈릴 때** 유용합니다.
(메서드 단위를 쓰려면 별도로 기능을 켜 줘야 합니다.)

> **순서에 주의하세요.** 보안 규칙은 **위에서부터 처음 매칭되는 것**을 적용하고 멈춥니다.
> "누구나 허용" 규칙은 반드시 **"전부 인증 필요" 규칙보다 앞에** 와야 합니다.
> 순서를 뒤집으면 공개 경로까지 막혀 버립니다.

## 정리 — 401과 403을 눈으로 구분하기

같은 관리자 API를 세 가지로 호출해 보면 차이가 분명해집니다.

| 호출 | 결과 | 왜 |
|---|---|---|
| 토큰 없이 | **401** | 누구인지 모름 (인증 실패) |
| 일반 사용자 토큰으로 | **403** | 누구인지는 알지만 권한이 없음 (인가 실패) |
| 관리자 토큰으로 | **200** | 인증·인가 모두 통과 |

**이 세 줄이 [01](01-인증과-인가.md)에서 배운 인증/인가 구분의 실체입니다.**
