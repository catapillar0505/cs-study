# 장애 격리

## 한 줄로

**남의 서비스가 실패하거나 느릴 때 내 서비스가 어떻게 버틸 것인가.** 몇 번 더 시도해보고(Retry), 계속 실패하면 아예 차단하고(Circuit Breaker), 자원을 다 뺏기지 않게 구획을 나누고(Bulkhead), 그래도 안 되면 대체 응답을 준다(Fallback).

## 왜 필요한가 — 실패 확률은 곱해집니다

모놀리식에서 메서드 호출은 **거의 실패하지 않습니다.** 같은 프로세스 안이니까요.

하지만 서비스를 쪼개면 그 호출이 **네트워크를 건너갑니다.** 그리고 네트워크는 항상 실패합니다.

- 상대 서버가 재배포 중이라 잠깐 죽음
- 네트워크 패킷이 유실됨
- 상대 서버가 과부하로 느려짐
- DB 커넥션이 말라서 상대가 응답을 못 함

**호출 한 번의 성공률이 99%라고 해봅시다.** 서비스 5개를 연쇄 호출하면?

```
0.99 × 0.99 × 0.99 × 0.99 × 0.99 = 0.951  →  약 5%가 실패
```

**서비스를 잘게 쪼갤수록 실패 확률은 곱해집니다.** 그래서 대비가 필수입니다.

## 최악의 시나리오 — 연쇄 장애

가장 무서운 것은 서비스 하나가 죽는 게 아니라, **그게 전체로 번지는 것**입니다.

```
① A 서비스가 느려짐  (죽은 게 아니라 "느려짐"이 더 위험합니다)
        ▼
② B 서비스의 스레드들이 응답을 기다리며 하나씩 묶임
        ▼
③ B의 스레드 풀이 고갈됨
        ▼
④ B가 다른 정상 요청도 처리 못 함   ← A와 무관한 기능까지 마비
        ▼
⑤ B를 호출하던 서비스들도 같은 과정으로 묶임
        ▼
⑥ 시스템 전체 마비 💀
```

이걸 **연쇄 장애(Cascading Failure)** 라고 합니다.

> **핵심 통찰: 죽은 서버보다 느린 서버가 훨씬 위험합니다.**
>
> | | 결과 |
> |---|---|
> | 죽은 서버 | 즉시 에러(`Connection refused`)를 주므로 **스레드가 바로 풀림** |
> | **느린 서버** | **타임아웃까지 스레드를 계속 붙잡고 있음** |

### 스레드 풀이란

웹 서버는 요청 하나를 처리할 때 **스레드 하나**를 씁니다.
요청마다 새로 만들면 비싸므로, 미리 몇 개 만들어두고 **돌려씁니다.**
이 미리 만들어둔 묶음이 **스레드 풀**이고, 기본값은 흔히 **200개**입니다.

```
[요청 1] ──▶ 스레드 #1  ┐
   ...                  ├─ 스레드 풀 (200개)
[요청 200] ─▶ 스레드 #200┘
[요청 201] ──▶ 대기 큐에서 하염없이 기다림 😰
```

**스레드 200개가 전부 묶이면 201번째 요청부터는 아무것도 처리할 수 없습니다.**

## 대응 도구 4종

| 도구 | 한 줄 설명 | 비유 |
|---|---|---|
| **Retry (재시도)** | 실패하면 몇 번 더 시도해본다 | 전화가 안 받으면 두어 번 더 걸어본다 |
| **Circuit Breaker (서킷 브레이커)** | 계속 실패하면 **아예 시도하지 않고** 즉시 실패시킨다 | **두꺼비집.** 과전류면 회로를 끊어버림 |
| **Bulkhead (격벽)** | **동시 호출 개수를 제한**해 자원 독점을 막는다 | **배의 방수 구획** |
| **Fallback (폴백)** | 최종 실패 시 **대체 응답**을 준다 | 실시간 시세 대신 마지막 값 안내 |

이 패턴들을 자바로 구현한 대표 라이브러리가 **Resilience4j**입니다.

> **Resilience(회복 탄력성)** 란 "장애를 겪어도 스스로 회복하는 능력"을 뜻합니다.
> 넷플릭스의 Hystrix가 개발 중단된 뒤 Resilience4j가 사실상 표준이 되었습니다.

## Retry — 재시도

```
시도 1 ──실패──▶ 잠깐 대기 ──▶ 시도 2 ──실패──▶ 대기 ──▶ 시도 3 ──실패──▶ Fallback
                                                        └──성공──▶ 결과 반환
```

> ⚠️ **"최대 3회"는 보통 "3번 재시도"가 아니라 "총 3번 시도"** 입니다.
> 최초 호출 1번 + 추가 재시도 2번. 헷갈리기 쉬운 부분입니다.

### 실무 주의사항 ① — 멱등하지 않은 작업은 재시도하면 안 됩니다

**멱등성(Idempotency)** = 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질입니다.

| 작업 | 멱등? | 재시도해도 되나 |
|---|---|---|
| 조회 (`GET /price`) | ✅ | 안전 |
| 삭제 (`DELETE /order/1`) | ✅ (이미 없으면 그대로) | 안전 |
| **결제/이체** (`POST /transfer`) | ❌ | **위험! 돈이 두 번 빠질 수 있음** |

**"응답을 못 받았다"와 "처리가 안 됐다"는 다릅니다.**
상대는 처리했는데 응답만 유실됐을 수도 있습니다. 그 상태에서 재시도하면 두 번 처리됩니다.

> 멱등성 전반과 중복 처리 방법은 [eda/14 멱등성](eda/14-멱등성.md)에 정리되어 있습니다.

### 실무 주의사항 ② — 고정 간격 재시도는 장애를 키웁니다

서버가 과부하로 느려졌는데 **클라이언트 1000대가 전부 1초 뒤에 동시에 재시도하면?**
→ 서버가 더 죽습니다. 이걸 **thundering herd(우르르 몰려감) 문제**라고 합니다.

그래서 실무에서는 두 가지를 함께 씁니다.

| 기법 | 뜻 |
|---|---|
| **지수 백오프 (Exponential Backoff)** | 대기 시간을 1초 → 2초 → 4초로 **점점 늘림** |
| **지터 (Jitter)** | 대기 시간에 **무작위성**을 섞어 동시 몰림을 분산 |

## Circuit Breaker — 서킷 브레이커

### 비유: 두꺼비집

집에 과전류가 흐르면 두꺼비집이 **회로를 끊어버립니다.** 그래야 집이 안 탑니다.
서킷 브레이커도 같습니다. **실패가 계속되면 아예 호출을 시도조차 하지 않고 즉시 실패시킵니다.**

**"왜 시도조차 안 하나?"** — 어차피 실패할 걸 알면서 호출하면:

- 상대 서버에 **불필요한 부하**를 더함 (회복할 시간을 안 줌)
- 내 스레드가 **타임아웃까지 묶임** (앞의 연쇄 장애)

**즉시 실패하는 게 훨씬 낫습니다.** 이걸 **Fail Fast(빠른 실패)** 라고 합니다.

### 상태 3개

```
                  실패율이 임계치 초과
      ┌────────┐ ─────────────────────▶ ┌────────┐
      │ CLOSED │                        │  OPEN  │
      │ (정상) │ ◀───────────────────── │ (차단) │
      └────────┘        시험 통과        └────────┘
           ▲                                 │
           │                                 │ 일정 시간 경과
           │                                 ▼
           │                          ┌─────────────┐
           └───────────────────────── │  HALF_OPEN  │
                                      │  (간보기)   │
                    실패 ────────────▶ └─────────────┘
                     │                       │
                     └───────▶ OPEN 으로 복귀 ┘
```

| 상태 | 뜻 | 호출이 어떻게 되나 |
|---|---|---|
| **CLOSED** | 정상. 회로가 **닫혀** 전류가 흐름 | 실제로 호출함 |
| **OPEN** | 차단. 회로가 **열려** 전류가 끊김 | **호출 안 하고 즉시 실패** |
| **HALF_OPEN** | 간보기 | **몇 개만** 통과시켜보고 결과로 판단 |

> ⚠️ **이름이 직관과 반대라 헷갈립니다.** 전기 회로 용어이기 때문입니다.
> **CLOSED = 회로가 닫혀서 전류가 흐름 = 정상**
> **OPEN = 회로가 열려서 끊김 = 차단**

### 설정에서 특히 중요한 것

| 설정 | 뜻 |
|---|---|
| 판단 창(sliding window) | **최근 N개** 또는 **최근 N초**의 결과만 보고 판단 |
| **최소 호출 수** | **N번도 안 해보고 판단하지 마라** |
| 실패율 임계치 | 몇 %를 넘으면 차단할 것인가 |
| OPEN 유지 시간 | 얼마 동안 차단할 것인가 = **상대에게 회복할 시간을 주는 것** |

> **"최소 호출 수"가 실무에서 특히 중요합니다.**
> 이게 없으면 **배포 직후 트래픽이 적을 때 우연한 실패 1건으로 실패율 100%가 되어**
> 서킷이 열려버립니다.

## Bulkhead — 격벽

### 서킷 브레이커가 못 잡는 상황

**상대가 에러를 내지 않고 그냥 느리기만 하면 어떻게 될까요?**

```
   응답: 항상 200 OK ✅
   다만: 3초 걸림
```

**실패율이 0%이므로 서킷 브레이커는 아무 일도 하지 않습니다.**
그런데도 스레드는 계속 묶이고, 결국 풀이 고갈됩니다.

**이게 Bulkhead가 따로 필요한 이유입니다.**

| | **Circuit Breaker** | **Bulkhead** |
|---|---|---|
| 막는 것 | **실패가 반복되는 것** | **자원을 독점하는 것** |
| 판단 기준 | 실패율 (%) | **동시 실행 개수** |
| 전제 | 상대가 **에러를 반환**함 | 상대가 **느림** (에러도 아님) |
| 비유 | 두꺼비집 | 배의 격벽 |

### 비유: 배의 격벽

배는 선체 내부를 **여러 개의 방수 구획(격벽, bulkhead)** 으로 나눕니다.

```
   ┌──────┬──────┬──────┬──────┐
   │ 구획1 │ 구획2 │ 구획3 │ 구획4 │
   └──────┴──▲───┴──────┴──────┘
             │
          여기 구멍이 나서 물이 차도
          구획 2에만 물이 참 → 배는 계속 항해
```

격벽이 없으면 구멍 하나에 배 전체가 침몰합니다. 소프트웨어도 똑같이 합니다.

```
        [ 격벽 없음 ]                     [ 격벽 있음 ]

   ┌──────────────────┐          ┌─────────┐  ┌──────────────┐
   │  공용 스레드 200  │          │ 검색 10개│  │ 나머지 190개  │
   │  전 기능이 공유   │          │ 전용    │  │ 다른 기능용   │
   └──────────────────┘          └─────────┘  └──────────────┘
   검색이 200개 다 먹으면          검색이 10개를 다 써도
   전체가 죽음 💀                  나머지 190개는 멀쩡 ✅
```

**"자원을 구획으로 나눠서, 한쪽이 다 써버려도 다른 쪽은 살아남게 한다."**

### 대기하지 말고 즉시 거절해야 합니다

격벽이 가득 찼을 때 **"자리가 날 때까지 기다리는" 설정**을 크게 잡으면
**요청이 대기하면서 스레드를 계속 붙잡습니다.** 그러면 격벽을 친 의미가 사라집니다.

**즉시 거절(Fail Fast)이 정석입니다.**

### 두 가지 구현 방식

| | **세마포어 방식** (기본) | **스레드 풀 방식** |
|---|---|---|
| 동작 | 요청 스레드가 **그대로 들어감**. 다만 몇 개까지인지 셈 | **별도 스레드 풀**에 작업을 넘김 |
| 장점 | 가볍다 (새 스레드를 안 만듦) | 원래 스레드를 **완전히 해방** |
| 단점 | 호출 스레드가 묶임 (단, **개수는 제한됨**) | 컨텍스트 전환 비용, 스레드에 딸린 정보가 **전파되지 않음** |
| 언제 | **대부분의 경우** | 외부 API가 매우 느려 스레드를 확실히 지켜야 할 때 |

> **세마포어(Semaphore)** 란 "동시에 몇 명까지 입장 가능"을 세는 카운터입니다.
> **놀이기구 입장 인원 제한**과 같습니다.

> ⚠️ 스레드 풀 방식은 **스레드가 바뀌므로**, 스레드마다 따로 갖는 저장소(`ThreadLocal`)에
> 들어 있던 정보(보안 컨텍스트, 로그 추적 ID)가 **전파되지 않습니다.**

## Fallback — 폴백

**최종 실패 시 대체 응답을 주는 것**입니다.

| 전략 | 예시 |
|---|---|
| **캐시된 옛 값** | "마지막으로 알려진 가격: 90.00" |
| **기본값** | 개인화 추천 대신 인기 상품 목록 |
| **부분 응답** | 상품 정보는 주되 리뷰는 생략 |
| **친절한 에러** | "잠시 후 다시 시도해주세요" |

**핵심은 "완전한 실패" 대신 "품질이 낮아진 성공"을 주는 것**입니다.
이걸 **Graceful Degradation(우아한 성능 저하)** 라고 합니다.

> 주식 앱에서 실시간 시세가 안 나올 때 화면이 통째로 하얗게 뜨는 것보다,
> **"10초 전 가격: 90.00"** 이 뜨는 게 훨씬 낫습니다.

### 폴백 메서드의 규칙

| 규칙 | 설명 |
|---|---|
| **반환 타입이 같아야 함** | 원본이 문자열이면 폴백도 문자열 |
| **파라미터가 같고 + 마지막에 예외 파라미터 추가** | 무엇 때문에 실패했는지 받기 위해 |
| 같은 클래스 안에 있어야 함 | 다른 클래스에 두면 못 찾음 |

> **"폴백을 만들었는데 안 불린다"면 시그니처부터 확인하세요.** 가장 흔한 원인입니다.

### 폴백은 격벽에 막혔을 때만 불리는 게 아닙니다

폴백은 원본 메서드에서 터진 **모든 예외**를 받습니다.

```
   상대 서비스가 꺼져 있음 → 연결 실패 예외
   격벽이 가득 참        → 격벽 초과 예외
```

**둘을 구분해야 사용자에게 정확한 안내**를 할 수 있습니다.

## 적용 순서 — 누가 바깥이냐

여러 패턴을 같이 쓸 때 **누가 바깥이냐에 따라 동작이 크게 달라집니다.**

권장 순서는 이렇습니다.

```
Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( 실제 호출 ) ) ) ) )
  ↑                                                      ↑
바깥                                                    안쪽
```

**Bulkhead가 가장 안쪽인 이유**: 자원 제한은 **실제 호출 직전**에 걸어야 의미가 있습니다.
바깥에 두면 재시도할 때마다 자리를 새로 잡느라 오히려 자원을 더 씁니다.

### Retry와 Circuit Breaker의 순서 — 트레이드오프

| 순서 | 결과 |
|---|---|
| **Retry가 바깥** | 재시도 3번이 **각각 서킷의 통계에 집계**됨 → 서킷이 **빨리** 열림 |
| CircuitBreaker가 바깥 | 재시도가 끝난 **최종 결과 1건만** 집계됨 → 서킷이 **늦게** 열림 |

**정답은 없고 트레이드오프입니다.** 중요한 건 **의도적으로 선택했는가**입니다.

> ⚠️ **자바 코드에서 어노테이션을 나열한 순서는 실행 순서와 무관합니다.**
> 반드시 설정에서 순서를 명시해야 합니다. 아주 흔한 오해입니다.

## 흔한 함정 — 같은 클래스 안에서 부르면 아무 일도 안 일어납니다

이 패턴들은 **AOP 프록시**로 동작합니다. 즉 [ipc/02](ipc/02-openfeign-선언적-http.md)에서 본
그 "대리인"이 앞에 서 있다가 호출을 가로채는 방식입니다.

```
   다른 빈에서 호출  →  [프록시]  →  실제 메서드   ✅ 패턴이 적용됨
   같은 클래스 안에서 this.메서드()  →  실제 메서드   ❌ 프록시를 안 거침
```

**같은 클래스 안에서 자기 메서드를 부르면(self-invocation) 프록시를 거치지 않아 아무 일도 안 일어납니다.**
컨트롤러 → 서비스처럼 **다른 빈을 거쳐야** 동작합니다.

> **AOP = Aspect Oriented Programming.** 공통 관심사를 프록시로 끼워 넣는 기법입니다.
> 이 기능을 쓰려면 AOP 의존성이 필요한데, **빠뜨려도 에러가 안 나고 조용히 동작만 안 합니다.**
> → [spring](../spring/README.md)

| | 보호 대상 |
|---|---|
| **Retry · CircuitBreaker · Bulkhead** | **내가 남을 호출할 때** |
| **Rate Limiter** | **남이 나를 호출할 때** → [gateway/04](gateway/04-요청-제한-rate-limiter.md) |

## 일부러 장애를 만들어 확인하기

실제 장애는 재현하기 어려우므로, **인위적으로 만들어** 시스템의 견고함을 검증합니다.

```
   30% 확률로 500 에러를 반환하는 가짜 서비스   → Retry·CircuitBreaker 확인
   항상 200이지만 3초 걸리는 가짜 서비스        → Bulkhead 확인
```

이런 방법론을 **카오스 엔지니어링(Chaos Engineering)** 이라고 합니다.

## 근본적인 대안 — 애초에 기다리지 않기

서킷 브레이커가 **"도미노를 중간에 끊는 것"** 이라면,
비동기 통신은 **"애초에 도미노를 세우지 않는 것"** 입니다.

```
   동기 호출  → 상대가 죽으면 나도 영향 → 서킷·격벽으로 방어
   이벤트 발행 → 상대가 죽어도 메시지가 남음 → 나중에 처리
```
