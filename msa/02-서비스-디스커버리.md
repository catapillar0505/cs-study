# 서비스 디스커버리

## 한 줄로

**"전화번호부"를 하나 두고**, 서비스들이 뜰 때 자기 주소를 등록한다. 부르는 쪽은 **이름만 알면** 되고, 주소는 번호부에 물어본다.

## 무엇이 문제인가

주소를 코드에 적으면 이렇게 됩니다.

```java
restTemplate.getForObject("http://192.168.0.5:9091/products/1", ...);
```

| 상황 | 문제 |
|---|---|
| 서버 IP가 바뀜 | **코드를 고치고 재배포** |
| 서버를 3대로 늘림 | 어디로 보낼지 **코드에서 직접 분배**해야 함 |
| 서버 한 대가 죽음 | **죽은 놈에게 계속 요청**을 보냄 |

컨테이너·클라우드 환경에서는 **주소가 수시로 바뀝니다.** 컨테이너를 다시 띄우면 IP가 달라지니까요.
**주소를 코드에 적는다는 전제 자체가 성립하지 않습니다.**

## 해결 — 전화번호부를 하나 둔다

```
                   ┌───────────────────────────┐
                   │  디스커버리 서버 (명부)     │
                   │  ───────────────────────  │
   ①등록 ────────► │  USER-SERVICE  → :8081    │ ◄──────── ①등록
                   │  BOARD-SERVICE → :8082    │
                   └───────────────────────────┘
                            ▲
                            │ ②"USER-SERVICE 주소 뭐야?"
                            │
                   [ board-service ]
```

**부르는 쪽 코드 어디에도 IP가 없습니다. "user-service"라는 이름만 압니다.**

이 명부 역할을 하는 것이 **Eureka**(Netflix가 만든 서비스 디스커버리 서버)입니다.

> **레지스트리(Registry)** 는 "등록부, 명부"라는 뜻입니다. Eureka가 들고 있는 서비스 목록을 가리킵니다.

## 클라이언트가 하는 세 가지 일

| 단계 | 하는 일 | 주기 |
|---|---|---|
| **등록(Register)** | 뜰 때 `{이름, IP, 포트}` 를 명부에 올림 | 부팅 시 1회 |
| **조회(Fetch)** | 명부 전체를 받아와 **로컬에 캐싱** | 기본 30초마다 |
| **하트비트(Heartbeat)** | "저 살아있어요" 신호 | 기본 30초마다 |

**하트비트(Heartbeat)** 는 심장박동이라는 뜻으로, **살아있음을 알리는 주기적 신호**입니다.
이 신호가 끊기면 명부에서 제거됩니다.

## 명부를 로컬에 캐싱한다 — 중요한 설계 선택

**호출할 때마다 명부에 묻지 않습니다.** 목록을 통째로 받아와 자기 메모리에 갖고 있습니다.

```
   장점: 명부 서버가 잠깐 죽어도 서비스끼리는 계속 통신할 수 있음 ✅
   단점: 최대 30초 정도는 옛 정보를 쓸 수 있음
```

**"실습 중에 왜 바로 반영이 안 되지?"** 하는 이유가 이것이고, **정상 동작**입니다.

> 이런 설계를 **AP 지향**이라고 합니다.
> 분산 시스템에서는 일관성(Consistency)과 가용성(Availability) 중 하나를 어느 정도 포기해야 하는데,
> Eureka는 **"정보가 조금 낡아도 좋으니 계속 동작하는 쪽"** 을 택했습니다.

## 서비스 이름이 결정하는 것

설정의 **애플리케이션 이름 한 줄**이 여러 가지를 동시에 결정합니다.

```yaml
spring:
  application:
    name: product-service
```

1. **명부에 등록되는 이름** → 다른 서비스가 이 이름으로 나를 부름
2. **설정 서버에서 찾을 파일 이름** → [msa/04 설정 관리](04-설정-관리.md)
3. **게이트웨이 라우팅의 목적지 이름** → `lb://PRODUCT-SERVICE`

> **Eureka는 서비스 이름을 대문자로 저장합니다.**
> `product-service` 라고 써도 명부에는 `PRODUCT-SERVICE` 로 올라갑니다.
> 대시보드에 보이는 그대로 쓰는 것이 안전합니다.

> **"왜 설정을 못 가져오지?" 할 때 8할은 이 이름이 안 맞아서입니다.**

## 자기보호모드 — 실습 중 헷갈리는 장치

**하트비트가 갑자기 많이 끊기면** Eureka는 이렇게 판단합니다.

> "서비스들이 한꺼번에 죽었을 리는 없다. **네트워크가 끊긴 것**이다."

그러고는 **명부를 지우지 않습니다.** 진짜 네트워크 장애 상황에서 **멀쩡한 서비스를 통째로
지워버리는 참사**를 막는 안전장치입니다.

```
   운영 환경  → 켜야 합니다 (기본값). 네트워크 장애에 시스템이 무너지지 않게
   학습 중    → 끄는 게 편합니다. 안 그러면 서비스를 껐는데도 계속 "UP"으로 보여 헷갈림
```

## 서버 사이드 vs 클라이언트 사이드

디스커버리를 쓰는 방식이 두 가지입니다.

| | 서버 사이드 | **클라이언트 사이드** |
|---|---|---|
| 누가 고르나 | 중간의 로드밸런서 장비 | **부르는 쪽이 직접** |
| 목록을 갖고 있는 곳 | 로드밸런서 | **부르는 쪽의 메모리(캐시)** |
| 홉(중간 단계) | 하나 더 있음 | **없음** |
| 대표 | Nginx, AWS ELB | **Eureka + Spring Cloud LoadBalancer** |

Spring Cloud는 **클라이언트 사이드** 방식입니다. → [gateway/02](gateway/02-라우팅과-로드밸런싱.md)

## 같은 서비스를 여러 개 띄울 때

**포트에 `0`을 주면 OS가 남는 포트를 아무거나 배정**해 줍니다. 포트 충돌을 피하는 표준 방법입니다.

```yaml
server:
  port: 0
```

다만 이때 **인스턴스 ID 때문에 함정이 하나 있습니다.**

> 명부는 기본적으로 `{호스트명}:{서비스이름}:{포트}` 를 인스턴스 ID로 씁니다.
> 한 PC에서 여러 개를 띄우면 호스트명이 전부 같아서 **뒤에 뜬 것이 앞의 것을 덮어씁니다.**
> **3개를 띄웠는데 대시보드에 1개만 보이는** 이유가 이것입니다.
>
> 인스턴스 ID에 **무작위 값을 섞어** 매번 다른 ID가 되게 하면 해결됩니다.

또 하나: 실제로 배정받은 포트는 설정값이 아니라 **`local.server.port`** 로 읽어야 합니다.

```
server.port        → 설정에 적은 값 (0)
local.server.port  → 실제로 배정받은 값 (51234 등)
```

## 흔한 오해

**"디스커버리 서버가 죽으면 전체가 멈춘다"**
아닙니다. 각 서비스가 **명부를 캐싱**하고 있으므로 기존 서비스끼리는 계속 통신합니다.
새 서비스 등록·발견만 지연됩니다.

**"어노테이션을 붙여야 클라이언트가 된다"**
요즘은 **의존성만 넣으면 자동으로 켜집니다.** 옛 예제의 `@EnableEurekaClient`는 이제 필요 없습니다.

**"이름은 아무거나 지어도 된다"**
그 이름이 **명부 등록 이름 + 설정 파일 이름 + 라우팅 목적지**를 동시에 결정합니다.

## 쿠버네티스에서는 어떻게 되나

**쿠버네티스는 같은 문제를 플랫폼 층에서 이미 풀고 있습니다.**

| | Spring Cloud | 쿠버네티스 |
|---|---|---|
| 이름으로 주소 찾기 | Eureka + 클라이언트 로드밸런싱 | **Service + CoreDNS** |
| 죽은 인스턴스 제외 | 하트비트 만료 | **readiness 프로브** |

**둘 다 켜면 중복입니다.** 무엇을 어디서 풀지는 [90 쿠버네티스와 겹치는 지점](90-쿠버네티스와-겹치는-지점.md)에 정리되어 있습니다.
