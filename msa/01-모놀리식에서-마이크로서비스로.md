# 모놀리식에서 마이크로서비스로

## 한 줄로

기능별로 **배포 단위를 쪼개면** 따로 배포하고 따로 늘릴 수 있다. 대신 **함수 호출이 네트워크 호출이 되고**, 하나였던 트랜잭션·로그·설정이 전부 갈라진다. 이 폴더는 그 대가를 치르는 방법들이다.

## 모놀리식이란

**모놀리식(Monolith)** 은 "하나의 큰 돌덩이"라는 뜻입니다. 하나의 프로그램에 모든 기능이 들어있습니다.

```
┌─────────────────────────────┐
│      shop-app.jar           │
│  회원 · 상품 · 주문 · 결제  │   ← 프로세스 하나. 배포도 하나
└─────────────────────────────┘
```

기능끼리 호출은 그냥 메서드 호출입니다. **간단하고, 빠르고, 실패하지 않습니다.**

**작은 서비스라면 이게 정답입니다.** 문제는 커졌을 때 생깁니다.

- 결제 코드 한 줄 고치려고 **전체를 다시 배포**해야 함
- 주문에만 트래픽이 몰려도 **회원 기능까지 통째로** 서버를 늘려야 함
- 코드베이스가 커지면 **한 팀이 고친 것이 다른 팀을 깨뜨림**

## 왜 쪼개는가

**마이크로서비스(MSA)** 는 기능별로 프로그램을 쪼갭니다.

```
┌──────────┐ ┌──────────┐ ┌──────────┐
│user-svc  │ │product-  │ │order-svc │  ← 각각 별도 프로세스, 별도 배포
│  :9090   │ │svc :9091 │ │  :9092   │
└──────────┘ └──────────┘ └──────────┘
```

### 배포 단위를 나누면 좋아지는 것

| | 모놀리식 | MSA |
|---|---|---|
| **배포 주기** | 전체를 한꺼번에 | **서비스별로 따로, 자주** |
| **장애 범위** | 한 기능이 죽으면 전체 다운 | 그 서비스만 (격리하면) |
| **팀 경계** | 코드가 얽혀 충돌 | 서비스가 곧 팀의 소유 경계 |

### 스케일 아웃 단위가 달라진다

**한 기능에만 트래픽이 몰릴 때** 차이가 확실합니다.

```
모놀리식:  주문이 몰림 → 회원·상품 코드까지 통째로 3배 복제  (낭비)
MSA:      주문이 몰림 → 주문 서비스만 3배                    (필요한 만큼만)
```

> **스케일 아웃**은 서버 **대수**를 늘리는 것, **스케일 업**은 한 대의 **성능**을 올리는 것입니다.
> MSA는 스케일 아웃을 전제로 설계됩니다. → [gateway/02](gateway/02-라우팅과-로드밸런싱.md)

## 쪼개면 새로 생기는 비용

**모놀리스에서 공짜였던 것들이 전부 유료가 됩니다.**

```java
@Transactional
public void createOrder(OrderRequest req) {
    orderRepository.save(order);     // 같은 DB
    stockService.deduct(req);        // 같은 JVM 안의 메서드 호출
    paymentService.charge(req);
}
```

이 코드에는 **두 가지 축복**이 있었습니다.

| 축복 | 왜 |
|---|---|
| **메서드 호출은 실패하지 않는다** | 같은 JVM, 같은 메모리. 네트워크가 개입하지 않음 |
| **`@Transactional` 하나로 전부 묶인다** | DB가 하나라 원자성(All or Nothing)이 자동 보장 |

**서비스를 쪼개는 순간 둘 다 사라집니다.**

```
Order Service (DB1) --HTTP--> Stock Service (DB2) --HTTP--> Payment Service (DB3)
```

### 실패 확률은 곱해집니다

호출 한 번의 성공률이 99%라고 해봅시다. 서비스 5개를 연쇄 호출하면?

```
0.99 × 0.99 × 0.99 × 0.99 × 0.99 = 0.951  →  약 5%가 실패
```

**잘게 쪼갤수록 실패 확률이 곱해집니다.** 그래서 [06 장애 격리](06-장애-격리.md)가 선택이 아니라 필수가 됩니다.

## 흔한 오해

**"작게 쪼갤수록 좋다"**
쪼갠 만큼 **네트워크 경계가 늘어납니다.** 경계 하나마다 위의 문제들이 전부 따라옵니다.
서비스를 나누는 기준은 "작게"가 아니라 **"함께 바뀌는 것끼리 묶는다"** 입니다.

**"MSA = Spring Cloud"**
Spring Cloud는 **구현 수단 중 하나**입니다. 같은 문제를 쿠버네티스가 플랫폼 층에서 풀기도 하고,
서비스 메시가 네트워크 층에서 풀기도 합니다. → [90 쿠버네티스와 겹치는 지점](90-쿠버네티스와-겹치는-지점.md)

**"MSA로 가면 개발이 빨라진다"**
**초기에는 확실히 느려집니다.** 위 목록의 인프라를 전부 갖춰야 하니까요.
효과는 **팀과 코드베이스가 충분히 커졌을 때** 나옵니다.

**"모놀리식은 나쁜 것이다"**
아닙니다. **잘 나눠진 모놀리식(모듈러 모놀리스)** 이 어설픈 MSA보다 낫습니다.
경계를 먼저 코드 안에서 그어보고, 정말 따로 배포할 필요가 생겼을 때 쪼개는 것이 안전한 순서입니다.
