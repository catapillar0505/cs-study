# 분산 트랜잭션 문제

## 한 줄로

`@Transactional`은 **커넥션 하나에 걸린 것**이라 서비스 경계를 넘지 못한다. 2PC는 락 때문에 못 쓰므로, **강한 일관성을 포기하고 최종 일관성으로 간다.**

## 문제 재확인

```java
@Transactional
public void createOrder() {
    orderRepo.save(order);      // DB1
    stockRepo.deduct(item);     // DB2  <- @Transactional이 여기까지 못 감
    paymentRepo.charge(pay);    // DB3
}
```

**`@Transactional`은 하나의 DB 커넥션에 걸린 것이다.**
DB가 3개면 3개의 독립된 트랜잭션이다. Payment가 실패해도 **Order와 Stock은 이미 커밋되었고**, 롤백할 방법이 없다.

이것이 **Database Per Service** 원칙의 대가다.

> 단일 DB 안에서의 트랜잭션·격리 수준은 [spring/08](../../spring/08-트랜잭션.md)과 [database/mysql](../../database/mysql/README.md)

## 2PC는 왜 안 쓰는가

이론적 해법으로 **2PC (Two-Phase Commit, 2단계 커밋)** 가 있다.

```
1단계 (Prepare): 코디네이터 -> 전원에게 "커밋 가능?"
                 전원이 "가능" 응답 (이때부터 락을 잡고 대기)
2단계 (Commit):  코디네이터 -> 전원에게 "커밋해"
```

**MSA에서 쓰지 않는 이유:**

- 모든 참여자가 1단계부터 2단계까지 **락을 잡고 대기**한다. 네트워크 지연이 있는 분산 환경에서 이 시간이 길어 처리량이 급락한다
- **코디네이터가 1, 2단계 사이에 죽으면** 참여자들이 락을 잡은 채 영원히 대기한다 (사람이 개입해야 함)
- 참여자 중 하나만 느려도 전체가 그 속도에 묶인다
- 애초에 **HTTP API로 통신하는 MSA에서는 지원조차 되지 않는다**

## 발상 전환: 강한 일관성 → 최종 일관성

| | 강한 일관성 (Strong Consistency) | 최종 일관성 (Eventual Consistency) |
|---|---|---|
| 의미 | 항상 모든 데이터가 정합 | **잠깐 어긋나도 결국엔 맞음** |
| 예시 | 계좌 이체 (단일 DB) | 주문 처리, SNS 좋아요 수 |
| 대가 | 성능/가용성 희생 | **중간 상태가 노출됨** |

"주문은 생성됐는데 재고 차감은 0.5초 후"가 허용된다는 뜻이다.
실무에서는 대부분 이것으로 충분하다. 사용자에게 "주문 접수 중"으로 표시하면 된다.
