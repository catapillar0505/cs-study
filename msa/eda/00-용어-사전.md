## EDA (Event-Driven Architecture, 이벤트 기반 아키텍처)

**한 줄 정의**
서비스끼리 직접 API를 호출하지 않고, **"무슨 일이 일어났다"는 사실(이벤트)** 을 메시지 브로커에 던져두면 관심 있는 서비스가 알아서 가져가 처리하는 아키텍처.

**단어 뜯어보기**

| 단어 | 뜻 |
|---|---|
| **Event (이벤트)** | 이미 일어난 사건. "주문이 생성되었다", "결제가 실패했다" |
| **Driven (구동되는)** | 그 사건이 **원동력**이 되어 다음 동작이 일어난다는 뜻 |
| **Architecture (아키텍처)** | 시스템 구성 방식 |

합치면 **"이벤트가 시스템을 굴러가게 만드는 구조"** 다.

**비유: 회사의 두 가지 일하는 방식**

전통적 방식 (직접 호출)
> 김대리가 박대리 자리로 **직접 찾아가서** "이 서류 처리해주세요"라고 말한다.
> 박대리가 자리에 없으면? 김대리는 계속 기다리거나 그냥 돌아가야 한다.
> 박대리가 퇴사하면? 김대리 업무 매뉴얼을 고쳐야 한다.

EDA 방식
> 김대리가 사내 게시판에 **"A건 서류 접수 완료"** 라고 글을 올린다.
> 누가 처리하는지 김대리는 모르고, 알 필요도 없다.
> 박대리가 휴가 중이면 게시글은 그대로 남아 있다가 복귀 후 처리된다.
> 나중에 회계팀도 이 글을 봐야 한다면? **게시판을 구독만 추가하면 되고 김대리는 아무것도 안 바꿔도 된다.**

**핵심은 이 문장 하나다**

```java
// 전통 방식: "너, 재고 차감해."   -> Stock을 알아야 함
stockClient.deduct(orderId, qty);

// EDA:      "주문이 생성됐어."   -> Stock이라는 단어가 코드에서 사라짐
eventPublisher.publish(new OrderCreatedEvent(orderId, qty));
```

**이벤트는 항상 과거형으로 쓴다.** `OrderCreatedEvent`, `PaymentFailedEvent`.
"이미 일어난 사실의 통보"이지 "너 이거 해"라는 명령이 아니기 때문이다.

**EDA로 얻는 것 3가지 (초간단 버전)** — 자세히는 [03](03-eda-도입의-3대-이점.md)

| 이점 | 쉬운 설명 |
|---|---|
| 느슨한 결합 | 상대방이 누군지, 어디 있는지 몰라도 됨 |
| 장애 격리 | 상대방이 죽어 있어도 내 일은 계속됨 |
| 확장 용이 | 처리가 밀리면 처리하는 사람만 늘리면 됨 |

## 이벤트와 명령

**한 줄 정의**
**이벤트는 "이미 일어난 사실의 통보"**, **명령은 "너 이거 해라는 지시"** 다. 문장 시제가 다르다.

| | **명령 (Command)** | **이벤트 (Event)** |
|---|---|---|
| 문장 | "재고를 차감**해라**" | "주문이 생성**되었다**" |
| 시제 | 명령형 / 미래 | **과거형** |
| 이름 | `CreateOrder` | `OrderCreated` |
| 수신자 | **특정 대상 1명** | 모름. 관심 있는 누구든 |
| 거부 가능? | 가능 | **불가능** (이미 일어난 일이니까) |
| 결합도 | 높음 | **낮음** |

**왜 이 구분이 중요한가**

```java
// 명령: 나는 Stock에게 시킨다 → Stock을 알아야 함
stockClient.deduct(orderId, qty);

// 이벤트: 나는 사실을 알린다 → 코드에서 Stock이라는 단어가 사라짐
publish(new OrderCreatedEvent(orderId, qty));
```

**"시켜라"에서 "알려라"로 바꾸는 것**, 이 한 걸음이 결합을 끊습니다.

> **이벤트는 불변(immutable)이어야 합니다.** 이미 일어난 사실은 나중에 바뀔 수 없기 때문입니다.
> 그래서 이벤트 클래스는 보통 `record`처럼 값을 바꿀 수 없는 형태로 만듭니다.

> 이 구분이 나중에 [11 코레오그래피](11-choreography-saga.md)와 [12 오케스트레이션](12-orchestration-saga.md)을 가르는 기준이 됩니다.
> **오케스트레이터가 주고받는 것은 이벤트가 아니라 명령**입니다.

## 브로커 (Message Broker)

**한 줄 정의**
메시지를 대신 보관하고 배달해주는 **별도의 서버 프로그램**.

**가장 중요한 오해 교정: 브로커는 개념이 아니라 "설치해서 켜는 프로그램"이다**

MySQL과 완전히 같은 종류의 것이라고 생각하면 된다.

| | MySQL | RabbitMQ (브로커) |
|---|---|---|
| 정체 | 별도 서버 프로그램 | **별도 서버 프로그램** |
| 설치 | 서버에 설치 후 실행 | 서버에 설치 후 실행 |
| 포트 | 3306 | 5672 |
| 접속 | 자바 앱이 JDBC로 접속 | 자바 앱이 AMQP로 접속 |
| 보관하는 것 | **현재 상태** (테이블의 행) | **아직 처리 안 된 메시지** |
| 앱을 껐다 켜면 | 데이터는 그대로 남음 | 메시지는 그대로 남음 |

```
[Order 앱]  ─── 메시지 넣음 ───▶  [RabbitMQ 서버]  ◀── 메시지 꺼냄 ───  [Stock 앱]
   JVM 1                            별도 프로세스                        JVM 2
   (포트 8080)                       (포트 5672)                        (포트 8081)
```

세 개가 **전부 다른 프로세스**다. 리눅스에서 `ps -ef`를 찍으면 세 개가 각각 보인다.

**비유: 브로커는 우편함이 아니라 우체국 건물 전체다**

```
우체국 (= 메시지 브로커)
 ├─ 분류소        (= Exchange)
 ├─ 우편함 A      (= Queue)
 ├─ 우편함 B      (= Queue)
 └─ 우편함 C      (= Queue)
```

우편함(Queue)은 브로커 **안에 들어있는 것**이다.
브로커는 메시지를 받고, 분류하고, 디스크에 저장하고, 소비자에게 넘겨주는 **시스템 전체**를 가리킨다.

**비유 2: 주방의 냉장고**

브로커 없이 (직접 호출)
> 배달원이 요리사에게 재료를 **손에 들고 직접 건넨다.**
> 요리사가 화장실 갔으면 배달원은 서서 기다린다.
> 요리사가 결근했으면 재료를 들고 되돌아가야 한다.

브로커 있으면
> 배달원이 **냉장고에 넣어두고 간다.**
> 요리사가 있든 없든 상관없다. 여유될 때 꺼내면 된다.
> 요리사가 결근해도 재료는 냉장고에 그대로 있다가 다음 날 쓰인다.

**냉장고 = 브로커.** 이 하나가 "공간적/시간적 결합 해제"를 전부 만들어낸다.

**Broker라는 단어 자체**는 **중개인**이라는 뜻이다. 부동산 중개인이 집주인과 세입자가 직접 만나지 않게 하듯, 메시지 브로커가 서비스 간 직접 연결을 끊어준다.

## AMQP와 4대 구성요소

**한 줄 정의**
**AMQP(Advanced Message Queuing Protocol)** 는 메시징의 **표준 프로토콜**이고, RabbitMQ는 그 구현체다.
핵심 원칙은 딱 하나 — **"발행자는 큐에 직접 넣지 않는다."**

> HTTP가 웹 통신의 표준인 것과 같은 위치입니다.
> AMQP를 따르는 브로커끼리는 클라이언트 라이브러리를 바꾸지 않고 교체할 수 있습니다.
> (Kafka는 AMQP를 쓰지 않습니다. 자체 프로토콜을 씁니다.)

**전체 그림**

```
                     ┌──────────────────────────────────────────┐
                     │              RabbitMQ                     │
                     │                                           │
  Producer ─────────▶│  ┌──────────┐  binding   ┌──────────┐    │──────▶ Consumer A
 (routing key:       │  │ Exchange │───(key)───▶│  Queue A │    │
  "order.created")   │  │ (분류기)  │            └──────────┘    │
                     │  │          │            ┌──────────┐    │──────▶ Consumer B
                     │  │          │───(key)───▶│  Queue B │    │
                     │  └──────────┘            └──────────┘    │
                     └──────────────────────────────────────────┘
```

**우체국 비유로 읽는 5개 등장인물**

| 구성요소 | 우체국 비유 | 역할 |
|---|---|---|
| **Producer** | 편지 보내는 사람 | 메시지를 만들어 Exchange로 보냄. **큐 이름을 모른다** |
| **Exchange** | 우체국 **분류기** | 규칙에 따라 어느 큐로 넣을지 결정. **저장하지 않는다** |
| **Binding** | 분류 **규칙표** | "이 Exchange로 온 `order.*` 는 Queue A로" 같은 연결 규칙 |
| **Queue** | **우편함** | 메시지가 실제로 **쌓여서 대기**하는 곳 |
| **Consumer** | 우편함 주인 | 큐에서 꺼내 처리 |

**여기서 꼭 짚어야 할 두 가지**

**(1) Exchange는 저장하지 않는다**

Exchange는 **분류만 하고 지나보냅니다.** 메시지가 실제로 고이는 곳은 **Queue**입니다.

> ⚠️ **매칭되는 큐가 하나도 없으면 메시지는 조용히 버려집니다.**
> 에러도 안 납니다. "발행은 성공했는데 아무도 못 받았다"는 상황의 정체가 대부분 이것입니다.
> 구독자를 먼저 띄워 큐가 만들어지게 한 뒤 발행해야 합니다.

**(2) 왜 굳이 Exchange를 거치게 만들었나**

Producer가 큐에 직접 넣으면, 나중에 **"이 메시지를 다른 서비스도 받아야 해"** 가 되었을 때
**Producer 코드를 고쳐야** 합니다.

Exchange를 두면 새 구독자가 **자기가 알아서 새 큐를 만들고 Exchange에 연결**하면 끝입니다.
**Producer는 그런 일이 있었는지도 모릅니다.** → 결합이 실제로 끊기는 지점이 여기입니다.

## Exchange (익스체인지)

**한 줄 정의**
RabbitMQ에서 **메시지를 어느 큐로 보낼지 결정하는 분류 담당자.**

**왜 필요한가 (문제부터)**

Producer가 큐에 직접 넣는다고 하면 이렇게 된다.

```java
queue.send("order-queue", msg);   // 큐 이름을 코드가 알아야 함
```

나중에 "재고 큐에도 보내고 통계 큐에도 보내야 해"가 되면 **Producer 코드를 고쳐야 한다.**
브로커를 뒀는데도 결합이 남아버린 것이다.

**해법: 한 겹을 더 둔다**

```
Producer ──▶ Exchange ──(규칙에 따라)──▶ Queue ──▶ Consumer
             "분류소"                     "우편함"
```

**Producer는 Exchange에만 보낸다. 어디로 갈지는 Exchange가 판단한다.**
라우팅 규칙이 코드가 아니라 **인프라 설정**으로 빠졌다.
새 Consumer를 추가하려면 큐를 만들고 Exchange에 연결만 하면 되고, **Producer는 그대로다.**

**비유: 우체국 분류소**

편지를 부칠 때 나는 상대방 우편함에 직접 넣지 않는다. 우체국에 맡긴다.
우체국 **분류소(Exchange)** 가 편지의 **주소(Routing Key)** 를 보고, **분류 규칙(Binding)** 에 따라 각 **우편함(Queue)** 으로 나눠 넣는다.

**함께 알아야 할 두 단어**

| 단어 | 뜻 | 비유 |
|---|---|---|
| **Routing Key** | 메시지에 붙는 **주소 라벨** (Producer가 지정) | 편지 봉투에 쓴 주소 |
| **Binding** | Exchange와 Queue를 잇는 **규칙** | "이 주소는 3번 우편함으로" 규칙표 |

**Exchange 타입 4가지** — 자세히는 [04](04-rabbitmq.md)

| 종류 | 규칙 | 비유 |
|---|---|---|
| **Direct** | 주소가 **정확히 일치**하는 우편함으로 | 지정 주소 배달 |
| **Topic** ★ | 주소를 **와일드카드 패턴으로 매칭** (`order.*`) | "강남구로 시작하는 모든 곳" |
| **Fanout** | 주소 무시, **모든 우편함에 복사** | 전단지 전체 배포 |
| Headers | 라우팅 키 대신 **헤더 값**으로 매칭 | 거의 안 씀 |

**Topic 와일드카드 규칙** (구분자는 점 `.`)

실무에서 가장 많이 쓰는 것이 Topic이고, **Spring Cloud Stream의 RabbitMQ 바인더도 기본이 Topic**입니다.

| 기호 | 의미 | `order.created` | `order.item.created` |
|---|---|---|---|
| `order.*` | `*` = **정확히 한 단어** | ✅ 매칭 | ❌ (단어가 3개) |
| `order.#` | `#` = **0개 이상의 단어** | ✅ 매칭 | ✅ 매칭 |
| `#` | 전부 | ✅ | ✅ |

**왜 이게 유용한가**

바인딩을 `order.*` 로 걸어두면 **"order로 시작하는 이벤트는 다 받겠다"** 는 뜻입니다.
나중에 `order.cancelled` 이벤트가 새로 생겨도 **설정을 안 고쳐도 자동으로 수신**됩니다.

`#.error` 로 걸면 **모든 서비스의 에러 이벤트만** 골라 받을 수도 있습니다.

Kafka에는 Exchange가 없다. **RabbitMQ만의 개념**이다. Kafka는 토픽에 그냥 던지고 끝이다.

## 컨슈머 그룹 = 경쟁 소비자 패턴

**한 줄 정의**
**같은 그룹에 속한 인스턴스들은 하나의 큐를 나눠 먹는다.** 이벤트 1건은 그룹 안에서 **딱 한 대만** 처리한다.

**문제부터**

재고 서비스를 트래픽 때문에 **3대로 늘렸다**고 합시다. 주문 이벤트 1건이 오면?

```
❌ 3대가 모두 받으면 → 재고가 3번 깎임 (재앙)
✅ 3대 중 딱 1대만 받아야 함
```

여러 인스턴스가 같은 큐에서 메시지를 **가져가려고 경쟁**하는 이 구조를
**경쟁 소비자 패턴(Competing Consumers)** 이라고 합니다.

**동작 원리**

그룹 이름을 주면 브로커에 **`목적지.그룹명` 이라는 이름 있는 물리적 큐 1개**가 만들어집니다.
인스턴스 3대는 **그 큐 하나를 나눠 먹습니다.**
큐에서 메시지를 꺼내가는 건 원래 한 번에 한 소비자뿐이므로, 자연스럽게 중복이 방지됩니다.

```
                         ┌──────────────────────────────────┐
                         │  order-created-topic (Exchange)  │
                         └───────┬──────────────────┬───────┘
                                 │                  │
              ┌──────────────────▼──────┐   ┌───────▼─────────────────┐
              │ .stock-group (큐)        │   │ .point-group (큐)        │
              └───┬──────┬──────┬────────┘   └──────────┬──────────────┘
                  │      │      │  (셋 중 하나만)         │
              재고1    재고2   재고3                   포인트 서비스
              ── 같은 그룹 = 나눠 먹기 ──          ── 다른 그룹 = 각자 다 받음 ──
```

**그룹을 주고 안 주고의 차이**

| | 그룹 **있음** | 그룹 **없음** |
|---|---|---|
| 만들어지는 큐 | `목적지.그룹명` — **이름 있고 영구적** | 인스턴스마다 **익명 임시 큐** |
| 인스턴스 3대일 때 | 1건 → **1대만** 처리 | 1건 → **3대 전부** 처리 (브로드캐스트) |
| 서비스가 꺼져 있는 동안 온 메시지 | 큐에 **쌓여 있다가** 재시작 후 처리 | 큐가 사라져서 **유실** |
| 쓰는 상황 | **대부분의 업무 처리** ★ | 각 인스턴스의 로컬 캐시 갱신 등 |

> ⚠️ **실무에서 가장 흔한 사고**: 그룹을 안 주고 배포했다가, **재배포 사이에 온 메시지를 통째로 잃어버리는 것.**
> 익명 큐는 인스턴스가 죽으면 큐째로 사라지기 때문입니다.
> **업무를 처리하는 컨슈머에는 반드시 그룹을 주세요.**

**"그룹이 다르면 각자 다 받는다"가 EDA의 확장 포인트입니다**

포인트 서비스가 나중에 생겨서 다른 그룹 이름으로 같은 Exchange를 구독하면,
**주문 서비스는 아무것도 모른 채 기능이 하나 늘어납니다.**

> **Kafka에도 같은 개념이 있습니다.** 이름도 그대로 Consumer Group입니다.
> 다만 나누는 단위가 큐가 아니라 **파티션**이라서, **파티션 수가 인스턴스 수의 상한선**이 됩니다. → [05](05-kafka.md)

## 파티션 (Partition)

**한 줄 정의**
Kafka에서 하나의 토픽을 **여러 조각으로 물리적으로 쪼개 놓은 저장 공간.**

**왜 쪼개는가 (문제부터)**

토픽 하나가 파일 하나라면, 그 파일은 **서버 한 대에만** 있다.
그러면 그 서버의 디스크 용량과 처리 속도가 곧 한계가 된다. 아무리 서버를 늘려도 소용없다.

**해법: 쪼개서 여러 서버에 나눠 담는다**

```
Topic: order-events  (논리적으로는 하나)
├─ Partition 0  (Broker 1에 저장)  [0][1][2][3]
├─ Partition 1  (Broker 2에 저장)  [0][1][2]
└─ Partition 2  (Broker 3에 저장)  [0][1][2][3][4]
```

용량도 3배, 처리량도 3배가 된다.

**비유: 은행 창구**

은행에 손님이 몰리는데 창구가 하나뿐이면 줄이 끝없이 길어진다.
창구를 3개로 늘리면(파티션 3개) 3배 빨리 처리된다.
그리고 **각 창구의 줄은 각자 순서가 지켜지지만, 창구끼리는 순서가 섞인다.**

**여기서 나오는 가장 중요한 결론 2가지**

**(1) 순서는 파티션 안에서만 보장된다**

토픽 전체의 순서는 보장되지 않는다. 3번 창구 손님이 1번 창구 손님보다 먼저 끝날 수 있다.

특정 주문의 이벤트 순서가 중요하다면 **메시지 키**를 준다.

```java
producer.send(new ProducerRecord<>("order-events", orderId, event));
//                                                  ↑ 키
```

**같은 키는 항상 같은 파티션으로 간다** (키의 해시 % 파티션 수).
`orderId`를 키로 주면 그 주문의 이벤트들은 전부 한 창구에 순서대로 줄을 선다.

**(2) Consumer 개수는 파티션 개수를 넘을 수 없다**

한 파티션은 그룹 내에서 **한 Consumer만** 소비할 수 있다(순서가 깨지지 않게 하려고).
창구가 3개인데 직원을 5명 배치하면 **2명은 논다.**

**파티션 수가 스케일 아웃의 상한선**이다. 늘릴 수는 있지만 줄일 수는 없으므로 처음에 넉넉히 잡아야 한다.

**Topic과 Partition의 관계 정리**

| | Topic | Partition |
|---|---|---|
| 성격 | **논리적** 분류 | **물리적** 저장 공간 |
| 비유 | 은행 지점 | 그 지점의 창구 |
| DB로 치면 | 테이블 | 샤딩된 조각 |
| 개수 | 도메인마다 하나씩 | 토픽당 여러 개 |

## 오프셋 (Offset)

**한 줄 정의**
파티션 안에서 **각 메시지에 매겨진 순번**이자, Consumer가 **어디까지 읽었는지 표시하는 위치.**

**비유: 책갈피**

Kafka의 파티션은 **책**이다. 메시지는 페이지고, 오프셋은 **쪽수**다.

```
Partition 0:  [0페이지][1페이지][2페이지][3페이지][4페이지]
                  ▲                  ▲
                  │                  └─ 통계팀 책갈피 (2까지 읽음)
                  └─ 재고팀 책갈피 (0까지 읽음)
```

**중요한 것은 책이 사라지지 않는다는 점이다.**
도서관 책은 누가 읽었다고 없어지지 않는다. 사람마다 책갈피만 다른 위치에 꽂혀 있을 뿐이다.

**이것이 RabbitMQ와의 결정적 차이다**

| | RabbitMQ (큐) | Kafka (로그 + 오프셋) |
|---|---|---|
| 소비하면 | **메시지가 사라짐** | 메시지는 그대로, **책갈피만 이동** |
| 비유 | 우편함에서 편지를 꺼냄 (없어짐) | 도서관 책을 읽음 (남아 있음) |
| 여러 명이 읽기 | 한 명만 가져감 | **각자 책갈피로 독립 열람** |
| 다시 읽기 | 불가능 | **책갈피를 앞으로 되돌리면 됨** |

**오프셋 덕에 가능해지는 것들**

- **재처리(Rewind)**: 컨슈머 로직에 버그가 있었다면 오프셋을 과거로 되돌려 처음부터 다시 읽는다
- **독립 소비**: 재고 서비스와 통계 서비스가 서로 방해하지 않고 각자 속도로 읽는다
- **나중 합류**: 6개월 뒤 만든 신규 서비스도 오프셋 0부터 읽으면 과거 데이터를 전부 받는다

**Commit(커밋)이란**

Consumer가 "나 여기까지 읽었어"라고 **책갈피 위치를 브로커에 기록하는 것**이다.
커밋을 해두면 서버가 재시작돼도 그 지점부터 이어서 읽는다.

**Retention(보존 기간)**

책을 영원히 보관할 수는 없으므로 보존 기간을 정한다. 기본 7일이고, 무기한도 설정 가능하다.
기간이 지난 오래된 메시지는 삭제된다.

## 폴링 (Polling)

**한 줄 정의**
결과를 기다리는 쪽이 **주기적으로 반복해서 "있어?"라고 물어보는 것.**

`poll`은 원래 "여론조사하다, 표를 묻다"는 뜻이다. **계속 물어본다**는 뉘앙스다.

**비유: 차 뒷자리의 아이**

```
아이: "아빠 다 왔어?"   ->  "아니"
(1분 후)
아이: "아빠 다 왔어?"   ->  "아니"
(1분 후)
아이: "아빠 다 왔어?"   ->  "응 도착!"
```

반대 방식은 이것이다.

```
아빠: (도착하자마자) "다 왔다!"
```

이것은 **Push(푸시)** 다. 알려줄 쪽이 **먼저** 알려준다.

| | Polling (당기기, Pull) | Push (밀기) |
|---|---|---|
| 주도권 | **받는 쪽** | **주는 쪽** |
| 동작 | 계속 물어봄 | 생기면 알려줌 |
| 일상 예시 | 새로고침(F5) | 카톡 알림 |
| 이 폴더에서 | **Kafka** | **RabbitMQ** |

**폴링이 등장하는 3곳**

**(1) Kafka Consumer**

```java
while (true) {
    records = consumer.poll(Duration.ofMillis(100));  // "새 메시지 있어?"
    for (record : records) { 처리(); }
}
```

Kafka는 브로커가 밀어주지 않는다. **Consumer가 무한 반복문으로 계속 물어본다.**
이것이 Kafka가 "Pull 모델"인 이유다. → [05](05-kafka.md)

**(2) Outbox의 Message Relay**

```java
@Scheduled(fixedDelay = 1000)   // 1초마다
public void publishPendingEvents() {
    List<OutboxEvent> events = outboxRepo.findByStatus(PENDING);  // "발행할 거 있어?"
    ...
}
```

**(3) CDC는 폴링이 아니다**

Debezium 같은 CDC는 물어보지 않고 **DB가 이미 남기고 있는 변경 로그를 흘려받아 읽는다.**
그래서 DB에 추가 부하가 없고 실시간이다. → [13](13-transactional-outbox.md)

**폴링의 트레이드오프**

| | 문제 |
|---|---|
| 너무 자주 물어보면 | 대부분 "없어"라는 답만 돌아옴 → **낭비** (DB에 초당 100번 쿼리, 99번은 빈 결과) |
| 너무 드물게 물어보면 | 메시지가 왔는데 다음 확인까지 놀고 있음 → **지연** |

이를 개선한 것이 **Long Polling**이다. "없으면 바로 대답하지 말고, 생길 때까지 최대 N초 기다렸다 대답해줘"라고 요청한다.
Kafka의 `poll(Duration.ofMillis(100))`에서 그 100ms가 바로 이 대기 시간이다.

## 백프레셔 (Backpressure)

**한 줄 정의**
받는 쪽이 **감당 못 할 속도로 일이 밀려올 때**, 완충하거나 늦추거나 거절해서 시스템이 무너지지 않게 하는 것.

**단어 유래**
직역하면 **"역방향 압력"**. 원래 배관 용어다.
하수구에 물을 너무 빨리 부으면 물이 안 내려가고 **역류한다.** 이때 위로 밀어 올리는 힘이 backpressure다.

**비유: 컨베이어 벨트와 포장 작업자**

```
[상자 투입기] ──벨트──▶ [작업자] ──▶ 완성
   초당 10개              초당 3개만 가능
```

초당 7개씩 쌓인다. 이대로 두면 상자가 작업대에 쌓이고, 바닥에 떨어지고, 통로가 막히고, **공장 전체가 마비된다.**

**해결책 3가지 — 그대로 소프트웨어 백프레셔 전략이다**

**(1) 버퍼 — 쌓아둘 공간을 만든다**

작업대 옆에 큰 바구니를 둔다. 넘치는 상자를 담아두고 여유될 때 꺼낸다.

→ **메시지 큐가 정확히 이 바구니다.** 트래픽 스파이크를 흡수한다.

**(2) 속도 제어 — 투입기에게 천천히 보내라고 신호를 보낸다**

작업자가 버튼을 눌러 벨트 속도를 늦춘다. **역방향으로 신호를 보내는 것**이라 이것이 백프레셔의 원래 의미다.

→ **Kafka의 Pull 모델**이 이것이다. Consumer가 자기 속도로 가져가므로 **자동으로 속도 제어**가 된다. 안 가져가면 안 온다.

**(3) 거절 — 바구니도 넘치면 투입 자체를 막는다**

바구니가 꽉 차면 컨베이어를 세우고 "지금 안 받습니다" 하고 돌려보낸다.

→ Resilience4j의 **Bulkhead**, **RateLimiter**, 톰캣 스레드 풀 고갈 시 커넥션 거부가 이것이다. → [msa/06 장애 격리](../06-장애-격리.md)

**가상 스레드 이야기와의 연결**

톰캣 스레드가 200개뿐이던 시절에는 201번째 요청이 **자동으로 거절**됐다. 즉 **(3)번 거절**이 의도치 않게 작동하고 있었다.
가상 스레드는 요청 10만 개를 다 받아버리므로 이 방어벽이 사라진다. 그래서 부하가 그대로 DB로 흘러가고, **명시적인 Bulkhead가 필요해진다.**

반면 EDA에서는 큐가 **(1)번 버퍼** 역할을 하므로, 10만 개가 와도 큐에 쌓이고 DB는 자기 속도로 처리한다.

**핵심 정리**
백프레셔는 하나의 기술 이름이 아니라 **"감당 못 할 유입을 어떻게 다룰 것인가"라는 문제의 이름**이다.
큐, Pull 모델, Bulkhead가 전부 그 답이다.

**주의: 버퍼는 만능이 아니다**

```
유입 10만/초, 처리 2만/초
-> 큐에 초당 8만 개씩 쌓임
-> 메모리 부족
-> OOM으로 서버 사망
```

버퍼는 **일시적 스파이크**를 흡수할 뿐이다. 유입이 지속적으로 처리량을 초과하면 **버퍼가 터진다.**
시간을 벌어줄 뿐 근본 해결이 아니므로, 처리 능력 자체를 늘리거나 상한선(거절)을 함께 둬야 한다.

## ACK/NACK와 DLQ

**한 줄 정의**
**ACK(확인 응답)를 받기 전까지 브로커는 메시지를 지우지 않는다.** 그런데 영원히 실패하는 메시지가 있으므로, 몇 번 실패하면 **격리 큐(DLQ)로 빼내** 정상 트래픽을 흐르게 한다.

**ACK — 택배 수령 사인과 같다**

```
1. 컨슈머가 큐에서 메시지를 꺼낸다
   → 이때 메시지는 아직 지워지지 않고 "처리 중" 상태가 된다
2. 처리에 성공하면 컨슈머가 브로커에 ACK 를 보낸다
   → 그제서야 큐에서 삭제된다
3. 처리에 실패하면 NACK
   → 브로커가 다시 큐에 넣거나(requeue), 다른 곳으로 보낸다
```

**2번 도중 컨슈머가 죽으면?** ACK가 안 왔으므로 브로커가 **다른 컨슈머에게 재전달**합니다.
**메시지가 유실되지 않습니다.**

> **ACK = Acknowledgement (확인 응답), NACK = Negative Acknowledgement (거부 응답)** 입니다.
> 이 재전달이 곧 **중복 수신**이기도 합니다. → [전달 보장 수준](#전달-보장-수준)

**독약 메시지 (Poison Message)**

여기서 위험한 상황이 생깁니다. **코드에 버그가 있거나 메시지 자체가 잘못돼 있으면
몇 번을 재시도해도 항상 실패합니다.**

```
실패 → 큐로 되돌아감 → 다시 실패 → 또 되돌아감 → ... 무한 루프
```

이런 메시지를 **독약 메시지(Poison Message)** 라고 합니다.
**큐 맨 앞에 박혀 있으면 뒤의 정상 메시지들이 전부 막혀 큐 하나가 통째로 마비됩니다.**

**DLQ — 격리 병실**

> **DLQ = Dead Letter Queue (데드 레터 큐).**
> **처리에 실패한 메시지를 버리지 않고 모아두는 격리 큐**입니다.

**Dead Letter(사서함 불명 우편)** 는 실제 우편 용어입니다.
주소 불명·수취인 불명으로 배달하지 못한 편지를 모아두는 **반송 우편물 취급소**에서 왔습니다.

**두 겹의 방어가 어떻게 도는가**

```
메시지 도착
   │
   ├─ 1회차 시도 → 예외 💥
   ├─ 2회차 시도 → 예외 💥      ← ① 최대 시도 횟수 (첫 시도 포함)
   ├─ 3회차 시도 → 예외 💥         이 재시도는 브로커를 안 거치고
   │                                애플리케이션 메모리 안에서 반복된다
   ▼
② DLQ로 이동:  order-created-topic.stock-group.dlq
   ③ 메시지 헤더에 에러 스택트레이스가 함께 붙는다
   │
   ▼
운영자가 나중에 DLQ를 열어보고 원인 파악 → 코드 수정 후 재처리
```

**핵심 효과**: 문제 메시지를 빼내어 **정상 트래픽이 계속 흐르게** 하는 것입니다.

> **DLQ가 없으면 실패 메시지는 그냥 사라집니다.**
> "주문은 됐는데 재고가 안 깎였다"는 사고가 나도 **증거가 안 남습니다.**
> DLQ는 EDA 운영의 필수품입니다. 그리고 **DLQ에 쌓이는 것을 아무도 안 보면 없는 것과 같으므로,
> 반드시 알림을 걸어야 합니다.**

> ⚠️ **재시도의 한계**: 이 재시도는 **애플리케이션 메모리 안에서 짧은 간격(1초 → 2초 …)으로 반복**됩니다.
> **DB 커넥션 일시 고갈처럼 순간적인 장애에는 유효하지만,
> 외부 API가 10분간 죽은 상황에는 무의미합니다.** 후자는 지연 재시도 큐 같은 별도 설계가 필요합니다.

자세히는 → [08 메시지 신뢰성](08-메시지-신뢰성-ack-nack-dlq.md)

## 전달 보장 수준

**한 줄 정의**
메시지가 **몇 번 도착하는가**에 대한 약속. 세 가지가 있고, 현실에서 쓰는 것은 사실상 하나다.

| 수준 | 의미 | 특징 |
|---|---|---|
| **At-most-once** (최대 1번) | **유실될 수 있지만 중복은 없음** | 빠름. 로그·통계용 |
| **At-least-once** (최소 1번) ★ | **중복될 수 있지만 유실은 없음** | **RabbitMQ·Kafka·Spring Cloud Stream의 기본값** |
| **Exactly-once** (정확히 1번) | 유실도 중복도 없음 | 분산 시스템에서 **사실상 불가능**하거나 매우 비쌈 |

**현실은 At-least-once입니다. 즉 같은 메시지가 2번 이상 도착할 수 있습니다.**

**왜 중복이 생기나**

```
컨슈머가 처리는 다 했는데 ACK 를 보내기 직전에 프로세스가 죽음
   → 브로커: "얘가 못 받았네" → 재전송
네트워크가 끊겨 ACK 가 유실됨
   → 마찬가지로 재전송
```

**"응답을 못 받았다"와 "처리가 안 됐다"는 다릅니다.** 브로커는 그 둘을 구분할 방법이 없습니다.
그래서 **안전한 쪽(다시 보내기)** 을 택합니다.

> **왜 Exactly-once가 어려운가**
> "처리"와 "ACK 전송"은 서로 다른 두 시스템에서 일어나는 별개의 일이라, **하나로 묶을 수 없기 때문**입니다.
> [13 Outbox](13-transactional-outbox.md)에서 다루는 이중 쓰기 문제와 뿌리가 같습니다.

**그래서 나오는 결론 한 줄**

> 중복을 **막을 수 없다면, 중복이 와도 괜찮게 만들면 된다.** → 그것이 [멱등성](#멱등성-idempotency)입니다.

## 멱등성 (Idempotency)

**한 줄 정의**
같은 작업을 **여러 번 실행해도 결과가 한 번 실행한 것과 똑같은 성질.**

수학에서 온 용어다.

```
f(f(x)) = f(x)
```

**한자 뜻**: 멱(冪)은 거듭제곱, 등(等)은 같음. **"거듭해도 같다"** 는 뜻이다.

**비유: 엘리베이터 버튼과 자판기 버튼**

**엘리베이터 버튼은 멱등하다.**
> 3층 버튼을 1번 누르나 10번 누르나 **결과는 3층에 가는 것 하나**다.
> 조급해서 여러 번 눌러도 아무 문제가 없다.

**자판기 동전 투입구는 멱등하지 않다.**
> 500원을 1번 넣는 것과 10번 넣는 것은 **완전히 다르다.**
> 5000원이 들어가버린다.

**멱등한 것과 아닌 것**

| 연산 | 멱등? | 이유 |
|---|---|---|
| "재고를 50으로 **설정**" | O | 몇 번을 해도 50 |
| "재고를 1 **차감**" | **X** | 3번 하면 3 차감 |
| "주문 상태를 CANCELLED로 **변경**" | O | 이미 취소면 그대로 |
| "포인트 1000점 **적립**" | **X** | 3번이면 3000점 |
| HTTP `GET` / `PUT` / `DELETE` | O | 조회/덮어쓰기/삭제 |
| HTTP `POST` | **X** | 호출마다 새 리소스 생성 |

**왜 EDA에서 필수인가**

[전달 보장 수준](#전달-보장-수준)에서 본 대로 현실은 **At-Least-Once**다.
즉 **최소 한 번은 확실히 가지만, 두 번 갈 수도 있다.**

중복이 발생하는 경로가 매우 많다.

- 브로커가 ACK를 못 받아 재전송
- Outbox Relay가 발행 후 상태 업데이트 전에 죽어서 재발행
- 네트워크 타임아웃 후 클라이언트 재시도
- Kafka Consumer Rebalance 중 오프셋 커밋 실패

**"재고 1 차감"은 멱등하지 않으므로, 중복 수신 시 재고가 2개 깎인다.**
따라서 받는 쪽에서 직접 막아야 한다.

**가장 쉬운 방법: 상태를 확인하고 바꾼다**

```java
public void complete() {
    if (this.status == OrderStatus.PENDING) {   // ★ PENDING일 때만 바꾼다
        this.status = OrderStatus.COMPLETED;
    }
}
```

이미 `COMPLETED`인데 같은 이벤트가 또 와도 **아무 일도 일어나지 않습니다** → 멱등.

**상태 변경은 이렇게 쉽게 멱등하게 만들 수 있지만, 숫자 증감(재고 차감, 포인트 적립)은 안 됩니다.**
그쪽은 **처리한 이벤트 ID를 기록해 중복을 걸러내야** 합니다. → [14](14-멱등성.md)

**한 문장 정리**
> **EDA를 도입하는 순간, 멱등성은 선택이 아니라 필수다.**

## 이중 쓰기와 유령 이벤트

**한 줄 정의**
**DB에 쓰기**와 **브로커에 쓰기**는 서로 다른 두 시스템에 대한 별개의 쓰기다. **하나로 묶을 수 없어서** 둘 중 하나만 성공하는 사고가 난다.

**이 하나가 두 가지 사고로 나타납니다**

```
[사고 A — 유령 이벤트]                [사고 B — 이벤트 유실]
① 이벤트 발행 성공 ✅                 ① DB 커밋 성공 ✅
② DB 커밋 직전 예외 → 롤백 💥         ② 바로 그 순간 앱이 죽거나 브로커 다운 💥
                                      ③ 이벤트는 영원히 발행되지 않음 ❌
결과: 주문은 없는데 재고만 깎임        결과: 주문은 남았는데 아무도 모름. 영구 미아
```

> **유령 이벤트(Phantom Event)** = **롤백되어 없던 일이 된 작업**에 대해 발행되어 버린 이벤트.
> "일어나지 않은 일"이 사실인 것처럼 세상에 퍼져 나간 상태입니다.

**사고 A를 막는 방법 — 커밋 후에 발행하기**

스프링에는 **네트워크를 타지 않고 컨테이너 안에서만 도는 인메모리 이벤트 버스**가 있습니다.

| 도구 | 정체 |
|---|---|
| **`ApplicationEventPublisher`** | 스프링 **내부**에서만 도는 이벤트 발행기. **네트워크를 안 탐** |
| **`@TransactionalEventListener`** | 그 내부 이벤트를 **트랜잭션의 특정 시점(커밋 후 등)** 에 처리하는 리스너 |

```
서비스 로직 ──▶ (내부 이벤트 발행) ──▶ 커밋 ──▶ 리스너가 그제서야 브로커로 발행
                                       ↑
                          롤백되면 리스너가 아예 안 불린다 → 유령 이벤트 없음 ✅
```

**"밖으로 바로 던지지 말고, 일단 안으로 던져놓고 커밋된 뒤에 밖으로 내보낸다"** 는 발상입니다.

**하지만 사고 B는 못 막습니다**

커밋 **직후에** 앱이 죽으면 발행이 영영 일어나지 않습니다.
이 구조를 **Best-effort 1-phase commit(최선을 다한 1단계 커밋)** 이라고 부릅니다.

| | 커밋 후 발행 | **Outbox 패턴** |
|---|---|---|
| 유령 이벤트 (롤백됐는데 발행) | ✅ 막음 | ✅ 막음 |
| 이벤트 유실 (커밋됐는데 미발행) | ❌ **가능** | ✅ 막음 |
| 복잡도 | 낮음 (어노테이션 하나) | 높음 (테이블 + 릴레이 프로세스) |

**근본 해결 — 보낼 메시지 자체를 DB 트랜잭션 안에 저장한다**

> **Outbox(발신함) 패턴**: 브로커로 직접 보내지 말고, **같은 DB의 outbox 테이블에 함께 저장**한 뒤
> 별도 프로세스가 그것을 읽어 발행합니다.
> **"커밋되었다"와 "이벤트가 존재한다"가 같은 사실이 되므로**, 발행이 늦어질 수는 있어도 **유실은 없습니다.**

자세히는 → [13 Transactional Outbox](13-transactional-outbox.md)

> **학습·중요도 낮은 이벤트에는 커밋 후 발행으로 충분합니다.**
> **결제·정산처럼 유실이 치명적인 곳에만 Outbox**를 씁니다. 복잡도를 치를 값어치가 있는지가 기준입니다.

| **유령 이벤트 (Phantom Event)** | **롤백되어 없던 일이 된 작업**에 대해 발행되어 버린 이벤트 | [위](#이중-쓰기와-유령-이벤트) |
| **Outbox 패턴** | 발행할 이벤트를 **DB 트랜잭션 안 테이블에 저장**한 뒤 별도 프로세스가 발행 | [13](13-transactional-outbox.md) |
| **`ApplicationEventPublisher`** | 스프링 컨테이너 **내부**에서만 도는 인메모리 이벤트 버스. 네트워크 안 탐 | [위](#이중-쓰기와-유령-이벤트) |
| **`@TransactionalEventListener`** | 내부 이벤트를 **트랜잭션 특정 시점(커밋 후 등)** 에 처리하는 리스너 | [위](#이중-쓰기와-유령-이벤트) |

### Spring Cloud Stream

| 용어 | 뜻 | 자세히 |
|---|---|---|
| **Spring Cloud Stream** | 브로커를 추상화해 **함수 빈만으로** 메시징을 구현하게 해주는 프레임워크 | [07](07-spring-cloud-stream.md) |
| **Binder (바인더)** | **브로커 어댑터.** 의존성 교체만으로 RabbitMQ ↔ Kafka 전환 | [07](07-spring-cloud-stream.md) |
| **Binding (SCSt)** | 함수의 **입출력 채널**과 브로커 목적지를 잇는 설정 | [07](07-spring-cloud-stream.md) |
| **destination** | SCSt의 **논리적 목적지.** RabbitMQ에서는 **Exchange 이름** | [07](07-spring-cloud-stream.md) |
| **StreamBridge** | 코드에서 원하는 지점에 **명령형으로 메시지를 발행**하는 도구 | [07](07-spring-cloud-stream.md) |

> ⚠️ **`Binding`이라는 단어가 두 층에서 다른 뜻으로 쓰입니다.**
> **RabbitMQ의 Binding** = Exchange와 Queue를 잇는 규칙.
> **SCSt의 Binding** = 코드의 함수 채널과 브로커 목적지를 잇는 설정.
> 설정 파일에서 `bindings:` 와 `rabbit.bindings:` 가 따로 나오는 이유가 이것입니다.
