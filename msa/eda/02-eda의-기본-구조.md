# EDA의 기본 구조

## 한 줄로

서비스 사이에 **브로커라는 우체통**을 하나 두고, "무엇을 해라"(명령) 대신 **"무슨 일이 일어났다"(이벤트)** 를 던진다. 그 순간 보내는 쪽 코드에서 받는 쪽 이름이 사라진다.

## 정의

**EDA (Event-Driven Architecture, 이벤트 기반 아키텍처)**

시스템 내부에서 발생한 중요한 상태 변화를 **이벤트(Event) 메시지**로 정의하고, **메시지 브로커(Message Broker)** 를 통해 비동기적으로 전파하는 아키텍처 스타일.

마이크로서비스 간에 직접적인 REST API(HTTP) 호출을 지양한다.

## 핵심 발상: 중간에 우체통을 둔다

**Before (강한 결합)**
```
[Order] ----직접 호출----> [Stock]
```
Order는 Stock의 IP, 포트, API 경로, 응답 형식을 전부 알아야 한다.

**After (느슨한 결합)**
```
[Order] --넣음--> [ 브로커 ] <--꺼냄-- [Stock]
```
Order는 "주문이 생성됐다"는 사실만 브로커에 넣고 끝. 누가 가져가는지 관심 없다.

## 이벤트 라이프 사이클

```
┌───────────────────┐
│ Producer Service  │
│  (상태 변화 발생)   │
└────────┬──────────┘
         │ 이벤트 발행 (Publish)
         ▼
┌───────────────────┐
│  Message Broker   │
│ (Kafka, RabbitMQ) │
└────────┬──────────┘
         │ 이벤트 구독 (Subscribe)
         ▼
┌───────────────────┐
│ Consumer Service  │
│   (비즈니스 처리)   │
└───────────────────┘
```

| 구성 요소 | 역할 |
|---|---|
| **Producer (발행처)** | 비즈니스 완료 시 이벤트를 생성해 브로커로 Push. 누가 가져갈지 알 필요 없음 |
| **Message Broker (중개 레이어)** | 메시지를 신뢰성 있게 보관 및 정렬. 큐(Queue) 또는 토픽(Topic) 형태 |
| **Consumer (구독처)** | 브로커를 구독하다가 메시지가 오면 자신의 비즈니스 로직 수행 |

**Broker(브로커)** 는 원래 **중개인**이라는 뜻이다. 부동산 중개인이 집주인과 세입자가 직접 만나지 않게 하듯, 메시지 브로커가 서비스 간 직접 연결을 끊어준다.

## 이벤트 vs 명령 (가장 중요한 개념 전환)

| | 명령(Command) | 이벤트(Event) |
|---|---|---|
| 문장 형태 | "재고를 차감**해라**" | "주문이 생성**되었다**" |
| 시제 | 명령형 / 미래 | **과거형** |
| 수신자 | **특정 대상 1명** | 모름. 관심 있는 누구든 |
| 거부 가능? | 가능 | **불가능** (이미 일어난 일) |
| 결합도 | 높음 | **낮음** |

**이벤트는 항상 과거형으로 명명한다.** `OrderCreatedEvent`, `PaymentFailedEvent`, `StockDeductedEvent`.
"이미 일어난 사실의 통보"이지 "너 이거 해"가 아니기 때문이다.

```java
// Before: 나는 Stock에게 재고 차감을 시킨다
stockClient.deduct(orderId, qty);

// After: 주문이 생성되었다는 사실을 알린다. 이후는 관심 없음
eventPublisher.publish(new OrderCreatedEvent(orderId, qty));
```

**Order 코드에서 Stock이라는 단어가 사라졌다.** 이것이 느슨한 결합의 실체다.

> 이 구분이 [11 Choreography](11-choreography-saga.md)와 [12 Orchestration](12-orchestration-saga.md)을 가르는 기준이 된다.
> 오케스트레이터가 주고받는 것은 이벤트가 아니라 **명령**이다.

## 대표적 실무 시나리오

**주문 도메인**
Order Service가 주문 생성 완료 이벤트 발행 → Stock(재고), Payment(결제), Delivery(배송)가 각자 캐치하여 병렬 처리

**회원 도메인**
User Service가 가입 완료 이벤트 발행 → Notification이 캐치하여 웰컴 메일 및 SMS 자동 발송

## 큐(Queue) — 1:1, 경쟁 소비

```
[Msg1][Msg2][Msg3] --┬--> Consumer A  (Msg1 가져감)
                     └--> Consumer B  (Msg2 가져감)
```

메시지 하나를 **한 명만** 가져간다. 작업 분배(work distribution)용.
예: 이메일 10만 통 발송을 여러 워커가 나눠 처리.

## 토픽(Topic) — 1:N, Pub/Sub

```
[Msg1] --┬--> 재고 서비스   (Msg1 받음)
         ├--> 알림 서비스   (Msg1 받음)
         └--> 통계 서비스   (Msg1 받음)
```

메시지 하나가 **구독자 전원에게** 복사된다. 사건 알림용.

**Pub/Sub (Publish-Subscribe)** 은 신문 구독과 같다. 신문사(Publisher)는 구독자가 누군지 몰라도 발행하고, 구독한 사람 전원이 같은 신문을 받는다.
