# Choreography-based Saga

## 한 줄로

지휘자 없이 **이벤트 체인**으로 이어간다. 구조가 단순하고 SPOF가 없는 대신, **전체 흐름이 코드 어디에도 없어서** 추적이 어렵다.

## 메커니즘

각 서비스가 자신의 로컬 트랜잭션을 실행하고, 결과를 **이벤트로 발행**한다.
다음 순서의 서비스가 그 이벤트를 **구독**하여 자신의 로컬 트랜잭션을 이어간다. (이벤트 체인)

```
[ 정상 처리 흐름 ]

┌───────────────┐
│ Order Service │  (1. 주문 생성)
└───────┬───────┘
   OrderCreated 발행
        ▼
┌───────────────┐
│ Stock Service │  (2. 재고 차감)
└───────┬───────┘
   StockDeducted 발행
        ▼
┌─────────────────┐
│ Payment Service │  (3. 결제 시도)
└─────────────────┘
```

## 보상 트랜잭션 전파

실패한 서비스가 **보상 이벤트(Fail Event)** 를 발행하면, 이전 단계 서비스들이 이를 감지해 자신의 트랜잭션을 역순으로 되돌린다.

```
[ 실패 및 보상 흐름 ]

┌───────────────┐
│ Order Service │  (3. 주문 상태 CANCELLED)
└───────▲───────┘
   StockRestored 수신
┌───────┴───────┐
│ Stock Service │  (2. 재고 복구)
└───────▲───────┘
   PaymentFailed 수신
┌───────┴─────────┐
│ Payment Service │  (1. 결제 실패)
└─────────────────┘
```

1. Payment Service 결제 승인 실패 → `PaymentFailedEvent` 발행
2. Stock Service 수신 → 차감했던 재고 원상복구 → `StockRestoredEvent` 발행
3. Order Service 수신 → 주문 상태를 `CANCELLED`로 최종 변경

## 장단점

**장점**

| 항목 | 설명 |
|---|---|
| 단순한 구조 | 중앙 컨트롤러가 없어 아키텍처가 단순 |
| **SPOF 없음** | 단일 장애 지점이 발생하지 않음 |
| 높은 자율성 | Pub/Sub 구조의 유연함과 확장성을 그대로 활용 |

**단점**

| 항목 | 설명 |
|---|---|
| **전체 흐름 파악 불가** | "주문 처리 순서가 뭐지?"를 알려면 각 서비스의 핸들러를 전부 뒤져 머릿속으로 조립해야 함 |
| 디버깅 어려움 | Distributed Tracing(Zipkin/Jaeger) 없이는 문제 지점 추적 불가 |
| **순환 의존성 위험** | 서비스 증가 시 서로 이벤트를 기다리는 순환 구조 발생 가능 |
| 설계 복잡도 급증 | 이벤트 종류와 보상 경우의 수가 늘면 통제 불가 |

**적합한 경우**: 참여 서비스 2~3개, 분기 로직이 단순한 워크플로우.
