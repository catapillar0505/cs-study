# 멱등성 (Idempotency)

## 한 줄로

분산 시스템에서 Exactly-Once는 사실상 불가능하므로 **At-Least-Once**를 택한다. 즉 중복이 온다. **받는 쪽에서 이벤트 ID로 중복을 걸러야** 한다.

## Outbox의 근본적 한계

```
Relay: 브로커로 발행 성공
Relay: PROCESSED로 업데이트하려는 순간 -> 서버 다운
재시작: 여전히 PENDING이므로 -> 다시 발행 (중복!)
```

이를 **At-Least-Once Delivery (최소 한 번 전달)** 라고 한다.
**최소 한 번은 확실히 가지만, 두 번 갈 수도 있다.**

정확히 한 번(Exactly-Once)은 분산 시스템에서 사실상 불가능에 가깝다.
그래서 **받는 쪽에서 중복을 처리**하는 방향으로 푼다.

## 멱등성이란

수학 용어. **같은 연산을 여러 번 적용해도 결과가 한 번 적용한 것과 같은 성질.**

```
f(f(x)) = f(x)
```

| 연산 | 멱등한가? |
|---|---|
| "재고를 50으로 **설정**" | O (몇 번을 해도 50) |
| "재고를 1 **차감**" | **X** (3번 하면 3 차감) |
| HTTP `GET`, `PUT`, `DELETE` | O |
| HTTP `POST` | X |

> 비유(엘리베이터 버튼 vs 자판기 투입구)와 더 넓은 표는 [00 용어 사전](00-용어-사전.md#멱등성-idempotency)

## 구현: 이벤트 ID 기반 중복 체크

```java
@Transactional
public void handleOrderCreated(OrderCreatedEvent event) {
    // 이미 처리한 이벤트인지 확인
    if (processedEventRepo.existsById(event.getEventId())) {
        return;   // 조용히 무시
    }
    stockService.deduct(event.getItemId(), event.getQty());
    processedEventRepo.save(new ProcessedEvent(event.getEventId()));
}
```

- 메시지에 **고유 ID(UUID)** 를 부여한다
- Consumer가 처리한 ID를 별도 테이블에 기록한다
- DB의 **유니크 제약**을 걸면 동시성 상황에서도 안전하다

## 왜 필수인가

EDA를 도입하는 순간 중복이 발생할 경로가 매우 많다.

- 브로커의 재전송 (Ack 유실) → [08](08-메시지-신뢰성-ack-nack-dlq.md)
- Outbox Relay의 중복 발행 → [13](13-transactional-outbox.md)
- 네트워크 타임아웃 후 재시도
- Kafka Consumer Rebalance 중 오프셋 커밋 실패 → [05](05-kafka.md)

**따라서 EDA에서 멱등성은 선택이 아니라 필수다.**
