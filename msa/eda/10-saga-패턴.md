# Saga 패턴

## 한 줄로

**롤백을 못 하면, 취소하는 작업을 하나 더 실행하면 된다.** 로컬 트랜잭션을 이어 붙이고 실패 시 **보상 트랜잭션**을 역순으로 돌려 최종 일관성을 맞춘다.

## 아이디어

> **롤백을 못 하면, 취소하는 작업을 하나 더 실행하면 되지 않나?**

```
정상:  주문 생성 -> 재고 차감 -> 결제 성공                끝
실패:  주문 생성 -> 재고 차감 -> 결제 실패
                              │
       주문 취소 <- 재고 복구 <-┘  (보상 트랜잭션 역순 실행)
```

## 정의

분산된 여러 마이크로서비스의 **로컬 트랜잭션을 연속적으로 묶어** 하나의 비즈니스 워크플로우를 완성하는 아키텍처 패턴.

예외 발생 시 이전 상태로 강제 롤백하는 대신, 이미 완료된 로컬 트랜잭션을 역순으로 취소하는 **보상 트랜잭션(Compensating Transaction)** 을 실행하여 최종 일관성을 보장한다.

## 보상 트랜잭션 vs 롤백

| | 롤백 | 보상 트랜잭션 |
|---|---|---|
| 흔적 | 남지 않음 | **남음** |
| 주체 | DB 엔진 | **애플리케이션 코드** |
| 예시 | 트랜잭션 취소 | 재고 복구, 주문 상태 CANCELLED로 변경 |

**은행 계좌 정정과 같다.** 잘못 이체된 돈은 기록을 지우는 게 아니라 **반대 방향 이체를 한 건 더 기록**한다. 원장에는 두 건이 다 남는다.

**흔한 오해**: "Saga = 롤백"이 아니다. 되돌리는 게 아니라 **반대 작업을 새로 하는 것**이다.

## 이름의 유래

**Saga(사가)** 는 고대 노르드어로 **긴 이야기, 서사시**를 뜻한다.
1987년 프린스턴 대학 논문에서 "오래 걸리는 트랜잭션(Long-Lived Transaction)을 여러 짧은 트랜잭션의 연속으로 쪼개자"는 개념을 제시하며 붙인 이름이다. **여러 장(章)으로 이어진 긴 이야기**라는 의미다.

## 반드시 알아야 할 제약

**모든 작업에 보상이 가능한 것은 아니다.**

| 작업 | 보상 가능? |
|---|---|
| 재고 차감 | O (재고 복구) |
| 결제 승인 | O (결제 취소) |
| **이메일 발송** | **X** |
| **외부 배송 접수 (트럭 출발)** | **X** |

따라서 Saga 설계 시 **되돌릴 수 없는 작업은 맨 마지막에 배치**한다.
이메일 발송을 첫 단계에 두면 뒤에서 실패했을 때 "취소 메일"을 또 보내야 하는 이상한 상황이 된다.

## 구현 유형 2가지

- **Choreography (코레오그래피)**: 중앙 제어자 없이 이벤트 기반으로 각 서비스가 자율 협력 → [11](11-choreography-saga.md)
- **Orchestration (오케스트레이션)**: 중앙 오케스트레이터가 전체 흐름을 지휘 → [12](12-orchestration-saga.md)

이름의 유래로 이해하면 쉽다.

- **Choreography = 안무**: 무용수들이 각자 음악과 다른 무용수를 보고 자기 동작을 한다. 지휘자가 없다
- **Orchestration = 오케스트라 지휘**: 지휘자가 각 연주자에게 신호를 준다
