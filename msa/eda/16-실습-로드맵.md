# 실습 로드맵

## Step 1. RabbitMQ 띄우고 눈으로 확인

```bash
docker run -d --name rabbitmq \
  -p 5672:5672 -p 15672:15672 \
  --memory=512m \
  rabbitmq:3-management
```

`http://localhost:15672` 접속 (guest / guest). **큐에 메시지가 쌓이고 빠지는 것을 눈으로 보는 것이 가장 중요하다.**

## Step 2. Spring Cloud Stream 단방향 이벤트

Order → Stock으로 `OrderCreatedEvent` 발행/구독 구현.
`Consumer<T>` 빈 하나와 `StreamBridge` 하나로 끝난다. → [07](07-spring-cloud-stream.md)

## Step 3. 예외를 일부러 던져 재시도와 DLQ 확인

Consumer에서 `throw new RuntimeException()`을 넣고 `max-attempts`, `auto-bind-dlq` 동작을 Management UI에서 확인. → [08](08-메시지-신뢰성-ack-nack-dlq.md)

## Step 4. Choreography Saga

Payment 실패 시 보상 이벤트가 역순으로 흐르는 것을 구현. → [11](11-choreography-saga.md)

## Step 5. Outbox 패턴

`outbox` 테이블 + `@Scheduled` Relay 추가. 브로커를 강제로 내리고(`docker stop rabbitmq`) 주문을 넣어본 뒤, 다시 올렸을 때 밀린 이벤트가 발행되는지 확인. → [13](13-transactional-outbox.md)

## Step 6. Kafka 바인더로 교체

`build.gradle` 의존성과 `application.yml`만 바꾸고 **코드가 그대로인지 확인.** 추상화의 의미가 체감된다.

## 리소스 주의사항

MSA 모듈 여러 개를 `bootRun`으로 동시에 띄우면서 브로커까지 올리면 서버 메모리가 부족해진다.

| 대상 | 대략적 메모리 |
|---|---|
| RabbitMQ 컨테이너 | 200~400MB |
| Kafka (KRaft 모드) | 1GB 이상 |
| Gradle Daemon (모듈당) | 512MB~1.5GB |
| Spring Boot JVM (모듈당) | 기본값이 물리 메모리의 1/4 |

권장 설정:

```properties
# gradle.properties
org.gradle.jvmargs=-Xmx512m -XX:MaxMetaspaceSize=256m
org.gradle.parallel=false
org.gradle.workers.max=2
org.gradle.daemon.idletimeout=1800000
```

```gradle
// build.gradle (각 모듈)
tasks.named('bootRun') {
    jvmArgs = ['-Xmx384m', '-XX:MaxMetaspaceSize=256m']
}
```

```yaml
# docker-compose.yml
services:
  rabbitmq:
    image: rabbitmq:3-management
    mem_limit: 512m
    ports: ["5672:5672", "15672:15672"]
```

실습 중인 모듈만 `bootRun`으로 띄우고, 나머지는 Docker Compose나 `bootJar` + `java -jar`로 실행하는 것이 안전하다.
