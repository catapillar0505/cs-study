# EDA 도입의 3대 이점

## 한 줄로

**결합이 풀리고**(누구인지·살아 있는지 몰라도 됨), **큐가 완충해 주고**(스파이크를 흡수), **인스턴스만 늘리면 확장된다**(락 경합 없음).

## 공간적 / 시간적 결합 해제 (Spatial & Temporal Decoupling)

**공간적 결합 해제**

- Producer는 Consumer의 호스트 IP, Port, API 엔드포인트 경로를 알 필요가 없다
- 오직 메시지 브로커의 주소만 알면 된다
- Consumer 인스턴스가 3개든 30개든 상관없다
- **새 Consumer(예: 통계 서비스)를 추가해도 Producer 코드는 한 줄도 바뀌지 않는다**

**시간적 결합 해제**

- Consumer가 일시적 장애로 다운되거나 점검 중이어도 이벤트는 브로커에 안전하게 저장된다
- Consumer가 복구되는 즉시 중단 지점부터 다시 소비한다

> 동기 호출이었다면 Stock 배포 중 5분 동안 주문이 전부 실패했을 것이다.
> EDA에서는 **주문은 다 받고, 재고 처리만 5분 늦어진다.**

## 배후 압력 조절 (Backpressure Control & Buffer)

```
[트래픽 폭주 10만 TPS]
        │
        ▼
   ┌─────────┐
   │  Queue  │  <- 10만 개가 여기 쌓임 (완충)
   └────┬────┘
        │ Consumer가 자기 속도로 꺼냄 (Pull)
        ▼
   [DB: 초당 2만 건 처리]
```

마케팅 푸시 발송, 이벤트 특가 판매 등 순간 트래픽(Spike Traffic)이 폭주해도 **트래픽이 DB나 다운스트림 서버로 직접 전달되지 않고 큐에 완충된다.**

Consumer는 자신의 처리 용량(Capacity)에 맞게 메시지를 가져오는(Pull) 조절력을 가지므로 인프라 붕괴를 방지한다.

**가상 스레드와의 연결점**: 가상 스레드로 동시 요청을 수만 개 받게 되면 병목이 뒤로 밀려 DB가 죽는다. Resilience4j Bulkhead가 "넘치면 거절"이라면, **메시지 큐는 "넘치면 저장했다가 나중에 처리"** 라는 더 근본적인 해법이다.

> 백프레셔 개념 자체와 "버퍼는 만능이 아니다"는 주의점은 [00 용어 사전](00-용어-사전.md#백프레셔-backpressure)

## 선형적 확장성 (Horizontal Scalability)

```
Queue --┬--> Consumer #1
        ├--> Consumer #2     (3배 처리)
        └--> Consumer #3
```

메시지가 밀리면 동일 Consumer Group으로 묶인 인스턴스 수만 늘리면(Scale-out) 된다.
각 Consumer가 서로 다른 메시지를 가져가므로 **물리적인 락(Lock) 충돌 없이 선형적으로 확장**된다.
