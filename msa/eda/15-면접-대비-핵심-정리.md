# 면접 대비 핵심 정리

**Q. EDA가 뭔가요?**
> 서비스 간 상태 변화를 이벤트로 정의하고 메시지 브로커를 통해 비동기 전파하는 아키텍처입니다. 직접 API를 호출하지 않으므로 Producer가 Consumer의 존재를 몰라도 되고(공간적 결합 해제), Consumer가 다운되어도 메시지가 브로커에 보관되어 나중에 처리됩니다(시간적 결합 해제).

**Q. 동기 호출 대신 EDA를 쓰면 뭐가 좋나요?**
> 세 가지입니다. 첫째 결합도가 낮아져 연쇄 장애가 전파되지 않고, 둘째 큐가 버퍼 역할을 해 트래픽 스파이크를 완충하며(백프레셔), 셋째 Consumer 인스턴스만 늘리면 락 경합 없이 선형 확장됩니다.

**Q. RabbitMQ와 Kafka의 차이는?**
> 본질이 다릅니다. RabbitMQ는 큐라서 소비하면 메시지가 삭제되고 Exchange를 통한 정교한 라우팅이 강점입니다. Kafka는 append-only 로그라서 소비해도 데이터가 남고 오프셋만 이동하므로 재처리가 가능하며, 순차 I/O 덕에 처리량이 압도적입니다. 메시지 하나하나의 정확한 배달이 중요하면 RabbitMQ, 대량 스트림의 저장과 재생이 중요하면 Kafka입니다.

**Q. Kafka에서 순서 보장은 어떻게 되나요?**
> 파티션 내부에서만 보장됩니다. 토픽 전체는 보장되지 않습니다. 특정 엔티티의 순서가 필요하면 해당 ID를 메시지 키로 지정해 같은 파티션으로 보내면 됩니다.

**Q. Consumer를 무한정 늘리면 처리량이 계속 늘어나나요?**
> 아닙니다. 한 파티션은 그룹 내 하나의 Consumer만 소비할 수 있으므로 **파티션 수가 스케일 아웃의 상한선**입니다.

**Q. Saga 패턴이 뭔가요?**
> MSA에서 서비스마다 DB가 분리되어 단일 트랜잭션으로 묶을 수 없기 때문에, 각 서비스의 로컬 트랜잭션을 연쇄로 실행하고 실패 시 보상 트랜잭션을 역순으로 수행해 최종 일관성을 보장하는 패턴입니다. 롤백이 아니라 "취소하는 작업을 한 번 더 실행"하는 것이라 흔적이 남습니다.

**Q. Choreography와 Orchestration 중 뭘 쓰나요?**
> 서비스가 2~3개고 분기가 단순하면 Choreography, 4개 이상이거나 조건 분기가 복잡하고 진행 상태 모니터링이 필요하면 Orchestration입니다. Choreography는 SPOF가 없는 대신 전체 흐름이 코드 어디에도 없어 추적이 어렵고, Orchestration은 흐름이 한곳에 모이는 대신 오케스트레이터가 SPOF가 됩니다.

**Q. Outbox 패턴은 왜 필요한가요?**
> DB 저장과 메시지 발행은 서로 다른 시스템이라 하나의 트랜잭션으로 묶을 수 없습니다. 그래서 브로커에 직접 보내는 대신 같은 DB의 outbox 테이블에 함께 저장해 원자성을 확보하고, 별도 Relay가 그것을 읽어 발행합니다.

**Q. Outbox를 쓰면 완벽한가요?**
> 아닙니다. Relay가 발행 후 상태 업데이트 전에 죽으면 중복 발행되므로 At-Least-Once입니다. 따라서 Consumer 쪽에서 이벤트 ID 기반 중복 체크로 멱등성을 반드시 보장해야 합니다.

**Q. DLQ가 왜 필요한가요?**
> 처리 불가능한 메시지(Poison Message)를 무한 재시도하면 큐 맨 앞에 박혀 뒤의 정상 메시지를 전부 막습니다. 재시도 횟수를 초과한 메시지를 별도 큐로 격리해 정상 트래픽이 계속 흐르게 하고, 원인 수정 후 재발행합니다.
