# 왜 비동기가 필요한가

## 한 줄로

모놀리스에서 공짜로 주어지던 **"호출은 실패하지 않는다"와 "하나의 트랜잭션"** 이 서비스를 쪼개는 순간 동시에 사라진다. EDA와 Saga는 그 두 구멍을 각각 메우려는 시도다.

## 모놀리스에서는 공짜였던 두 가지

```java
@Transactional
public void createOrder(OrderRequest req) {
    orderRepository.save(order);
    stockService.deduct(req);
    paymentService.charge(req);
}
```

이 코드에는 두 가지 축복이 있다.

**축복 1: 메서드 호출은 실패하지 않는다**
같은 JVM, 같은 메모리 공간이므로 네트워크가 개입하지 않는다.

**축복 2: DB가 하나라 `@Transactional` 하나로 전부 묶인다**
원자성(All or Nothing)이 자동으로 보장된다.

## MSA로 쪼개면 두 축복이 동시에 사라진다

```
Order Service (DB1) --HTTP--> Stock Service (DB2) --HTTP--> Payment Service (DB3)
```

- 메서드 호출이 **네트워크 호출**로 바뀜 → 느리고, 실패하고, 상대가 죽어 있을 수 있음
- DB가 갈라짐 → **`@Transactional`이 서비스 경계를 넘지 못함**

> 쪼개는 이유와 그때 생기는 비용 전반은 [msa/01](../01-모놀리식에서-마이크로서비스로.md)

## 동기(Synchronous) 통신

**정의**: 요청을 보낸 스레드가 응답이 올 때까지 블로킹되어 대기하는 방식.

```java
public OrderResponse createOrder(...) {
    stockClient.deduct(...);      // 응답까지 스레드 블로킹 (200ms)
    paymentClient.charge(...);    // 또 블로킹 (500ms)
    return ...;                   // 총 700ms
}
```

**한계 1 — 지연 누적(Latency Accumulation)**
호출 체인이 A → B → C → D로 길어지면 응답 시간이 **더해진다**. 각 서비스가 200ms면 총 800ms. 서비스를 잘게 쪼갤수록 악화된다.

**한계 2 — 연쇄 장애(Cascading Failure)**
Payment Service가 죽으면 Order Service의 톰캣 스레드가 타임아웃까지 묶인다. 스레드 풀이 고갈되면 Order Service도 함께 죽는다. 그러면 Order를 호출하던 Gateway도 죽는다. 도미노처럼 전파된다.

이것이 **강한 결합(Tight Coupling)** 이 만들어내는 위험이다.

## 비동기(Asynchronous) 통신

**정의**: 요청을 보낸 스레드가 응답을 기다리지 않고 즉시 제어권을 반환받아 다음 작업을 계속하는 방식. 응답 처리는 콜백이나 이벤트 리스너로 처리한다.

## 카페 비유

| | 동기 | 비동기 |
|---|---|---|
| 상황 | 카운터 앞에 서서 커피 기다림 | 사이렌 오더 주문 후 사무실 복귀 |
| 내 시간 | 묶임 | 자유 |
| 카페가 잠깐 닫히면 | 나는 그냥 서 있음 | **주문은 서버에 남아 있음** |

마지막 행이 핵심이다. 이것이 뒤에 나올 **시간적 결합 해제**([03](03-eda-도입의-3대-이점.md))의 씨앗이다.

## 흔한 오해

**동기/비동기 ≠ 블로킹/논블로킹**

엄밀히는 다른 축이다.

- **블로킹 / 논블로킹**: 
Blocking / Non-Blocking은 함수를 호출했을 때 나(호출자)의 실행 흐름이 멈추는지 여부

- **동기 / 비동기**:

동기: 앞 작업의 결과가 나오기를 기다렸다가, 그에 맞춰 순서대로 다음 작업을 진행해야 할 때.

비동기: 앞 작업의 결과가 언제 나오든 내 작업 흐름과 상관없이 따로 놀아도 될 때.

실무 대화에서는 거의 붙여 쓰지만, 개념적으로는 구분된다.
