# 게이트웨이란

## 한 줄로

모든 요청이 반드시 지나는 **단일 관문**을 하나 둔다. 클라이언트는 주소 하나만 알면 되고, 인증·로깅·요청 제한 같은 **공통 관심사를 여기서 한 번만** 처리한다.

## 문제 ① — 클라이언트가 주소를 몇 개나 알아야 하나

마이크로서비스가 20개면 클라이언트가 20개 주소를 알아야 할까요? 아닙니다.

```
                    ┌──────────────────────┐
   브라우저 ───────▶│   API Gateway :8000  │
   모바일앱 ───────▶│                      │
                    └───┬──────┬──────┬────┘
              /api/products│  /api/orders│  /api/users
                    ┌──────▼┐  ┌───▼───┐  ┌▼──────┐
                    │product│  │ order │  │ user  │
                    └───────┘  └───────┘  └───────┘
```

**클라이언트는 `localhost:8000` 하나만 압니다.** 뒤에 서비스가 몇 개든, 어디로 옮겨 가든 상관없습니다.

## 문제 ② — 공통 기능을 서비스마다 복붙할 것인가

서비스 5개가 전부 **로그인 여부를 검사**해야 한다고 합시다.

```
[ 게이트웨이가 없다면 ]

  payment-service   → 인증 검사 코드 (복붙)
  order-service     → 인증 검사 코드 (복붙)
  user-service      → 인증 검사 코드 (복붙)
  product-service   → 인증 검사 코드 (복붙)
  delivery-service  → 인증 검사 코드 (복붙)
                       ↑ 정책이 바뀌면 5곳을 고쳐야 함
                         하나 빼먹으면 보안 구멍 💀
```

인증·로깅·요청 제한처럼 **여러 서비스에 공통으로 필요하지만 비즈니스 로직은 아닌 것**을
**횡단 관심사(Cross-Cutting Concern)** 라고 합니다.

> **"횡단"이라는 말**: 서비스들이 세로로 늘어서 있다면, 이 기능들은 **그것들을 가로질러** 관통합니다.
> 어느 한 서비스의 것이 아니라 **전부의 것**이라는 뜻입니다.

```
[ 게이트웨이가 있다면 ]

                    ┌─────────────────────────┐
   요청 ──────────▶ │  Gateway                │
                    │   [인증 필터] ← 여기 한 곳 │
                    └──┬───┬───┬───┬───┬──────┘
                       ▼   ▼   ▼   ▼   ▼
                    payment order user product delivery
                       ↑ 각 서비스는 비즈니스 로직만 신경 쓰면 됨
```

**모든 요청이 반드시 게이트웨이를 지나므로, 거기서 한 번만 검사하면 됩니다.**

## 두 가지 버전 — MVC냐 Reactive냐 (아주 헷갈리는 지점)

Spring Cloud Gateway에는 **두 가지 버전**이 있습니다.
인터넷 예제가 뒤섞여 있어서, 따라 하다 막히는 원인의 상당수가 이것입니다.

| | **Gateway Reactive** (기존) | **Gateway MVC** (최근) |
|---|---|---|
| 기반 | Spring WebFlux (비동기·논블로킹) | Spring MVC (동기·블로킹) |
| 코드 스타일 | `Mono` / `Flux` 반환 | **평범한 객체 반환** |
| 동시성 처리 | 이벤트 루프 | **가상 스레드** |
| 학습 난이도 | 높음 (리액티브 사고방식 필요) | **낮음 (평소 쓰던 MVC 그대로)** |

**왜 MVC 버전이 생겼나?**

예전에는 "대량의 동시 요청을 적은 스레드로 처리"하려면 리액티브가 유일한 답이었습니다.
그런데 **자바 21의 가상 스레드**가 나오면서 상황이 바뀌었습니다.

> **가상 스레드(Virtual Thread)** 란 OS가 관리하는 진짜 스레드가 아니라
> **JVM이 관리하는 아주 가벼운 스레드**입니다.
>
> | | 기존 스레드 | 가상 스레드 |
> |---|---|---|
> | 관리 주체 | 운영체제 | **JVM** |
> | 하나당 메모리 | 약 1MB | 아주 작음 |
> | 만들 수 있는 개수 | 수천 개가 한계 | **수십만 개** |
>
> 덕분에 **"코드는 평범한 블로킹 방식으로 쓰되, 성능은 논블로킹처럼"** 이 가능해졌습니다.

> ⚠️ **인터넷 예제를 볼 때의 구분법**: 코드에 `Mono`, `Flux`, `exchange`가 보이면 **Reactive 버전**입니다.
> 설정 파일의 경로도 다릅니다(`cloud.gateway.routes` vs `cloud.gateway.server.webmvc.routes`).

## 게이트웨이의 한계 — 미리 알아둘 것

게이트웨이에서 인증을 하면 편하지만, **결정적인 전제**가 하나 있습니다.

```
   정상 경로                        우회 경로
   클라이언트 → 게이트웨이 → 백엔드    클라이언트 ───────────▶ 백엔드
                 ↑ 인증 검사                        ↑ 검사 없음 😱
```

**백엔드에 직접 접근할 수 있다면 인증이 통째로 우회됩니다.**
게이트웨이 인증은 **"백엔드에 직접 붙을 수 없다"는 전제 위에서만** 안전합니다.

실무에서 이 구멍을 막는 방법:

| 방법 | 설명 |
|---|---|
| **네트워크 격리** | 백엔드를 사설망(private subnet)에 두어 외부에서 못 붙게 함 (**가장 흔한 답**) |
| **K8s ClusterIP** | Service를 클러스터 내부에서만 접근 가능하게 열기 → [kubernetes/04](../../kubernetes/04-서비스디스커버리-service와-coredns.md) |
| **mTLS** | 게이트웨이와 백엔드가 서로 인증서로 신원 확인 (서비스 메시) |
| **백엔드도 다시 검증** | 관문을 통과했어도 백엔드가 토큰을 한 번 더 검증 (**제로 트러스트**) → [auth/04](../auth/04-역할-기반-인가.md) |

> **"관문은 1차 방어선, 백엔드는 최후 방어선"** 이라고 기억하면 됩니다.
