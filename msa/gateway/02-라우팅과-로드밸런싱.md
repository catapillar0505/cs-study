# 라우팅과 로드밸런싱

## 한 줄로

라우팅 규칙은 **"언제(조건) · 어떻게(가공) · 어디로(목적지)"** 세 조각으로 이루어진다. 목적지를 주소 대신 **서비스 이름**으로 적으면, 게이트웨이가 명부에서 실제 주소 목록을 받아 **골고루 나눠** 보낸다.

## 먼저 — 스케일 업과 스케일 아웃

트래픽이 늘면 두 가지 방법이 있습니다.

| | **스케일 업 (Scale Up)** | **스케일 아웃 (Scale Out)** |
|---|---|---|
| 방법 | 서버 **한 대의 성능**을 올림 (CPU·메모리 증설) | 서버 **대수**를 늘림 |
| 그림 | 🖥️ → 🖥️💪 | 🖥️ → 🖥️🖥️🖥️ |
| 한계 | 물리적 한계가 있고 비쌈 | 이론상 무한 |
| 장애 | 그 한 대가 죽으면 끝 | 한 대 죽어도 나머지가 버팀 |

**마이크로서비스는 스케일 아웃을 전제로 합니다.** 그런데 여기서 새 문제가 생깁니다.

```
                      ???
  [클라이언트] ─────────────▶  [product-service #1]
                              [product-service #2]
                              [product-service #3]
```

- 클라이언트가 3개 주소를 다 알아야 하나? (서버가 늘고 줄 때마다 클라이언트를 고쳐야 함)
- 누가 어디로 보낼지 정하나?
- 한 대가 죽으면 어떻게 알고 피하나?

이 일을 하는 것이 **로드밸런서(Load Balancer)** 입니다.

## 로드밸런싱의 두 가지 위치

### ① 서버 사이드 로드밸런싱 (전통 방식)

```
  [클라이언트] ──▶ [ 로드밸런서 ] ──┬──▶ [서버 #1]
                   (Nginx, ELB)    ├──▶ [서버 #2]
                                   └──▶ [서버 #3]
                   ↑ 별도 장비/프로세스가 중간에 있음
```

- 클라이언트는 로드밸런서 주소 하나만 알면 됨
- 로드밸런서가 **단일 장애 지점(SPOF)** 이 될 수 있음
- 요청이 한 번 더 거쳐 가므로 **홉(hop)** 이 늘어남

> **SPOF = Single Point Of Failure.** "거기가 죽으면 전체가 죽는 지점"입니다.
> **홉(hop)** 은 "중간에 거쳐 가는 단계"를 뜻하는 네트워크 용어입니다.

### ② 클라이언트 사이드 로드밸런싱

```
  [호출하는 쪽] ─── 명부에게 "PRODUCT-SERVICE 주소 다 줘"
        │                     ↓
        │           [주소1, 주소2, 주소3]  ← 목록을 받아 로컬에 캐싱
        │
        └── 내가 직접 하나 골라서 ──▶ [서버 #2]
```

- **호출하는 쪽이 직접** 목록을 갖고 있다가 하나 골라서 부릅니다
- 중간 장비가 없어 홉이 하나 줄어듭니다
- 서버 목록은 **서비스 디스커버리**에서 받아옵니다 → [msa/02](../02-서비스-디스커버리.md)

**Spring Cloud LoadBalancer가 이 ② 방식**이고, 게이트웨이가 이걸 씁니다.
([OpenFeign](../ipc/02-openfeign-선언적-http.md) 호출도 내부적으로 같은 것을 씁니다.)

## Route의 3요소 — 이것만 알면 됩니다

게이트웨이의 라우팅 규칙 하나를 **Route**라고 부르고, **딱 세 조각**으로 이루어집니다.

```
┌─────────────────────────────────────────────────────────┐
│  Route (라우트) = 하나의 라우팅 규칙                    │
│                                                         │
│   ① Predicate  "언제?"    - 조건 (경로, 메서드, 헤더)   │
│   ② Filter     "어떻게?"  - 요청/응답 가공 (선택)       │
│   ③ URI        "어디로?"  - 목적지                      │
└─────────────────────────────────────────────────────────┘
```

### ① Predicate — 조건

**Predicate(프레디케이트)** 는 논리학·수학에서 온 말로 **"참/거짓을 판정하는 것(술어)"** 입니다.
여기서는 **"이 요청이 이 라우트에 해당하는가?"** 를 판단합니다.

```yaml
predicates:
  - Path=/api/products/**
```

`**` 는 "그 아래 모든 경로"를 뜻합니다. `/api/products/port`, `/api/products/1/detail` 모두 매칭됩니다.

자주 쓰는 조건:

| 조건 | 예시 | 뜻 |
|---|---|---|
| `Path` | `Path=/api/products/**` | 경로 매칭 |
| `Method` | `Method=GET,POST` | HTTP 메서드 |
| `Header` | `Header=X-Request-Id, \d+` | 헤더 존재/정규식 매칭 |
| `Query` | `Query=type, mobile` | 쿼리 파라미터 |
| `Host` | `Host=**.example.com` | 호스트 |
| `After`/`Before` | 시각 조건 | 점진적 오픈에 유용 |

여러 개를 나열하면 **AND** 조건입니다(전부 참이어야 매칭).

### ② Filter — 가공

요청을 백엔드에 보내기 전, 또는 응답을 받은 후에 무언가를 합니다.
→ [03 필터로 요청 가로채기](03-필터로-요청-가로채기.md)

### ③ URI — 목적지

**여기가 로드밸런싱과 만나는 지점입니다.**

| 스키마 | 뜻 | 예 |
|---|---|---|
| `http://` | **그 주소로 직접** 보냄 | `http://localhost:8081` |
| **`lb://`** | **서비스 이름으로 찾아서** 로드밸런싱해 보냄 | `lb://PRODUCT-SERVICE` |

**`lb`는 LoadBalancer의 약자입니다.**

`lb://PRODUCT-SERVICE`를 만나면 게이트웨이가 이렇게 동작합니다.

```
1. "PRODUCT-SERVICE" 라는 이름을 서비스 명부(캐시)에서 조회
2. → [주소1:51234, 주소2:51235, 주소3:51236] 목록 획득
3. 로드밸런서가 그중 하나 선택 (기본: 라운드로빈)
4. lb://PRODUCT-SERVICE/api/products/port
     → http://localhost:51235/api/products/port  로 변환해서 전송
```

> **서비스 이름이 대문자인 이유**: Eureka는 서비스 이름을 **대문자로 저장**합니다.
> 설정에 `product-service`라고 써도 명부에는 `PRODUCT-SERVICE`로 올라갑니다.
> 대시보드에 보이는 그대로 쓰는 것이 안전합니다.

## 기본 알고리즘 — 라운드로빈

**라운드로빈(Round Robin)** 은 **순서대로 돌아가며** 하나씩 배정하는 방식입니다.

```
요청 1 → 인스턴스 A
요청 2 → 인스턴스 B
요청 3 → 인스턴스 C
요청 4 → 인스턴스 A   ← 다시 처음으로
```

가장 단순하고 예측 가능해서 기본값입니다. 인스턴스 성능이 비슷할 때 잘 맞습니다.
(무작위로 고르는 `Random` 방식 등으로 바꿀 수도 있습니다.)

> **"라운드로빈"이라는 말**은 원래 "돌려 가며 서명한 탄원서"에서 왔고,
> 지금은 "순서대로 돌아가며"라는 뜻으로 널리 쓰입니다.

## 로드밸런싱을 눈으로 확인하는 방법

**응답에 자기 포트를 담게 하는 것**이 가장 간단한 확인법입니다.

```java
@GetMapping("/port")
public String getPort() {
  return "실행 중인 Product Service PORT: " + env.getProperty("local.server.port");
}
```

같은 주소를 여러 번 호출했을 때 **포트가 번갈아 나오면** 로드밸런싱이 동작하는 것입니다.

```
실행 중인 Product Service PORT: 51234
실행 중인 Product Service PORT: 51235
실행 중인 Product Service PORT: 51236
실행 중인 Product Service PORT: 51234    ← 다시 처음으로 (라운드로빈!)
```

> **`server.port`가 아니라 `local.server.port`** 를 읽는 것이 포인트입니다.
> `server.port`는 **설정에 적은 값**(0)이고, `local.server.port`는 **실제로 배정받은 값**입니다.
>
> 같은 서비스를 여러 개 띄우려면 포트 충돌을 피해야 하는데,
> **포트에 `0`을 주면 OS가 남는 포트를 아무거나 배정**해 줍니다. 그게 표준 방법입니다.

## 알아둘 함정 — 캐시 때문에 생기는 지연

로드밸런서는 서비스 명부를 **로컬에 캐싱**합니다(대략 35초 주기).

- 새 인스턴스를 띄워도 **바로 트래픽이 안 갈 수 있습니다**
- 인스턴스를 껐는데 **잠깐 그쪽으로 요청이 갈 수 있습니다**

실습 중 "왜 바로 반영이 안 되지?" 싶은 이유가 이것이고, **정상 동작**입니다.
대신 **명부 서버가 잠깐 죽어도 통신은 계속된다**는 장점이 함께 옵니다.

## 인스턴스가 하나로만 보일 때

여러 개를 띄웠는데 명부에 **1개만** 보이는 일이 흔합니다.

원인: 명부는 기본적으로 `{호스트명}:{서비스이름}:{포트}` 를 인스턴스 ID로 씁니다.
그런데 한 PC에서 여러 개를 띄우면 호스트명이 전부 같아서 **뒤에 뜬 것이 앞의 것을 덮어씁니다.**

해결: 인스턴스 ID에 **무작위 값을 섞어** 매번 다른 ID가 되게 합니다.

```yaml
eureka:
  instance:
    instance-id: ${spring.application.name}:${random.value}
```
