# 요청 제한 (Rate Limiter)

## 한 줄로

**"누가, 얼마나 자주" 요청할 수 있는지 제한한다.** 물이 일정 속도로 채워지는 **양동이(토큰 버킷)** 에서 요청마다 한 컵씩 퍼가고, 비어 있으면 거절한다.

## 왜 필요한가

서버는 무한하지 않습니다. 누군가 초당 10만 번 요청을 보내면 서비스가 마비됩니다.

| 상황 | 예 |
|---|---|
| **악의적 공격** | DDoS, 비밀번호 무차별 대입 |
| **버그** | 클라이언트가 무한루프로 API 호출 |
| **크롤러** | 데이터를 통째로 긁어가는 봇 |
| **공정성** | 한 사용자가 자원을 독식해 다른 사용자가 느려짐 |

> **방향이 반대라는 점을 짚어둘 만합니다.**
>
> | | 보호 대상 |
> |---|---|
> | 서킷 브레이커·격벽 → [msa/06](../06-장애-격리.md) | **내가 남을 호출할 때** |
> | **Rate Limiter** | **남이 나를 호출할 때** |

## 토큰 버킷 알고리즘

가장 널리 쓰이는 요청 제한 방식입니다. 비유가 아주 직관적입니다.

```
        ┌───────────────┐
        │   💧 💧 💧    │  ← 물이 일정 속도로 채워짐 (초당 1개)
        │   💧 💧       │
        │  (용량 5개)   │  ← 넘치면 버려짐 (최대 5개까지만 고임)
        └───────┬───────┘
                │
       요청이 올 때마다 물 1개를 퍼감
                │
        ┌───────▼───────┐
        │ 물이 있으면?  │ → 통과 ✅
        │ 물이 없으면?  │ → 429 Too Many Requests ❌
        └───────────────┘
```

**설정 두 개가 전부입니다.**

| 값 | 뜻 |
|---|---|
| **용량 (capacity)** | 양동이에 최대 몇 개까지 고이나 = **순간 허용량(버스트)** |
| **충전 속도 (refill rate)** | 초당 몇 개씩 채워지나 = **지속 허용량** |

"용량 5개 + 초당 1개 충전"의 의미:

> **평소엔 초당 1회, 하지만 한동안 안 쓰다가 갑자기 몰아서 5번까지는 봐준다.**

**왜 몰아치기(버스트)를 허용하나?**
사람의 사용 패턴은 균등하지 않기 때문입니다.
웹 페이지 하나를 열면 API를 3~4개 동시에 부르는 게 정상입니다.
"무조건 초당 1회"로 막으면 **정상 사용자도 막힙니다.**

## 다른 알고리즘과 비교

| 알고리즘 | 동작 | 문제 |
|---|---|---|
| **Fixed Window** | "1분에 60회"를 분 단위로 리셋 | **경계에서 몰림** — 59초에 60회 + 61초에 60회 = 2초에 120회 |
| **Sliding Window** | 최근 60초를 계속 이동하며 계산 | 정확하지만 저장 비용이 큼 |
| **Token Bucket** | 위 설명 | **버스트 허용 + 구현 단순.** 가장 널리 쓰임 |
| **Leaky Bucket** | 일정 속도로만 흘려보냄 | 버스트를 전혀 허용 안 함 |

## 누구를 기준으로 제한할 것인가

"초당 1회"라고 할 때 **누구의 초당 1회**인지 정해야 합니다.

| 기준 | 장점 | 단점 |
|---|---|---|
| **사용자 ID** | 정확. 같은 사람이 기기를 바꿔도 추적됨 | 로그인해야만 알 수 있음 |
| **IP 주소** | 로그인 없이도 가능 | 회사·학교는 여러 명이 IP를 공유 → **억울하게 막힘** |
| API 키 | 회사 간(B2B) API에 적합 | 발급 체계가 필요 |

실무에서는 **"있으면 사용자 ID, 없으면 IP"** 라는 조합을 흔히 씁니다.

```
로그인 사용자 → 헤더의 사용자 ID로 버킷 구분
비로그인      → 접속한 IP 주소로 버킷 구분
```

> 이 사용자 ID는 앞선 **인증 필터가 채워줬다고 가정**한 값입니다.
> 게이트웨이가 토큰을 검증해 사용자 ID를 헤더에 실어 주면, 뒤의 필터들이 그걸 씁니다.
> → [03 헤더 주입](03-필터로-요청-가로채기.md) · [auth](../auth/README.md)

## 왜 Redis가 필요한가 — 이 주제의 핵심

"게이트웨이 메모리에 카운터를 두면 되지 않나?" — **안 됩니다.**

```
        [ 메모리 방식 — 게이트웨이가 2대면? ]

   요청 ─┬─▶ [게이트웨이 #1]  메모리: 홍길동 5회 사용
         └─▶ [게이트웨이 #2]  메모리: 홍길동 5회 사용
                                     ↑ 서로 모름!
         → 실제로는 10회를 허용해버림 💀
```

```
        [ 공유 저장소 방식 ]

   요청 ─┬─▶ [게이트웨이 #1] ─┐
         └─▶ [게이트웨이 #2] ─┼─▶ [ Redis ]  홍길동 5회 사용
                              ┘      ↑ 하나의 진실 공급원
         → 정확히 5회만 허용 ✅
```

**Redis**는 메모리에 데이터를 저장하는 초고속 key-value 저장소입니다.
게이트웨이 여러 대가 **상태를 공유**해야 하므로 외부 저장소가 필수입니다.
→ [database/redis](../../database/redis/README.md)

> **이게 "게이트웨이는 상태를 갖지 않는다"는 원칙과 어긋나 보이지만** 그렇지 않습니다.
> 상태는 게이트웨이가 아니라 **Redis가** 갖습니다. 게이트웨이는 여전히 몇 대든 늘릴 수 있습니다.

## 왜 스크립트로 묶어야 하나 — 원자성

토큰 버킷은 이런 단계를 거칩니다.

```
① 현재 토큰 수를 읽는다
② 흐른 시간만큼 충전한다
③ 1개 빼도 되는지 확인한다
④ 뺀 값을 다시 저장한다
```

**여러 요청이 동시에 오면 문제가 생깁니다.**

```
시각  요청 A                요청 B
 t1   ① 읽기 → 토큰 1개
 t2                        ① 읽기 → 토큰 1개    ← A가 아직 저장 안 함!
 t3   ③④ 1 - 1 = 0 저장
 t4                        ③④ 1 - 1 = 0 저장
 결과: 토큰 1개인데 2개 요청이 통과 💀
```

이렇게 **동시 접근 때문에 결과가 어긋나는 현상**을 **경쟁 상태(Race Condition)** 라고 합니다.

**해결: 네 단계를 하나의 스크립트로 묶어 통째로 실행합니다.**

Redis는 **Lua 스크립트를 중간에 끊기지 않게(원자적으로) 실행**합니다.

```
  요청 A ──▶ [스크립트 ①②③④ 통째로 실행] ──▶ 완료
  요청 B ──▶ (A가 끝날 때까지 대기) ──▶ [①②③④] ──▶ 정확히 판단 ✅
```

Redis는 명령을 하나씩 처리하므로, 스크립트 하나가 도는 동안 다른 명령이 끼어들 수 없습니다.

> **원자성(Atomicity)** = "쪼갤 수 없다". 중간에 끼어들 수 없이 **한 덩어리로** 실행되는 성질입니다.
> DB 트랜잭션의 A가 바로 이것입니다. → [database/basics](../../database/basics/README.md)
>
> **Lua**는 Redis에 내장된 작은 스크립트 언어입니다. 여러 명령을 한 덩어리로 보내기 위해 씁니다.
> 명령을 따로따로 보내면(`GET` 후 `SET`) 그 사이에 다른 요청이 끼어듭니다.

## 구현에서 눈여겨볼 세 가지

| | 내용 |
|---|---|
| **"흐른 시간만큼 충전"** | 타이머로 주기적으로 채우는 게 아니라, **요청이 올 때 계산**합니다. 훨씬 효율적입니다 (게으른 충전, Lazy Refill) |
| **용량을 넘지 않게 자르기** | 아무리 오래 안 써도 용량 이상은 고이지 않습니다. 양동이가 넘치면 버려지는 것 |
| **자동 만료(TTL)** | 일정 시간 뒤 키를 자동 삭제합니다. **안 쓰는 사용자의 데이터가 영원히 쌓이는 것을 막습니다** |

> **TTL = Time To Live.** "이 데이터는 언제까지 살아 있을 것인가"를 정하는 값입니다.

## 429와 Retry-After

**429 Too Many Requests** 는 "요청이 너무 잦다"를 뜻하는 표준 HTTP 상태 코드입니다.

| 코드 | 뜻 |
|---|---|
| 401 Unauthorized | 너 누군지 모르겠다 (인증 실패) |
| 403 Forbidden | 누군지는 아는데 권한이 없다 (인가 실패) |
| **429 Too Many Requests** | **너무 자주 온다** |

실무에서는 **`Retry-After` 헤더**를 같이 주는 것이 예의입니다.
"몇 초 뒤에 다시 오라"고 알려주면 클라이언트가 무작정 재시도하지 않습니다.

## 반드시 생각해야 할 것 — Redis가 죽으면?

```
Redis 중단 → 게이트웨이가 토큰을 확인할 수 없음 → 500 에러 → 서비스 전체 마비 💀
```

**요청 제한 장치 때문에 서비스가 죽는 것은 본말전도입니다.**

그래서 **Fail-Open** 전략을 씁니다.

| 전략 | 뜻 | 어디에 |
|---|---|---|
| **Fail-Open** | 장애 시 **통과시킴** (가용성 우선) | **Rate Limiter** |
| **Fail-Close** | 장애 시 **차단함** (보안 우선) | **인증 필터** |

> **인증이 Fail-Open이면 인증 서버가 죽었을 때 전부 통과되는 참사**가 납니다.
> 반대로 Rate Limiter가 Fail-Close면 Redis 장애에 서비스가 통째로 멈춥니다.
>
> **어느 쪽이 맞는지는 그 기능의 성격이 정합니다.** 설계 판단의 좋은 예입니다.
