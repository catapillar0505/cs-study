# 필터로 요청 가로채기

## 한 줄로

필터는 요청을 **가로채서** 앞뒤로 무언가를 하는 장치다. **"다음으로 넘기는 함수를 부르면 통과, 안 부르면 차단"** — 이 한 줄이 필터의 전부다.

## 필터가 동작하는 위치 — Pre와 Post

```
                 ┌────────── 필터 ──────────┐
   요청 ────────▶│  ① Pre 처리              │
                 │     (헤더 검사, 로깅...)  │
                 │         │                │
                 │         ▼                │
                 │    다음으로 넘김 ────────┼────▶ 백엔드 서비스
                 │         │                │           │
                 │         ▼                │◀──────────┘
                 │  ② Post 처리             │
   응답 ◀────────│     (응답 로깅, 헤더 추가)│
                 └──────────────────────────┘
```

| 위치 | 하는 일 | 예 |
|---|---|---|
| **Pre** | 백엔드에 보내기 **전** | 인증 검사, 헤더 추가, 요청 로깅 |
| **Post** | 백엔드 응답을 받은 **후** | 응답 로깅, 응답 헤더 추가 |

코드로는 이렇게 생겼습니다. **"다음으로 넘기는 호출"의 앞뒤에 코드를 두는 것**이 전부입니다.

```java
public ServerResponse filter(ServerRequest request, HandlerFunction<ServerResponse> next) {

    log.info("요청 경로: {}", request.path());       // ← Pre

    ServerResponse response = next.handle(request);  // ← 다음 단계로 진행

    log.info("응답 상태: {}", response.statusCode()); // ← Post
    return response;
}
```

## 차단의 실체 — "다음을 부르지 않는 것"

**Pre 단계에서 `next.handle()`을 부르지 않고 바로 응답을 반환하면, 백엔드에는 요청이 전혀 가지 않습니다.**

```java
// 차단 — 여기서 끝. 백엔드는 이런 요청이 왔다는 사실조차 모릅니다
return ServerResponse.status(HttpStatus.UNAUTHORIZED).body("Unauthorized");

// 통과 — 다음 필터, 그다음 백엔드로 진행
return next.handle(request);
```

**이 두 줄의 차이가 필터의 전부입니다.**

> **이걸 눈으로 확인하는 방법**: 백엔드 서비스의 로그를 켜놓고 인증 실패 요청을 보내보세요.
> **백엔드 쪽에는 아무 로그도 찍히지 않습니다.** 그게 "관문에서 차단했다"의 증거이고,
> 동시에 **백엔드의 부담이 0이라는 뜻**입니다.

## 자주 쓰는 내장 필터 두 가지

직접 만들지 않아도 게이트웨이가 기본 제공하는 필터들이 있습니다.

### ① 경로 재작성 (rewritePath)

```
게이트웨이가 받은 경로:  /delivery/status
                            ↓ 재작성
백엔드로 보내는 경로:    /status
```

**왜 필요한가?**

게이트웨이는 여러 서비스를 하나의 입구로 모읍니다. 그래서 URL 앞에 **서비스를 구분할 접두사**가 필요합니다.

```
http://gateway/delivery/status  →  배송 서비스의 /status
http://gateway/payment/info     →  결제 서비스의 /info
```

그런데 **백엔드 서비스는 그 접두사를 모릅니다.** 배송 서비스는 자기 경로가 `/status`인 줄만 압니다.
그래서 게이트웨이가 **넘겨주기 직전에 접두사를 떼어냅니다.**

> **접두사를 붙일지, 백엔드 경로를 그대로 쓸지는 설계 선택입니다.**
> 백엔드도 `/api/products` 처럼 접두사를 포함한 경로를 쓴다면 재작성이 필요 없습니다.

### ② 헤더 주입 (addRequestHeader)

백엔드로 가는 요청에 헤더를 하나 추가합니다.

```
브라우저가 보낸 요청              백엔드가 실제로 받는 요청
GET /delivery/status      ──▶    GET /status
X-User-ID: hong                  X-User-ID: hong
                                 X-Gateway-Source: delivery-gateway  ← 새로 생김
```

백엔드가 그 헤더를 **필수로 요구**하면, 헤더가 없는 요청은 실행되기도 전에 거절됩니다.
즉 **"게이트웨이를 거치지 않은 직접 요청을 걸러내는 아주 단순한 장치"** 가 됩니다.

> ⚠️ **하지만 이것은 보안 장치가 아닙니다.**
> 누구나 `-H "X-Gateway-Source: 아무거나"` 로 흉내낼 수 있습니다.
> 헤더 검사만으로는 직접 접근을 막을 수 없습니다. → [01의 "게이트웨이의 한계"](01-게이트웨이란.md)
>
> 여기서는 **"게이트웨이가 헤더를 주입한다"는 메커니즘 자체**를 보여주는 용도로 이해하세요.
> 실무에서 이 자리에 실리는 것은 **JWT 검증 결과(사용자 ID)** 입니다. → [auth](../auth/README.md)

## 필터의 실행 순서 — 껍질처럼 겹칩니다

필터를 여러 개 달면 **먼저 추가한 것이 바깥에서** 실행됩니다.

```
┌─ ① 경로 재작성 ────────────────────────────────┐
│ ┌─ ② 헤더 주입 ───────────────────────────────┐│
│ │ ┌─ ③ 로깅 [Pre] ──────────────────────────┐││
│ │ │ ┌─ ④ 요청 제한 ────────────────────┐    │││
│ │ │ │        실제 백엔드 전달           │    │││
│ │ │ └──────────────────────────────────┘    │││
│ │ │   ③ 로깅 [Post]                         │││
│ │ └─────────────────────────────────────────┘││
│ └────────────────────────────────────────────┘│
└───────────────────────────────────────────────┘
```

**순서를 어떻게 정하느냐가 실제 동작을 바꿉니다.**

위 예시에서 요청 제한(④)이 가장 **안쪽**에 있으면:

- 어차피 거절될 요청도 **경로 재작성과 헤더 주입을 먼저 거칩니다** → 낭비
- 대신 **거절된 요청도 로그에 남습니다** → 장점

그래서 실무에서는 보통 **요청 제한을 로깅 바로 다음(바깥쪽)** 에 둡니다.

> **정답이 하나로 정해져 있지 않습니다.** 중요한 건 **"왜 그 순서인지 설명할 수 있는가"** 입니다.

**인증 필터는 특히 앞쪽에 두는 것이 맞습니다.**

```
인증 검사 → (실패하면 여기서 끝) → 주소 찾기 → 전송
```

인증에 실패할 요청이라면 **서비스 명부를 조회하고 인스턴스를 고르는 일조차 할 필요가 없기 때문**입니다.

## 라우팅을 YAML로 쓸까, 자바 코드로 쓸까

라우팅 규칙을 두 가지 방식으로 쓸 수 있습니다.

| | YAML | 자바 코드(DSL) |
|---|---|---|
| 작성 위치 | `application.yml` | `@Configuration` 클래스 |
| 커스텀 필터 연결 | 번거로움 | **빈을 그대로 꽂으면 됨** |
| 조건 분기 | 불가 | 가능 (`if`, 반복문) |
| 재시작 없이 변경 | 설정 서버로 가능 → [msa/04](../04-설정-관리.md) | 불가 (재빌드 필요) |
| 가독성 | 선언적, 한눈에 보임 | IDE 지원(자동완성·리팩터링) |

**직접 만든 필터를 쓸 때는 자바 코드 쪽이 훨씬 편합니다.** 스프링 빈을 파라미터로 받아 바로 끼우면 되니까요.

> **DSL = Domain Specific Language (도메인 특화 언어)**.
> "라우팅을 표현하기 위한 전용 문법"이라는 뜻이고, 여기서는 메서드를 이어 붙이는 자바 코드 형태입니다.

## 흔한 오해

**"필터를 만들어 두면 알아서 적용된다"**
아닙니다. **라우트에 붙여야** 적용됩니다. 만들어만 두고 안 붙이면 아무 일도 일어나지 않습니다.

**"`@Order`로 필터 순서를 정한다"**
라우트에 **직접 순서대로 꽂았다면 `@Order`는 무시됩니다.** 순서는 꽂은 순서로 결정됩니다.
`@Order`는 스프링이 필터를 **자동으로 수집해 정렬할 때** 쓰는 것입니다.

**"인터넷 예제의 `Mono`가 컴파일이 안 된다"**
Reactive 버전 예제를 MVC 버전에 붙인 것입니다. → [01의 MVC vs Reactive](01-게이트웨이란.md)
