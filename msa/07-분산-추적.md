# 분산 추적

## 한 줄로

**요청 하나에 고유 번호(traceId)를 붙이고 서비스에서 서비스로 넘겨준다.** 나중에 그 번호로 모으면 흩어진 로그와 구간별 시간이 **한 줄로 이어진다.**

> 이 문서는 개요입니다. 관측 전반(지표·추적·로그)은 [observation](observation/README.md)에 있습니다.

## 무엇을 해결하려는 기능인가

**"느리다"는 신고가 들어왔을 때, 어느 서비스에서 시간이 갔는지 어떻게 아는가**

지표는 **"order-service가 2초 걸렸다"** 까지만 알려줍니다. 그 2초가 어디서 갔는지는 말해주지 않습니다.

```
  ① order-service 내부 로직이 느린가?
  ② 호출한 payment-service 가 느린가?
  ③ payment-service 의 DB 쿼리가 느린가?
```

**서비스마다 로그가 따로 쌓이면 한 요청을 어떻게 이어 붙이는가**

서비스가 3대씩 떠 있으면 로그 파일이 수십 개고, **어느 줄이 그 요청의 것인지 알 방법이 없습니다.**

## 어떻게 동작하는가

### traceId(요청 하나 전체) / spanId(구간 하나)

| | 뜻 |
|---|---|
| **Trace** | 요청 하나의 **전체 여정**. 고유한 `traceId`를 가짐 |
| **Span** | 그 안의 **개별 작업 하나** (HTTP 호출, DB 쿼리 등). `spanId`와 **부모 ID**를 가짐 |

부모 ID 덕분에 나중에 **트리 구조를 복원**할 수 있습니다.

### 전파 — HTTP 헤더에 실려 다음 서비스로 넘어간다

서비스 A와 B는 다른 프로세스라 메모리를 공유하지 않습니다. 그래서 **헤더에 실어 보냅니다.**

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ↑        ↑ Trace ID              ↑ Span ID        ↑ 수집 여부
```

**W3C Trace Context**라는 웹 표준입니다. 예전에는 도구마다 헤더가 달라 추적이 끊겼습니다.
→ [observation/04](observation/04-분산-추적.md) · [observation/05](observation/05-opentelemetry.md)

### 비동기·스레드 전환 구간에서 끊기는 문제

추적 정보는 **스레드에 매달려** 다닙니다(`ThreadLocal`). **스레드가 바뀌면 끊깁니다.**

- `@Async`·`CompletableFuture` 등 비동기 실행
- 스레드 풀 기반 격벽 → [06 장애 격리](06-장애-격리.md)
- 메시지 브로커를 건너는 구간 → [eda](eda/README.md)

프레임워크가 대부분 이어 붙여 주지만, **직접 만든 스레드 풀은 따로 처리**해야 합니다.

### 샘플링 — 전부 수집하지 않는 이유

```
초당 1만 요청 × Span 10개 × 하루 = 하루 86억 개
```

**저장 비용과 오버헤드가 감당이 안 됩니다.** 그래서 일부만 수집합니다(기본 10%).

> ⚠️ **실습에서 "요청은 보냈는데 안 보인다"는 대부분 이것 때문입니다.** 100%로 올려두세요.

## 무엇을 보고 판단하는가

**구간별 소요 시간 — 시간은 중첩됩니다**

```
[Order]    GET /orders ──────────────▶  250ms  (전체)
  └ [Payment] POST /payments ────▶      180ms  (그 안에 포함)

→ Order 자체 시간 = 250 - 180 = 70ms
→ 범인은 Order 가 아니라 Payment
```

**"Order가 250ms 걸렸으니 Order가 문제"는 잘못된 독법입니다.**

**대기 시간 vs 처리 시간**

Span 사이에 **빈 구간**이 있으면 큐 대기·스레드 대기를 의심합니다.

**평균이 아니라 p95를 봐야 하는 이유** → [performance/01](../performance/01-p95와-백분위수.md)

## 흔한 오해

**"추적을 켜면 원인이 나온다"**
**어디가 느린지는 알려 주지만 왜 느린지는 아닙니다.**
"Payment가 180ms 걸렸다"까지가 추적이고, **왜 그랬는지는 로그와 코드**를 봐야 합니다.

**"추적만 있으면 된다"**
관측은 **지표·추적·로그 셋**이 함께 있어야 성립합니다.
**지표로 범위를 좁히고 → 추적으로 지점을 특정하고 → 로그로 원인을 확인**하는 순서입니다.
→ [observation/01](observation/01-관측-가능성이란.md)
