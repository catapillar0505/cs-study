# 설정 관리

## 한 줄로

설정 파일을 **Git 저장소 한 곳에 모아두고** 서비스들이 뜰 때 받아가게 한다. 값이 바뀌면 **재시작 없이** 갈아끼우고, 인스턴스가 여러 대면 **한 번에 방송**한다.

## 무엇이 문제인가

서비스가 20개면 설정 파일도 20개입니다.

```
   DB 비밀번호를 바꾸려면?
   → 20개 파일을 고치고
   → 20번 다시 빌드하고
   → 20번 다시 배포
```

게다가 **누가 언제 왜 바꿨는지 기록이 남지 않고**, 잘못 바꿨을 때 되돌리기도 어렵습니다.

## 해결 — 설정을 코드 밖으로

설정 파일들을 **Git 저장소 한 곳**에 모아두고, 서비스들은 뜰 때 그걸 받아옵니다.

```
   ┌────────────────────────────┐
   │ Git 저장소                  │  ← 설정 파일들의 원본
   │   application.yml          │
   │   product-service.yml      │
   │   user-service.yml         │
   └─────────────┬──────────────┘
                 │ clone / pull
                 ▼
   ┌────────────────────────────┐
   │ 설정 서버 (Config Server)   │  ← 설정 배포 창구
   └──┬────────┬────────┬───────┘
      ▼        ▼        ▼
  product   user     order      ← 부팅 시 자기 설정을 받아감
```

**왜 하필 Git인가?**

| 파일에 두면 | Git에 두면 |
|---|---|
| 바꾸려면 재빌드·재배포 | **push만 하면 됨** |
| 누가 언제 왜 바꿨는지 모름 | **커밋 이력으로 전부 남음** |
| 서비스 20개면 20군데 수정 | **한 곳에서 관리** |
| 되돌리기 어려움 | **`git revert`** |

> 설정도 코드처럼 **버전 관리·리뷰·롤백**의 대상이 된다는 것이 이 방식의 진짜 가치입니다.

## 파일 이름 규칙 — 가장 중요합니다

설정 서버는 **파일 이름으로** 어느 서비스의 설정인지 판단합니다.

```
{서비스이름}-{프로필}.yml
      │           │
      │           └─ dev, prod 등. 생략 가능
      └─ 각 서비스의 애플리케이션 이름
```

**여러 개가 합쳐져서** 전달됩니다.

| 우선순위 | 파일 | 적용 대상 |
|---|---|---|
| 높음 | `product-service-prod.yml` | product-service의 prod 환경 |
| ↓ | `product-service.yml` | product-service 전체 |
| 낮음 | `application.yml` | **모든 서비스 공통** |

**공통 설정은 `application.yml`에, 서비스별 차이만 개별 파일에** 두면 중복이 사라집니다.

> **프로필(Profile)** 이란 `dev`, `prod` 같은 **환경 구분자**입니다.
> 같은 코드를 개발용·운영용으로 다르게 동작시킬 때 씁니다.

> ⚠️ **"왜 설정을 못 가져오지?" 할 때 8할은 이 이름이 안 맞아서입니다.**
> 서비스의 애플리케이션 이름과 파일명이 **정확히** 같아야 합니다. → [msa/02](02-서비스-디스커버리.md)

## 확인하는 법 — 설정 서버 자체가 REST API입니다

**서비스를 안 띄우고도** 설정이 제대로 읽히는지 확인할 수 있습니다.

```
GET http://설정서버주소/{서비스이름}/{프로필}
```

응답에 그 서비스가 받게 될 설정이 **합쳐진 결과**로 나옵니다.

**디버깅할 때 가장 먼저 해볼 일입니다.** "서비스가 값을 못 받는다"는 문제를
**설정 서버 문제인지, 서비스 쪽 문제인지** 한 번에 가릅니다.

## 클라이언트 쪽에서 알아둘 것

### `optional:` — 설정 서버가 없어도 뜰 것인가

설정을 가져올 주소를 적을 때 `optional:` 을 붙일 수 있습니다.

| | 동작 |
|---|---|
| `optional:` **있음** | 설정 서버에 못 붙어도 **죽지 말고 그냥 떠라** |
| `optional:` **없음** | 설정 서버가 안 떠 있으면 **부팅 실패** |

> **실습 중엔 붙여두는 게 편하지만, 운영에서는 일부러 빼기도 합니다.**
> **설정 없이 잘못된 기본값으로 뜨는 것보다 아예 안 뜨는 게 나은 경우**가 많기 때문입니다.

### 기본값을 적어두는 습관

값을 꺼내 쓸 때 **기본값**을 함께 적어둘 수 있습니다.

```java
@Value("${message.owner:기본오너}")   // 콜론 뒤가 기본값
```

**기본값을 안 적으면 그 키가 없을 때 부팅이 실패합니다.** 넣어두는 습관을 들이는 게 좋습니다.

## 재시작 없이 반영하기

### 문제

**설정을 받아오는 시점은 부팅할 때 딱 한 번**입니다.
Git의 값을 바꿔도 **이미 떠 있는 서비스는 모릅니다.**

### 해결 — 갱신 엔드포인트

**Actuator**란 애플리케이션의 상태를 들여다보고 조작할 수 있는 **관리용 HTTP 엔드포인트 모음**입니다.
그중 하나가 "설정을 다시 읽어와라"는 갱신 엔드포인트입니다.

```
POST /actuator/refresh
  → ["message.owner"]     ← 바뀐 키 목록이 응답으로 옴
```

> ⚠️ **POST입니다.** 브라우저 주소창(GET)으로는 `405 Method Not Allowed`가 납니다.

> ⚠️ **Actuator 엔드포인트는 기본적으로 거의 다 닫혀 있습니다.** 필요한 것만 골라 열어야 합니다.
> **전부 여는 것은 운영에서 절대 금물**입니다. 환경변수를 통째로 보여주는 엔드포인트도 있기 때문입니다.

### 갱신 대상 지정 — `@RefreshScope`

**갱신 엔드포인트를 호출해도 아무 빈이나 다 갱신되지는 않습니다.**
`@RefreshScope`가 붙은 빈만 대상입니다.

**원리**: `@RefreshScope`가 붙으면 스프링은 실제 빈 대신 **프록시(대리인)** 를 주입합니다.
갱신이 호출되면 **프록시 뒤의 진짜 객체를 버리고 새로 만듭니다.**
새로 만들어질 때 설정값이 다시 채워집니다.

```
   [프록시]  →  [진짜 객체 v1]        ← 부팅 시
       ↓ refresh 호출
   [프록시]  →  [진짜 객체 v2]        ← 새 설정으로 다시 생성
```

> **`@RefreshScope`가 없으면 갱신을 호출해도 값이 안 바뀝니다.** 가장 흔한 실수입니다.

## 인스턴스가 여러 대일 때 — 방송하기

### 문제

같은 서비스를 **3대** 띄웠다면 갱신을 **3번** 호출해야 합니다.
30대면 30번입니다. 게다가 **각 인스턴스의 주소(랜덤 포트!)를 알아야** 합니다.

### 해결 — 메시지 브로커로 방송

```
                    ┌──────────────────────┐
   ① 아무 데나       │   메시지 브로커       │
   한 번만 호출  ───▶│   (RabbitMQ 등)      │
                    └───┬────┬────┬────────┘
                        │    │    │  ② 갱신 이벤트 방송
                        ▼    ▼    ▼
                      [#1] [#2] [#3]        ③ 전부 동시에 갱신
```

**메시지 브로커**란 "메시지를 받아서, 그걸 듣고 있는 모두에게 전달해주는 중계소"입니다.
이 기능을 **Spring Cloud Bus**라고 부릅니다.

> **버스(Bus)** 라는 이름은 컴퓨터 구조의 "버스"에서 왔습니다.
> 여러 부품이 함께 연결된 **공용 통로**를 뜻합니다.
> 여기 신호를 흘리면 **연결된 전원이 받습니다.**

> 브로커·이벤트 전반은 [eda](eda/README.md)에 자세히 정리되어 있습니다.

## 비밀값을 평문으로 두지 마세요

```yaml
password: 1234        # ⚠️ 설정 파일은 Git에 올라갑니다
```

| 방법 | 설명 |
|---|---|
| **환경변수** | `password: ${DB_PASSWORD}` 로 두고 실행 환경에서 주입 |
| **설정 서버 암호화** | 암호화된 값을 저장하고 설정 서버가 복호화해서 전달 |
| **전용 비밀 관리 서비스** | Vault, AWS Secrets Manager 등 |
| **쿠버네티스 Secret** | K8s 환경이라면 → [kubernetes/08](../kubernetes/08-configmap과-secret.md) |

**설정 파일은 Git에 올라가므로, 비밀은 항상 밖에서 주입하는 것이 원칙입니다.**

## 흔한 오해

**"로컬 폴더의 설정 파일을 고치면 반영된다"**
설정 서버는 **원격 Git에서 pull** 해옵니다. **push 하지 않으면 반영되지 않습니다.**
(로컬 파일을 직접 읽는 모드도 있어서, 실습할 때는 그쪽이 훨씬 빠릅니다.)

**"refresh를 호출했으니 다 바뀌었을 것이다"**
`@RefreshScope`가 붙은 빈만 바뀝니다. 그리고 **일부 설정은 아예 갱신되지 않습니다**
(DB 커넥션 풀 크기처럼 기동 시점에 확정되는 것들).

## 쿠버네티스에서는 어떻게 되나

**쿠버네티스는 같은 문제를 ConfigMap과 Secret으로 풉니다.**
설정 서버 자체가 필요 없어지는 경우가 많습니다.
