# observation — 관측 가능성 (Observability)

서비스를 여러 개로 쪼갠 뒤 **"지금 시스템 안에서 무슨 일이 벌어지고 있는가"** 를 알아내는 방법을 정리합니다.

모놀리식에서는 로그 파일 하나만 열면 됐지만, MSA에서는 하나의 요청이 여러 서비스를 거치므로
**지표 · 추적 · 로그** 세 가지를 갖추고 **Trace ID로 엮어야** 원인에 도달할 수 있습니다.

[msa/07 분산 추적](../07-분산-추적.md)을 포함해, 관측 전반을 펼친 하위 폴더입니다.

## 세 요소를 한눈에

| | 답하는 질문 | 정체 | 대표 도구 |
|---|---|---|---|
| **Metrics (지표)** | **"무슨 일이 발생했는가?"** | 일정 간격으로 수집되는 **숫자** | Actuator, Micrometer, Prometheus, Grafana |
| **Tracing (추적)** | **"요청이 어디를 거쳐 갔는가?"** | 요청 하나의 **전체 경로와 구간별 시간** | Micrometer Tracing, Zipkin, Jaeger, Tempo |
| **Logging (로그)** | **"구체적으로 어떤 일이 있었는가?"** | 특정 시점의 **상세 기록** | ELK/EFK, Loki, CloudWatch Logs |

```
                        Trace ID: 4bf92f3577b34da6...
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
   [ Metrics ]                 [ Tracing ]                 [ Logging ]
   "이 시각에 지연 급증"    "이 요청이 여기서 180ms"    "그 순간 이 로그가 찍힘"
        │                           │                           │
        └──── 지표에서 이상 발견 → 그 시각의 Trace 로 점프 → 그 Trace ID 로 로그 검색 ────┘
```

**이 "끊김 없이 파고들기(drill-down)"가 관측 가능성의 최종 목표**이고, 이 폴더의 문서들이 전부 그 한 줄을 향합니다.

## 이 폴더를 관통하는 문장들

> **지표는 "문제가 있다"까지, 추적은 "어디서"까지, 로그는 "왜"까지** 알려준다. 셋 다 있어야 원인에 닿는다.

> **모니터링은 "내가 미리 정해둔 게 정상인가", 관측 가능성은 "처음 보는 문제에도 답할 수 있는가"** 다.

> **평균은 소수의 느린 요청을 감춘다.** p95·p99를 봐라.

> **라벨·태그에 ID를 넣지 마라.** 시계열이 무한히 늘어나 저장소가 터진다.
