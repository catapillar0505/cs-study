# OpenTelemetry

## 한 줄로

**"어느 관측 도구를 쓰든 애플리케이션 코드는 똑같이 짜자"** 는 업계 표준이다. 코드를 안 고치고 백엔드 도구만 갈아끼울 수 있게 한다.

## 문제부터 — 벤더 종속

**Vendor Lock-in(벤더 종속)** 이란 **특정 업체의 제품에 묶여서 갈아탈 수 없게 되는 상태**입니다.

관측 도구는 예전에 이 문제가 심했습니다.

```
   Zipkin 을 쓰려면   →  Zipkin 전용 SDK 를 코드에 심는다
   Jaeger 로 바꾸려면 →  코드를 전부 걷어내고 Jaeger SDK 로 다시 심는다
   Datadog 으로 가려면 →  또 다시…
```

**계측 코드는 애플리케이션 곳곳에 흩어져 있습니다.** 컨트롤러, 서비스, 클라이언트 전부에요.
그걸 다 바꾸는 건 사실상 불가능하고, 그래서 **한 번 고른 도구에 영원히 묶입니다.**

게다가 **메트릭·추적·로그가 각자 다른 에이전트**를 쓰면, 서버 한 대에 에이전트가 세 개 떠서 자원을 먹습니다.

## OpenTelemetry란

**OpenTelemetry(줄여서 OTel)** 는 그 문제를 풀기 위한 **표준화 프로젝트**입니다.

> **Metrics·Traces·Logs 세 가지를 특정 벤더에 종속되지 않고 수집·전송하기 위한
> CNCF 오픈소스 표준**

> **CNCF = Cloud Native Computing Foundation.**
> 쿠버네티스·Prometheus 같은 클라우드 인프라 표준을 관리하는 재단입니다.
> **여기서 관리한다 = 특정 회사 소유가 아니다**라는 뜻이라, 업계가 안심하고 채택합니다.
>
> OpenTelemetry는 CNCF에서 **쿠버네티스 다음으로 활발한 프로젝트**입니다.

**핵심 발상**

```
   [ 애플리케이션 ]  ← 여기는 OTel 표준 API 로만 짠다 (한 번만)
          │
          │  OTLP (표준 프로토콜)
          ▼
   [ Collector ]     ← 여기서 어디로 보낼지 정한다 (설정만 바꾸면 됨)
          │
   ┌──────┼───────┬──────────┐
   ▼      ▼       ▼          ▼
Zipkin  Jaeger  Tempo    Datadog
```

**"계측은 표준으로, 목적지는 설정으로"** 가 한 줄 요약입니다.

## Spring Boot에서의 변천사

이 부분이 인터넷 예제를 볼 때 가장 헷갈리는 지점입니다. **Boot 버전에 따라 완전히 다릅니다.**

### Spring Cloud Sleuth (Boot 2.x 시절)

- Boot 2.x 시절 분산 추적의 표준 라이브러리
- 독자 규격인 **B3 Propagation**(`X-B3-TraceId`, `X-B3-SpanId` 헤더) 사용
- **현재 공식 지원 종료(EOL)** — Boot 3부터는 아예 없습니다

### Micrometer Tracing (Boot 3.x / 4.x)

Boot 3.0부터 Sleuth를 **대체**하며 들어왔습니다.

| 특징 | 설명 |
|---|---|
| **메트릭과 추적을 하나로** | `ObservationRegistry` 하나로 통합 → [02 Observation API](02-메트릭.md) |
| **OTel 표준을 네이티브 지원** | 브릿지 의존성 하나로 연결 |
| **W3C `traceparent` 기본 채택** | B3 대신 웹 표준 → [04](04-분산-추적.md) |

### 비교표

| 구분 | **Spring Cloud Sleuth** (Boot 2.x) | **Micrometer Tracing** (Boot 3.x/4.x) |
|---|---|---|
| 추상화 계층 | Sleuth 독자 인터페이스 | **Micrometer Tracing & Observation API** |
| 표준 브릿지 | Brave 기반 | **OpenTelemetry** (Brave도 선택 가능) |
| 전파 규격 | B3 (`X-B3-*`) | **W3C Trace Context (`traceparent`)** |
| 메트릭과의 관계 | 별개 | **한 API 로 통합** |
| 현재 상태 | **EOL (제거됨)** | **현재 표준** |

> ⚠️ **인터넷 예제에 `spring-cloud-starter-sleuth`가 보이면 Boot 2.x 시절 자료입니다.**
> 그대로 따라 하면 의존성부터 찾을 수 없습니다.

### 브릿지(Bridge)라는 단어

```
   [ Micrometer Tracing API ]   ← 내 코드가 쓰는 것
              │
        ┌─────┴─────┐   여기를 잇는 것이 "브릿지"
        ▼           ▼
   [ OTel 구현 ]  [ Brave 구현 ]
```

**브릿지 = 추상 API와 실제 구현체를 연결하는 어댑터**입니다.
`micrometer-tracing-bridge-otel` 의존성을 넣으면 **OTel 구현체로 동작**합니다.

> [02](02-메트릭.md)에서 본 **Micrometer가 "메트릭 계의 SLF4J"** 라는 비유가 여기서도 그대로입니다.
> SLF4J도 `slf4j-logback` 같은 바인딩을 골라 넣죠. 똑같은 구조입니다.

## OTLP — 표준 전송 규격

**OTLP = OpenTelemetry Protocol.** 텔레메트리를 실어 나르는 **표준 통신 규격**입니다.

| 방식 | 기본 포트 | 특징 |
|---|---|---|
| **gRPC** | **4317** | 이진 형식이라 빠르고 효율적 |
| **HTTP** | **4318** | 방화벽·프록시 환경에서 다루기 쉬움 |

> **gRPC**는 이진 데이터 + HTTP/2 기반의 고성능 통신 방식입니다. → [msa/ipc/03](../ipc/03-grpc와-protobuf.md)

**예전에는 도구마다 포맷이 달랐습니다** (Zipkin은 JSON, Jaeger는 Thrift 등).
OTLP가 그걸 **하나로 통일**했습니다.

## OTel Collector

**Collector(수집기)** 는 **텔레메트리의 중계소**입니다.
애플리케이션에서 데이터를 받아, 가공한 뒤, 여러 목적지로 나눠 보냅니다.

```
┌────────────────────────────────────────┐
│     Spring Boot Application            │
│   (micrometer-tracing-bridge-otel)     │
└───────────────────┬────────────────────┘
                    │  OTLP (gRPC 4317 / HTTP 4318)
┌───────────────────▼─────────────────────┐
│        OPENTELEMETRY COLLECTOR          │
│  ┌───────────────────────────────────┐  │
│  │ Receivers   — 데이터를 받는 입구   │  │
│  └────────────────┬──────────────────┘  │
│  ┌────────────────▼──────────────────┐  │
│  │ Processors  — 가공 (배치·필터·마스킹)│  │
│  └────────────────┬──────────────────┘  │
│  ┌────────────────▼──────────────────┐  │
│  │ Exporters   — 내보내는 출구        │  │
│  └────────────────┬──────────────────┘  │
└───────────┬───────┴────────┬────────────┘
            │                │
    ┌───────▼─────────┐  ┌───▼──────────────┐
    │ Jaeger / Tempo  │  │ Prometheus / Loki │
    │ (추적)          │  │ (지표 · 로그)      │
    └─────────────────┘  └───────────────────┘
```

**세 부분으로 이루어진 파이프라인입니다.**

| 단계 | 하는 일 | 예 |
|---|---|---|
| **Receivers** | 데이터를 **받는 입구** | OTLP 수신, Prometheus 스크래핑 |
| **Processors** | **가공** | 여러 건을 **묶어서**(batch) 보내기, 메모리 상한, **민감정보 마스킹**, 샘플링 |
| **Exporters** | **내보내는 출구** | Zipkin으로, Prometheus로, S3로 |

### Collector를 두면 좋은 점

| | 설명 |
|---|---|
| **백엔드 교체가 설정 한 줄** | 애플리케이션은 Collector만 보고 있으므로, **Exporter만 바꾸면** 도구가 바뀜 |
| **애플리케이션 부담 감소** | 배치·재시도·버퍼링을 Collector가 대신함 |
| **한 번 보내 여러 곳으로** | 같은 데이터를 Zipkin과 S3에 **동시에** 보낼 수 있음 |
| **민감정보 제거** | 애플리케이션을 안 고치고 **중앙에서 마스킹** |

> **Collector가 항상 필요한 건 아닙니다.**
> 소규모나 실습에서는 **애플리케이션이 Zipkin으로 직접 보내는 것**으로 충분합니다.
> → [07 실습](07-실습-plg-스택.md)이 그 구성입니다.
> **서비스가 많아지고 목적지가 여러 개가 될 때** Collector의 값어치가 나옵니다.

## 과거 방식과의 비교

| 비교 항목 | **과거 (벤더 종속)** | **OpenTelemetry 표준** |
|---|---|---|
| 애플리케이션 SDK | 도구마다 **독자 SDK 개별 탑재** | **단일 표준 추상화** |
| 전송 규격 | 도구마다 **다른 포맷** (JSON, Thrift…) | **OTLP 하나** |
| 백엔드 교체 | **소스 코드와 의존성 재작업** | **Collector 설정만 수정** |
| 시스템 오버헤드 | 지표·추적·로그별로 **에이전트가 각각** | **파이프라인 하나로 통합** |

## 흔한 오해

**"OpenTelemetry가 대시보드도 준다"**
아닙니다. **OTel은 수집과 전송까지만** 합니다.
저장과 시각화는 Jaeger·Tempo·Prometheus·Grafana 같은 **백엔드의 몫**입니다.

**"OTel을 쓰면 Zipkin은 못 쓴다"**
쓸 수 있습니다. **Zipkin은 백엔드(저장·조회)** 이고 OTel은 **계측·전송 표준**이라 층이 다릅니다.
Exporter를 Zipkin으로 지정하면 됩니다. [07 실습](07-실습-plg-스택.md)이 정확히 그 조합입니다.

**"표준이니까 다 똑같이 동작한다"**
언어별·라이브러리별로 **성숙도가 다릅니다.** 추적은 안정적이지만
**OTel 로그는 상대적으로 늦게 표준화**되었습니다.
