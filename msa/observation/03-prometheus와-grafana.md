# Prometheus와 Grafana

## 한 줄로

**Prometheus가 주기적으로 찾아와 숫자를 긁어가 저장**하고, **Grafana가 그것을 그림으로 보여준다.** 저장하는 쪽과 보여주는 쪽이 분리되어 있다.

## 기초 — Pull과 Push

메트릭을 모으는 방식은 크게 둘입니다.

| | **Push (밀기)** | **Pull (당기기)** |
|---|---|---|
| 누가 시작하나 | **애플리케이션이** 서버로 보냄 | **수집 서버가** 애플리케이션에 가지러 옴 |
| 비유 | 직원이 보고서를 상사에게 **제출** | 상사가 직원 자리에 **와서 확인** |
| 대표 | Graphite, StatsD, Datadog Agent | **Prometheus** |

**Prometheus는 Pull 방식입니다.**

```
   Prometheus ──(15초마다 HTTP GET)──▶ /actuator/prometheus
              ◀──(현재 값 전부 텍스트로)──
```

**Pull의 장점**

| | 이유 |
|---|---|
| **대상이 살아있는지 자동으로 알 수 있다** | 긁으러 갔는데 응답이 없으면 = 죽은 것 (`up` 지표가 0이 됨) |
| **애플리케이션이 단순해진다** | 수집 서버 주소를 몰라도 됨. 그냥 값을 노출만 하면 끝 |
| **수집 서버가 속도를 조절한다** | 애플리케이션이 폭주해도 수집 부하는 일정 |
| **테스트가 쉽다** | 브라우저로 그 주소를 열면 사람이 눈으로 확인 가능 |

**Pull의 단점**

- **수집 서버가 대상 주소를 알아야** 합니다 (그래서 서비스 디스커버리와 붙여 씁니다)
- **짧게 살다 죽는 작업**(배치 잡)은 긁으러 갔을 때 이미 없을 수 있습니다
  → 이런 경우만 예외적으로 Push용 중계 서버(Pushgateway)를 씁니다

## 기초 — TSDB

**TSDB = Time Series Database (시계열 데이터베이스)**

**(시각, 값)** 쌍을 **엄청나게 많이, 빠르게** 저장하고 조회하도록 특화된 DB입니다.

**일반 관계형 DB와 뭐가 다른가?**

```
일반 DB에 넣으면:  타임스탬프(8바이트) + 값(8바이트) + 인덱스 …  → 한 점에 수십 바이트
TSDB 는:          "앞 값이랑 비슷하네"  → 차이만 저장            → 한 점에 1~2바이트
```

시계열 데이터는 **연속된 값이 서로 비슷하다**는 성질이 있습니다.
(CPU가 32% → 33% → 33% → 34%처럼 급변하지 않죠.)

TSDB는 그 성질을 이용해 **차이만 저장하는 압축**을 합니다. 그래서 수억 개의 점을 감당할 수 있습니다.

> 대신 **업데이트·삭제가 거의 없다**는 전제가 깔려 있습니다. 시계열은 **쓰고 나면 안 바뀌니까요.**
> 그리고 **오래된 데이터는 통째로 버립니다** (보존 기간, retention).

## 전체 수집 아키텍처

```
┌──────────────────────────────────────────────────────────────┐
│                  SPRING BOOT APPLICATION                     │
│                                                              │
│  ┌────────────────────┐   ┌──────────────────────────────┐   │
│  │ JVM / HTTP / DB    │   │      Spring Boot Actuator    │   │
│  │ 내부 메트릭         │   │                              │   │
│  └─────────┬──────────┘   │  ┌────────────────────────┐  │   │
│            │              │  │ Micrometer Observation │  │   │
│  ┌─────────▼──────────┐   │  │  (메트릭 + 추적 통합)   │  │   │
│  │ 내가 심은 계측       │──▶│  └───────────┬────────────┘  │   │
│  │ (@Timed, Counter)  │   │  ┌───────────▼────────────┐  │   │
│  └────────────────────┘   │  │ Prometheus Registry    │  │   │
│                           │  │ (텍스트 포맷으로 변환)  │  │   │
│                           │  └────────────────────────┘  │   │
│                           └──────────────┬───────────────┘   │
└──────────────────────────────────────────┼───────────────────┘
                                           │  HTTP GET 으로 노출
                                           ▼
                                  /actuator/prometheus
                                           │
                                           │  Scrape (Pull)  — 15초마다
                                           ▼
                              ┌────────────────────────┐
                              │   PROMETHEUS SERVER    │
                              │  ┌──────────────────┐  │
                              │  │ Retrieval (수집) │  │
                              │  └────────┬─────────┘  │
                              │  ┌────────▼─────────┐  │
                              │  │ TSDB (저장)      │  │
                              │  └────────┬─────────┘  │
                              └───────────┼────────────┘
                                          │  PromQL 질의
                                          ▼
                              ┌────────────────────────┐
                              │   GRAFANA DASHBOARD    │
                              │   [ 실시간 차트 ]       │
                              │   [ 알림 규칙 ]         │
                              └────────────────────────┘
```

**흐름을 여섯 단계로 읽으면**

| 단계 | 무슨 일이 |
|---|---|
| ① **메트릭 발생** | JVM·HTTP·커넥션 풀·비즈니스 로직에서 숫자가 만들어짐 |
| ② **관측 추상화** | Micrometer Observation이 **메트릭과 추적을 한 번에** 수집 |
| ③ **포맷 변환** | Prometheus용 레지스트리가 값을 **텍스트 규격**으로 변환 |
| ④ **노출** | Actuator가 `/actuator/prometheus` 주소로 **웹에 공개** |
| ⑤ **수집(Scrape)** | Prometheus가 정해진 주기로 **HTTP GET 해서 가져가 저장** |
| ⑥ **시각화** | Grafana가 **PromQL로 질의**해 차트를 그리고 알림을 보냄 |

> **엔드포인트를 열지 않으면 ④에서 막힙니다.** → [02의 Actuator 노출 설정](02-메트릭.md)

## Prometheus 구성 요소

| 컴포넌트 | 역할 |
|---|---|
| **Retrieval** | 대상의 엔드포인트를 주기적으로 **Pull(Scrape)** |
| **TSDB** | 시계열을 **고도로 압축**해 메모리·디스크에 블록 단위로 저장 |
| **PromQL** | 집계·추세·비율 계산을 위한 **전용 질의 언어** |
| **Alertmanager** | 규칙에 걸리면 **중복 제거·그룹화** 후 Slack·이메일 등으로 알림 |

### 수집 주기(scrape_interval)의 트레이드오프

```yaml
global:
  scrape_interval: 15s     # 15초마다 긁어온다
```

| 짧게 하면 (예: 5초) | 길게 하면 (예: 1분) |
|---|---|
| 그래프가 **촘촘하고 반응이 빠름** | 저장 공간·부하가 **적음** |
| 저장량과 부하가 **커짐** | **짧은 스파이크를 놓칠 수 있음** |
| 실습·디버깅에 적합 | 운영의 일반적인 선택 |

**공식 권장은 보통 15초~1분**입니다. 실습에서는 그래프가 빨리 움직이는 걸 보려고 짧게 잡습니다.

> ⚠️ **수집 주기보다 짧게 일어난 일은 관측되지 않습니다.**
> 15초 주기인데 3초짜리 스파이크가 있었다면, **아예 없었던 일이 됩니다.**
> "분명 장애가 있었는데 그래프엔 안 보인다"의 흔한 원인입니다.

### PromQL 맛보기

메트릭은 **누적값(Counter)** 으로 저장되므로, 대부분의 질문은 **가공**을 거칩니다.

| 하고 싶은 것 | PromQL |
|---|---|
| **초당 요청 수 (RPS)** | `rate(http_server_requests_seconds_count[1m])` |
| **에러율** | `rate(...{status="500"}[1m]) / rate(...[1m])` |
| **p95 응답 시간** | `histogram_quantile(0.95, ...)` |
| **Heap 사용률** | `jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"}` |

> **`rate()`가 핵심입니다.** [02](02-메트릭.md)에서 본 대로 Counter는 **누적값**이라 그 자체로는 의미가 적습니다.
> `rate()`는 **"단위 시간당 얼마나 늘었나"(기울기)** 를 계산해 줍니다.
> `[1m]`은 **"최근 1분 구간을 보고 계산해라"** 는 뜻입니다.

> **메트릭 이름이 자바 쪽과 조금 다릅니다.**
> 자바에서는 `http.server.requests`, Prometheus에서는 `http_server_requests_seconds_count`.
> **점(`.`)이 밑줄(`_`)로 바뀌고 단위와 접미사가 붙습니다.** Prometheus 명명 규칙에 맞춰 변환되기 때문입니다.

## Grafana

**Grafana(그라파나)** 는 **여러 데이터 소스를 연결해 대시보드를 만드는 시각화 도구**입니다.

### 왜 저장과 시각화가 분리되어 있나

```
   [ Prometheus ]  숫자를 모으고 저장하는 데 집중
   [ Loki ]        로그를 모으고 저장
   [ Zipkin/Tempo ] 추적을 모으고 저장
          │  전부 서로 다른 저장소
          ▼
   [ Grafana ]     이 셋을 한 화면에 붙여서 보여줌
```

**Grafana는 데이터를 저장하지 않습니다.** 필요할 때마다 각 저장소에 **질의해서 그립니다.**

이 구조 덕분에 **지표·추적·로그를 한 화면에서 오갈 수 있습니다.** 그게 [01](01-관측-가능성이란.md)에서 말한 드릴다운입니다.

### 특징

| 기능 | 설명 |
|---|---|
| **다양한 패널** | 시계열 그래프, 게이지, 단일 수치(Stat), 히트맵, 로그 뷰 |
| **템플릿 변수** | `$instance`, `$uri` 같은 **드롭다운 변수**로 특정 인스턴스·API만 골라 보기 |
| **알림 규칙** | 조건에 걸리면 Slack 등으로 통보 |
| **대시보드 Import** | 남이 만든 대시보드를 **ID 하나로 가져오기** |

> **대시보드를 처음부터 만들 필요가 없습니다.**
> Spring Boot용으로 잘 만들어진 공개 대시보드(예: ID `11378`, `19004`)를 **Import**하면 바로 씁니다.
> 자기 상황에 맞게 고쳐 쓰는 것이 빠릅니다.

### 세 도구의 역할 분담

```
    Spring Boot          Prometheus              Grafana
   ─────────────       ─────────────           ───────────
   숫자를 만들고        긁어가서 저장하고        질의해서 그린다
   웹으로 노출          시간 축으로 쌓는다        + 알림을 보낸다
```

**한 문장으로**: **애플리케이션은 내놓고, Prometheus는 모으고, Grafana는 보여줍니다.**

## 흔한 오해

**"Grafana가 데이터를 저장한다"**
아닙니다. **대시보드 정의만** 저장합니다. 실제 데이터는 Prometheus·Loki 등에 있습니다.

**"Prometheus만 있으면 된다"**
Prometheus에도 간단한 그래프 화면(`:9090`)이 있습니다. **질의를 확인하는 용도로는 충분**하지만,
여러 데이터 소스를 묶고 대시보드를 꾸미는 건 Grafana의 몫입니다.

**"메트릭에 사용자 ID를 태그로 넣자"**
[02의 카디널리티 폭발](02-메트릭.md) 그대로입니다. TSDB가 감당하지 못합니다.
**개별 식별자는 메트릭이 아니라 [로그](06-분산-로깅.md)나 [추적](04-분산-추적.md)의 영역**입니다.
