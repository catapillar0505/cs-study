# 분산 추적 (Distributed Tracing)

## 한 줄로

**요청 하나에 고유 번호를 붙이고, 그 번호를 서비스에서 서비스로 넘겨준다.** 나중에 그 번호로 모으면 **"어디서 얼마나 걸렸는지"** 가 한 줄로 이어진다.

## 문제부터 — 메트릭은 "왜"를 말해주지 않는다

Grafana에서 이런 알림을 받았다고 합시다.

> ⚠️ `order-service` 응답 시간이 2초를 넘었습니다.

**메트릭은 여기까지입니다.** 문제가 있다는 **사실**만 알려주고, **원인과 지점**은 말해주지 않습니다.

```
2초가 걸렸다는데, 어디서?

  ① order-service 내부 로직이 느린 건가?
  ② order-service 가 호출한 product-service 가 느린 건가?
  ③ product-service 가 실행한 DB 쿼리가 느린 건가?
  ④ 아니면 그냥 네트워크가 느린 건가?
```

**로그를 뒤져서 알아낼 수 있을까요?** 서비스가 3대씩 떠 있으면 로그 파일이 9개고,
그중 **어느 줄이 그 요청의 것인지 알 방법이 없습니다.**

**분산 추적은 이 질문에 답하기 위한 것입니다.**

## 핵심 개념 세 가지

### ① Trace — 요청 하나의 전체 여정

**Trace(트레이스)** 는 **클라이언트 요청 하나가 시스템에 들어와 끝날 때까지의 전체 흐름**입니다.

```
/orders 요청 → Order → Payment → Stock → 응답
└──────────────── 이 전체가 하나의 Trace ────────────────┘
```

**고유한 `Trace ID`** 하나를 가집니다. 이게 **요청의 주민등록번호**입니다.

### ② Span — 그 안의 작업 하나

**Span(스팬)** 은 Trace를 구성하는 **개별 작업 단위**입니다.

> **span**은 "구간, 폭"이라는 뜻입니다. **다리의 경간(span)** 처럼 **시작과 끝이 있는 한 구간**입니다.

무엇이 Span이 되나:

- HTTP 요청 처리 하나
- 다른 서비스로의 HTTP 호출 하나
- DB 쿼리 실행 하나
- 메시지 발행/수신 하나

각 Span이 기록하는 것:

| 항목 | 예 |
|---|---|
| **Span ID** | `00f067aa0ba902b7` |
| **시작 시각** | 14:20:15.123 |
| **소요 시간(Duration)** | 180ms |
| **작업 이름** | `GET /orders` |
| **태그** | `http.status_code=200`, `db.statement=SELECT ...` |

**같은 Trace 안의 모든 Span은 같은 `Trace ID`를 공유합니다.** 그래서 나중에 모을 수 있습니다.

### ③ 부모-자식 관계

Span들은 **나무(tree) 구조**를 이룹니다.

```
Root Span            GET /orders            (최초 진입점에서 생성)
   │
   ├─ Child Span     POST /payments         (Parent = Root)
   │      │
   │      └─ Grandchild Span   SELECT ...   (Parent = POST /payments)
   │
   └─ Child Span     PUT /stock
```

각 Span은 **`Parent ID`(부모가 누구인지)** 를 들고 있습니다.
이 정보만으로 **나중에 트리 전체를 복원**할 수 있습니다.

## 컨텍스트 전파 (Context Propagation)

**가장 핵심적인 메커니즘입니다.**

**문제**: 서비스 A와 B는 **다른 프로세스**입니다. A의 메모리에 있는 Trace ID를 B가 어떻게 알까요?

**답**: **HTTP 헤더에 실어 보냅니다.**

```
        ┌──────────────────────────────────────────┐
        │ ORDER-SERVICE                            │
        │  Trace ID : 4bf92f3577b34da6a3ce929d0e0e4736
        │  Span ID  : 00f067aa0ba902b7  (Root Span)│
        └────────────────────┬─────────────────────┘
                             │
              HTTP 요청 헤더에 실어서 전달
    traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                             │
        ┌────────────────────▼─────────────────────┐
        │ PAYMENT-SERVICE                          │
        │  Trace ID  : 4bf92f...4736  ← 같은 Trace ID│
        │  Span ID   : 5a15d3d8d8812bc4 ← 새 Span   │
        │  Parent ID : 00f067aa0ba902b7 ← 부모 기억 │
        └──────────────────────────────────────────┘
```

**두 동작으로 이루어집니다.**

| 동작 | 하는 일 |
|---|---|
| **Inject (주입)** | 나갈 때 현재 Trace 정보를 **헤더에 써 넣는다** |
| **Extract (추출)** | 들어올 때 헤더에서 **읽어내 이어 붙인다** |

**개발자가 직접 할 일은 없습니다.** 라이브러리가 HTTP 클라이언트·서버에 자동으로 끼어들어 처리합니다.

### `traceparent` 헤더 뜯어보기

**W3C Trace Context**라는 **웹 표준 규격**입니다.

```
traceparent: 00 - 4bf92f3577b34da6a3ce929d0e0e4736 - 00f067aa0ba902b7 - 01
             ↑            ↑                              ↑              ↑
          버전      Trace ID (32자)              Span ID (16자)      플래그
                    이 요청 전체의 ID           지금 이 구간의 ID    01=수집함
```

마지막 **플래그가 샘플링 여부**입니다. `01`이면 "이 요청은 수집 대상"이라는 표시고,
**하위 서비스들도 그 결정을 따릅니다.** (그래야 절반만 수집되는 반쪽 Trace가 안 생깁니다.)

> **표준이 왜 중요한가?** 예전에는 도구마다 헤더 이름이 달랐습니다(`X-B3-TraceId` 등).
> 그러면 **서로 다른 도구를 쓰는 팀 사이에서 추적이 끊깁니다.**
> W3C 표준으로 통일되면서 **회사·언어·도구가 달라도 이어집니다.** → [05](05-opentelemetry.md)

## 타임라인 읽는 법

수집된 Span은 **폭포수(waterfall) 형태**로 보여집니다.

```
Trace ID: 4bf92f3577b34da6...        (전체 250ms)

[Order-Service]        GET /orders ──────────────────▶  250ms  (Root)
│
├─ [Payment-Service]   POST /payments ──────────▶       180ms  (Child)
│   │
│   └─ [Database]      SELECT * FROM accounts ──▶        50ms  (Grandchild)
```

**중요한 해석 포인트 — 시간은 중첩됩니다**

| | 시간 | 뜻 |
|---|---|---|
| Root Span 250ms | **전체** | 요청 시작부터 응답까지 |
| Child Span 180ms | **그 안에 포함** | Payment 호출에 쓴 시간 |
| **Order 자체 시간** | **250 - 180 = 70ms** | Order 본인의 로직 + 네트워크 |

**"Order가 250ms 걸렸으니 Order가 문제다"는 잘못된 독법입니다.**
**실제로는 Payment 대기가 180ms(72%)** 였습니다. 여기서 **범인이 바뀝니다.**

이런 식으로 읽습니다.

```
✅ 어느 구간이 전체의 대부분을 차지하는가?
✅ 자식 Span들의 합과 부모 시간의 차이가 큰가?  → 그 서비스 내부가 느린 것
✅ Span 사이에 빈 구간이 있는가?               → 큐 대기, 스레드 대기 의심
```

## 샘플링 (Sampling)

**모든 요청을 추적하면 어떻게 될까요?**

```
초당 1만 요청 × Span 10개 × 하루 = 하루 86억 개의 Span
```

**저장 비용과 네트워크 오버헤드가 감당이 안 됩니다.**
그래서 **일부만 골라 수집**합니다. 이게 **샘플링**입니다.

```yaml
management:
  tracing:
    sampling:
      probability: 1.0    # 1.0 = 100% 전부 수집 (기본값은 0.1 = 10%)
```

| 값 | 뜻 | 언제 |
|---|---|---|
| `1.0` | **전부 수집** | **실습·개발** — 내가 보낸 요청이 반드시 보여야 하니까 |
| `0.1` | 10%만 | 기본값 |
| `0.01` | 1%만 | 트래픽이 아주 많은 운영 환경 |

> ⚠️ **실습에서 "요청은 보냈는데 Zipkin에 안 보인다"는 대부분 샘플링 때문입니다.**
> 기본값이 10%라 10번 중 9번은 수집되지 않습니다. **반드시 `1.0`으로 올려두세요.**

> **더 똑똑한 샘플링도 있습니다.**
> - **Head-based**: 요청 시작 시점에 동전을 던져 결정 (단순, 기본 방식)
> - **Tail-based**: **끝나고 나서** "느렸거나 에러난 것만" 남김 (유용하지만 구현이 복잡)
>
> 이상적인 건 "정상 요청은 조금만, **문제 있는 요청은 전부**" 수집하는 것입니다.

## 비동기·스레드 전환에서 끊기는 문제

Trace 정보는 보통 **스레드에 매달려 다닙니다**(`ThreadLocal`).
그래서 **스레드가 바뀌면 끊깁니다.**

```
   [요청 스레드]  Trace ID 있음 ✅
        │  비동기로 다른 스레드에 작업을 넘김
        ▼
   [워커 스레드]  Trace ID 없음 ❌  → 여기서부터 추적이 끊김
```

**언제 발생하나**

- `@Async`, `CompletableFuture` 등 비동기 실행
- 스레드 풀 기반 격벽 → [msa/06 Bulkhead](../06-장애-격리.md)
- 메시지 브로커를 통한 비동기 처리 → [eda](../eda/README.md)

**대응**: 프레임워크가 대부분 자동으로 이어 붙여 주지만,
**직접 만든 스레드 풀에는 컨텍스트를 넘기는 처리를 따로 해줘야** 합니다.

> **메시지 브로커를 건너는 경우**는 HTTP 헤더가 아니라 **메시지 헤더**에 Trace 정보를 실어 보냅니다.
> 원리는 같습니다 — **경계를 넘을 때 컨텍스트를 같이 보낸다.**

## 흔한 오해

**"추적을 켜면 원인이 나온다"**
**어디가 느린지는 알려주지만, 왜 느린지는 아닙니다.**
"Payment가 180ms 걸렸다"까지가 추적의 몫이고, **왜 그랬는지는 [로그](06-분산-로깅.md)와 코드**를 봐야 합니다.

**"Trace ID만 있으면 된다"**
Span ID와 Parent ID가 있어야 **트리를 복원**할 수 있습니다. Trace ID만으로는 순서와 포함 관계를 모릅니다.

**"평균 응답 시간을 보면 된다"**
평균은 소수의 느린 요청을 감춥니다. **p95·p99**를 봐야 합니다.
