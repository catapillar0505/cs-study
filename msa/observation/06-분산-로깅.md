# 분산 로깅 (Distributed Logging)

## 한 줄로

**서버마다 흩어진 로그를 한곳에 모으고, 모든 줄에 Trace ID를 박아 둔다.** 그러면 요청 하나의 로그를 서비스 경계를 넘어 **한 번에 뽑아낼 수 있다.**

## 문제부터 — 로그 파편화

모놀리식에서는 **로그 파일 하나만 열면** 전체 흐름이 보였습니다.

MSA에서는 이렇게 됩니다.

```
   하나의 주문 요청이 남긴 로그

   gateway 인스턴스 #2      →  로그 3줄
   order-service #1         →  로그 12줄
   payment-service #3       →  로그 8줄
   stock-service #2         →  로그 5줄

   서버 4대 × 인스턴스 여러 개에 흩어져 있고,
   각 서버에는 다른 사용자의 로그 수만 줄이 섞여 있다 💀
```

두 가지 문제가 동시에 생깁니다.

| 문제 | |
|---|---|
| **흩어짐** | 어느 서버에 있는지 모름. 인스턴스가 오토스케일링으로 사라지면 로그도 사라짐 |
| **섞임** | 한 서버 안에서도 **어느 줄이 내 요청의 것인지** 구분할 수 없음 |

## 해결 ① — 한곳에 모은다 (중앙 집중식 로깅)

**모든 서비스의 로그를 중앙 저장소로 보내는 것**이 첫 번째 단추입니다.

```
   service A ─┐
   service B ─┼──▶ [ 중앙 로그 저장소 ] ◀── 검색 UI
   service C ─┘
```

이렇게 하면 **서버에 SSH로 들어갈 일이 없어지고**, 인스턴스가 죽어도 로그는 남습니다.

## 해결 ② — 요청마다 표식을 박는다 (Trace ID 연계)

모아만 놓으면 여전히 **섞여 있습니다.** 그래서 **모든 로그 줄에 Trace ID를 함께 찍습니다.**

```
2026-09-07T14:20:15.123 INFO [order-service,4bf92f3577b34da6,00f067aa0ba902b7] : Order created
                                    ↑ 서비스명      ↑ Trace ID        ↑ Span ID
```

**그러면 이런 일이 가능해집니다.**

```
   중앙 저장소에서  traceId = "4bf92f3577b34da6"  로 검색
        ↓
   order-service 의 12줄 + payment-service 의 8줄 + stock-service 의 5줄이
   시간 순으로 정렬되어 한 화면에 나온다 ✅
```

**[01](01-관측-가능성이란.md)에서 말한 "셋을 잇는 접착제"가 실제로 작동하는 지점입니다.**

### MDC란

이 Trace ID는 **어떻게 모든 로그 줄에 자동으로 붙을까요?**

**MDC = Mapped Diagnostic Context (진단 문맥 맵)**

> **스레드마다 따로 갖는 작은 Map**입니다. 여기에 값을 넣어두면,
> **그 스레드에서 찍는 모든 로그에 자동으로 딸려 나옵니다.**

```
   [요청 스레드]
      MDC = { traceId: "4bf92f...", spanId: "00f067..." }
         │
         ├─ log.info("주문 조회")     → 자동으로 traceId 가 붙음
         ├─ log.info("재고 확인")     → 자동으로 붙음
         └─ log.error("결제 실패")    → 자동으로 붙음
```

**개발자가 매번 `log.info("[" + traceId + "] 주문 조회")` 라고 쓸 필요가 없습니다.**

**Micrometer Tracing이 요청 시작 시 MDC에 `traceId`·`spanId`를 자동으로 넣어줍니다.**
로그 패턴에 `%X{traceId}` 라고 써두면 그 값이 출력됩니다.

> ⚠️ **MDC는 스레드에 매달려 있습니다(`ThreadLocal` 기반).**
> **스레드가 바뀌면 사라집니다.** [04에서 본 추적 끊김 문제](04-분산-추적.md)와 같은 뿌리입니다.

## 구조화 로깅 (Structured Logging)

로그를 **사람이 읽는 문장**이 아니라 **JSON 같은 구조**로 찍는 방식입니다.

```
사람이 읽는 로그:
  2026-09-07 14:20:15 INFO Order 1234 created for user hong, amount=50000

구조화된 로그:
  {"time":"...","level":"INFO","traceId":"4bf92f...","orderId":1234,"userId":"hong","amount":50000}
```

**왜 이렇게 하나?**

| | 이유 |
|---|---|
| **검색이 정확해진다** | `amount > 10000` 같은 **필드 조건 검색**이 가능 |
| **파싱이 필요 없다** | 문장에서 값을 정규식으로 긁어낼 필요가 없음 |
| **필드 추가가 안전** | 형식이 조금 바뀌어도 파서가 안 깨짐 |

> 사람이 읽기엔 불편하므로, 보통 **콘솔에는 사람이 읽는 형식, 중앙 저장소에는 JSON**으로 이중 출력합니다.
> → [07 실습의 logback 설정](07-실습-plg-스택.md)이 정확히 그렇게 되어 있습니다.

## 파이프라인 ① — ELK / EFK Stack

가장 오래되고 널리 쓰인 구성입니다.

```
┌─────────────────────────────────────┐
│ 애플리케이션                          │
│ (로그 파일 또는 표준 출력)             │
└──────────────────┬──────────────────┘
                   │  로그를 읽어감
                   ▼
┌─────────────────────────────────────┐
│ Filebeat / Fluent Bit  (수집 에이전트)│  ← 각 서버에 상주하는 가벼운 프로그램
└──────────────────┬──────────────────┘
                   │  원본 로그 전달
                   ▼
┌─────────────────────────────────────┐
│ Logstash  (가공 엔진)                │  ← 파싱·필터링·마스킹
└──────────────────┬──────────────────┘
                   │  색인 요청
                   ▼
┌─────────────────────────────────────┐
│ Elasticsearch  (검색 엔진 겸 저장소)  │
└──────────────────┬──────────────────┘
                   │  질의
                   ▼
┌─────────────────────────────────────┐
│ Kibana  (검색·시각화 화면)            │
└─────────────────────────────────────┘
```

> **ELK / EFK 이름의 뜻**: **E**lasticsearch + **L**ogstash + **K**ibana.
> Logstash 대신 더 가벼운 **F**luentd/Fluent Bit를 쓰면 **EFK**입니다.

| 구성요소 | 역할 |
|---|---|
| **Filebeat / Fluent Bit** | 각 서버에 상주하는 **초경량 에이전트**. 로그 파일을 실시간으로 따라 읽어(tailing) 전송 |
| **Logstash** | 원시 로그를 **구조화·정규화·마스킹**하는 무거운 가공 서버 |
| **Elasticsearch** | 로그를 **색인해서 저장**하는 검색 엔진 |
| **Kibana** | 검색·필터·차트를 제공하는 **웹 대시보드** |

### 기초 — 역색인이란

Elasticsearch가 빠른 이유이자, **동시에 비싼 이유**입니다.

**역색인(Inverted Index)** 은 **책 뒤의 "찾아보기"** 와 같습니다.

```
   원본 (문서 → 단어)                 역색인 (단어 → 문서)
   문서1: "주문 결제 실패"      →     "주문"  : [문서1, 문서3]
   문서2: "재고 조회 성공"             "결제"  : [문서1]
   문서3: "주문 완료"                  "실패"  : [문서1]
                                      "재고"  : [문서2]
```

**"실패"를 검색하면 문서 전체를 훑지 않고 색인만 보면 됩니다.** 그래서 압도적으로 빠릅니다.

**대신 대가가 있습니다.**

```
   로그 한 줄이 들어올 때마다
   → 단어를 전부 쪼개고
   → 각 단어의 목록에 문서 번호를 추가하고
   → 그 색인을 디스크에 저장한다

   → 색인 크기가 원본보다 커지기도 한다. CPU·디스크·메모리를 많이 먹는다.
```

## 파이프라인 ② — Grafana Loki

**"Prometheus for Logs"** 를 표방하는, 훨씬 가벼운 접근입니다.

```
┌──────────────────────────────────────┐
│ 애플리케이션 (JSON 로그 + Trace ID)   │
└──────────────────┬───────────────────┘
                   │  표준 출력 또는 직접 전송
                   ▼
┌──────────────────────────────────────┐
│ Alloy / Promtail / Vector (수집기)    │  ← 라벨을 붙여 전송
└──────────────────┬───────────────────┘
                   │  라벨 + 압축된 로그 덩어리
                   ▼
┌──────────────────────────────────────┐
│ Grafana Loki  (저장 엔진)             │  ← 라벨만 색인, 본문은 압축 보관
└──────────────────┬───────────────────┘
                   │  LogQL
                   ▼
┌──────────────────────────────────────┐
│ Grafana  (지표·추적·로그 통합 화면)    │
└──────────────────────────────────────┘
```

### 핵심 발상 — 본문을 색인하지 않는다

```
   Elasticsearch:  로그 본문의 모든 단어를 색인   → 무엇이든 빨리 찾음, 비쌈
   Loki:          라벨만 색인, 본문은 압축 보관  → 라벨로 좁힌 뒤 훑음, 아주 쌈
```

**라벨(Label)** 은 [02에서 본 메트릭 태그](02-메트릭.md)와 같은 개념입니다.

```
{app="order-service", env="prod", level="ERROR"}
```

**검색 방식이 이렇게 됩니다.**

```
① 라벨로 범위를 좁힌다     {app="order-service", level="ERROR"}  → 대상이 1/1000 로 줄어듦
② 그 안에서 텍스트를 훑는다  |= "결제 실패"                        → 양이 적으니 충분히 빠름
```

**"어차피 시간 범위와 서비스는 지정하고 검색하잖아"** 라는 현실적인 관찰에서 나온 설계입니다.

### 관측 3요소가 한 화면에서 이어진다

Loki의 진짜 강점은 **Grafana 한 화면에서 끊김 없이 이동**할 수 있다는 점입니다.

```
   Prometheus 그래프에서 이상 급증 발견
        ↓ 클릭
   그 시각의 Trace 로 점프 (Tempo/Zipkin)
        ↓ Trace ID 복사
   그 Trace ID 로 Loki 로그 즉시 조회
```

**[01](01-관측-가능성이란.md)에서 말한 드릴다운이 UI 수준에서 구현된 것**입니다.

### LogQL 기초

Loki의 질의 언어입니다. PromQL과 문법이 닮아서 배우기 쉽습니다.

```
{app="observability-service"} |= "ERROR"
└──────── 라벨 선택 ────────┘ └─ 필터 ─┘
```

**기호 읽는 법**

| 앞 글자 | 뜻 |
|---|---|
| `\|` (파이프) | **일치하는 것** 찾기 |
| `!` (느낌표) | **일치하지 않는 것** 찾기 |

| 뒷 글자 | 뜻 |
|---|---|
| `=` (등호) | **텍스트** 그대로 찾기 |
| `~` (물결) | **정규식**으로 찾기 |

조합하면 이렇게 됩니다.

| 표현 | 뜻 |
|---|---|
| `\|= "ERROR"` | "ERROR"가 **포함된** 줄 |
| `!= "health"` | "health"가 **없는** 줄 |
| `\|~ "5\\d\\d"` | 정규식으로 5xx 에러 찾기 |

## ELK와 Loki 비교

| 비교 항목 | **Grafana Loki** | **ELK (Elasticsearch)** |
|---|---|---|
| **인덱싱 방식** | **라벨만** 색인, 본문은 압축 저장 | **전체 필드 역색인** |
| **리소스·비용** | **적음** (비용 효율이 압도적) | 큼 (디스크 I/O, 대용량 메모리 요구) |
| **검색 성능** | 라벨로 좁힌 뒤 훑기 — **범위를 지정하면 충분히 빠름** | **복잡하고 정교한 전문 검색에서 월등** |
| **쿼리 언어** | **LogQL** (PromQL과 유사, 학습 쉬움) | Lucene Query / KQL |
| **관측성 통합** | Grafana에서 **지표·추적·로그 완전 연동** | Elastic 자체 APM 중심 |
| **운영 난이도** | **단순** (S3 등 오브젝트 스토리지 기반) | 샤딩·레플리카·인덱스 수명주기 등 **전문성 필요** |

**어느 쪽을 고르나**

| 상황 | 선택 |
|---|---|
| 이미 Prometheus·Grafana를 쓰고 있다 | **Loki** — 한 화면에서 다 보임 |
| 비용을 아껴야 한다 | **Loki** |
| **로그 전체에서 임의의 단어를 정교하게 검색**해야 한다 | **Elasticsearch** |
| 로그를 **검색 서비스처럼** 활용한다 | **Elasticsearch** |

## 흔한 오해

**"로그를 전부 오래 보관하면 된다"**
로그는 **양이 폭발적**입니다. 비용이 감당이 안 되고, 많다고 잘 찾아지는 것도 아닙니다.
**보존 기간을 정하고, 중요한 것만 오래 두는 것**이 현실적입니다.

**"Loki가 느리다"**
**라벨과 시간 범위를 지정하지 않으면** 느립니다. 전체를 훑어야 하니까요.
**Loki는 "범위를 좁혀서 쓰는 도구"** 라는 전제를 알고 써야 합니다.

**"라벨을 많이 붙이면 좋다"**
[02의 카디널리티 폭발](02-메트릭.md)이 여기서도 똑같이 일어납니다.
**라벨에 사용자 ID나 Trace ID를 넣으면 안 됩니다.** 그건 **본문에 넣고 텍스트로 검색**하는 것이 맞습니다.
