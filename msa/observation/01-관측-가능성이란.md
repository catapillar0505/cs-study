# 관측 가능성이란

## 한 줄로

**"밖에서 보이는 것만으로 안에서 무슨 일이 벌어지는지 알아낼 수 있는가"** 를 묻는 성질이다. 서비스를 쪼개는 순간 로그 파일 하나로는 알 수 없게 되므로, **지표·추적·로그** 세 가지를 갖춰야 한다.

## 문제부터 — 모놀리식에서는 필요 없었다

**모놀리식**에서는 프로그램이 하나입니다. 문제가 생기면 할 일도 하나입니다.

```
"주문이 안 돼요"  →  shop-app.log 를 연다  →  스택 트레이스 발견  →  끝
```

로그 파일 하나만 뒤지면 **처음부터 끝까지 전부** 거기 있습니다.

**MSA에서는 이게 무너집니다.**

```
"주문이 안 돼요"

   Gateway 로그 ─── order-service 로그 ─── payment-service 로그 ─── stock-service 로그
        ?                  ?                      ?                       ?
   서버 4대에 흩어져 있고, 각 서비스는 3대씩 떠 있어서 실제로는 로그 파일이 12개
   그중 어느 것이 그 사용자의 요청인지 알 방법이 없다 💀
```

**하나의 요청이 여러 프로그램을 거쳐 가는데, 각자 자기 부분만 기록**하기 때문입니다.

## Observability라는 단어

**Observability(관측 가능성)** 는 원래 **제어 이론(control theory)** 의 용어입니다.

> **시스템의 외부 출력만 보고, 내부 상태를 얼마나 알아낼 수 있는가**

자동차에 비유하면 이렇습니다.

```
계기판에 속도계 하나만 있는 차     → 관측 가능성이 낮다
  "차가 이상해요" → 뭐가 이상한지 알 방법이 없음

속도·회전수·수온·유압·연료·경고등  → 관측 가능성이 높다
  "수온이 110도네" → 원인을 좁힐 수 있음
```

**소프트웨어에서도 똑같습니다.** 내부를 열어볼 수 없으니, **밖으로 내보낸 신호(텔레메트리)** 로만 판단해야 합니다.

> **텔레메트리(Telemetry)** = 원격(tele) + 측정(metry). **시스템이 밖으로 내보내는 측정 데이터**를 통칭합니다.
> 지표·추적·로그가 전부 텔레메트리입니다.

## 모니터링과 무엇이 다른가

자주 섞어 쓰지만 결이 다릅니다.

| | **모니터링 (Monitoring)** | **관측 가능성 (Observability)** |
|---|---|---|
| 묻는 것 | **"내가 미리 정해둔 게 정상인가?"** | **"지금 무슨 일이 벌어지고 있나?"** |
| 대비하는 것 | **알려진 문제** (CPU 90% 넘으면 알림) | **처음 보는 문제** |
| 비유 | 건강검진 항목표 | 의사가 이것저것 물어보고 검사해가며 원인을 좁히는 것 |

**"CPU가 90%를 넘으면 알려줘"** 는 모니터링입니다. **CPU가 문제일 거라고 미리 알고 있었기 때문**입니다.

문제는 실무의 장애 대부분이 **미리 예상 못 한 것**이라는 점입니다.

> **Known unknowns / Unknown unknowns**
> - **알고 있는 모르는 것**: "CPU가 높아질 수 있다는 건 안다. 지금 몇 %인지만 모른다" → 모니터링으로 충분
> - **모르는 것조차 모르는 것**: "특정 사용자의 특정 상품 조회에서만 DB 락이 걸린다" → **관측 가능성이 필요**

관측 가능성이 높다는 것은 **미리 질문을 정해두지 않아도, 나중에 아무 질문이나 던져서 답을 얻을 수 있다**는 뜻입니다.

## 3대 요소 (3 Pillars)

관측 가능성은 보통 **세 종류의 데이터**로 구성됩니다.

| | 답하는 질문 | 정체 | 대표 도구 |
|---|---|---|---|
| **Metrics (지표)** | **"무슨 일이 발생했는가?"** | 일정 간격으로 수집되는 **숫자** | Actuator, Micrometer, Prometheus, Grafana |
| **Tracing (추적)** | **"요청이 어디를 거쳐 갔는가?"** | 한 요청의 **전체 경로와 구간별 시간** | Micrometer Tracing, Zipkin, Jaeger, Tempo |
| **Logging (로그)** | **"구체적으로 어떤 일이 있었는가?"** | 특정 시점의 **상세 기록** | ELK/EFK, Loki, CloudWatch Logs |

### 셋의 관계를 수사에 비유하면

```
Metrics  →  "오후 3시에 이 건물에서 경보가 울렸다"       ← 사건이 있었다는 사실
Tracing  →  "범인은 1층 → 엘리베이터 → 5층 → 창문 순으로 이동했다"  ← 경로와 시간
Logging  →  "5층 CCTV: 3시 12분 유리창을 깼음"          ← 그 지점의 구체적 정황
```

**셋은 서로를 대체하지 않습니다.** 어느 하나만으로는 원인에 도달하지 못합니다.

| 이것만 있으면 | 이런 한계 |
|---|---|
| 지표만 | **"느리다"는 건 아는데 어디가 느린지 모른다** |
| 추적만 | **"payment-service가 느렸다"는 아는데 왜인지 모른다** |
| 로그만 | 흩어져 있어서 **한 요청을 이어 붙일 수가 없다** |

### 셋을 잇는 접착제 — Trace ID

세 가지가 따로 놀면 소용이 없습니다. **하나의 값이 셋을 꿰뚫습니다.**

```
                        Trace ID: 4bf92f3577b34da6...
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
   [ Metrics ]                 [ Tracing ]                 [ Logging ]
   "이 시각에 지연 급증"    "이 요청이 여기서 180ms"    "그 순간 이 로그가 찍힘"
        │                           │                           │
        └──── 지표에서 이상 발견 → 그 시각의 Trace 로 점프 → 그 Trace ID 로 로그 검색 ────┘
```

**이 "끊김 없이 파고들기(drill-down)"가 관측 가능성의 최종 목표입니다.**
그래서 이 폴더의 문서들이 전부 **Trace ID를 중심으로** 이어집니다.

## 이 폴더 전체의 지도

```
01 관측 가능성이란 (지금 문서)
     │
     ├─ Metrics ── 02 메트릭 ── 03 Prometheus와 Grafana
     │              (무엇을 세나)   (어떻게 모으고 보여주나)
     │
     ├─ Tracing ── 04 분산 추적 ── 05 OpenTelemetry
     │              (Trace/Span)    (표준과 도구)
     │
     └─ Logging ── 06 분산 로깅
                    (Trace ID 연계, ELK vs Loki)
                          │
                          ▼
                07 실습 — 셋을 한 화면에서 보기 (PLG 스택)
```

## 흔한 오해

**"로그만 잘 남기면 된다"**
로그는 **양이 폭발**합니다. 서비스 20개가 초당 수천 줄을 찍으면 사람이 읽을 수 없습니다.
**지표로 범위를 좁히고 → 추적으로 지점을 특정하고 → 그때 비로소 로그를 읽는 것**이 실제 순서입니다.

**"도구를 붙이면 관측 가능해진다"**
도구는 **데이터를 모아줄 뿐**입니다. **무엇을 계측할지 정하는 것은 개발자**입니다.
비즈니스적으로 중요한 지점(주문 성공률, 결제 실패 사유)은 직접 심어야 합니다.

**"관측은 공짜다"**
모든 요청을 추적하고 모든 로그를 저장하면 **비용과 성능 오버헤드가 큽니다.**
그래서 [샘플링](04-분산-추적.md)과 [라벨 기반 인덱싱](06-분산-로깅.md) 같은 절충이 등장합니다.
