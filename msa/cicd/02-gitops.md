# GitOps

## 한 줄로

**"Git에 적힌 상태가 곧 실제 서버의 상태다."** 배포를 "명령을 밀어 넣는 일"이 아니라 **"Git과 클러스터를 계속 맞추는 일"** 로 바꾼 것.

## 기초 — 선언적이란 무엇인가

GitOps를 이해하려면 이 구분이 먼저입니다.

| | **명령적 (Imperative)** | **선언적 (Declarative)** |
|---|---|---|
| 적는 것 | **어떻게** 할지 절차 | **무엇이** 되어야 하는지 결과 |
| 예 | "컨테이너를 3개 띄워라" | "컨테이너가 3개 있어야 한다" |
| 하나가 죽으면 | **아무 일도 안 일어남** (명령은 이미 끝났으니까) | **시스템이 알아서 하나 더 띄움** |
| 명령어 | `kubectl run ...` | `kubectl apply -f deployment.yaml` |

**비유: 택시와 내비게이션**

```
   명령적:  "여기서 우회전, 300m 직진, 좌회전…"
            → 중간에 길이 막히면 그대로 멈춘다

   선언적:  "서울역으로 가주세요"
            → 길이 막히면 알아서 다른 길로 간다. 목적지는 변하지 않는다
```

**쿠버네티스는 태생부터 선언적입니다.**
YAML에 "이렇게 되어 있어야 한다"를 적어두면, **쿠버네티스가 계속 그 상태를 유지하려고 노력합니다.**
이 과정을 **조정 루프(reconciliation loop)** 라고 합니다.

> **매니페스트(Manifest)** 는 "적하목록, 명세서"라는 뜻으로,
> **쿠버네티스에게 원하는 상태를 적어 주는 YAML 파일**을 가리킵니다.
> → [kubernetes/06 오브젝트 구조](../../kubernetes/06-오브젝트구조-metadata-namespace-label.md)

## GitOps란

**GitOps = Git + Operations**

> **인프라와 애플리케이션의 "원하는 상태"를 전부 Git에 적어두고,
> 클러스터가 그 Git 내용과 일치하도록 자동으로 맞추는 방식**

핵심 문장은 이겁니다.

> **Git 저장소의 상태 = 실제 클러스터의 상태**
> Git이 **유일한 진실 공급원(Single Source of Truth)** 이 된다.

### Single Source of Truth라는 말

**"이게 맞는지 궁금하면 여기만 보면 된다"** 는 하나의 기준점을 뜻합니다.

```
   ❌ 진실이 여러 곳에 흩어진 상태
      Git 의 YAML 은 replicas: 2 인데
      실제 클러스터는 누가 손으로 바꿔서 replicas: 5
      → "지금 몇 개가 맞는 거지?"

   ✅ Git 이 유일한 기준
      Git 이 replicas: 2 면 클러스터도 반드시 2
      누가 손으로 5로 바꿔도 자동으로 2로 돌아온다
```

### Git을 쓰면 따라오는 것들

인프라 설정을 Git에 두면 **Git의 기능을 그대로 얻습니다.**

| | 설명 |
|---|---|
| **변경 이력** | 누가 언제 무엇을 왜 바꿨는지 **커밋 로그**에 전부 남음 |
| **리뷰** | 인프라 변경도 **Pull Request로 리뷰**받을 수 있음 |
| **롤백** | 이전 커밋으로 되돌리면 **인프라도 되돌아감** |
| **감사(Audit)** | 규제 대응 시 "누가 운영 설정을 바꿨나"를 증명 가능 |

**"배포 이력 관리가 비표준적"이라는 [01의 문제](01-ci-cd란.md)가 여기서 해결됩니다.**

## Push와 Pull — 배포의 두 방향

**같은 CI/CD라도 "누가 배포를 시작하느냐"에 따라 완전히 다릅니다.**

### Push 방식 (전통적 CI/CD)

```
   [ CI 도구 ]  ──── kubectl apply ────▶  [ 쿠버네티스 클러스터 ]
    (외부에 있음)      명령을 밀어 넣음
```

CI 도구(GitHub Actions, Jenkins)가 빌드를 끝낸 뒤 **직접 클러스터에 명령을 보냅니다.**

### Pull 방식 (GitOps)

```
   [ Git 저장소 ]  ◀──── 주기적으로 확인 ────  [ 클러스터 안의 에이전트 ]
                                                   │
                                                   │ 변경 발견 → 스스로 적용
                                                   ▼
                                             [ 쿠버네티스 ]
```

**클러스터 안에 있는 에이전트**(ArgoCD, Flux)가 **Git을 지켜보다가**,
바뀐 걸 발견하면 **스스로 가져와서 적용합니다.**

### 비교

| 비교 항목 | **Push (전통 CI/CD)** | **Pull (GitOps)** |
|---|---|---|
| **주도 주체** | 외부 CI 도구 (GitHub Actions, Jenkins) | **클러스터 내부의 CD 에이전트** (ArgoCD, Flux) |
| **작동 원리** | CI가 빌드 후 `kubectl apply`로 **직접 명령** | 에이전트가 Git을 지켜보다 **스스로 가져와 동기화** |
| **보안** | **CI 서버가 클러스터 접근 권한을 가져야 함** ⚠️ | **클러스터 밖으로 권한을 안 내보냄** |
| **상태 불일치** | 누가 손으로 고치면 **Git과 어긋난 채 방치** | **자동으로 Git 상태로 복원** |
| **도구** | Jenkins, GitHub Actions 직접 배포 | **ArgoCD, Flux CD** |

### 보안 차이가 왜 중요한가

**Push 방식의 문제:**

```
   [ GitHub Actions ]  ← 인터넷에 있는 SaaS 서비스
          │
          │ 여기에 클러스터 접근 자격증명(kubeconfig)을 저장해야 함
          ▼
   [ 우리 회사 쿠버네티스 클러스터 ]
```

**외부 서비스에 운영 클러스터의 열쇠를 맡기는 셈**입니다.
그 열쇠가 유출되면 **클러스터 전체가 뚫립니다.**

게다가 클러스터가 **외부에서 접근 가능하도록 열려 있어야** 합니다.

**Pull 방식:**

```
   [ 클러스터 ] ──── 밖으로 나가서 Git 을 읽어옴 ────▶ [ Git ]
        ↑
   외부에서 들어오는 문을 열 필요가 없다
```

**나가는 방향만 있으면 됩니다.** 방화벽 안쪽에 있는 클러스터도 그대로 쓸 수 있습니다.

> **`kubeconfig`** 는 쿠버네티스 클러스터에 접속하기 위한 **주소 + 인증 정보 파일**입니다.
> → [kubernetes/03](../../kubernetes/03-kubectl-context와-kubeconfig.md)

### Drift — 구성 편차

**Drift(드리프트)** 는 "표류, 흘러감"이라는 뜻으로,
**Git에 적힌 상태와 실제 상태가 시간이 지나며 어긋나는 것**을 말합니다.

```
   급한 장애 → 운영자가 kubectl 로 직접 수정 → 문제 해결 → 그리고 잊어버림
        │
        ▼
   Git 에는 그 수정이 없음
        │
        ▼
   다음 배포 때 그 수정이 사라져서 장애 재발 💀
```

**GitOps는 이걸 두 가지로 막습니다.**

| 기능 | 하는 일 |
|---|---|
| **Drift 감지** | Git과 실제 상태가 다르면 **UI에 "OutOfSync"로 표시** |
| **Self-Heal (자가 치유)** | 다르면 **자동으로 Git 상태로 되돌림** |

> **부작용도 있습니다.** Self-Heal이 켜져 있으면 **긴급하게 손으로 고쳐도 곧 되돌아갑니다.**
> 그래서 "급하면 Git을 고쳐라"가 GitOps의 규율이 됩니다. 불편하지만, **그게 목적입니다.**

## 전체 아키텍처

```
┌─────────────────────────────────┐
│         개발자의 코드            │
│  (애플리케이션 + K8s 매니페스트)  │
└────────────────┬────────────────┘
                 │ git push
┌────────────────▼────────────────┐  트리거   ┌────────────────────────────┐
│          GIT 저장소              ├─────────▶│         CI 서버             │
│  (GitHub / GitLab / Bitbucket)  │          │ (GitHub Actions / Jenkins) │
└────────────────┬────────────────┘          └─────────────┬──────────────┘
                 │                                          │ 이미지 push
                 │ 주기적으로 확인 (기본 3분)                 │
┌────────────────▼────────────────┐          ┌─────────────▼──────────────┐
│         GITOPS 에이전트          │          │      컨테이너 레지스트리     │
│         (ArgoCD / Flux)         │          │    (Docker Hub / ECR)      │
└────────────────┬────────────────┘          └────────────────────────────┘
                 │ 선언된 상태를 적용
┌────────────────▼────────────────┐
│         쿠버네티스 클러스터        │
└─────────────────────────────────┘
```

**흐름을 문장으로 읽으면**

```
① 개발자가 코드를 Push 한다
② CI 가 빌드·테스트하고 컨테이너 이미지를 만들어 레지스트리에 올린다
③ CI 가 "새 이미지 태그"를 매니페스트에 반영해 Git 에 커밋한다
④ GitOps 에이전트가 Git 변경을 발견한다
⑤ 에이전트가 그 매니페스트를 클러스터에 적용한다
⑥ 쿠버네티스가 새 이미지로 파드를 교체한다 (롤링 업데이트)
```

> **③이 GitOps의 핵심 연결 고리입니다.**
> CI는 **클러스터를 건드리지 않습니다.** 대신 **Git에 커밋만 합니다.**
> 그러면 CD 에이전트가 알아서 나머지를 합니다. **두 세계가 Git으로 이어집니다.**

## 흔한 오해

**"GitOps는 도구 이름이다"**
아닙니다. **방법론**입니다. ArgoCD·Flux는 그 방법론을 구현한 **도구**입니다.

**"GitOps를 하면 CI가 필요 없다"**
아닙니다. **CI(빌드·테스트·이미지 생성)는 그대로 필요**합니다.
GitOps가 대체하는 것은 **CD의 마지막 배포 단계**입니다.

**"저장소 하나에 코드와 매니페스트를 같이 두면 된다"**
작게 시작할 땐 그래도 됩니다([실습1](04-실습-github-actions와-argocd.md)).
다만 **CI가 자기 저장소에 커밋을 하게 되면서 무한 빌드 루프 위험**이 생기고,
**애플리케이션 개발과 인프라 변경의 권한이 섞입니다.**
실무에서는 **저장소를 분리**하는 경우가 많습니다([실습2](06-실습-jenkins와-argocd.md)).
