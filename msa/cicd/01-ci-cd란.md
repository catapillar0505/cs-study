# CI/CD란

## 한 줄로

**"코드를 Push하면 나머지는 기계가 한다."** 사람이 손으로 하던 빌드·테스트·배포를 자동화해서, **자주·안전하게·되돌릴 수 있게** 만드는 것.

## 문제부터 — 손으로 배포하면 어떻게 되나

### 수동 배포의 순서

```
① 개발자가 기능을 구현한다
② 빌드 결과물(JAR/WAR)과 "배포 가이드 문서"를 운영팀에 넘긴다
③ 운영자가 서버에 SSH 로 접속해 배포 스크립트를 직접 실행한다
```

> **JAR/WAR**는 자바 애플리케이션을 하나의 파일로 묶은 **배포 단위**입니다.
> **SSH**는 원격 서버에 터미널로 접속하는 프로토콜입니다.

**동작은 합니다.** 문제는 이게 **반복될 때** 생깁니다.

### 무엇이 문제인가

| 문제 | 어떻게 나타나나 |
|---|---|
| **배포 주기가 늘어진다** | 검증·전달·일정 조율에 시간이 걸려 **하루에 여러 번 배포하는 게 불가능**해짐 |
| **사람이 실수한다** | 명령어 오타, 환경 변수 하나 누락, **운영 서버에 개발 설정 적용** — 전부 흔한 사고 |
| **되돌리기가 어렵다** | "지난주엔 뭘 배포했더라?" 기록이 표준화되어 있지 않아 **원인 파악과 롤백이 오래 걸림** |

**세 번째가 가장 무섭습니다.** 장애가 났을 때 **"일단 이전 상태로 되돌린다"** 를 못 하면
사고가 길어집니다.

### 왜 이게 MSA에서 더 심각해지나

서비스가 하나면 배포도 한 번입니다. 그런데 **MSA는 서비스가 20개**입니다.

```
   모놀리식:  한 달에 한 번, 큰 배포 한 번
   MSA:      하루에 수십 번, 서비스마다 따로
```

**"작게 자주 배포한다"는 MSA의 장점 자체가 자동화 없이는 성립하지 않습니다.**

## CI — 지속적 통합

**CI = Continuous Integration (지속적 통합)**

> **개발자가 코드를 저장소에 Push할 때마다 자동으로 빌드하고 테스트하는 것**

```
   git push
      │
      ▼
   [ 자동 빌드 ]  → 컴파일이 되는가?
      │
      ▼
   [ 자동 테스트 ] → 기존 기능이 안 깨졌는가?
      │
      ▼
   결과 통보 (성공 ✅ / 실패 ❌)
```

### "통합(Integration)"이 무슨 뜻인가

여러 명이 각자 다른 브랜치에서 작업하다가, **나중에 한꺼번에 합치면** 이런 일이 벌어집니다.

```
   3주간 각자 작업 → 합치기 시작 → 충돌 200개 💀
   "누구 코드가 맞는 거지?" → 며칠 소요 → 이걸 '머지 지옥'이라 부른다
```

**CI의 발상은 이겁니다.**

> **"아프면 더 자주 해라."**
> 합치는 게 고통스러우니까, **매일 여러 번 합쳐서** 충돌을 작게 만들자.

**자주 합치려면 매번 검증이 필요**하고, 그 검증을 자동화한 것이 CI입니다.

| 얻는 것 | 설명 |
|---|---|
| **버그를 일찍 발견** | 3주 뒤가 아니라 **10분 뒤에** 안다 |
| **되돌릴 범위가 작다** | 실패한 커밋 하나만 보면 됨 |
| **코드 품질이 유지된다** | 테스트를 통과 못 하면 합쳐지지 않음 |

## CD — 두 가지 뜻이 있습니다

**CD는 약자가 두 개**입니다. 자주 혼용되지만 **의미가 다릅니다.**

### Continuous Delivery (지속적 제공)

> CI를 통과한 결과물을 **"언제든 배포할 수 있는 상태"로 항상 유지**하는 것.
> **다만 운영 환경으로 나가는 마지막 버튼은 사람이 누른다.**

```
   빌드 → 테스트 → 스테이징 배포 → 검증  ────  [사람의 승인] ────▶ 운영 배포
                                              ↑ 여기만 수동
```

### Continuous Deployment (지속적 배포)

> **사람의 개입 없이 운영 환경까지 100% 자동**으로 나간다.

```
   빌드 → 테스트 → 스테이징 → 검증 ──────────────────────────▶ 운영 배포
                                              ↑ 승인 단계가 없음
```

### 둘의 차이

| | **Continuous Delivery** | **Continuous Deployment** |
|---|---|---|
| 마지막 단계 | **사람이 승인** | **자동** |
| 전제 조건 | 자동 테스트가 어느 정도 갖춰짐 | **자동 테스트를 전적으로 신뢰**할 수 있어야 함 |
| 흔한 상황 | 금융·의료 등 규제 산업, 대부분의 기업 | 테스트가 아주 촘촘한 조직 |

> **"CD를 한다"고 하면 보통 Delivery 쪽입니다.**
> Deployment까지 가려면 **테스트만 믿고 운영에 내보낸다**는 뜻이라, 그만큼 자동 검증이 탄탄해야 합니다.

> **스테이징(Staging)** 은 **운영과 최대한 비슷하게 만든 검증용 환경**입니다.
> "무대에 올리기 직전"이라는 뜻이죠.

## 파이프라인이라는 말

**파이프라인(Pipeline)** 은 **여러 단계가 순서대로 이어진 흐름**을 뜻합니다.

```
[체크아웃] → [빌드] → [테스트] → [이미지 생성] → [푸시] → [배포]
     ↓ 하나라도 실패하면 여기서 멈춘다
```

**핵심은 "실패하면 멈춘다"** 입니다. 테스트가 깨졌는데 배포까지 진행되면 자동화의 의미가 없습니다.

## 전체 그림

```
 개발자              CI 도구                    레지스트리          쿠버네티스
   │                                                                    
   │ git push                                                           
   ├──────────▶ [빌드]                                                  
               [테스트]                                                 
               [컨테이너 이미지 생성] ──push──▶ [ 이미지 저장소 ]

                     │ 배포 지시                         │ 이미지 내려받기

```

## 흔한 오해

**"CI/CD 도구를 도입하면 CI/CD를 하는 것이다"**
아닙니다. **자동 테스트가 없으면 CI가 아닙니다.**
빌드만 자동화하고 테스트가 없으면, 그냥 **"자동으로 빌드해주는 도구"** 를 쓰는 것입니다.

**"자동 배포는 위험하다"**
반대입니다. **손으로 하는 배포가 더 위험합니다.**
자동화된 배포는 **매번 똑같이** 실행되고, **기록이 남고**, **되돌리기 쉽습니다.**
위험한 건 자동화가 아니라 **검증 없는 자동화**입니다.

**"CI/CD는 배포 시간을 줄이는 것이다"**
시간 단축은 부수 효과입니다. **진짜 목적은 "자주, 작게, 안전하게" 바꾸는 것**입니다.
작게 바꾸면 **문제가 생겨도 원인이 명확**하고 **되돌리기 쉽습니다.**
