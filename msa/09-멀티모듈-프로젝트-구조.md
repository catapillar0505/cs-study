# 멀티모듈 프로젝트 구조

## 한 줄로

**하나의 저장소를 여러 개의 독립된 코드 묶음(모듈)으로 쪼갠다.** 공용 코드를 한 벌만 두고, 의존 방향을 **빌드 도구가 강제**하게 만드는 것이 목적이다.

## 먼저 — 빌드 도구가 하는 일

자바 코드는 그냥 실행되지 않습니다. 누군가가 이 일들을 대신 해줘야 합니다.

1. 인터넷에서 필요한 라이브러리 내려받기 — **의존성 관리**
2. `.java` → `.class` 로 변환 — **컴파일**
3. 테스트 실행
4. 결과물을 하나의 파일로 묶기 — **패키징**

이걸 자동화해주는 도구가 **Gradle**입니다. (경쟁 도구로 Maven이 있습니다.)

지시를 내리는 파일이 두 개 있습니다.

| 파일 | 역할 | 비유 |
|---|---|---|
| `settings.gradle` | **어떤 모듈들이 이 빌드에 참여하는지** 목록 | **참가자 명단** |
| `build.gradle` | **그 모듈을 어떻게 빌드할지** 규칙 | **조리법** |

> **모듈(module)** 이란 "독립적으로 컴파일되는 코드 묶음" 하나입니다.
> 폴더 하나에 `src/`와 `build.gradle`이 있으면 그게 모듈입니다.

## 왜 모듈을 나누는가

프로젝트가 커지면 이런 문제가 생깁니다.

```
[ 하나의 거대한 프로젝트 ]
  ├─ 관리자용 코드
  ├─ 사용자용 코드
  ├─ 배치 작업 코드
  └─ 공용 유틸/DTO       ← 위 셋이 전부 이걸 씁니다
```

- 공용 코드를 복사-붙여넣기 하면 **세 군데를 똑같이 고쳐야** 합니다. 하나만 빼먹으면 버그입니다
- 그렇다고 한 덩어리로 두면 **관리자 코드가 사용자 코드를 마음대로 import** 해서 경계가 무너집니다

멀티모듈은 이렇게 바꿉니다.

```
[ 루트 프로젝트 ]                      ← 실행 안 됨. 공통 규칙만 정의
  ├─ common   (라이브러리)             ← 공용 코드. 딱 한 벌만 존재
  └─ api      (실행 가능)              ← common 을 "의존"함
```

얻는 것:

| | 설명 |
|---|---|
| **중복 제거** | 공용 코드가 한 곳에만 존재 |
| **의존 방향 강제** | `api → common`은 되지만 **반대는 컴파일 에러** |
| **버전 일괄 관리** | 자바 버전, 라이브러리 버전을 루트에서 한 번만 정의 |

**두 번째가 핵심입니다.** "그러지 말자"는 팀의 약속이 아니라, **빌드 도구가 물리적으로 막아 줍니다.**

## jar가 두 종류라는 것

이 구분이 멀티모듈에서 자주 걸리는 지점입니다.

| 종류 | 내용물 | 용도 |
|---|---|---|
| **실행 jar** (Fat Jar) | 내 코드 + **의존 라이브러리 전부** + 내장 웹서버 | `java -jar`로 **바로 실행** |
| **라이브러리 jar** | 내 `.class` 파일만 | 남이 **가져다 쓰는 부품** |

공용 모듈은 실행할 앱이 아니라 **부품**입니다. 그래서 실행 jar를 끄고 라이브러리 jar를 켭니다.

```gradle
bootJar { enabled = false }   // 실행 jar 만들지 마라
jar     { enabled = true  }   // 라이브러리 jar를 만들어라
```

> **이 두 줄을 빼먹으면** 실행 jar를 만들려는데 `main()` 메서드가 없어 빌드가 실패하거나,
> 만들어진 Fat Jar를 다른 모듈이 의존했을 때 **클래스를 못 찾는 이상한 에러**가 납니다.

크기를 눈으로 보면 차이가 확실합니다.

```
api 모듈의 실행 jar      → 수십 MB   (웹서버까지 들어있음)
common 모듈의 라이브러리 jar → 수 KB   (.class 몇 개)
```

## `implementation`과 `api` — 의존성이 전파되는가

의존성을 선언하는 키워드가 두 가지입니다. **이 차이가 멀티모듈에서 가장 자주 막히는 지점입니다.**

```
   api 모듈
       │ project(':common')  으로 common 을 의존
       ▼
   common 모듈
       │ implementation 'some-library'   ← 여기서 막힘. 밖으로 안 새어나감
       ▼
   some-library                          ← api 모듈은 이걸 못 봄 ✗
```

| 키워드 | 뜻 |
|---|---|
| **`implementation`** | "이건 **내 안에서만** 쓴다" — 나를 가져다 쓰는 모듈에게는 **안 보임** |
| **`api`** | "이건 **내 인터페이스의 일부다**" — 나를 가져다 쓰는 모듈에게도 **보임** |

**어느 쪽을 써야 하나?**

```
공용 모듈의 클래스가 그 라이브러리 타입을 밖으로 노출하는가?
   예 (메서드 파라미터·반환 타입에 등장) → api
   아니오 (내부 구현에만 쓰임)          → implementation
```

> **예시**: 공용 모듈이 gRPC의 `StreamObserver` 타입을 밖으로 내보낸다면,
> 그걸 쓰는 모듈도 그 타입을 알아야 하므로 **`api`** 로 선언해 전파시켜야 합니다.
>
> 반대로 **내부에서만 쓰는 라이브러리를 `api`로 선언하면** 불필요하게 전파되어
> **컴파일이 느려지고 모듈 경계가 흐려집니다.**

> `api` 키워드를 쓰려면 루트에서 `java` 대신 **`java-library` 플러그인**을 적용해야 합니다.

## 루트가 하는 일 — 공통 규칙 일괄 적용

루트 프로젝트는 실제 코드가 없는 **껍데기**입니다. 대신 **공통 규칙을 한 번만 정의**합니다.

| 블록 | 적용 대상 |
|---|---|
| `allprojects { }` | 루트 + 모든 하위 모듈 |
| `subprojects { }` | **하위 모듈만** (루트 제외) |

```gradle
plugins {
  id 'org.springframework.boot' version '4.1.1' apply false   // ← apply false
}
```

**`apply false`가 핵심입니다.** 뜻은 이렇습니다.

> "플러그인의 **버전은 정해두되**, **루트 프로젝트 자신에게는 적용하지 마라.**"

루트는 부트 앱으로 빌드될 필요가 없습니다. 버전만 선언해두고,
**실제 적용은 `subprojects` 블록에서 각 하위 모듈에** 합니다.

이 덕분에 각 모듈의 `build.gradle`에는 **그 모듈만의 고유한 몇 줄**만 남습니다.

> **`toolchain`** 은 "내 PC에 설치된 JDK가 몇이든 상관없이 **이 자바 버전으로 빌드해라**"는 뜻입니다.
> 없으면 팀원마다 자바 버전이 달라 **"내 컴퓨터에선 되는데요"** 문제가 생깁니다.

> **BOM (Bill of Materials, 자재 명세서)**: 관련 라이브러리들의 궁합 맞는 버전을 한꺼번에 정해주는 목록입니다.
> BOM을 가져오면 **개별 의존성에 버전 번호를 안 적어도** 됩니다. 버전 충돌 지옥을 피하는 표준 방법입니다.
>
> 단, **BOM이 관리하지 않는 서드파티 라이브러리는 버전을 직접 적어야** 합니다.
> "왜 이것만 버전이 필요하지?" 싶으면 그 라이브러리가 BOM 밖이라는 뜻입니다.

## 함정 ① — 스캔 범위가 모듈 경계 밖으로 나갑니다

멀티모듈에서 가장 자주 겪는 문제입니다.

Spring Boot의 메인 클래스는 기본적으로 **자기가 있는 패키지와 그 하위만** 훑습니다.

```
com.example.api          ← 메인 클래스가 여기 있음
  └─ (여기 아래만 자동으로 스캔됨)

com.example.member       ← 다른 모듈. 패키지가 다름 → 스캔 안 됨! ✗
com.example.point        ← 다른 모듈. 패키지가 다름 → 스캔 안 됨! ✗
```

**모듈을 나누면 패키지가 갈라지면서 스캔 범위 밖으로 나가버립니다.**
그래서 "분명 클래스는 만들었는데 빈을 못 찾는다"는 에러를 만납니다.

**그리고 스캐너가 하나가 아닙니다.** 이게 특히 헷갈리는 부분입니다.

| 무엇을 찾나 | 누가 찾나 |
|---|---|
| `@Service`, `@Component`, `@RestController` | Spring Boot의 기본 컴포넌트 스캐너 |
| `@Entity` | Hibernate(JPA) |
| `JpaRepository` 인터페이스 | Spring Data |
| `@Mapper` 인터페이스 | MyBatis |

**넷이 각자 따로 스캔합니다.** 기본값은 모두 "메인 클래스가 있는 패키지 아래"인데,
멀티모듈에서는 그 범위를 벗어납니다.

그래서 **네 스캐너 전부에게** "우리 최상위 패키지 전체를 봐라"고 각각 알려줘야 합니다.
하나라도 빼먹으면 **그 종류만** 못 찾습니다.

> **"왜 빈을 못 찾지?" 라는 에러를 만나면 제일 먼저 여기를 의심하세요.**

## 함정 ② — 설정 파일이 여러 개인데 하나만 읽힙니다

각 모듈에 `application.yml`을 하나씩 두면, 초보자가 크게 헷갈립니다.

**Spring Boot는 실행되는 애플리케이션의 클래스패스에서 `application.yml`을 딱 하나 찾습니다.**
같은 이름의 파일이 여러 jar에 있으면 **먼저 발견된 것 하나만** 쓰고 나머지는 무시합니다.

```
   api 모듈의 application.yml       → ✅ 읽힘 (실행 주체니까)
   common 모듈의 application.yml    → ❌ 무시됨
```

**그래서 부품 모듈에 적어둔 설정이 조용히 적용되지 않습니다.** 에러도 안 나서 더 헷갈립니다.

| 해결 | 방법 |
|---|---|
| **가장 간단** | 필요한 설정을 전부 **실행 모듈의 설정 파일 한 곳에** 모은다 |
| 명시적 분리 | 부품 모듈의 파일 이름을 다르게 두고 **명시적으로 불러온다** |

> **부품 모듈에 `server.port`가 적혀 있는 것은 의미가 없습니다.** 그 모듈은 서버로 뜨지 않으니까요.
> 프로젝트를 만들 때 자동 생성된 값이 남아 있는 경우가 많고, 오히려 혼란을 줍니다.

## 함정 ③ — 이름 불일치

```gradle
// settings.gradle 은 이렇게 등록하는데
include 'module-jpa'

// 다른 곳에서는 없는 이름을 참조
implementation project(':module-core-jpa')      // ✗ 이런 모듈 없음
```

폴더 이름을 나중에 바꾸면서 참조를 같이 안 고친 전형적인 경우입니다.

> **에러 메시지 읽는 법**: `Project with path ':xxx' could not be found` 는
> **"`settings.gradle`에 그 이름이 없다"** 는 뜻입니다.
>
> 반대로 **모듈 폴더를 만들어놓고 `settings.gradle`에 등록을 안 하면**
> Gradle이 그 폴더를 아예 무시합니다. 초보자가 가장 많이 하는 실수입니다.

## MSA와의 관계

멀티모듈은 **MSA 그 자체는 아닙니다.** 하지만 실습·소규모 팀에서는 자주 함께 씁니다.

```
   한 저장소 (모노레포)
     ├─ discovery-service   [실행]
     ├─ gateway-service     [실행]
     ├─ user-service        [실행]
     └─ common-module       [라이브러리]  ← 공용 DTO·예외를 여기 두고 공유
```

- 서비스마다 **별도 프로세스로 실행**되므로 MSA가 맞습니다
- 다만 **코드는 한 저장소에** 있어 공용 모듈을 공유하기 쉽습니다

> **공용 모듈로 DTO를 공유하는 것**은 [ipc/04](ipc/04-무엇을-언제-쓰는가.md)에서 말한
> "REST는 계약이 문서에만 있다"의 완화책이기도 합니다.
> 다만 **서비스 간 결합이 생긴다**는 대가가 따르므로, 실제 조직에서는
> 저장소를 서비스별로 나누고(폴리레포) 공용 코드를 별도 라이브러리로 배포하기도 합니다.
