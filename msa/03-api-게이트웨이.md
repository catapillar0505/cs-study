# API 게이트웨이

## 한 줄로

**모든 요청이 반드시 지나는 단일 관문**을 하나 둔다. 클라이언트는 주소 하나만 알면 되고, 인증·로깅·요청 제한 같은 **횡단 관심사를 여기서 한 번만** 처리한다.

> 이 문서는 개요입니다. 라우팅·필터·요청 제한의 자세한 내용은 [gateway](gateway/README.md)에 있습니다.

## 무엇을 해결하려는 기능인가

**문제 ① 클라이언트가 서비스 10개의 주소를 각각 알아야 하는가**

아닙니다. 게이트웨이 주소 하나만 알면 됩니다. 뒤에 서비스가 몇 개든, 어디로 옮겨 가든 상관없습니다.

**문제 ② 인증·CORS·로깅·요청 제한을 서비스마다 구현할 것인가**

이런 것들을 **횡단 관심사(Cross-Cutting Concern)** 라고 합니다.
여러 서비스에 공통으로 필요하지만 **어느 한 서비스의 비즈니스 로직도 아닌 것**들입니다.

서비스마다 복붙하면 **정책이 바뀔 때 전부 고쳐야 하고, 하나만 빼먹으면 보안 구멍**이 됩니다.
모든 요청이 관문을 지나므로 **거기서 한 번만** 하면 됩니다.

## 어떻게 동작하는가

### Route = predicate + filter + uri

```
┌─────────────────────────────────────────────────────────┐
│  Route (라우트) = 하나의 라우팅 규칙                    │
│   ① Predicate  "언제?"    - 조건 (경로, 메서드, 헤더)   │
│   ② Filter     "어떻게?"  - 요청/응답 가공 (선택)       │
│   ③ URI        "어디로?"  - 목적지                      │
└─────────────────────────────────────────────────────────┘
```

→ [gateway/02 라우팅과 로드밸런싱](gateway/02-라우팅과-로드밸런싱.md)

### pre 필터 / post 필터, 실행 순서

필터는 요청을 **가로채서** 앞뒤로 무언가를 합니다.

- **Pre** — 백엔드에 보내기 **전** (인증 검사, 헤더 추가, 로깅)
- **Post** — 응답을 받은 **후** (응답 로깅, 헤더 추가)

**"다음으로 넘기는 함수를 부르면 통과, 안 부르면 차단"** 이 필터의 전부입니다.
필터를 여러 개 달면 **먼저 추가한 것이 바깥에서** 실행되고, **그 순서가 실제 동작을 바꿉니다.**

→ [gateway/03 필터로 요청 가로채기](gateway/03-필터로-요청-가로채기.md)

### 디스커버리와 붙여 쓰기 (`lb://`)

목적지를 주소가 아니라 **서비스 이름**으로 적으면, 게이트웨이가 명부에서 실제 주소 목록을 받아
**골고루 나눠** 보냅니다.

```
lb://PRODUCT-SERVICE/api/products/1
        │  명부 조회 + 로드밸런싱
        ▼
http://192.168.0.5:51235/api/products/1
```

→ [gateway/02](gateway/02-라우팅과-로드밸런싱.md) · [msa/02 서비스 디스커버리](02-서비스-디스커버리.md)

### 게이트웨이에서 인증하고 뒤로는 신뢰? — 내부망 신뢰의 위험

**게이트웨이 인증은 "백엔드에 직접 붙을 수 없다"는 전제 위에서만 안전합니다.**

```
   정상 경로                        우회 경로
   클라이언트 → 게이트웨이 → 백엔드    클라이언트 ───────────▶ 백엔드
                 ↑ 인증 검사                        ↑ 검사 없음 😱
```

전제를 지키는 방법은 **네트워크 격리**(사설망, ClusterIP)가 가장 현실적이고,
그 위에 **백엔드도 토큰을 다시 검증**하는 것이 정석입니다. 이를 **제로 트러스트**라고 합니다.

→ [gateway/01 게이트웨이의 한계](gateway/01-게이트웨이란.md) · [auth/04 제로 트러스트](auth/04-역할-기반-인가.md)

## 흔한 오해

**"게이트웨이 = 로드밸런서"**
로드밸런싱도 하지만, **L7에서 요청의 내용을 이해하고 바꾼다**는 점이 다릅니다.
경로를 보고 목적지를 정하고, 헤더를 붙이고, 토큰을 검증합니다. → [network](../network/README.md)의 L4/L7 구분

**"게이트웨이를 두면 안전하다"**
관문은 **1차 방어선**일 뿐입니다. 백엔드가 그대로 노출돼 있으면 의미가 없습니다.

**"게이트웨이는 단일 장애점이다"**
맞습니다. **여러 대로 띄워 이중화**해야 합니다. 그래서 게이트웨이는 상태를 갖지 않게 설계하고,
꼭 상태가 필요하면(세션, 요청 제한 카운터) **외부 저장소로 뺍니다.**
→ [gateway/04 왜 Redis가 필요한가](gateway/04-요청-제한-rate-limiter.md)

**"인터넷 예제를 그대로 따라 했는데 안 된다"**
Spring Cloud Gateway는 **MVC 버전과 Reactive 버전**이 있고 설정 경로와 코드 스타일이 다릅니다.
→ [gateway/01](gateway/01-게이트웨이란.md)
