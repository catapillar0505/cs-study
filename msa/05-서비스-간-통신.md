# 서비스 간 통신

## 한 줄로

같은 프로그램 안의 **메서드 호출**이 **네트워크를 건너는 일**로 바뀐다. 응답을 기다릴 것인가(동기), 던져만 놓을 것인가(비동기) — 이 선택이 결합도를 결정한다.

> 이 문서는 개요입니다.
> 동기(REST·gRPC)는 [ipc](ipc/README.md), 비동기(브로커·이벤트)는 [eda](eda/README.md)에 펼쳐져 있습니다.

## 무엇이 달라지는가

```
[ 모놀리식 ]                        [ 마이크로서비스 ]

bankingService.transfer(...)        ??? 어떻게 부르지 ???
   ↑ 그냥 메서드 호출                  ↑ 네트워크를 건너야 함
     (나노초, 실패 없음)                 (밀리초, 실패 가능)
```

네트워크를 건너야 하니 고민거리가 줄줄이 생깁니다. **어떤 형식으로, 어떤 프로토콜로,
기다릴 것인지 말 것인지, 상대가 죽어 있으면 어떻게 할지.**
이 선택지들을 통틀어 **IPC(프로세스 간 통신)** 라고 부릅니다.

## 동기 호출

**요청을 보낸 스레드가 응답이 올 때까지 기다리는** 방식입니다.

**선언형 HTTP 클라이언트(OpenFeign) — 인터페이스가 곧 호출 규약**

구현체를 만들지 않고 **인터페이스만 선언**하면, 스프링이 런타임에 **프록시**를 만들어 줍니다.
주소 찾기·URL 조립·JSON 변환을 전부 대신합니다.
→ [ipc/02](ipc/02-openfeign-선언적-http.md)

**내부적으로는 결국 HTTP 요청**

Feign은 껍데기일 뿐 실제 전송은 그 아래 HTTP 클라이언트가 합니다.
그래서 **연결 풀·타임아웃 설정은 그 클라이언트 쪽**에 있습니다.
**타임아웃을 안 걸면 상대가 느릴 때 스레드가 무한정 묶입니다.**

**호출이 사슬처럼 이어질 때 지연이 누적된다**

```
A → B → C → D,  각 200ms  →  총 800ms
```

응답 시간이 **더해집니다.** 서비스를 잘게 쪼갤수록 악화됩니다.

**더 빠르고 엄격한 선택지 — gRPC**

이진 형식(Protobuf) + HTTP/2를 쓰고, **`.proto` 계약서에서 양쪽 코드를 자동 생성**합니다.
오타가 **컴파일 타임에** 잡힙니다. 대신 브라우저가 직접 부를 수 없고 디버깅이 어렵습니다.
→ [ipc/03](ipc/03-grpc와-protobuf.md)

## 비동기 호출

**메시지 브로커를 두면 무엇이 달라지는가**

호출자가 응답을 기다리지 않습니다. **상대가 누구인지, 살아 있는지 몰라도 됩니다.**

```
[Order] --넣음--> [ 브로커 ] <--꺼냄-- [Stock]
```

Stock이 배포 중이어도 **주문은 다 받고, 재고 처리만 나중에** 됩니다.

**최소 한 번 전달과 멱등성**

분산 시스템에서 "정확히 한 번"은 사실상 불가능해서, 대부분 **최소 한 번(At-Least-Once)** 을 택합니다.
즉 **중복이 옵니다.** 받는 쪽에서 이벤트 ID로 중복을 걸러야 합니다.

**순서 보장은 어디까지 되는가**

Kafka 기준으로 **파티션 안에서만** 보장됩니다. 토픽 전체는 보장되지 않습니다.

> 브로커·RabbitMQ·Kafka·Spring Cloud Stream까지 펼친 내용은 [eda](eda/README.md)

## 언제 무엇을 쓰는가

**응답이 즉시 필요한가 / 결과만 전달하면 되는가**

| 상황 | 선택 |
|---|---|
| 화면에 바로 보여줘야 하는 조회 | **동기** |
| 이체·재고 차감처럼 결과를 확인해야 하는 핵심 처리 | **동기** (정확성이 중요하면 gRPC) |
| 알림·로그·통계처럼 나중에 처리해도 되는 것 | **비동기** |
| 상대가 죽어 있어도 내 일은 계속돼야 하는 것 | **비동기** |

**강한 결합을 만드는 쪽은 어느 쪽인가**

동기 호출은 **상대를 알아야 하고, 상대가 살아 있어야 하고, 상대가 느리면 나도 느려집니다.**
비동기는 그 셋이 전부 풀립니다. 이걸 **공간적·시간적 결합 해제**라고 합니다.
→ [eda/03](eda/03-eda-도입의-3대-이점.md)

**한 요청 안에서 섞어 쓰는 것이 실제 모습입니다**

```
[이체 요청] ──동기(gRPC)──▶ [은행 서비스]   ← 돈이 걸린 핵심 처리
           ──비동기(이벤트)─▶ [알림 서비스]   ← 부가 기능
```

> ⚠️ **부가 기능의 실패가 핵심 기능을 실패로 만들면 안 됩니다.**
> 알림 발송을 동기로 부르면, 알림 서비스가 죽었을 때 **이체는 성공했는데 사용자에게는 실패로 보입니다.**
> → [ipc/04](ipc/04-무엇을-언제-쓰는가.md)

## 흔한 오해

**"비동기로 바꾸면 빨라진다"**
응답 지연이 아니라 **결합도**가 바뀌는 것입니다. 처리 자체가 빨라지지는 않습니다.

**"동기/비동기 = 블로킹/논블로킹"**
엄밀히는 다른 축입니다. 블로킹은 **호출한 함수가 즉시 리턴하는가**,
동기/비동기는 **결과를 누가 언제 확인하는가**입니다. 실무에서는 거의 붙여 씁니다.

**"gRPC가 빠르니 무조건 gRPC"**
브라우저가 직접 못 부르고, 이진이라 눈으로 디버깅할 수 없습니다. → [ipc/04](ipc/04-무엇을-언제-쓰는가.md)
