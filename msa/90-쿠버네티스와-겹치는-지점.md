# 쿠버네티스와 겹치는 지점

<!-- 뼈대 문서. 아래 항목을 채우면서 완성 -->

같은 문제를 **애플리케이션 층(Spring Cloud)** 과 **플랫폼 층(쿠버네티스)** 이 각각 푼다.
둘 다 켜면 중복이고, 둘 다 없으면 구멍이다. 무엇을 어디서 풀 것인지 정리한다.

| 문제 | Spring Cloud | 쿠버네티스 |
|---|---|---|
| 서비스 주소 찾기 | Eureka + 클라이언트 로드밸런싱 | [Service + CoreDNS](../kubernetes/04-서비스디스커버리-service와-coredns.md) |
| 외부 진입점 | Gateway | [Ingress](../kubernetes/09-ingress.md) |
| 설정 주입 | Config Server | [ConfigMap / Secret](../kubernetes/08-configmap과-secret.md) |
| 죽은 인스턴스 제외 | 하트비트 만료 | [readiness 프로브](../kubernetes/11-노드-rollout-프로브.md) |
| 무중단 배포 | — | [롤링 업데이트](../kubernetes/05-워크로드-deployment-replicaset-service.md) |
| 타임아웃·리트라이·서킷 | Resilience4j | (서비스 메시 영역) |

## 채울 항목

- 각 줄마다: 어느 쪽이 더 적합한가, 그 판단 기준은 무엇인가
- 둘 다 켰을 때 실제로 무슨 일이 나는가 (부하 분산이 두 번 일어나는 경우)
- 애플리케이션 코드에 남기는 것과 플랫폼에 맡기는 것의 경계
- 서비스 메시가 이 표에서 차지하는 자리
