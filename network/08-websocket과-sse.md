# WebSocket과 SSE

> 한 줄 요약
> **WebSocket은 HTTP에서 다른 프로토콜로 갈아타 양방향이 되고, SSE는 HTTP 응답을 끝내지 않은 채 서버가 계속 흘려보낸다.**

## 연결을 만드는 방식이 다르다

**WebSocket**은 처음에 HTTP로 접속한 뒤 "이제부터 다른 규칙으로 얘기하자"고 **프로토콜을 전환(Upgrade)** 한다. 그때부터는 HTTP가 아니라 **양쪽이 아무 때나 서로에게 보낼 수 있는 연결**이다.

**SSE(Server-Sent Events)** 는 프로토콜을 바꾸지 않는다. 그냥 **HTTP 응답을 끝내지 않고 열어둔 채로, 서버가 조금씩 계속 흘려보내는 방식**이다. 응답이 끝나지 않은 상태가 계속 유지되는 것뿐이다.

## 그래서 생기는 차이 세 가지

| | WebSocket | SSE |
|---|---|---|
| **방향** | 양방향 | **서버 → 클라이언트 단방향** |
| **재연결** | 직접 구현 | **브라우저가 자동 재연결** + `Last-Event-ID`로 이어받기 |
| **중간 장비** | 프로토콜 전환을 막는 프록시가 있음 | **그냥 HTTP라 대체로 통과** |
| **데이터 형식** | 텍스트/바이너리 | 텍스트만 |

**알림처럼 서버가 일방적으로 밀어주면 되는 기능에는 SSE로 충분하다.** 채팅·게임처럼 클라이언트도 수시로 보내야 하면 WebSocket이 맞다.

## SSE의 함정 — 프록시 버퍼링

그냥 HTTP인 게 장점인데, **프록시가 응답을 모았다가 한꺼번에 보내는 습성 때문에 데이터가 중간에 갇힌다.** 서버는 보냈는데 클라이언트에 안 도착하는 것처럼 보인다.

Nginx라면 버퍼링을 꺼야 한다.

```nginx
location /events {
    proxy_pass http://backend;
    proxy_buffering off;        # 모았다 보내지 않기
    proxy_cache off;
    proxy_read_timeout 24h;     # 오래 열어두는 연결이라 타임아웃도 늘림
}
```

`X-Accel-Buffering: no` 응답 헤더로 요청 단위로 끌 수도 있다.
