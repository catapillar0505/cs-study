# 가상화 — 네 가지 자원을 어떻게 나누는가


## Lv.1 — 기초: 한 문장으로

> **가상화의 핵심은, 여러 VM이 실제로는 하나의 물리 자원을 나눠 쓰면서도 각자 자기가 그 장치를 혼자 독점하고 있다고 착각하게 만드는 기술입니다.**
>
> 이 착각을 유지시켜 주는 소프트웨어를 **하이퍼바이저**라고 합니다. 하이퍼바이저가 **물리 CPU·메모리·디스크·네트워크를 나눠서 각 VM에게 "이게 네 하드웨어야"라고 보여줍니다.**
>
> VM 안의 게스트 OS는 **자기가 진짜 물리 서버 위에서 도는 줄 알고** 동작합니다. **커널까지 통째로 자기 것을 갖고 있습니다.**
>
> **그래서 가상화를 설명할 때는 "무엇을 어떻게 속이는가"를 자원별로 나눠서 말하는 게 정확하다**고 생각합니다. **네 가지입니다. CPU, 메모리, 디스크, 네트워크.**

**하이퍼바이저 두 종류**
> **Type 1(베어메탈)** 은 하드웨어 위에 직접 올라갑니다. ESXi, Hyper-V, KVM, Xen입니다. **오버헤드가 적어서 서버 환경의 표준**입니다.
> **Type 2(호스티드)** 는 일반 OS 위에 프로그램처럼 올라갑니다. VirtualBox, VMware Workstation입니다. **호스트 OS를 한 번 더 거쳐 느리고**, 개발·테스트용입니다.
>
> KVM은 **리눅스 커널 모듈**이라 형태상 애매하지만, **커널이 곧 하이퍼바이저가 되는 구조라 실질적으로 Type 1**로 봅니다.

## Lv.2 — 원리: 네 가지 자원을 각각 어떻게 속이는가

### ① CPU 가상화 — 특권 명령을 가로채는 것

> **문제의 출발점부터 봅니다.**
>
> OS 커널은 **특권 명령**을 씁니다. 인터럽트를 끄거나, 페이지 테이블을 바꾸는 것처럼 **하드웨어를 직접 건드리는 명령**입니다. 그런데 **VM 안의 게스트 커널은 진짜 커널이 아닙니다.** 게스트가 인터럽트를 진짜로 꺼버리면 **호스트 전체가 멈춥니다.**
>
> **그래서 원래 방식은 "잡아서 대신 처리하기"** 였습니다. 게스트를 **권한이 낮은 상태로 실행**시켜 두고, 게스트가 특권 명령을 쓰려는 순간 **CPU가 예외를 발생시켜 하이퍼바이저에게 제어를 넘기면**, 하이퍼바이저가 **"이 게스트에게는 이렇게 보이도록" 대신 처리**해 주고 다시 게스트를 돌립니다.
>
> **그런데 x86은 원래 이게 안 됐습니다.** 특권 명령 중 일부가 **권한 없는 상태에서 실행해도 예외를 안 내고 그냥 조용히 다르게 동작**했습니다. **잡을 수가 없으니 대신 처리할 수도 없습니다.**
> 그래서 초기에는 **실행 직전에 코드를 검사해 위험한 명령을 바꿔치기하는 방식(이진 변환)** 이나, **게스트 커널을 아예 고쳐서 "나는 VM이니 하이퍼바이저한테 부탁할게"라고 만드는 방식(반가상화)** 을 썼습니다. **둘 다 무겁거나 게스트 수정이 필요했습니다.**
>
> **지금은 CPU가 직접 지원합니다.** 인텔 **VT-x**, AMD **AMD-V**입니다.
> **CPU에 실행 모드를 하나 더 만든 것**이라고 이해하면 쉽습니다. **하이퍼바이저가 도는 Root 모드**와 **게스트가 도는 Non-Root 모드**로 나뉩니다.
> 게스트는 Non-Root 모드에서 **자기 딴에는 커널 권한으로 그대로 실행**되고, **하이퍼바이저가 처리해야 하는 상황이 왔을 때만 CPU가 자동으로 하이퍼바이저 쪽으로 빠져나옵니다.** 이 빠져나오는 것을 **VM Exit**, 다시 게스트로 돌아가는 것을 **VM Entry**라고 합니다.
>
> **핵심은 오버헤드의 정체가 이 VM Exit 횟수라는 점입니다.**
> **게스트 코드 대부분은 CPU에서 그냥 네이티브로 돕니다.** 성능이 거의 안 깎입니다. **Exit이 일어날 때만 비용이 나옵니다.**
> 그래서 **가상화 성능 튜닝은 대부분 "Exit을 어떻게 줄일 것인가"로 귀결**됩니다.

### ② 메모리 가상화 — 주소를 두 번 번역하는 것

> **게스트 OS는 자기가 0번지부터 메모리를 통째로 갖고 있다고 믿습니다.** 그런데 **실제로는 호스트 물리 메모리 여기저기에 흩어진 조각들**입니다.
>
> 그래서 주소 변환이 **두 단계**가 됩니다.
> **게스트 안의 가상주소 → 게스트가 믿는 물리주소 → 진짜 호스트 물리주소**
>
> 앞의 한 단계는 **게스트 커널의 페이지 테이블**이 하고, **뒤의 한 단계를 하이퍼바이저가 책임집니다.**
>
> **예전 방식은 그림자 페이지 테이블**이었습니다. 하이퍼바이저가 **"게스트 가상주소 → 호스트 물리주소"를 바로 잇는 표를 몰래 하나 더 만들어서** CPU에게는 그걸 쓰게 했습니다.
> 문제는 **게스트가 자기 페이지 테이블을 고칠 때마다 하이퍼바이저가 알아채서 그림자 표를 갱신해야 한다**는 것이고, **그때마다 VM Exit이 났습니다. 아주 비쌌습니다.**
>
> **지금은 CPU가 2단계 변환을 직접 해줍니다.** 인텔의 **EPT**, AMD의 **NPT**입니다.
> **하이퍼바이저는 "게스트 물리 → 호스트 물리" 표만 CPU에 등록해 두면 되고, 게스트가 자기 페이지 테이블을 아무리 고쳐도 Exit이 나지 않습니다.**
>
> **대신 새 비용이 생겼습니다.** 주소 변환 캐시(TLB)에 없는 주소를 찾을 때, **원래는 표를 몇 번 뒤지면 됐는데 이제 2차원으로 뒤져야 해서 메모리 접근 횟수가 크게 늘어납니다.**
> 그래서 **메모리를 많이 쓰는 VM에서 huge page를 쓰면 효과가 큽니다.** **페이지가 크면 표를 뒤지는 단계 자체가 줄어들기 때문**입니다.

### ③ 디스크 I/O 가상화 — 하이퍼바이저가 중재하는 것

> **물리 디스크는 하나인데 VM 10대가 동시에 읽고 쓰겠다고 하면 정리가 안 됩니다.** 그래서 **하이퍼바이저가 중간에서 중재**합니다.
>
> **VM에게는 가상 디스크를 보여줍니다.** 게스트 입장에서는 **평범한 디스크 한 대**로 보이는데, **실제로는 호스트의 파일 하나이거나(KVM의 qcow2), 네트워크 너머의 블록 스토리지(Ceph RBD, AWS EBS)** 입니다.
> 게스트가 디스크 요청을 보내면 **가상 블록 장치 드라이버가 그걸 가로채서, 물리 디스크의 실제 블록 위치로 바꾸거나 네트워크를 통해 스토리지로 전달**합니다.
>
> **여기서 방식이 세 가지로 나뉘고, 뒤로 갈수록 빠릅니다.**
>
> **첫째, 완전 에뮬레이션입니다.** 하이퍼바이저가 **실제로 존재하는 옛날 디스크 컨트롤러를 소프트웨어로 흉내**냅니다. 게스트는 표준 드라이버를 그냥 쓰면 되니 **호환성은 최고**입니다. 그런데 **게스트가 장치 레지스터를 건드릴 때마다 VM Exit이 납니다. 아주 느립니다.**
>
> **둘째, virtio입니다. 지금 실무의 기본값입니다.**
> 발상이 다릅니다. **"게스트에게 가상화 중이라는 걸 알려주고, 하이퍼바이저와 대화하기 좋은 전용 장치를 쓰게 하자"** 는 것입니다.
> 게스트와 하이퍼바이저가 **메모리 한 조각을 공유해서 링 버퍼로 씁니다.** 게스트는 요청을 **거기에 여러 개 쌓아두고 한 번만 알립니다.** **Exit이 요청마다가 아니라 묶음마다** 나므로 횟수가 급감합니다.
> **가상화를 숨기지 않고 인정한 대신 빨라진 방식**입니다.
>
> **셋째, 패스스루입니다.** 물리 장치를 **특정 VM에게 통째로 넘겨줍니다.** 성능은 최고지만 **다른 VM과 못 나눠 쓰고 라이브 마이그레이션이 어렵습니다.**
>
> **운영에서 중요한 건 캐시 정책입니다.** 호스트가 쓰기를 **메모리에 모았다가 나중에 디스크로 내리면 빠르지만, 정전 시 데이터가 날아갈 수 있습니다.** **DB처럼 정합성이 중요한 게스트는 캐시를 끄는 쪽**을 씁니다. **속도와 안전을 바꾸는 설정**입니다.

### ④ 네트워크 가상화 — 소프트웨어 스위치와 오버레이

> **물리 랜카드는 한 장인데 VM은 여러 대**입니다. 그래서 **하이퍼바이저 안에 소프트웨어로 만든 스위치를 띄우고, VM의 가상 랜카드들을 거기에 꽂습니다.**
> 리눅스에서는 **Linux Bridge**나 **Open vSwitch(OVS)** 를 씁니다. **실제 스위치가 하는 일을 소프트웨어가 하는 것**이라고 이해하면 됩니다. VM끼리 통신하면 **물리 랜카드까지 안 나가고 이 소프트웨어 스위치 안에서 끝납니다.**
>
> **여기서 한 걸음 더 나간 게 오버레이 네트워크입니다.**
> 문제 상황이 이렇습니다. **테넌트가 여러 개인 환경에서 각자 원하는 IP 대역을 쓰고 싶은데, 물리 네트워크는 하나**입니다. **물리 스위치 설정을 매번 바꾸는 건 현실적이지 않습니다.**
> 그래서 **VM이 보낸 패킷을 한 번 더 감싸서, 물리 네트워크 입장에서는 그냥 평범한 통신처럼 보이게** 만듭니다. **VXLAN** 같은 방식입니다. **물리 네트워크 위에 가상 터널을 뚫는 것**입니다.
>
> **이렇게 하면 물리 장비를 안 건드리고도 논리적인 네트워크를 마음대로 만들 수 있습니다.** 쿠버네티스의 CNI가 하는 일도 이것과 같은 계열입니다. 제가 쓴 **Calico의 IPIP 모드도 패킷을 한 번 더 감싸는 방식**입니다.
>
> **대가도 분명합니다.** **감싸는 만큼 헤더가 붙어서 실제로 보낼 수 있는 데이터 크기가 줄고(MTU 문제), 감싸고 푸는 데 CPU를 씁니다.** 그래서 **네트워크를 직접 통제할 수 있는 환경에서는 오버레이를 끄고 순수 라우팅으로 가는 게 낫습니다.**
>
> **성능이 정말 중요하면 SR-IOV를 씁니다.** **물리 랜카드 한 장이 자기 자신을 여러 개의 가상 랜카드로 쪼개서 노출**하고, 그 조각을 VM에 직접 붙여줍니다. **게스트가 하이퍼바이저를 거치지 않고 하드웨어와 직접 대화**하니 거의 물리 성능이 나옵니다.
> 이때 **DMA 때문에 위험이 생길 수 있습니다.** 게스트가 아무 주소나 적어서 **다른 VM 메모리를 덮어쓸 수 있기 때문**입니다. **그래서 IOMMU가 필요합니다.** IOMMU가 **장치의 메모리 접근 주소를 번역하고 범위를 제한해서 격리를 지켜줍니다.**
> **단점은 유연성입니다.** 물리 장치에 묶이니 **라이브 마이그레이션이 어렵습니다.**

### ▸ 네 가지를 한 문장으로 묶으면

> **CPU와 메모리는 하드웨어(VT-x, EPT)의 도움을 받아 거의 오버헤드 없이 직접 처리하고, 디스크와 네트워크는 하이퍼바이저와 소프트웨어 계층(virtio, 소프트웨어 스위치)이 중재하면서 격리와 유연성을 확보하는 것이 현대 가상화의 구조입니다.**
>
> **그래서 성능 문제가 생겼을 때 보는 곳도 다릅니다.** **CPU·메모리 쪽은 Exit 횟수와 페이지 설정**을 보고, **디스크·네트워크 쪽은 중재 계층의 방식(에뮬레이션인지 virtio인지 패스스루인지)** 을 먼저 확인합니다.

## Lv.3 — 심화: 운영에서 실제로 부딪히는 것들

### ▸ 게스트가 느린데 게스트 안에서는 원인이 안 보인다 — steal time
> **호스트가 CPU를 안 주고 있는 시간**입니다. 게스트의 `vmstat`에서 `st` 값으로 보입니다.
> **게스트 안에서 `top`을 봐도 아무도 CPU를 안 쓰는데 느리면 steal을 의심**해야 합니다. 원인은 대개 **호스트의 CPU 오버커밋**입니다.
> **게스트 안에서는 절대 해결할 수 없고 호스트 쪽에서 봐야 하는 문제**라는 점이 중요합니다.

### ▸ 오버커밋 — CPU는 비교적 안전, 메모리는 위험
> **물리 자원보다 많이 할당하는 것**입니다. 모든 VM이 동시에 최대치를 쓰진 않는다는 전제입니다.
> **CPU 오버커밋은 부족하면 느려질 뿐**입니다(위의 steal time). **메모리 오버커밋은 부족하면 VM이 죽습니다.**
> 완화 기술로 **balloon 드라이버**(게스트 안에 풍선을 부풀려 안 쓰는 메모리를 호스트가 회수)와 **KSM**(내용이 같은 페이지를 하나로 합침)이 있지만, **근본적으로는 여유를 남겨야** 합니다.

### ▸ NUMA — VM 크기를 잘못 잡으면 그것만으로 느려진다
> 물리 서버에 CPU 소켓이 여러 개면 **각 소켓에 붙은 메모리가 따로 있습니다.** 자기 소켓 메모리는 빠르고 **다른 소켓 메모리는 느립니다.**
> VM의 vCPU와 메모리가 **NUMA 노드를 걸치면 성능이 떨어집니다.** 그래서 **VM 크기를 한 노드 안에 들어가게 잡거나 CPU를 고정**합니다.

### ▸ 라이브 마이그레이션 — 원리와 조건
> **VM을 끄지 않고 다른 호스트로 옮기는** 기능입니다. **호스트 패치를 게스트 중단 없이 할 수 있어서 운영 가치가 큽니다.**
>
> **원리는 메모리 반복 복사**입니다. VM을 돌린 채로 메모리를 대상 호스트에 복사하고, 그동안 변경된 페이지를 다시 복사하고, **남은 양이 충분히 작아지면 아주 짧게 VM을 멈추고 마지막 차이와 CPU 상태를 넘긴 뒤 대상에서 재개**합니다.
>
> **조건이 세 가지**입니다.
> **① 공유 스토리지** — 디스크는 안 옮기고 양쪽이 같은 스토리지를 봅니다.
> **② CPU 호환성** — 세대가 섞였으면 **공통 기능으로 낮춰서** 잡아야 합니다([x86 아키텍처와 서버](../hardware/01-x86-아키텍처와-서버.md) 참고).
> **③ 같은 L2 네트워크** — IP를 유지한 채 옮기려면 필요합니다.
>
> **실패하는 경우도 있습니다. 메모리가 바뀌는 속도가 전송 속도보다 빠르면 영원히 안 끝납니다.** 이때는 **게스트 CPU를 일부러 늦춰 변경 속도를 낮추거나, 먼저 옮겨놓고 필요한 페이지를 나중에 당겨오는 방식**으로 전환합니다.

### ▸ VM과 컨테이너의 차이
| | VM | 컨테이너 |
|---|---|---|
| 격리 방식 | **하드웨어 가상화 — 게스트 커널이 따로 있음** | **커널 공유 — namespace + cgroup** |
| 부팅 | 수십 초 | 수백 ms |
| 격리 강도 | 강함 | 상대적으로 약함(커널을 공유하므로) |
| 용도 | 다른 OS, 강한 격리, 테넌트 분리 | 밀집 배치, 빠른 배포 |

> **핵심은 컨테이너는 커널을 공유한다**는 것입니다. 그래서 가볍지만 커널 수준 격리는 안 됩니다.
> **둘은 대체 관계가 아닙니다.** 실무에서는 **VM 위에 컨테이너를 올리는 구성**이 일반적입니다. 예를 들어 OpenStack Guest VM 위에 쿠버네티스를 올리는 식으로, **VM으로 테넌트를 나누고 컨테이너로 밀집 배치**하는 조합입니다.

### ▸ Guest VM을 운영할 때 실제로 챙기는 것
> **① virtio 드라이버가 제대로 붙었는지** — 에뮬레이션으로 떨어져 있으면 원인 모르게 느립니다.
> **② 게스트 에이전트** — 설치돼 있어야 호스트에서 **정상 종료, 파일시스템 정지 후 정합성 있는 스냅샷**이 가능합니다. 없으면 스냅샷이 "전원 뽑은 상태"가 됩니다.
> **③ 시간 동기화** — 가상 환경은 시계가 틀어지기 쉽습니다. **로그 상관분석과 인증서·토큰 검증이 다 깨집니다.**
> **④ 디스크 캐시 모드** — 위에서 말씀드린 속도와 안전의 트레이드오프입니다.
> **⑤ 스냅샷을 백업으로 착각하지 않기** — 스냅샷은 원본에 의존하므로 **원본이 깨지면 같이 갑니다.**

## ⚠️ 흔한 오해

- ❌ "하이퍼바이저가 자원을 나눠준다"에서 끝내기 → **CPU·메모리·디스크·네트워크를 각각 어떻게 속이는지**가 원리
- ❌ CPU·메모리·디스크만 보고 **네트워크를 빼먹기** → 소프트웨어 스위치와 오버레이는 사설 클라우드 운영의 핵심

- ❌ 스냅샷과 백업을 같은 것으로 다루기 → **스냅샷은 백업이 아니다**
