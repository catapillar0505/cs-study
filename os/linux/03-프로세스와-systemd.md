# 프로세스와 systemd

## systemd
- **system + d(daemon)** = "시스템 전체를 관리하는 데몬".
- 커널이 부팅 후 **가장 먼저 직접 생성·실행**하는 사용자 영역의 첫 프로세스 (**PID 1**).
- 서비스 관리(`systemctl`), 로그(`journald`), 타이머, 마운트, 네트워크 등 시스템 전반을 관리.

## 시스템 vs 서비스 vs 유닛
- **서비스(Service)**: `sshd`, `nginx` 같은 개별 백그라운드 프로그램(데몬).
- **시스템(System)**: 서비스 + 마운트 + 소켓 + 타이머 + 부팅 순서 등 컴퓨터가 정상 작동하기 위한 모든 것.
- **유닛(Unit)**: systemd가 관리하는 모든 대상의 공통 단위. 서비스·마운트·타이머·소켓이 각각 유닛의 한 종류.
  - 서비스 = `.service` 유닛

## 데몬(daemon)이란?
- 그리스 신화의 "다이몬(보이지 않게 자기 역할을 수행하는 존재)"에서 유래.
- 사용자 눈에 안 보이는 **백그라운드에서 계속 돌며 요청을 처리하는 프로그램**.
- 이름 끝에 `d`가 붙는 관례: `sshd`, `httpd`, `crond`, `systemd`, `kthreadd`.

## systemd vs systemctl (중요 패턴!)
- **systemd**: 실제로 백그라운드에서 계속 돌며 유닛을 관리하는 **데몬 그 자체** (PID 1).
- **systemctl**: systemd에게 명령을 전달하는 **도구(리모컨)**. 자체 관리 기능 없음.
- 계층은 상하 관계가 아니라 "몸통과 리모컨" 관계.

```bash
systemctl start nginx     # nginx 시작
systemctl status sshd     # 상태 확인
systemctl enable/disable  # 부팅 시 자동 시작 설정
journalctl -u 서비스명     # 특정 서비스 로그
```

## 커널이 직접 만드는 프로세스는 딱 2개
```
커널
 ├── systemd  (PID 1) ← 사용자 공간 프로세스들의 시조
 └── kthreadd (PID 2) ← 커널 공간 스레드들의 시조
```
- **kthreadd** (kernel thread daemon): 커널 내부 작업용 커널 스레드들을 생성.
- 둘은 **부모-자식이 아니라 형제** 관계. 각자 커널이 독립적으로 생성 (PPID=0).
- **그 외 모든 프로세스/데몬은 이 둘로부터 `fork()`(자기 복제)로 파생됨.**
- 커널 스레드는 `ps`에서 `[kthreadd]`처럼 대괄호로 표시됨.

## 포그라운드 / 백그라운드 / 데몬
| 구분 | 터미널 연결 | 키보드 입력 수신 |
|---|---|---|
| 포그라운드 | 연결됨 | 받음 (입력 자리 차지) |
| 백그라운드 (`&`, `bg`) | 연결됨 | 안 받음 (입력 자리만 안 차지) |
| 데몬 | **연결 자체 없음** | 해당 없음 |

- 포그라운드/백그라운드는 **쉘의 작업 제어(job control)** 개념. systemd 소관이 아님.
- 모든 프로세스를 실제로 스케줄링/관리하는 근본은 **커널**.

## 프로세스 상태 (ps의 STAT 컬럼)
| 상태 | 이름 | 의미 |
|---|---|---|
| **R** | Running | 실행 중 또는 실행 대기 |
| **S** | Sleep | 이벤트 대기 중, **시그널로 깨울 수 있음**(interruptible) |
| **D** | Disk Sleep | 하드웨어 I/O 대기 중, **시그널로 못 깨움**(uninterruptible). `kill -9`도 불가. 파일시스템 손상 방지를 위해 커널이 보호 |
| **T** | Stopped | `Ctrl+Z`나 디버거로 **정지**됨(CPU 안 씀) |
| **Z** | Zombie | 작업은 끝났으나 부모가 종료 정보를 아직 안 가져간 상태 |

- **D 상태 주의**: 정상이면 밀리초 단위로 지나감. 오래 지속되면 하드웨어/네트워크 스토리지 문제 신호.

## 좀비 프로세스와 wait()
- 자식이 `exit()` → 종료 정보만 프로세스 테이블에 남음(좀비).
- 부모가 `wait()`/`waitpid()` 호출 → 커널이 그 정보를 부모에게 전달하고 **프로세스 테이블에서 완전히 제거**.
- `wait()`은 "기다리다"가 아니라 "**자식의 종료 정보를 수거한다**"는 능동적 행위.
- **고아 프로세스(orphan)**: 부모가 먼저 죽으면 PID 1(systemd)이 입양해서 대신 `wait()` 처리.
- 좀비 정리 방법: `SIGCHLD` 시그널 핸들러 안에서 `waitpid()` 호출이 정석.

## 프로세스 조회 명령어
```bash
ps aux                # 전체 프로세스 (BSD 스타일) — 모든 상태 다 보임
ps -ef                # 전체 프로세스 (System V 스타일)
ps aux | grep ' D '   # 특정 상태 필터링
top / htop            # 실시간 상태 확인 (ps는 스냅샷 한 장)
pstree                # 부모-자식 트리 구조
```
- `a`=모든 사용자, `u`=사용자 중심 상세정보, `x`=제어 터미널 없는 프로세스(데몬)까지 포함.
- **TTY** (TeleTYpewriter): 옛날 물리 입출력 기계 이름에서 유래. `ps`의 TTY 컬럼이 `?`면 터미널 연결 없음(데몬).

## 작업 제어 (Job Control)
```bash
sleep 100 &     # 백그라운드 실행 → [1] 12345 (작업번호 / PID)
jobs            # 작업 목록
fg %1           # 1번 작업을 포그라운드로
bg %1           # 1번 작업을 백그라운드에서 재개
Ctrl+Z          # 포그라운드 작업을 정지(T 상태)
```
- **작업번호(Job Number)**: 그 터미널 세션 안에서만 유효. `%` 붙여서 지정.
- **PID**: 시스템 전체에서 고유.
- ⚠️ `Ctrl+Z` 직후는 "백그라운드 실행"이 아니라 **정지(T)** 상태. `bg`를 쳐야 실제 실행(R/S)됨.

## 프로세스 종료 (kill)
```bash
kill 1234       # 기본값 SIGTERM(15) — 정중한 종료 요청
kill -15 1234   # SIGTERM (위와 동일)
kill -9 1234    # SIGKILL — 강제 즉시 종료
kill %1         # 작업번호로 지정
```

| | SIGTERM (15) | SIGKILL (9) |
|---|---|---|
| 성격 | 정중한 종료 요청 | 강제 즉시 종료 |
| 프로세스가 정리작업 가능? | 가능 | 불가능 |
| 무시/커스텀 가능? | 가능 | 불가능 |
| 기본값? | **kill의 기본** | `-9` 명시 필요 |

- ⚠️ **`kill`만 치면 기본은 SIGTERM(15)**, SIGKILL 아님.
- ⚠️ **D 상태 프로세스는 `kill -9`로도 못 죽임**.
- 정석: 먼저 SIGTERM → 안 죽으면 최후로 SIGKILL.

## 시그널과 상태 전환
- S 상태 프로세스에 `kill`을 보내면 → **시그널 자체가 깨우는 트리거** → S→R로 전환 → 종료 처리 실행.
- "먼저 깨우고 kill"이 아니라 "kill 신호 = 깨움". 그 R 상태는 매우 짧아 `ps`로 포착하기 어려움.
- D 상태는 이 "시그널 도착 → S→R 전환" 자체를 커널이 차단.

## 대표 시그널
| 번호 | 이름 | 의미 |
|---|---|---|
| 1 | SIGHUP | 터미널 연결 끊김 |
| 2 | SIGINT | `Ctrl+C` 인터럽트 |
| 9 | SIGKILL | 강제 즉시 종료(무시 불가) |
| 15 | SIGTERM | 정중한 종료 요청(기본값) |
| 19 | SIGSTOP | 강제 일시정지 |
