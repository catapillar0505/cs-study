# 관리형 클러스터 vs 직접 구축(kubeadm)

> 한 줄 요약
> **관리형은 컨트롤 플레인을 대신 운영해 주고, 직접 구축은 그 일이 전부 내 몫이 된다.**

## 무엇이 다른가

| | 관리형 (EKS/GKE/AKS) | 직접 구축 (kubeadm) |
|---|---|---|
| 컨트롤 플레인 | **클라우드가 띄우고 이중화·업그레이드까지 담당** | 직접 띄우고 직접 이중화 |
| 노드 등록 | 붙이면 됨 | 부트스트랩 토큰·인증서 직접 처리 |
| 레지스트리 인증 | 대체로 자동 연결 | **직접 구성** |
| 외부 통신(NAT), LB | 관리형 서비스로 제공 | **직접 세움** |
| etcd 백업 | 대행 | 직접 |

## 직접 세우면 드러나는 것들

관리형을 쓰면 **잘 돌아가는데 왜 돌아가는지는 모르는 상태**가 되기 쉽다. 직접 세우면 그 아래가 보인다. 실제로 직접 구축에서 부딪히는 문제들은 **대부분 쿠버네티스 문제가 아니다.**

| 증상 | 실제 원인 |
|---|---|
| 노드가 이미지를 못 받아옴 | **인증** 구성 (→ [레지스트리 인증](../container/05-레지스트리-인증.md)) |
| 내부망 노드가 밖으로 못 나감 | **리눅스 네트워크·NAT** (→ [NAT 동작 원리](../network/06-nat-동작-원리.md)) |
| 배포가 중간에 멈춤 | **자원 배분과 배포 전략** (→ [고가용성 설계](../cloud/public-cloud/aws/12-고가용성-설계.md)) |

쿠버네티스 문서가 아니라 **리눅스와 네트워크를 봐야 풀리는 문제들**이다.

## 어느 쪽을 고르나

- **운영 환경이면 관리형이 유리하다.** 컨트롤 플레인 이중화와 버전 업그레이드는 손이 많이 가고, 실수하면 클러스터 전체가 영향을 받는다.
- **온프레미스·프라이빗 클라우드에는 관리형이라는 선택지가 없다.** 위 항목들이 그대로 해야 할 일이 된다.
- **학습 목적이라면 직접 구축이 압도적으로 많이 남는다.**
