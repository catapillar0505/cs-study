## 1. 자바 실행 원리

### 1.1 시점이 두 개다

모든 혼란의 출발점입니다.

```
① 컴파일 (javac)            ② 실행 (java)
Camp.java  →  Camp.class  →  메모리에 올라가 동작
```

**서로 다른 시간에 일어납니다.** 컴파일은 개발자 PC에서, 실행은 며칠 뒤 서버에서 일어날 수 있습니다.

| 용어 | 의미 |
|---|---|
| 컴파일 타임 | `javac`가 도는 시점. 아직 프로그램이 실행 안 됨 |
| 런타임 | `java`로 실행 중인 시점. 메모리에 객체가 존재 |

> **컴파일러가 결정하는 것**과 **실행 중에 결정되는 것**이 다르다 — 이 문서 전체를 관통하는 주제입니다.

### 1.2 `.class` 파일은 "완성품"이 아니다

`.class`는 이진 파일이지만, 열어보면 **글자(문자열)가 많이 들어있습니다.**

```java
c.open();
```

이 한 줄이 파일에 남기는 것:

```
"Camp"     ← 클래스 이름 (글자)
"open"     ← 메서드 이름 (글자)
"()V"      ← 시그니처 (글자)
```

주소나 기계어가 아니라 **이름 그 자체**가 저장됩니다.

**왜?** 컴파일하는 순간엔 프로그램이 실행조차 안 됐습니다. `Camp`가 메모리 몇 번지에 놓일지 컴파일러는 알 수 없어요. 그래서 이렇게 합니다.

```
컴파일러 : "주소는 모르겠고, 'Camp의 open'이라고 적어둘게. 실행할 때 찾아."
JVM      : (실행 시점) "Camp 찾았다 → open 찾았다 → 0x7F3A. 실행!"
```

> **`.class` 파일 = 완성품이 아니라 "실행할 때 조립하라는 지시서"**
> 그래서 어떤 건 이름만, 어떤 건 값만, 어떤 건 재료만 적혀 있습니다. (자세한 내용은 [9장](#9-클래스-로딩과-상수-풀)에서 다룹니다.)

## 2. 메모리 구조

### 2.1 변수의 3분류

```java
class Dog {
    static int count;   // ① 클래스 변수 (static 변수)
    String name;        // ② 인스턴스 변수

    void bark() {
        int volume = 10;  // ③ 지역 변수
    }
}
```

| 구분 | 선언 위치 | 생성~소멸 | 개수 |
|---|---|---|---|
| ① 클래스 변수 | 메서드 밖 + `static` | 프로그램 시작~끝 | **딱 1개** (모든 객체 공유) |
| ② 인스턴스 변수 | 메서드 밖, `static` 없음 | `new`~GC | **객체 수만큼** |
| ③ 지역 변수 | 메서드 안 | 메서드 시작~끝 | 호출마다 |

용어 계층은 대등한 선택지가 아닙니다.

```
멤버 변수 (= 필드)
 ├─ 클래스 변수   (static O) — 클래스당 1개
 └─ 인스턴스 변수 (static X) — 객체당 1개

지역 변수 — 멤버 변수가 아님
```

`static`이 없는 필드는 **인스턴스 변수이면서 동시에 멤버 변수**입니다.

```java
Dog a = new Dog();  a.name = "뽀삐";
Dog b = new Dog();  b.name = "초코";
// 서로 독립적 — 이것이 "객체가 상태를 가진다"의 실체
```

`static`을 붙이면 강아지가 100마리여도 `count`는 하나뿐 → 전체 마릿수 세기 등에 사용합니다.

### 2.2 메모리 3영역

| 영역 | 담는 것 | 특징 |
|---|---|---|
| **스택** | 지역 변수, 참조값(주소) | 메서드 호출마다 생성/소멸. **스레드마다 따로** |
| **힙** | 실제 객체, 인스턴스 변수 값 | GC 대상. **모든 스레드가 공유** |
| **메서드 영역**<br>(메타스페이스) | 클래스 설계 정보 | 클래스당 하나. JVM 명세상의 논리적 개념 |

```java
Camp c = new Camp();
//   ↑스택            ↑힙
```

`c`는 객체가 아니라 **힙 주소 4~8바이트**만 담고 있습니다.

**설계 정보 vs 실제 값**의 구분이 중요합니다.

| 항목 | 위치 |
|---|---|
| 필드 **목록** (이름·타입·offset) | 메서드 영역 |
| 필드의 **실제 값** | 힙 (객체 안) |
| 메서드 **바이트코드** | 메서드 영역 |
| `static` 필드 값 | 힙 (Java 8+) |

이 스택/힙 구분은 이후 [람다 캡처](#7-람다와-변수-캡처)와 [스레드 안전성](#10-동시성) 모두의 근거가 됩니다.

### 2.3 static 변수는 실제로 어디 있나

"메서드 영역"은 JVM **명세서상의 논리적 개념**일 뿐, 물리적 구현은 JVM 구현체(HotSpot 등)의 자유입니다.

| 버전 | 클래스 메타데이터 | **static 변수** |
|---|---|---|
| ~Java 6 | PermGen (힙 내부) | PermGen |
| Java 7 | PermGen | **힙으로 이동** |
| Java 8~ | **Metaspace** (네이티브 메모리) | **힙** |

현재(Java 8+) 구조:

```
[Metaspace]  Dog 클래스 메타데이터 (바이트코드, 필드 구조, 상수 풀)
                    │ 참조
[Heap]       Dog.class 객체 ── count = 0   ← static 변수는 여기
             Dog 인스턴스 ──── name = "뽀삐"
```

static 변수는 힙에 만들어진 `java.lang.Class` 객체의 필드로 존재합니다.

**변경 이유**

- PermGen은 크기가 고정 → 클래스 다량 로딩 시 `OutOfMemoryError: PermGen space` 발생
- Metaspace는 네이티브 메모리라 자동 확장
- static 변수도 GC 대상이어야 하므로 힙에 두면 기존 GC 메커니즘 재사용 가능

**헷갈리기 쉬운 지점**

```java
static List<String> cache = new ArrayList<>();
```

- `cache` **참조 변수(주소값)** → 위 표의 위치
- `new ArrayList<>()` **실제 객체** → **언제나 힙** (예전부터)

"PermGen → 힙 이동"은 **참조 슬롯**의 이야기이지 객체 본체 이야기가 아닙니다.

> **면접 답변**: "명세상 메서드 영역에 속하고, Java 7까지는 PermGen, Java 8부터는 힙의 `Class` 객체에 저장된다."

## 3. 값과 참조 — String으로 배우기

### 3.1 `==` vs `equals()`

| | 비교 대상 |
|---|---|
| `==` | 참조(주소)가 같은 객체인지 |
| `equals()` | 실제 내용이 같은지 |

```java
String a = "camping";
String b = "camping";
String c = new String("camping");

a == b        // true  (같은 객체)
a == c        // false (c는 새 객체)
a.equals(c)   // true  (내용 동일)
```

**문자열 내용 비교는 반드시 `equals()`.**

리터럴은 재사용되어 `==`가 우연히 `true`가 되는 경우가 많습니다. 하지만 사용자 입력, DB 조회, JSON 파싱 결과는 매번 새 객체라 `false`가 됩니다. → **테스트는 통과하는데 실서비스에서 터지는** 버그의 원인입니다. (`==`가 왜 이렇게 동작하는지는 [9.4](#9-클래스-로딩과-상수-풀)에서 상수 풀 구조까지 파고들어 완전히 설명합니다.)

```java
// NPE 방지 — 상수를 앞에
if ("ROLE_ADMIN".equals(user.getRole())) { }

// 양쪽 null 안전
Objects.equals(a, b);
```

> `Integer`도 같은 함정이 있습니다 (-128~127 캐싱 범위 밖에서 `==`는 `false`).

### 3.2 String은 불변 → 반복 연산에 불리

`String`은 한번 만들면 내용을 못 바꿉니다. `+`는 **새 객체를 계속 생성**합니다.

```java
String s = "";
for (int i = 0; i < 10000; i++) {
    s += i;   // 매번 새 String 생성 → 버려진 객체가 GC 대상으로 쌓임, O(n²)
}
```

```java
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 10000; i++) {
    sb.append(i);   // 내부 버퍼에 추가, 객체 재사용
}
String result = sb.toString();   // 마지막에 한 번만 생성
```

| | 가변성 | 동기화 | 용도 |
|---|---|---|---|
| `String` | 불변 | – | 값이 안 바뀌는 문자열 |
| `StringBuilder` | 가변 | X | 단일 스레드 (기본 선택) |
| `StringBuffer` | 가변 | O | 멀티스레드 |

**단, 한 줄짜리 연결은 괜찮습니다.**

```java
String s = "Base" + "Camp";   // 컴파일 타임에 합쳐짐
```

Java 9+는 단일 표현식의 `+`도 `StringConcatFactory`로 최적화합니다. **문제가 되는 건 반복문 안의 누적 연산**입니다.

## 4. 자바의 불변 객체

### 4.1 대표적인 불변 클래스들

**1. 래퍼 클래스 (Wrapper)** — `Integer`, `Long`, `Double`, `Boolean`, `Character`, `Byte`, `Short`, `Float`

```java
Integer i = 10;
i = i + 5;  // 새 Integer 객체 생성, 기존 객체 수정 아님
```

**2. `BigInteger`, `BigDecimal`**

```java
BigDecimal a = new BigDecimal("100");
a.add(new BigDecimal("50"));     // ❌ 반환값을 안 받으면 아무 일도 안 일어남
a = a.add(new BigDecimal("50")); // ✅ 재할당해야 함
```

정산·금액 계산에서 자주 실수하는 부분입니다.

**3. `java.time` 패키지 (Java 8+)** — `LocalDate`, `LocalDateTime`, `LocalTime`, `Instant`, `Duration`, `Period`, `ZonedDateTime`

```java
LocalDate date = LocalDate.now();
date.plusDays(7);        // ❌ 무의미
date = date.plusDays(7); // ✅
```

구버전의 `Date`, `Calendar`는 **가변**이라 스레드 안전하지 않았고, 그게 java.time이 나온 주요 이유 중 하나입니다.

**4. `String`과 관련 클래스** — `String`, `Pattern`(정규식 컴파일 결과), `UUID`, `URI`

**5. `Enum`** — 상수 자체가 싱글턴이라 불변으로 취급합니다. (단, enum에 가변 필드를 넣으면 깨집니다)

**6. 불변 컬렉션 (Java 9+)**

```java
List<String> list = List.of("a", "b");
Set<String> set = Set.of("a", "b");
Map<String, Integer> map = Map.of("a", 1);

list.add("c");  // UnsupportedOperationException
```

`Collections.unmodifiableList()`는 조금 다릅니다 — 원본 리스트를 감싸는 **뷰**라서, 원본을 수정하면 뷰에도 반영됩니다. 진짜 불변이 필요하면 `List.copyOf()`를 쓰세요.

**7. `Optional`** — `Optional`도 불변이지만, 안에 담긴 객체가 가변이면 그 내용은 바뀔 수 있습니다.

### 4.2 불변 객체 직접 만들기

```java
public final class Money {           // 1. final 클래스 (상속 차단)
    private final BigDecimal amount; // 2. 모든 필드 private final
    private final List<String> tags;

    public Money(BigDecimal amount, List<String> tags) {
        this.amount = amount;
        this.tags = List.copyOf(tags);   // 3. 방어적 복사 (생성자에서)
    }

    public List<String> getTags() {
        return tags;                     // 4. 이미 불변이라 그대로 반환 가능
    }                                    //    가변 컬렉션이면 반환할 때도 복사해야 함

    public Money add(BigDecimal v) {     // 5. setter 없음, 변경 시 새 객체 반환
        return new Money(amount.add(v), tags);
    }
}
```

Java 16+ 라면 `record`가 이걸 상당 부분 자동화해줍니다.

```java
public record Money(BigDecimal amount, List<String> tags) {
    public Money {
        tags = List.copyOf(tags);   // record도 얕은 불변이므로 컴팩트 생성자에서 방어적 복사
    }
}
```

### 4.3 왜 중요한가

- **스레드 안전**: 상태가 안 바뀌니 동기화가 필요 없습니다 ([10장](#10-동시성)에서 왜 이게 큰 이점인지 다룹니다)
- **캐시/Map 키로 안전**: `HashMap` 키로 쓴 객체의 필드가 바뀌면 해시값이 달라져 영영 못 찾게 됩니다. `String`이 키로 많이 쓰이는 이유죠
- **사이드 이펙트 방지**: 메서드에 넘긴 객체가 몰래 바뀌는 일이 없습니다

Spring에서도 이 원칙이 보입니다 — DTO를 record로 만들거나 `@Value` 같은 어노테이션으로 불변 객체를 권장하고, 생성자 주입(`private final` 필드)을 권장하는 것도 같은 맥락입니다.

## 5. 캐스팅과 다형성

### 5.1 업캐스팅 (자식 → 부모)

**명시적 캐스팅 없이 자동으로 일어납니다.**

```java
class Parent { }
class Child extends Parent { }

Parent p = new Child();            // OK — 자동 형변환
Parent p2 = (Parent) new Child();  // 가능하지만 (Parent)는 불필요
```

**이유**: `Child`는 항상 `Parent`입니다(is-a 관계). 타입 안전성이 컴파일 시점에 100% 보장됩니다.

### 5.2 다운캐스팅 (부모 → 자식)

**명시적 캐스팅이 필수이며, 런타임에 `ClassCastException` 위험이 있습니다.**

컴파일러는 "이 `Parent`가 정말 `Child`인가?"를 알 수 없습니다. 개발자가 `(Child)`로 책임지겠다고 선언하는 것이고, 그 책임이 틀리면 런타임에 터집니다.

```java
if (p instanceof Child c) {   // Java 16+ 패턴 매칭으로 안전하게
    c.onlyChild();
}
```

### 5.3 업캐스팅의 대가 — 접근 가능 범위 축소

**참조 변수의 타입이 접근 가능한 멤버를 결정합니다.**

```java
class Parent { void common() {} }
class Child extends Parent {
    void common() { }    // 오버라이딩
    void onlyChild() {}  // 자식 고유
}

Parent p = new Child();
p.common();      // OK → Child의 common() 실행 (동적 바인딩)
p.onlyChild();   // 컴파일 에러! Parent 타입엔 없는 메서드
```

- 인스턴스는 여전히 `Child`지만 **컴파일러는 `Parent`의 멤버만 보여줍니다**
- 오버라이딩된 메서드는 **런타임에 실제 객체 타입**을 따라갑니다 → 다형성의 핵심

이 성질을 활용해 `List<Parent>`에 여러 자식 타입을 담아 순회하며 같은 메서드를 호출하면 각자의 구현이 실행됩니다. 그런데 "런타임에 실제 객체 타입을 따라간다"는 게 정확히 무슨 뜻일까요? 아래에서 메모리 수준으로 파고듭니다.

### 5.4 다형성이 실제로 동작하는 방식

**타입과 실체의 분리**

```java
Payment p = new CardPayment();
//  ↑타입          ↑실체
```

힙에 올라가는 실체는 **항상 구현이 완성된 클래스**입니다. 추상 클래스·인터페이스는 그걸 가리키는 **타입(리모컨)** 역할만 합니다.

> **참고** — 추상 클래스와 인터페이스도 **메서드 영역에는 로딩됩니다.** "메모리에 못 올라간다"가 아니라 **"힙에 인스턴스가 안 생긴다"**는 뜻입니다.

**메서드 호출의 4단계**

```java
p.pay();
```

1. 스택에서 `p`의 값(힙 주소)을 읽는다
2. 힙의 그 주소로 이동한다
3. **객체 헤더의 클래스 포인터**를 따라간다 → `CardPayment`
4. `CardPayment`의 메서드 테이블에서 `pay()` 주소를 찾아 실행

**핵심은 3번.** 변수 `p`의 타입이 `Payment`인 건 상관없습니다. 실제 호출 대상은 **힙 객체가 스스로 밝히는 신분**으로 결정됩니다. → **동적 디스패치**

그럼 타입은 왜 필요한가? **컴파일러 검사용**입니다.

```java
p.pay();        // OK — Payment에 선언이 있음
p.getCardNo();  // ❌ 컴파일 에러 — Payment 명세에 없음
```

| | 담당 | 시점 |
|---|---|---|
| 타입 (`Payment`) | **무엇을 호출할 수 있는가** | 컴파일 타임 |
| 실체 (`CardPayment`) | **실제로 무엇이 실행되는가** | 런타임 |

### 5.5 필드는 다르다 — 정적 바인딩

```java
class Parent {
    int x = 10;
    void print() { System.out.println("Parent"); }
}
class Child extends Parent {
    int x = 20;
    @Override void print() { System.out.println("Child"); }
}

Parent p = new Child();
System.out.print(p.x + " ");   // 10
p.print();                      // Child
```

**출력: `10 Child`**

필드는 오버라이딩되지 않고 **가려지기만(hiding) 합니다.** 힙 객체 안에 `x`가 **물리적으로 두 개** 존재합니다.

```
힙의 Child 객체
┌──────────────────────┐
│ 헤더 (클래스 포인터 → Child) │
├──────────────────────┤
│ Parent.x = 10        │  ← offset 16
│ Child.x  = 20        │  ← offset 20
└──────────────────────┘
```

컴파일러는 `p.x`를 볼 때 **`p`의 선언 타입이 `Parent`니까 offset 16을 읽어라**로 굳혀버립니다. 런타임에 객체를 확인하지 않습니다.

> **상태(필드)는 타입을 따라가고, 행동(메서드)은 실체를 따라간다.**

**자식의 x에 접근하려면**

```java
((Child) p).x        // 20   ※ (Child) p.x 로 쓰면 여전히 10 (괄호 위치 주의)

Child c = new Child();
c.x                   // 20
```

```java
// 실무 정답 — getter로 감싸면 다형성이 정상 작동
class Parent { int x = 10; int getX() { return x; } }
class Child extends Parent { int x = 20; @Override int getX() { return x; } }

Parent p = new Child();
p.getX();            // 20
```

```java
// 클래스 내부에서
this.x               // 20 (자기 것)
super.x              // 10 (부모 것)
```

**필드 은닉은 시험엔 나오지만 코드엔 쓰면 안 됩니다.** 실무에선 필드를 하나만 두고 값만 바꿉니다.

```java
class Parent { protected int x = 10; }
class Child extends Parent { Child() { this.x = 20; } }
```

### 5.6 메서드 테이블 (vtable)

> **상수 풀 = 내가 "쓰는" 것들의 명단 (밖으로, 주소록)**
> **메서드 테이블 = 내가 "가진" 것들의 목차 (안으로)**

```
Parent 테이블            Child 테이블
  [0] print → 0xAAAA      [0] print → 0xBBBB
```

**핵심은 `print()`가 양쪽 다 0번 칸**이라는 것입니다. 자식이 오버라이딩하면 **같은 번호 칸의 주소만 갈아끼웁니다.**

그래서 JVM은:
1. 컴파일러가 정해둔 **슬롯 번호**(0번 칸)를 알아내고
2. 런타임에 객체의 클래스 포인터를 따라가 **어느 테이블인지** 결정하고
3. 그 테이블의 0번 칸을 실행합니다

> 컴파일러는 "몇 번 칸"까지, 객체는 "어느 테이블"을 결정한다.

필드는 이런 테이블이 없습니다. 객체 안 offset으로 직접 읽습니다 → 그래서 `p.x`가 `10`.

| | 상수 풀 | 메서드 테이블 |
|---|---|---|
| 내용 | 이 클래스가 **참조하는** 이름들 | 이 클래스가 **가진** 메서드 주소 |
| 방향 | 밖으로 | 안으로 |
| 위치 | 메타스페이스 | 메타스페이스 |
| 상속 시 | 각자 따로 | 부모 것 복사 후 오버라이딩분만 교체 |

## 6. 추상 클래스와 인터페이스

### 6.1 추상 클래스

```java
abstract class Payment {
    protected final int amount;

    Payment(int amount) {        // 생성자 있음!
        this.amount = amount;
    }

    abstract void pay();          // 몸통 없음 = 미구현
    void printAmount() { }        // 일반 메서드도 가능
}

class CardPayment extends Payment {
    CardPayment(int amount) { super(amount); }
    @Override void pay() { System.out.println("카드 결제"); }
}
```

```java
Payment p = new Payment(1000);      // ❌ 컴파일 에러
Payment p = new CardPayment(1000);  // ✅
```

**추상 클래스도 생성자가 있고 실제로 호출됩니다.** 다만 `Payment` 객체가 따로 생기는 게 아니라, **하나의 객체 안에 부모 필드까지 포함**되고 부모 생성자가 그 부분을 초기화합니다.

**익명 클래스** — 한 번만 쓸 때:

```java
Payment p = new Payment(1000) {
    @Override void pay() { System.out.println("일회성"); }
};
```

`new Payment()`처럼 보이지만, 컴파일하면 `Payment$1.class`라는 **이름 없는 자식 클래스**가 생깁니다. 여전히 자식을 통한 생성입니다.

### 6.2 인터페이스

```java
public interface CampService {
    int MAX = 10;                  // 자동 public static final
    void reserve();                // 자동 public abstract

    default void log() {           // Java 8+
        validate();
    }
    private void validate() { }    // Java 9+, 구현부 필수
}
```

| 종류 | 가능한 접근제어자 |
|---|---|
| 추상 메서드 | `public`만 |
| `default` / `static` | `public`만 |
| `private` 메서드 | Java 9+, 구현부 필수 |
| 필드 | `public static final`만 |

**`protected`는 어떤 경우에도 불가능합니다.**

인터페이스 필드가 `public static final`로 자동 지정되는 건 우연이 아닙니다. `javap`로 바이트코드를 보면 실제로 세 키워드가 찍혀 있습니다.

| | `static` | `final` | `public` |
|---|---|---|---|
| 이유 | 인스턴스화 불가하므로 | 규약은 바뀌면 안 되므로 | 규약은 숨길 이유가 없으므로 |

**설계 철학**: 인터페이스는 "이 타입이라면 이런 걸 할 수 있다"는 **규약**을 선언하는 곳이지 **상태(state)**를 갖는 곳이 아닙니다. 변경 가능한 필드가 있으면 구현 클래스 수십 개가 하나의 값을 공유하며 덮어쓰는 전역 변수 창고가 됩니다.

상태가 없으므로 파생되는 것들:
- 인스턴스 변수 없음 → 초기화할 상태 없음 → **생성자 불필요**
- 생성자 없음 → **`new` 불가**

예외적으로 `new`처럼 보이는 코드가 있는데, 사실은 아닙니다.

```java
Runnable r = new Runnable() {    // Runnable의 인스턴스가 아니라
    public void run() { ... }    // 익명 구현 클래스의 인스턴스
};
// 컴파일하면 Runnable$1.class 파일이 실제로 생성됨
```

### 6.3 default 메서드

Java 8 이전에는 인터페이스에 **선언만** 가능했습니다.

```java
interface Payment {
    void pay();
    void cancel();
}
```

이러면 구현체는 전부 두 개를 다 만들어야 합니다. `cancel()`이 대부분 똑같은 로직이라면? 클래스마다 같은 코드를 복붙해야 했습니다.

Java 8부터 인터페이스 안에 **몸통(body)까지 넣을 수 있게** 됐습니다.

```java
interface Payment {
    void pay();                    // 이건 구현체가 알아서

    default void cancel() {        // 이건 기본 동작 제공
        System.out.println("결제 취소 처리");
    }
}

class CardPayment implements Payment {
    @Override
    public void pay() { System.out.println("카드 결제"); }
    // cancel()은 안 만들어도 됨 — 인터페이스 것을 그대로 씀
}
```

**필요한 구현체만 골라서 덮어쓸 수도 있습니다.**

```java
class KakaoPayment implements Payment {
    @Override public void pay() { }
    @Override public void cancel() {         // 얘만 다르게 동작
        System.out.println("카카오 API로 취소 요청");
    }
}
```

**왜 만들어졌나 — 진짜 이유**는 **기존 코드를 안 깨고 인터페이스에 메서드를 추가하기 위해서**입니다.

Java 8에서 스트림이 도입될 때 `Collection` 인터페이스에 `stream()`을 추가해야 했습니다. 그냥 추가하면 전 세계의 모든 `Collection` 구현체가 **한순간에 컴파일 에러**가 납니다. 안 만든 메서드가 생겼으니까요. 그래서 `default`로 넣었습니다.

```java
interface Collection<E> {
    default Stream<E> stream() {
        return StreamSupport.stream(spliterator(), false);
    }
}
```

기존 코드는 그대로 돌아가고, 새 기능은 공짜로 얻습니다. `List.forEach()`, `Map.getOrDefault()`, `Comparator.reversed()` 전부 default 메서드입니다.

**실전에서 써먹는 방식** — 추상 메서드로 "최소한의 재료"를 요구하고, default 메서드로 "그 재료로 만들 수 있는 것들"을 제공합니다.

```java
public interface Reservable {
    LocalDate getStartDate();
    LocalDate getEndDate();

    // 아래 두 개는 위 두 개만 있으면 자동으로 계산됨
    default long getNights() {
        return ChronoUnit.DAYS.between(getStartDate(), getEndDate());
    }

    default boolean isOverlapping(Reservable other) {
        return getStartDate().isBefore(other.getEndDate())
            && other.getStartDate().isBefore(getEndDate());
    }
}
```

구현체는 날짜 두 개만 제공하면, 박 수 계산과 중복 체크는 공짜로 따라옵니다.

```java
public class CampReservation implements Reservable {
    private LocalDate startDate;
    private LocalDate endDate;

    public LocalDate getStartDate() { return startDate; }
    public LocalDate getEndDate() { return endDate; }
    // getNights(), isOverlapping()은 그냥 쓸 수 있음
}
```

**Spring에서 이미 쓰고 있는 패턴입니다.** `JpaRepository`가 내부적으로 이렇습니다.

```java
// Spring Data JPA 내부
public interface CrudRepository<T, ID> extends Repository<T, ID> {
    default Optional<T> findById(ID id) { ... }
}
```

Spring Security의 `UserDetails`도 마찬가지입니다.

```java
public interface UserDetails {
    String getUsername();
    String getPassword();

    default boolean isAccountNonExpired() { return true; }   // 대부분 true면 됨
    default boolean isAccountNonLocked() { return true; }
    default boolean isEnabled() { return true; }
}
```

원래는 이 네 개를 전부 구현해야 했는데, Spring Security 6부터 default로 바뀌어서 `getUsername()`, `getPassword()`만 만들면 됩니다.

**주의할 점 두 가지**

1. **default 메서드는 인스턴스 필드에 접근 못 합니다.** 인터페이스에 상태가 없다는 원칙은 그대로입니다. 그래서 default 메서드는 **자기가 선언한 추상 메서드(getter 같은)를 통해서만** 데이터를 얻을 수 있습니다. 위 `getNights()`가 `getStartDate()`를 호출한 게 그래서입니다.

2. **두 인터페이스에 같은 default 메서드가 있으면 충돌합니다.**

```java
interface A { default void hello() { } }
interface B { default void hello() { } }

class C implements A, B { }   // ❌ 컴파일 에러
```

이 경우 구현체가 직접 정해줘야 합니다.

```java
class C implements A, B {
    @Override
    public void hello() {
        A.super.hello();   // 명시적으로 선택
    }
}
```

다중 상속의 다이아몬드 문제가 여기서 다시 나타나는데, **자바는 "컴파일 에러를 내고 개발자에게 결정시킨다"**로 해결했습니다.

> 한 줄로 정리하면 — **default 메서드는 "구현체가 다 만들기 귀찮은 것, 혹은 대부분 똑같을 것"을 인터페이스가 미리 채워주는 장치**입니다. 상속 카드(`extends`)를 안 쓰고도 공통 로직을 나눠줄 수 있는 게 장점입니다.

### 6.4 결정적 차이 — 상태의 유무

표를 외우지 말고 **이것 하나만** 기억하면 됩니다.

> **인터페이스는 상태(인스턴스 필드)를 가질 수 없다. 추상 클래스는 가질 수 있다.**

나머지는 전부 여기서 파생됩니다.

**왜 상태를 금지했나?** 다중 구현을 허용하기 위해서입니다.

```java
interface A { int count = 0; }
interface B { int count = 0; }
class C implements A, B { }   // count가 두 개? → 다이아몬드 문제
```

상태가 없으면 이 충돌이 안 생깁니다. → 인터페이스는 여러 개 구현 가능, 클래스는 하나만 상속 가능. **생성자가 없는 이유도 같습니다** (초기화할 필드가 없으니까).

| | 추상 클래스 | 인터페이스 |
|---|---|---|
| 의미 | "~이다" (is-a) | "~할 수 있다" (can-do) |
| 인스턴스 필드 | O | X |
| 생성자 | O (단, `new`는 불가) | X |
| 개수 | `extends` 1개 | `implements` 무제한 |

```java
class CardPayment extends Payment implements Refundable, Loggable {
    // 부모는 하나, 능력은 여러 개
}
```

**"상속 카드를 소모한다"** — `extends`는 하나뿐입니다. 추상 클래스를 상속하는 순간 다른 클래스는 상속 못 합니다. 처음엔 이 설계가 멀쩡해 보입니다.

```java
abstract class Payment {
    protected final int amount;
    abstract void pay();
}

class CardPayment extends Payment { }
class KakaoPayment extends Payment { }
```

그런데 나중에 요구사항이 추가됩니다. "카드 결제는 외부 라이브러리의 `AbstractHttpClient`를 상속해야 한다"거나.

```java
class CardPayment extends Payment extends AbstractHttpClient { }  // ❌ 불가능
```

이때 선택지는 `Payment`를 포기하고 코드 중복을 감수하거나, `AbstractHttpClient`를 포기하고 위임(composition)으로 우회하거나, 상속 계층 전체를 리팩터링하는 것뿐입니다. 셋 다 아픕니다. **처음에 인터페이스로 갔으면 애초에 생기지 않았을 문제**입니다.

```java
interface Payment { void pay(); }

class CardPayment extends AbstractHttpClient implements Payment {
    // extends 자리가 비어 있었으니 자유롭게 씀
}
```

**왜 자바는 다중 상속을 금지했나** — 다이아몬드 문제 때문입니다. 부모 둘이 같은 이름의 필드나 메서드를 가지면 어느 쪽을 따라야 할지 결정할 수 없습니다. C++는 허용하지만 그만큼 복잡해졌고, 자바는 "클래스 상속은 하나, 인터페이스는 여러 개"로 타협했습니다. 인터페이스는 상태가 없으니 충돌 여지가 적으니까요.

추상 클래스가 나쁘다는 게 아니라, **비용이 있다**는 뜻입니다. 공통 필드와 템플릿 로직을 진짜로 공유해야 한다면 그 카드를 쓸 가치가 있습니다. 하지만 "그냥 공통 메서드 몇 개 묶고 싶어서"라면 인터페이스 + `default` 메서드로 충분한 경우가 많고, 그러면 카드를 아껴둘 수 있습니다.

> 실무 기본값은 **인터페이스**. 추상 클래스는 공통 상태를 진짜 공유할 때만 꺼내는 카드.
> → **"상속보다 조합(composition over inheritance)"**

### 6.5 왜 인스턴스화가 불가능한가

메서드는 결국 **실행할 코드 주소를 찾아가서 실행**하는 겁니다. 추상 메서드는 그 **주소 칸이 비어 있는 상태**입니다.

```
Payment 의 메서드 테이블
  pay()  →  (비어 있음)        ← 불완전

CardPayment 의 메서드 테이블
  pay()  →  0x7F3A            ← 완전
```

`new Payment()`가 허용되면 `p.pay()` 호출 시 **점프할 주소가 없습니다.** 그래서 컴파일 단계에서 차단합니다.

**단, 정확한 인과는 이렇습니다.**

```java
abstract class Base { void hello() { } }   // 추상 메서드 0개
new Base();     // ❌ 그래도 에러

interface Marker { }                        // 텅 빔
new Marker();   // ❌ 그래도 에러
```

진짜 이유는 "추상 메서드가 있어서"가 아니라 **`abstract` / `interface` 키워드 자체가 인스턴스화를 금지**하기 때문입니다. 추상 메서드는 그게 필요한 대표적 상황일 뿐입니다.

> 추상 메서드 개수가 강제되는 건 `@FunctionalInterface`뿐입니다(정확히 1개 → 람다 가능).
> 텅 빈 인터페이스도 정상이며, `Serializable`·`Cloneable` 같은 **마커 인터페이스**로 실제 쓰입니다.

## 7. 람다와 변수 캡처

### 7.1 핵심 규칙

> **람다 안에서 쓰는 바깥 지역 변수는 값이 바뀌면 안 된다.**

```java
void method() {
    int a = 10;
    int b = 10;
    b = 20;                          // b는 값이 바뀜

    Runnable r = () -> {
        System.out.println(a);       // OK
        System.out.println(b);       // 컴파일 에러
    };
}
```

`final` 키워드를 직접 붙일 필요는 없습니다. **안 바꾸면** 컴파일러가 알아서 통과시킵니다 → **effectively final(사실상 final)**. Java 8부터의 완화입니다.

**순서 무관**

```java
int a = 10;
Runnable r = () -> print(a);
a = 20;              // 람다보다 뒤에서 바꿔도 에러
```

컴파일러는 **메서드 전체에서 단 한 번만 값이 정해지는가**를 봅니다.

**런타임 예외가 아니라 컴파일 에러**

```
error: local variables referenced from a lambda expression
       must be final or effectively final
```

`.class` 파일 자체가 만들어지지 않습니다. 배포 후 특정 조건에서만 터지는 게 아니라 **개발 중 100% 잡힙니다** → 더 나은 설계입니다.

### 7.2 "캡처"의 정확한 정의

> 람다 **바깥쪽 메서드/블록에서 선언된 지역 변수·파라미터**를 람다 본문에서 사용하는 것

즉 **스택에 있는 변수**를 가져다 쓰는 행위입니다.

| 람다 본문에 등장하는 것 | 캡처? | effectively final 제약 |
|---|---|---|
| 람다 파라미터 `(x) -> ...` | X (자기 것) | 없음 |
| 람다 내부 선언 변수 | X (자기 것) | 없음 |
| **바깥 메서드의 지역 변수/파라미터** | **O** | **있음** |
| 인스턴스 필드 | `this`를 캡처 | 없음 |
| static 필드 | X | 없음 |

### 7.3 왜 지역 변수만 막는가

**지역 변수 = 스택 = 곧 사라짐 → 값을 복사**

```java
Runnable makeTask() {
    int local = 10;
    return () -> System.out.println(local);  // 람다를 밖으로 던짐
}                                            // ← 여기서 local 소멸
```

메서드가 끝나 `local`이 사라진 뒤 람다가 실행되면 참조할 변수가 없습니다. 그래서 자바는 **캡처 시점에 값을 복사**합니다. 위 람다는 `local`이 아니라 숫자 `10`을 들고 간 것입니다.

복사본이므로 이런 불일치가 생깁니다.

```java
int local = 10;
Runnable r = () -> System.out.println(local);  // 10을 복사해 감
local = 999;   // 원본만 바뀜
r.run();       // 10 출력 — 버그의 온상
```

→ 아예 **"복사본과 달라질 일이 없게, 바꾸지 마라"**로 못 박은 것입니다.

**필드 = 힙 = 안 사라짐 → 원본 직접 접근**

```java
class Example {
    private int field = 0;
    void method() {
        Runnable r = () -> field++;
        // 컴파일러가 보는 실제 코드: () -> this.field++;
    }
}
```

인스턴스 필드를 쓸 때 람다가 실제로 캡처하는 건 **`this`**입니다. `this`는 재할당 불가이므로 태생적으로 final → 제약이 이미 만족된 상태이고, 참조를 따라간 힙의 값은 얼마든지 바꿀 수 있습니다.

static 필드는 `this`조차 필요 없이 클래스로 직접 접근 → **캡처 개념 자체가 없습니다.**

| | 사는 곳 | 람다가 하는 일 | 결과 |
|---|---|---|---|
| 지역 변수 | 스택 (곧 사라짐) | 값을 **복사** | 원본과 어긋나니까 → 변경 금지 |
| 필드 | 힙 (안 사라짐) | 원본을 **직접 접근** | 어긋날 일 없으니까 → 변경 허용 |

### 7.4 제약은 "참조"에 걸리지 "내용물"에 걸리지 않는다

```java
List<String> list = new ArrayList<>();
Runnable r = () -> list.add("hi");   // OK! list 참조는 안 바뀜
list = new ArrayList<>();            // ← 이걸 하면 위쪽이 컴파일 에러
```

**우회 방법 (권장하지 않음)**

```java
// 1. 배열 트릭 — 참조는 고정, 내용물은 힙에 있으므로 변경 가능
int[] counter = {0};
list.forEach(x -> counter[0]++);

// 2. AtomicInteger — 스레드 안전성이 필요하면 이쪽
AtomicInteger counter2 = new AtomicInteger();
list.forEach(x -> counter2.incrementAndGet());
```

스트림에서 이런 부수효과는 안티패턴입니다. 대부분 `reduce`, `count`, `collect`로 대체 가능합니다.

### 7.5 실무 함정

**for문 종류에 따른 차이**

```java
for (int i = 0; i < 3; i++) {
    runnables.add(() -> print(i));  // 컴파일 에러! i는 계속 재할당됨
}

for (String s : list) {
    runnables.add(() -> print(s));  // OK! 매 반복마다 새 변수로 취급
}
```

**`this` 캡처로 인한 메모리 누수**

람다를 리스너나 캐시에 오래 등록해두면, 필드 하나 쓰려고 캡처한 `this` 때문에 **바깥 객체 전체가 GC되지 않습니다.**

```java
int snapshot = this.field;         // 값만 복사
Runnable r = () -> use(snapshot);  // this를 붙잡지 않음
```

**effectively final vs 인터페이스의 `public static final`** — 완전히 별개 개념입니다. "final"이라는 단어만 겹칩니다.

| | 람다의 effectively final | 인터페이스 필드의 `public static final` |
|---|---|---|
| 누가 final을 붙이나 | **아무도 안 붙임.** 여전히 일반 지역 변수 | **컴파일러가 실제로 붙임.** 바이트코드에 플래그 |
| 개발자 의무 | "바꾸지 마라" 규칙을 지켜야 함 | 없음. 애초에 바꿀 수 없게 만들어짐 |
| 이유 | 스택 변수의 복사본/원본 불일치 방지 | 인터페이스는 상태가 아닌 규약이라는 설계 철학 |
| 대상 | 메서드 안의 지역 변수 | 인터페이스 안의 필드 |
| 제약 범위 | 람다에서 쓸 때만 | 태생부터 상수 |

## 8. 제네릭

> ⚠️ 제네릭은 **Java 5(2004)** 도입입니다. "Java 8 도입"은 흔한 오류입니다. Java 8에서는 람다와 맞물린 타입 추론이 개선됐을 뿐입니다.

### 8.1 왜 생겼나

제네릭 이전:

```java
List list = new ArrayList();
list.add("사과");
list.add(3);                       // 문자열 리스트인데 숫자도 들어감
String s = (String) list.get(1);   // 런타임 ClassCastException 폭발
```

컴파일은 멀쩡히 통과 → 배포 후 터집니다.

제네릭은 상자에 **이름표**를 붙입니다.

```java
List<String> list = new ArrayList<>();
list.add(3);        // 컴파일 에러! 실행 전에 잡힘
```

→ [람다 캡처 제약](#7-람다와-변수-캡처)과 같은 철학입니다: **런타임 예외를 컴파일 에러로 앞당긴다.**

### 8.2 불공변(Invariance)

- **변(變)** = 변하다
- **공변(共變)** = 함께 변한다
- **불공변(不共變)** = 함께 변하지 **않는다**

무엇이 함께 변하느냐 = **안쪽 타입의 상속 관계**와 **바깥 상자의 상속 관계**입니다.

```
        안쪽                      바깥
   String → Object      vs    List<String> → List<Object>
   (자식)   (부모)             (자식?)        (부모?)
```

안쪽이 "자식 → 부모"로 변했을 때, 바깥도 똑같이 변하면 **공변**, 안 변하면 **불공변**입니다.

```
String 은 Object 의 자식이다              → 참
List<String> 은 List<Object> 의 자식이다  → 거짓  ← 불공변
```

`List<String>`과 `List<Object>`는 **완전히 무관한 별개의 타입**입니다.

배열과 대비하면 단어의 의미가 드러납니다.

```java
// 배열 — 공변 (함께 변함)
Object[] arr = new String[10];                 // 됨!

// 제네릭 — 불공변 (함께 안 변함)
List<Object> list = new ArrayList<String>();   // 안 됨!
```

**왜 막았나** — 허용한다고 가정하면:

```java
List<String> 문자열들 = new ArrayList<>();
문자열들.add("사과");
List<Object> 아무거나 = 문자열들;    // 가정: 이게 된다면

아무거나.add(999);                  // Object 상자니까 숫자도 OK
String s = 문자열들.get(1);          // 999를 String으로 꺼냄 → 폭발
```

```
   문자열들 ──┐
              ├──→ [ "사과", 999 ]   ← 실제 상자는 하나
   아무거나 ──┘
```

두 변수는 **같은 상자를 가리키는 다른 이름**입니다. 한쪽 문으로 이상한 값을 밀어넣으면 다른 쪽에서 터집니다. 컴파일러가 막을 방법이 없으므로 **대입 자체를 금지**했습니다.

**배열 공변은 자바 초기의 설계 실수입니다.**

```java
Object[] objects = new String[10];
objects[0] = Integer.valueOf(42);    // 컴파일 통과!
// → 런타임 ArrayStoreException
```

배열은 런타임까지 자기 타입을 기억하므로 실행 중 검사해 예외를 던집니다. 제네릭은 타입 소거로 정보가 사라져 런타임 검사가 불가능 → **컴파일 시점에 막을 수밖에 없었고, 결과적으로 더 나은 설계가 됐습니다.**

| | 배열 | 제네릭 |
|---|---|---|
| 변성 | 공변 | **불공변** |
| 타입 검사 | 런타임 | **컴파일타임** |
| 실패 방식 | `ArrayStoreException` | 컴파일 에러 |

**세 가지 변성**

| 이름 | 뜻 | 예시 |
|---|---|---|
| **공변**(共變) | 안쪽 관계가 그대로 전달 | `List<? extends Number>` |
| **반공변**(反共變) | 안쪽 관계가 **뒤집혀** 전달 | `List<? super Integer>` |
| **불공변**(不共變) | 전달 안 됨 | `List<T>` (기본) |

와일드카드는 결국 **"기본은 불공변인데, 필요할 때만 공변/반공변으로 바꿔주는 장치"**입니다.

반공변이 "뒤집힌다"는 뜻:

```java
Integer → Number                                (안쪽: Integer가 자식)
List<? super Number> → List<? super Integer>    (바깥: 방향이 반대)
```

### 8.3 타입 소거 (Type Erasure)

컴파일하면 이름표가 지워집니다.

```java
// 내가 쓴 코드                      // 컴파일 후 바이트코드
List<String> list = new ArrayList<>();   List list = new ArrayList();
String s = list.get(0);                  String s = (String) list.get(0);
                                         //          ↑ 컴파일러가 캐스팅 삽입
```

```java
// 클래스도 마찬가지
class Box<T> {                    class Box {
    T item;                           Object item;              // T → Object
    void set(T item) {...}            void set(Object item){...}
    T get() { return item; }          Object get() {...}
}                                 }
```

**증거**

```java
new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()  // true
```

**왜 지웠나** — Java 5 도입 당시 이미 제네릭 없이 짜인 코드가 산더미였습니다. 그 코드들이 계속 돌아가도록 "컴파일 후엔 옛날 코드와 같은 모습"이 되게 만든 **하위 호환성 타협**입니다.

### 8.4 T는 어디까지 쓸 수 있나

> **`T`를 "타입 이름표"로 쓰는 것은 되고, "실제 클래스"로 쓰는 것은 안 된다.**

**되는 것 — Object로 바꿔도 말이 됨**

```java
class Box<T> {
    private T item;                        → Object item;              ✅
    void set(T item) { this.item = item; } → void set(Object item)     ✅
    T get() { return item; }               → Object get()              ✅
    void print() {
        T temp = item;                     → Object temp = item;       ✅
        List<T> list = new ArrayList<>();  → List list = ...           ✅
    }
}
```

**안 되는 것 — Object로 바꾸면 의미가 망가짐**

```java
if (o instanceof T) {}      → if (o instanceof Object) {}    ❌ 항상 true
T t = new T();              → Object t = new Object();       ❌ 빈 Object
T[] arr = new T[10];        → Object[] arr = new Object[10]; ❌ 잘못된 배열
Class<T> c = T.class;       → Class c = Object.class;        ❌ 엉뚱한 클래스
```

`Box<String>`을 만들었을 때 내 의도는 "String을 만들어줘", "o가 String이냐?"인데 결과는 전혀 다릅니다. **의도와 결과가 어긋나므로 컴파일 자체를 거부합니다.**

`T`를 **택배 상자의 라벨**이라 하면, 되는 것은 "여기에 상자를 놓는다"(라벨 내용과 무관하게 자리만 있으면 됨)이고, 안 되는 것은 "라벨에 적힌 물건을 만들어와"(**라벨을 읽어야 하는데 실행 시점엔 떼여 있음**)입니다.

| 코드 | 되나? | 실행 중 T의 정체를 알아야 하나? |
|---|---|---|
| `T item;` | O | 아니오 — 변수 선언뿐 |
| `void set(T x)` | O | 아니오 — 받아서 넣기만 |
| `T get()` | O | 아니오 — 꺼내주기만 |
| `List<T> list` | O | 아니오 — 담기만 |
| `new T()` | **X** | **예** — T의 생성자를 찾아야 |
| `o instanceof T` | **X** | **예** — T와 비교해야 |
| `new T[10]` | **X** | **예** — T 배열 타입 필요 |
| `T.class` | **X** | **예** — T의 클래스 정보 필요 |

그 밖의 소거 부작용:

```java
class Box<T> {
    static T item;              // 에러 — static은 클래스당 1개인데
                                //        Box<String>과 Box<Integer>가 공유하면 T가 뭐가 되나?
}

void m(List<String> l) {}
void m(List<Integer> l) {}      // 에러: name clash (소거 후 시그니처 동일)
```

### 8.5 와일드카드와 PECS

불공변 때문에 읽기만 할 때도 못 받는 불편이 생깁니다 → `?` 도입.

**`List<?>` — 비제한 (아무거나)**

```java
List<?> list = new ArrayList<String>();
Object o = list.get(0);   // OK — 뭐가 들었든 Object인 건 확실
list.add("사과");          // 에러 — 무슨 상자인지 모르니 넣을 수 없음
list.add(null);           // 유일한 예외
```

"무슨 상자인지 모른다" = "뭘 넣어도 안전하다고 보장할 수 없다"

**`List<? extends Number>` — 상한 제한 (꺼내기 전용)**

```java
double 합계(List<? extends Number> list) {
    double sum = 0;
    for (Number n : list) sum += n.doubleValue();  // 읽기 OK
    return sum;
    // list.add(...) 불가
}
합계(List.of(1, 2, 3));      // List<Integer> OK
합계(List.of(1.5, 2.5));     // List<Double>  OK
합계(List.of("가", "나"));    // 에러
```

`Integer` 상자인지 `Double` 상자인지 모르므로 넣기 불가.

**`List<? super Integer>` — 하한 제한 (넣기 전용)**

```java
void 채우기(List<? super Integer> list) {
    list.add(1);      // OK — 넣기 가능
    // Integer로 꺼내는 건 불가 (Object로만)
}
채우기(new ArrayList<Integer>());   // OK
채우기(new ArrayList<Number>());    // OK
채우기(new ArrayList<Object>());    // OK
```

**PECS**

> **P**roducer → **E**xtends, **C**onsumer → **S**uper

- 리스트에서 **꺼내 쓸** 것(리스트가 데이터를 생산) → `extends`
- 리스트에 **넣을** 것(리스트가 데이터를 소비) → `super`
- 둘 다 필요하면 와일드카드 없이 정확한 타입

| | 읽기 | 쓰기 |
|---|---|---|
| `List<? extends Number>` | O | X |
| `List<? super Integer>` | 애매 (Object로만) | O |

### 8.6 `<T>` vs `<?>`

```java
// T: 이름이 있어서 반환 타입에서 재사용 가능
<T> T 첫번째(List<T> list) { return list.get(0); }
String s = 첫번째(List.of("가", "나"));    // 정확히 String으로 받아짐

// ?: 이름이 없어서 재사용 불가
Object 첫번째2(List<?> list) { return list.get(0); }
String s = 첫번째2(List.of("가", "나"));   // 에러, Object로만
```

| | 타입 파라미터 `<T>` | 와일드카드 `<?>` |
|---|---|---|
| 용도 | **선언**할 때 | **사용**할 때 (주로 매개변수) |
| 이름 | 있음 → 본문에서 재사용 가능 | 없음 |
| 쓰기 | 가능 | `<? extends>`는 불가 |

```java
<T> void copy(List<T> dst, List<? extends T> src) { }
//  ↑선언          ↑사용         ↑사용
```

`T`는 이름이 있어 "dst와 src의 타입이 서로 연결돼 있다"를 표현할 수 있습니다. 와일드카드는 이런 **관계 표현**을 못 합니다.

> **여러 자리의 타입을 서로 묶어야 하면 `T`, 유연하게 받기만 하면 `?`**

### 8.7 제네릭 문법 정리

```java
// 제네릭 메서드 — 메서드 단위 타입 파라미터
static <T> void swap(T[] arr, int i, int j) {
    T tmp = arr[i]; arr[i] = arr[j]; arr[j] = tmp;
}

// 제한된 타입 파라미터
class NumBox<T extends Number> {
    T value;
    double twice() { return value.doubleValue() * 2; }  // Number 메서드 사용 가능
}

// 다중 제한 (클래스 1개, 인터페이스 여러 개)
<T extends Number & Comparable<T>> void sort(List<T> list) { }
```

**관례적 이름**: `T`(Type), `E`(Element), `K`/`V`(Key/Value), `R`(Result), `N`(Number)

## 9. 클래스 로딩과 상수 풀

### 9.1 상수 풀 = 중복을 없앤 "목록 페이지"

같은 글자가 반복되면 낭비입니다. 그래서 **글자를 한 곳에 모으고 번호를 붙입니다.**

```java
// Camp.java
public class Camp {
    static final int MAX = 100;
    void open()  { System.out.println("열림"); }
    void close() { }
}
```

```
[목록 페이지 = 상수 풀]
#1  "Camp"
#2  "open"
#3  "close"
#4  Methodref → #1.#2      (Camp의 open)
#5  Methodref → #1.#3      (Camp의 close)
#6  100
#7  "camping"

[명령어 페이지 = 바이트코드]
invokevirtual #4     ← "4번 항목 보고 실행해"
```

**별거 아닙니다. 중복 제거용 색인표입니다.**

### 9.2 같은 목록, 사는 곳이 3군데

| | 위치 | 개수 | 정체 |
|---|---|---|---|
| 클래스 파일 상수 풀 | `.class` 파일 (디스크) | 클래스마다 | 아직 파일일 뿐 |
| **런타임 상수 풀** | 메타스페이스 | **클래스마다 하나** | 메모리에 올라온 목록표 |
| **String Constant Pool** | **힙** | **JVM 전체에 하나** | 실제 `String` **객체 창고** |

**런타임 상수 풀 ≠ String Pool.** 하나는 **목록표**, 하나는 **객체 창고**입니다.

관계는 이렇습니다.

```
Main의 목록표   #7 ─┐
                    ├→ 힙 String Pool의 "camping" 객체 (딱 1개)
Camp의 목록표   #3 ─┘
```

### 9.3 로딩 후 항목마다 운명이 다르다

전부 주소로 바뀌는 게 **아닙니다.**

```
클래스 파일 상수 풀        →   런타임 상수 풀 (로딩 후)
#1 "Camp"                     #1 "Camp"          글자 그대로
#4 Methodref → #1.#2          #4 → 0x7F3A        주소로 교체  ✅
#6 100                        #6 100             바꿀 게 없음  ❌
#7 "camping"                  #7 → 힙 객체 주소   힙을 가리킴  ✅
```

**한꺼번에 바뀌지 않습니다.** `#4`를 **처음 실제로 호출할 때** 그 항목만 주소로 바뀝니다(lazy resolution). 안 쓰는 항목은 영영 이름인 채로 남습니다.

세 개념의 결정적 차이를 아래 예로 확인해봅시다.

```java
// Camp.java
public class Camp {
    static final int MAX = 100;
    void open() { System.out.println("열림"); }
}

// Main.java
public class Main {
    public static void main(String[] args) {
        Camp c = new Camp();
        c.open();
        System.out.println(Camp.MAX);
        String s = "camping";
    }
}
```

**`Main.class` 안에 무엇이 남는가:**

| 소스 코드 | Main.class에 남는 것 | 정체 |
|---|---|---|
| `new Camp()` | `"Camp"` 라는 **이름 글자** | 심볼릭 레퍼런스 |
| `c.open()` | `"Camp.open()"` 라는 **이름 글자** | 심볼릭 레퍼런스 |
| `Camp.MAX` | 숫자 `100` | 컴파일 타임 상수 (인라인) |
| `"camping"` | 글자 `camping` | 리터럴 |

**심볼릭 레퍼런스 — 이름을 남기고, 런타임에 찾아간다**

`Main.class`에는 `Camp`의 주소가 없습니다. `"Camp"`, `"open"`이라는 **글자**만 있습니다. 실행할 때 JVM이 그 이름으로 찾아서 주소로 바꿉니다(**Resolution**).

`symbolic` = 기호로, 즉 **주소 대신 이름으로**.

| 종류 | 담는 정보 |
|---|---|
| `Class` | 클래스 이름 |
| `Fieldref` | 클래스 + 필드명 + 타입 |
| `Methodref` | 클래스 + 메서드명 + 시그니처 |

**왜 이렇게?** 클래스를 따로따로 컴파일해도 나중에 연결되게 하려고입니다. `Camp`를 수정해 재컴파일해도 `Main`은 그대로 둘 수 있습니다.

**대가:**

```
NoClassDefFoundError: Camp        ← Camp.class를 지우고 Main 실행하면
NoSuchMethodError: Camp.open()    ← 라이브러리 버전 올렸는데 시그니처가 바뀌면
```

컴파일 에러가 아니라 **런타임 에러**인 게 핵심입니다.

**컴파일 타임 상수 — 이름을 안 남기고, 값을 복사한다**

`MAX`는 `static final int`, 절대 안 바뀌는 숫자입니다. 컴파일러가 값을 알고 있으니 **그냥 써버립니다.**

```
bipush 100        ← Camp를 참조하지 않음. 100이 복사됨
```

`Main.class` 어디를 뒤져도 `"MAX"`라는 글자가 없습니다.

**유명한 함정** — `MAX = 200`으로 고치고 `Camp.java`만 재컴파일하면, `Main`은 여전히 `100`을 출력합니다. 값이 이미 복사됐으니까요. → 상수 바꿨는데 반영이 안 되면 **클린 빌드**.

**인라인 조건 (전부 만족해야 함)**
- `static final`이고
- 타입이 **원시 타입 또는 String**이고
- 초기값이 **컴파일 타임에 계산 가능**

```java
static final int MAX = 100;              // ✅ 인라인
static final int CALC = 10 * 20;         // ✅ 인라인 (컴파일러가 200 계산)
static final String NAME = "camp";       // ✅ 인라인

static final int SIZE = compute();       // ❌ Fieldref (getstatic으로 매번 조회)
static final List<String> L = List.of(); // ❌ 참조 타입 → Fieldref
static final Logger log = getLogger();   // ❌ Fieldref
```

**리터럴 — 글자를 남기고, 런타임에 객체가 된다**

`.class` 파일에는 **객체를 저장할 수 없습니다.** 객체는 실행 중 힙에 만들어지니까요. 그래서 파일에는 **재료(글자)만** 저장하고, 실행할 때 JVM이 `String` 객체를 만듭니다.

| 단계 | `"camping"`의 정체 |
|---|---|
| 소스 코드 | 문법 요소인 리터럴 |
| `.class` 파일 | UTF-8 바이트열. **아직 객체 아님** |
| 첫 실행 시점 | String Pool에 `String` 객체 생성 |
| 그 이후 | 이미 만들어진 객체의 **참조** |

평가되고 나면 객체이므로 메서드 호출이 됩니다.

```java
"camping".length();        // 6
"camping".equals(name);    // NPE 방지 패턴
```

**String만 그렇습니다.** `int x = 100;`의 `100`은 원시값이고 String Pool과 무관합니다.

### 9.4 다시 `==`로 — 이제 완전히 설명된다

```java
String a = "camping";              // 창고에서 꺼냄
String b = "camping";              // 창고에 이미 있음 → 같은 객체
String c = new String("camping");  // new는 창고 무시, 새로 생성

a == b            // true
a == c            // false
c.intern() == a   // true  — 풀에 있는 객체 참조를 반환
```

`new`는 **"창고에 있든 말든 새로 만들어라"**는 명령이라 항상 별개 객체입니다. ([3.1](#3-값과-참조-string으로-배우기)에서 봤던 결과가 왜 그렇게 나오는지 이제 근거가 확실해졌습니다.)

### 9.5 왜 String Pool만 힙으로 옮겼나

Java 6까지 String Pool은 PermGen(메서드 영역)에 있었습니다. PermGen은 크기가 고정이고 GC가 거의 안 돌아서:

```
java.lang.OutOfMemoryError: PermGen space
```

- **Java 7** — String Pool을 힙으로 이동 → GC 대상이 됨
- **Java 8** — PermGen 폐지, 메타스페이스(네이티브 메모리)로 대체
- `static` 필드 값도 힙으로 이동 ([2.3](#2-메모리-구조)과 같은 흐름입니다)

## 10. 동시성

### 10.1 문제의 근원

**프로세스** = 실행 중인 프로그램. 독립된 메모리.
**스레드** = 프로세스 내 실행 흐름. **메모리(힙)를 공유.**

```
[프로세스]
 ├─ Heap, Method Area          ← 모든 스레드 공유 (문제의 근원)
 ├─ 스레드1: Stack, PC 레지스터  ← 각자 따로
 ├─ 스레드2: Stack, PC 레지스터
 └─ 스레드3: Stack, PC 레지스터
```

[2장](#2-메모리-구조)의 스택/힙 구분이 그대로 적용됩니다. **지역 변수는 스택 = 스레드마다 따로 = 안전**, **필드는 힙 = 공유 = 위험**.

### 10.2 Race Condition (경쟁 상태)

```java
class Counter {
    int count = 0;              // 인스턴스 변수 (힙)
    void increment() { count++; }
}
```

`count++`는 한 줄처럼 보이지만 **세 단계**입니다.

```
1. count 값을 읽는다   (read)
2. 1을 더한다          (modify)
3. count에 다시 쓴다   (write)
```

```
시간  스레드 A        스레드 B      count 실제값
 1    읽음 (0)                          0
 2                    읽음 (0)          0    ← A가 아직 안 씀
 3    +1 계산 (1)                       0
 4                    +1 계산 (1)       0
 5    씀 (1)                            1
 6                    씀 (1)            1    ← 덮어씀!
```

**두 번 더했는데 1이 됐습니다.** 원인은 `count++`가 **원자적(atomic)이지 않기** 때문입니다. (원자적 = 중간에 끼어들 수 없는 하나의 덩어리)

**위험의 판단 기준**은 `static`이냐가 아니라 **여러 스레드가 같은 객체에 접근하느냐**입니다.

```java
Counter c = new Counter();
new Thread(() -> c.increment()).start();      // 같은 c → 위험
new Thread(() -> c.increment()).start();

new Thread(() -> new Counter().increment()).start();  // 각자 다른 객체 → 안전
new Thread(() -> new Counter().increment()).start();
```

| | 개수 | 스레드 안전성 |
|---|---|---|
| 클래스 변수 | 항상 1개 | 공유가 강제됨 → **항상 동기화 필요** |
| 인스턴스 변수 | 객체마다 1개 | 객체를 공유할 때만 위험 |
| 지역 변수 | 호출마다 1개 | **항상 안전** (스택이 스레드마다 따로) |

**실전 함정 — Spring 싱글톤**

**Spring 빈은 기본이 싱글톤**이라 객체가 하나뿐이고 모든 요청 스레드가 공유합니다.

```java
@Service
public class ReservationService {
    private int count = 0;        // 위험! 인스턴스 변수인데 사실상 공유됨
    public void reserve() { count++; }   // Race Condition
}
```

→ **Spring 빈에는 상태(가변 필드)를 두지 않는 것이 원칙입니다.** 필요한 값은 지역 변수나 파라미터로 넘기세요. ([4장](#4-자바의-불변-객체)에서 본 불변 객체 선호 원칙과 같은 이유입니다.)

### 10.3 동기화 도구

**`synchronized` — 모니터 락**

모든 자바 객체는 자물쇠를 하나씩 갖고 태어납니다. `synchronized` 진입 시 획득, 탈출 시 반납. 못 얻은 스레드는 **BLOCKED 상태로 대기**합니다.

```java
synchronized void m() { ... }              // this의 락
static synchronized void s() { ... }       // 클래스 객체의 락

void m() {
    // 락 없이 할 수 있는 일
    synchronized (this) {
        count++;                           // 여기만 보호 (더 효율적)
    }
}
```

락으로 보호되는 구간 = **임계 영역(Critical Section)**

**`volatile` — 가시성 문제**

```java
class Flag {
    boolean running = true;
    void stop() { running = false; }
    void loop() { while (running) { ... } }   // 영원히 안 멈출 수 있음!
}
```

CPU마다 캐시가 있어 A가 `false`로 바꿔도 B는 **자기 캐시의 옛날 값**을 계속 볼 수 있습니다 → **가시성(Visibility)** 문제.

```java
volatile boolean running = true;   // 항상 메인 메모리에서 읽고 씀
```

| | 해결하는 문제 |
|---|---|
| `volatile` | **가시성**만 |
| `synchronized` | **가시성 + 원자성** |

> `volatile`은 원자성을 보장하지 않으므로 `count++` 문제는 못 고칩니다. 흔한 착각입니다.

**Atomic 클래스 — 락 없는 원자성**

```java
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();     // 원자적으로 +1
```

내부적으로 **CAS(Compare-And-Swap)** CPU 명령을 사용합니다. "값이 아직 0이면 1로 바꿔라, 아니면 실패"를 하드웨어 수준에서 원자적으로 수행하고 실패 시 재시도합니다. 락이 없어 훨씬 빠릅니다.

**이 CAS가 곧 낙관적 락의 원리입니다.**

### 10.4 데드락 (Deadlock)

> **두 개 이상의 스레드가 서로가 가진 자원을 기다리며 영원히 멈춘 상태**

```java
// 스레드1                      // 스레드2
synchronized (A) {              synchronized (B) {
    Thread.sleep(100);              Thread.sleep(100);
    synchronized (B) { ... }        synchronized (A) { ... }
}                               }
```

```
스레드1: [A 보유] ──기다림──→ B (스레드2 보유)
스레드2: [B 보유] ──기다림──→ A (스레드1 보유)
```

순환이 생겨 둘 다 영원히 멈춥니다.

**발생 조건 4가지 (모두 만족해야 발생)**

| 조건 | 뜻 |
|---|---|
| **상호 배제** | 한 자원은 한 번에 한 스레드만 |
| **점유와 대기** | 자원을 쥔 채 다른 자원을 기다림 |
| **비선점** | 남의 자원을 강제로 뺏을 수 없음 |
| **순환 대기** | 대기 관계가 원을 그림 |

**하나만 깨도 데드락은 안 생깁니다.**

**해결 ① 순환 대기 제거 (가장 실용적)**

```java
// 모든 스레드가 항상 A → B 순서로만 락을 잡는다
synchronized (A) {
    synchronized (B) { ... }
}
```

계좌 이체처럼 두 자원을 잡아야 하면 **계좌번호 순으로 정렬해서 잠급니다.**

**해결 ② 타임아웃**

```java
ReentrantLock lock = new ReentrantLock();
if (lock.tryLock(1, TimeUnit.SECONDS)) {   // 1초 못 얻으면 포기
    try { ... } finally { lock.unlock(); }
}
```

`synchronized`는 포기가 불가능하지만 `ReentrantLock`은 가능합니다.

### 10.5 비관적 락 vs 낙관적 락

> 데드락과는 **다른 층위**의 개념입니다. 데드락은 "락을 쓰다 생기는 사고", 비관적/낙관적은 "동시성을 다루는 두 전략"입니다. 주로 **DB 레벨**에서 논의됩니다.

**비관적 락 (Pessimistic Lock)** — "충돌이 **자주 날 거야**" → **미리 잠근다**

```sql
SELECT * FROM product WHERE id = 1 FOR UPDATE;   -- 행에 락
UPDATE product SET stock = stock - 1 WHERE id = 1;
COMMIT;                                           -- 락 해제
```

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Product p WHERE p.id = :id")
Product findByIdForUpdate(@Param("id") Long id);
```

`synchronized`와 본질적으로 같습니다 — 자물쇠를 채우고 들어갑니다.

**낙관적 락 (Optimistic Lock)** — "충돌이 **잘 안 날 거야**" → **잠그지 않고, 저장할 때 검증**

```java
@Entity
class Product {
    @Id Long id;
    int stock;
    @Version int version;    // 핵심
}
```

```
1. 조회:  id=1, stock=10, version=3
2. 수정:  stock = 9
3. 저장:  UPDATE product SET stock=9, version=4
          WHERE id=1 AND version=3      ← 버전이 아직 3일 때만
```

그 사이 다른 트랜잭션이 먼저 커밋했다면 version이 이미 4 → `WHERE version=3`에 걸리는 행이 없어 **0건 수정** → `OptimisticLockException`.

**CAS와 완전히 같은 원리**: "내가 읽은 값이 그대로면 바꾸고, 아니면 실패."

| | 비관적 락 | 낙관적 락 |
|---|---|---|
| 가정 | 충돌이 잦다 | 충돌이 드물다 |
| 방식 | 미리 잠금 | 안 잠그고 나중에 검증 |
| 구현 | DB `FOR UPDATE` | `@Version` 컬럼 |
| 충돌 시 | 대기 | 예외 → **재시도** |
| 데드락 | **가능** | **불가능** (락이 없으므로) |
| 성능 | 대기 비용 | 재시도 비용 |
| 적합 | 재고 차감, 좌석 예약 | 게시글 수정, 프로필 변경 |

**판단 기준**: 충돌이 실제로 잦으면 비관적(재시도 폭풍이 더 비쌈), 드물면 낙관적(불필요한 대기 회피).

### 10.6 동기 vs 비동기

> 락과는 **다른 축**입니다. **"결과를 기다리느냐"**의 문제입니다.

```java
// 동기 — 끝날 때까지 멈춰서 기다림
String result = api.call();
System.out.println(result);

// 비동기 — 요청만 하고 다음 일 진행
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> api.call());
System.out.println("다른 일 하는 중");
String result = future.get();    // 필요할 때 결과 수령
```

| | 동기 | 비동기 |
|---|---|---|
| 결과 | 호출한 쪽이 즉시 받음 | 나중에 콜백/Future로 |
| 흐름 | 순차적 | 병렬 가능 |

**블로킹/논블로킹과 혼동 주의**

- 동기/비동기 = **결과를 언제 받나**
- 블로킹/논블로킹 = **기다리는 동안 스레드를 붙잡고 있나**

자주 같이 다니지만 같은 말이 아닙니다.

## 11. 부록 A. 자주 틀리는 포인트

- [ ] 문자열 비교에 `==` → **`equals()`**
- [ ] 반복문 안 `+=` → **`StringBuilder`**
- [ ] `BigDecimal`·`LocalDate` 메서드 호출 후 **재할당 안 함**
- [ ] `(Child) p.x` → **`((Child) p).x`**
- [ ] 필드 은닉으로 다형성 기대 → **getter로 감싸기**
- [ ] `Collections.unmodifiableList()`는 원본 수정이 반영되는 **뷰** → 진짜 불변은 `List.copyOf()`
- [ ] `record`는 **얕은 불변** → 가변 필드는 컴팩트 생성자에서 복사
- [ ] 상수 고쳤는데 반영 안 됨 → **클린 빌드** (인라인 때문)
- [ ] 추상 메서드가 0개여도 **인스턴스화는 불가능**
- [ ] 제네릭은 **Java 5** 도입 (Java 8 아님)
- [ ] `volatile`은 **가시성만** 보장, 원자성은 못 고침 (`count++`엔 무력)
- [ ] `List<Object>` 자리에 `List<String>` 대입 불가 — **불공변**

**직접 확인해보기**

```bash
javap -c -p -constants Camp.class
```

`ldc`, `getstatic`, `invokevirtual` 옆의 `#숫자`가 전부 상수 풀 인덱스입니다. 개념으로만 읽는 것보다 한 번 찍어보는 게 훨씬 빠릅니다.

## 12. 부록 B. 전체 요약표

**무엇이 어디에 있나**

| 항목 | 위치 |
|---|---|
| 지역 변수, 참조값 | 스택 (스레드마다 따로) |
| 객체, 인스턴스 필드 값 | 힙 (GC 대상) |
| `static` 필드 값 (Java 8+) | 힙 (`Class` 객체 안) |
| **String Constant Pool** (Java 7+) | **힙** |
| 필드 목록, 메서드 바이트코드 | 메서드 영역 (Java 8+: 메타스페이스) |
| 메서드 테이블 (vtable) | 메서드 영역 |
| **런타임 상수 풀** | 메서드 영역 |

**컴파일 타임 vs 런타임**

| 컴파일 타임에 결정 | 런타임에 결정 |
|---|---|
| 필드 접근 (`p.x`) | 메서드 호출 (`p.print()`) |
| `static` 메서드 | 오버라이딩된 메서드 |
| 오버로딩 선택 | 오버라이딩 선택 |
| 컴파일 타임 상수 값 | 심볼릭 레퍼런스 해석 |

**객체지향**

| 개념 | 한 줄 |
|---|---|
| 업캐스팅 | 자식→부모. 자동. 안전 |
| 다운캐스팅 | 부모→자식. 명시적 필수. `ClassCastException` 위험 |
| 동적 바인딩 | 참조 변수 타입이 접근 범위를 정하고, 오버라이딩은 실제 객체를 따라감 |
| 인터페이스 | 상태 없음 → 필드는 자동 `public static final`, 생성자·`new` 불가, 다중 구현 가능 |
| 추상 클래스 | 상태 있음 → 생성자 있음(`new`는 불가), 단일 상속 |

**람다**

| 개념 | 한 줄 |
|---|---|
| 캡처 | 바깥 메서드의 지역 변수/파라미터를 람다에서 사용하는 것 |
| effectively final | 캡처된 지역 변수는 재할당 금지. 위반 시 **컴파일 에러** |
| 왜? | 지역 변수는 스택에 있어 값이 복사되므로 원본과 어긋남 |
| 필드는 예외 | `this`(또는 클래스)를 통해 힙의 원본을 직접 접근하므로 |
| 제약 범위 | 참조에만 걸림. 객체 내용물은 변경 가능 (`int[]` 트릭) |

**제네릭**

| 개념 | 한 줄 |
|---|---|
| 목적 | 런타임 `ClassCastException`을 컴파일 에러로 앞당김 |
| 불공변 | 안쪽 상속 관계가 바깥 상자로 전달되지 **않음** |
| 왜 불공변? | 허용하면 다른 이름으로 이상한 값을 넣을 수 있어서 |
| 배열 vs 제네릭 | 배열은 공변(런타임 예외), 제네릭은 불공변(컴파일 에러) |
| 타입 소거 | 컴파일 후 `T`가 `Object`로 치환됨. 하위 호환성 목적 |
| T 사용 가능 범위 | 타입 자리엔 자유. `new T()`, `instanceof T`, `new T[]`, `T.class`는 불가 |
| `? extends` | 꺼내기 전용 (공변) |
| `? super` | 넣기 전용 (반공변) |
| PECS | Producer-Extends, Consumer-Super |
| T vs ? | 여러 자리의 타입을 묶어야 하면 `T` |

**동시성**

| 개념 | 한 줄 |
|---|---|
| Race Condition | 여러 스레드가 공유 데이터를 동시에 건드려 값이 깨짐 |
| 임계 영역 | 한 번에 한 스레드만 들어가야 하는 구간 |
| `synchronized` | 모니터 락으로 임계 영역 보호 (원자성 + 가시성) |
| `volatile` | 메인 메모리 직접 사용 (가시성만, 원자성 X) |
| CAS | "읽은 값 그대로면 바꾸고 아니면 재시도"의 CPU 명령 |
| 데드락 | 서로의 자원을 기다리며 영구 정지. 4조건 중 하나만 깨면 방지 |
| 비관적 락 | 미리 잠금. 충돌이 잦을 때 |
| 낙관적 락 | `@Version` 검증 후 실패 시 재시도. 충돌이 드물 때 |
| 동기/비동기 | 결과를 언제 받나 |
| 블로킹/논블로킹 | 기다리는 동안 스레드를 붙잡나 |
