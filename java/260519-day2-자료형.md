<< 파이썬과 자바의 차이>>
자바는 빌드타임과 실행타임 (런타임) 이 분리됨

그러나 파이썬은 별도의 빌드 단계없이 파이썬 인터프리터가 바로 한줄씩 실행함
빌드 동시에 실행
오류가 그 줄에 도달해야 터짐

컴파일러가 하는 일은 보통 이렇게 단계별로 나뉘는데, 타입체크랑 바이트코드 변환 말고도 이런 것들이 있어:

**1. 어휘 분석 (Lexical Analysis / Tokenizing)**
소스코드를 토큰(token) 단위로 쪼개는 단계. `int x = 10;` → `int`, `x`, `=`, `10`, `;` 이런 식으로 나눔.

**2. 구문 분석 (Parsing / Syntax Analysis)**
토큰들을 문법 규칙에 맞게 트리 구조(AST, 추상 구문 트리)로 만드는 단계. 문법 오류(괄호 안 닫음, 세미콜론 빠짐 등)를 여기서 잡아냄.

**3. 의미 분석 (Semantic Analysis)**
타입체크가 여기 포함되는데, 그 외에도:

- 변수가 선언되기 전에 쓰였는지 체크
- 메서드 오버로딩이 모호하지 않은지 체크
- final 변수에 재할당 시도했는지 체크
- 접근 제어자(private/public) 위반 체크

**4. 최적화 (Optimization)**

- 안 쓰는 코드 제거 (dead code elimination)
- 상수 폴딩 (`1 + 2`를 컴파일 시점에 `3`으로 미리 계산)
- 단, javac은 최적화를 거의 안 하고 대부분 JIT(런타임)에서 함

**5. 코드 생성 (Code Generation)**
바이트코드로 변환하는 단계.

**6. 심볼 테이블 관리**
컴파일 전 과정에서 변수명, 메서드명, 클래스명 등을 심볼 테이블에 등록하고 추적함. 같은 이름이 여러 스코프에 있을 때 어떤 걸 가리키는지 결정하는 데 씀.

## 자바 기준으로 한 줄 요약하면: **소스코드 → 토큰화 → AST 생성 → 의미분석(타입체크 포함) → 바이트코드 생성** 순서로 진행돼.

public class

각 단어의 첫글자만 대문자를 쓰는 방식
PascalCase: 첫글자가 대문자인 경우
camelCase: 첫글자가 소문자인 경우 (중간에 톡 튀어나온 낙타등처럼)

kebab-case: 하이픈으로 연결하는 경우 (java에서는 지원하지 않음) (꼬치구이처럼 생겨서)
snake_case: 언더바로 연결하는 경우 (바닥에 기어가는 뱀처럼 생겨서)

1.  기본 타입

    비객체타입
    실제 값을 스택 메모리에 저장하는 방식

    기본 타입의 종류
    = 4가지
    = 논리, 정수, 실수, 문자
    => boolean / byte(127까지), short, int(21억까지), long(922경)/ double float / char
    byte 크기: - / 1 2 4 8 / 4 8 / 2

        - 논리 타입이 정해진 바이트 크기를 갖지 않는 이유
        1비트면 충분한데 CPU가 비트 단위로 못 읽으니까,
        크기를 애매하게 두고 JVM한테 위임한 것!
        ----------------------------------------------
        - char 문자형 타입은 한글자

ram = 메모리 = 바이트 단위로 저장됨

타입의 표현 범위를 넘어가는 값을 저장하려고 하면 overflow 발생
= 최솟값으로 돌아가는 현상
= 제대로 저장되지 않음
ex) byte a = 128을 저장하려고 하면 byte가 -128~127범위 이므로 가장 작은 -128로 회귀함

double 대신 float를 쓸 이유가 없음..!

각 자료형 타입이 사용할 수 있는 최댓값은 코드를 통해 확인가능
.MAX_VALUE

long 변수 선언시 int 범위를 벗어날 경우에만 L 붙여주기
