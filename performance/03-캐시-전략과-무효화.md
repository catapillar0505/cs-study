# 캐시 전략과 무효화

> 한 줄 요약
> **"이 값이 얼마나 틀려도 되는가"와 "계산이 얼마나 비싼가"를 같이 보고 정한다.**

## TTL을 하나로 두지 않는다

집계 대시보드처럼 여러 지표가 한 화면에 있으면, 지표마다 **허용 오차와 계산 비용이 다르다.** 전부 같은 TTL을 걸 이유가 없다.

| 지표 성격 | TTL 예 | 근거 |
|---|---|---|
| 정산·결제 관련 | 1분 | 틀리면 안 되지만 1분은 견딜 수 있음 |
| 입장·예약 현황 | 3분 | 실시간성이 중요하나 정산만큼 민감하지 않음 |
| 여러 테이블을 묶는 무거운 집계 | 10분 | 자주 안 바뀌는데 계산 비용이 큼 |

**"캐시를 걸까 말까"가 아니라 "얼마나 오래 둘까"를 지표마다 정하는 것**이다.

## 무효화 — 지우는 것보다 안 쓰게 만드는 쪽이 확실하다

집계 로직을 고쳐 배포했는데 화면에는 예전 숫자가 계속 나오는 일이 흔하다. 캐시에 옛 결과가 남아 있기 때문이다.

**해당 키를 찾아 지우는 방식은 위험하다.** 지울 대상이 여럿이면 하나 빠뜨리기 쉽고, **빠뜨린 것은 티도 나지 않는다.**

**키 이름에 버전을 붙이는 방식**이 확실하다.

```
stats:entry:v6:{eventId}
             ↑ 계산 방식이 바뀌면 번호를 올린다
```

이름 자체가 달라지므로 **예전 캐시는 아무도 찾지 않게 되고, 배포하는 순간 새로 계산된다.** 지울 필요가 없다. (옛 키는 TTL로 알아서 사라진다.)

## 키 생성은 한 곳에 모은다

조회·갱신·삭제 세 군데에 같은 키 문자열을 각각 적어두면, 키 이름을 고칠 때 **한 곳을 빠뜨리는 순간 그 코드는 에러 없이 엉뚱한 키를 지운다.** 동작은 하는데 아무것도 안 지우는 상태가 되고, 발견이 매우 늦다.

```java
// 키를 만드는 방법을 한 곳에 모으고 모든 곳이 이것을 부른다
private String statsKey(Long eventId) {
    return "stats:entry:v6:" + eventId;
}
```

> **같은 값이 여러 군데 적혀 있으면 언젠가 어긋난다.** 포트 번호, 경로, 키 이름 모두 같은 종류의 문제다.

## 캐시는 없어도 되는 것이다

캐시에서 꺼낸 값이 기대한 형태가 아니면 **붙들고 고치려 하지 말고 캐시가 없는 것으로 치고 원본을 읽는다.**

특히 객체를 직렬화해 저장하는 캐시는, **역직렬화할 때 원래 타입 정보가 온전히 남지 않아 일반 맵으로 복원되는 경우**가 있다. 이 버그는 **캐시가 맞았을 때만 터지고 캐시가 비면 멀쩡해서** 재현이 어렵다.

```java
Object cached = cache.get(key);
if (!(cached instanceof StatsDto dto)) {
    return loadFromDb(eventId);   // 이상하면 버리고 원본
}
```

## 공유 캐시를 손댈 때

여러 서비스가 같은 Redis를 공유하면 **키를 지우는 순간 남의 작업에도 영향이 간다.** 기술적으로는 명령 하나지만 **공유 자원이라 절차(공지·범위 한정)가 필요하다.** `KEYS *` 대신 `SCAN`을 쓰고, 접두사로 범위를 좁힌다.
