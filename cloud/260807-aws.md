# 시작하기 전에

## 0. 클라우드 5계층 — 전체 지도

> **한 줄 요약**
> 클라우드가 만들어지는 과정을 **아래에서 위로 5단계**로 쪼갠 것. 아래층이 있어야 위층이 존재한다.

### 아파트로 보면

```
5. 서비스 계층      🏠 세입자가 실제로 쓰는 집 + 입주 신청 앱
        ↑
4. 서비스 관리체계   👮 관리사무소 (관리비, 고장 신고, 보안)
        ↑
3. 프로비저닝       🔑 계약하면 열쇠 주고 입주시키기
        ↑
2. 가상화          🧱 칸막이로 세대 나누기
        ↑
1. 물리적 시스템     🏢 건물, 땅, 전기
```

### 한 줄씩

| 계층 | 한 줄 설명 | AWS 예시 |
|---|---|---|
| **1. 물리적 시스템** | 진짜 **쇳덩이**. 서버, 저장장치, 네트워크 장비, 건물 | 데이터센터, 물리 서버 |
| **2. 가상화** | 그 쇳덩이를 **칸막이로 쪼갬** | Nitro 하이퍼바이저 |
| **3. 프로비저닝** | 필요한 만큼 **자동으로 만들어서 건네줌** | 버튼 누르면 EC2 생성, Auto Scaling |
| **4. 서비스 관리체계** | **감시하고 요금 매기고 지켜줌** | CloudWatch, IAM, 요금 청구 |
| **5. 서비스 계층** | 사용자가 **실제로 만나는 화면과 기능** | EC2·S3·RDS 콘솔, API |

### 각 층의 핵심 질문

| 계층 | 질문 |
|---|---|
| 1. 물리 | **뭘로 만드나?** → 쇳덩이 |
| 2. 가상화 | **어떻게 쪼개나?** → 하이퍼바이저 |
| 3. 프로비저닝 | **어떻게 나눠주나?** → 자동 생성 |
| 4. 관리체계 | **어떻게 관리하나?** → 감시·과금·보안 |
| 5. 서비스 | **뭘 쓰나?** → IaaS / PaaS / SaaS |

### 가장 헷갈리는 3번

**프로비저닝 = "준비해서 건네주는 것"** 입니다.

2번(가상화)이 칸막이를 세우는 것이라면, 3번은 **"302호를 김철수 씨에게 배정하고 열쇠를 주는 것"** 이에요.

옛날엔 서버 한 대 받는 데 몇 주가 걸렸지만 지금은 몇 분이면 끝나는데, **그 자동화를 담당하는 층**입니다.

> 💡 이 문서의 Part 2~6은 주로 **5번(서비스 계층)에서 네트워크를 다루는 법**,
> Part 7은 **2번(가상화)의 원리**를 설명합니다.

# Part 1. 주소의 기초

## 1. IP 주소와 CIDR

> **한 줄 요약**
> `/24` 같은 표기는 **주소 하나가 아니라 주소의 "범위"** 를 뜻한다.

### 비유

전화번호로 생각해보세요.

- `010-1234-5678` → 한 사람
- `010-1234-****` → 만 명 (뒤 네 자리는 아무거나)
- `010-****-****` → 전부

CIDR도 똑같아요. **뒤쪽을 얼마나 열어두느냐**의 차이입니다.

### 자세히

`/` 뒤 숫자는 **앞에서부터 몇 칸을 고정할지**를 뜻합니다.

| 표기 | 뜻 | 몇 개? |
|---|---|---|
| `172.31.1.10/32` | 딱 이 주소 하나 | 1개 |
| `172.31.1.0/24` | 앞 3자리 고정 | 256개 |
| `172.31.0.0/16` | 앞 2자리 고정 | 65,536개 |
| `0.0.0.0/0` | 아무것도 고정 안 함 | **전부** |

**숫자가 작을수록 범위가 넓습니다.**

### 외우는 요령

| 표기 | 고정되는 것 |
|---|---|
| `/8` | 첫 덩어리 |
| `/16` | 두 덩어리 |
| `/24` | 세 덩어리 |
| `/32` | 전부 (= IP 하나) |
| `/12` | 첫 덩어리 + **둘째 덩어리 절반** ← 헷갈림 주의 |

**8의 배수는 딱 떨어지고, 아닌 것(`/12`, `/20`)은 덩어리 중간이 잘립니다.**
실무에선 `/16`과 `/24`가 대부분이에요.

### 서브넷 마스크로 바꾸기

`/20` 같은 표기를 `255.255.240.0`으로 바꾸는 법이에요.

한 덩어리(8칸) 안에서 **1이 몇 개냐**에 따른 값:

| 1의 개수 | 2진수 | 값 |
|---|---|---|
| 0 | 0000 0000 | **0** |
| 1 | 1000 0000 | 128 |
| 2 | 1100 0000 | 192 |
| 3 | 1110 0000 | 224 |
| **4** | **1111 0000** | **240** |
| 5 | 1111 1000 | 248 |
| 6 | 1111 1100 | 252 |
| 7 | 1111 1110 | 254 |
| 8 | 1111 1111 | **255** |

앞에서부터 **128, 64, 32, 16, 8, 4, 2, 1**을 더해가는 것뿐이에요.
`1111 0000` = 128+64+32+16 = **240**

**계산 순서**

```
/20  →  20 ÷ 8 = 2 나머지 4

255 . 255 . ??? . 0
 ↑     ↑     ↑     ↑
 8칸   8칸  나머지4칸  0

나머지 4 → 표에서 240
→ 255.255.240.0
```

**예시**

| 표기 | 2진수 | 마스크 |
|---|---|---|
| `/12` | 11111111.11110000.00000000.00000000 | **255.240.0.0** |
| `/16` | 11111111.11111111.00000000.00000000 | **255.255.0.0** |
| `/20` | 11111111.11111111.11110000.00000000 | **255.255.240.0** |
| `/24` | 11111111.11111111.11111111.00000000 | **255.255.255.0** |

> 💡 `/12`의 마스크가 `255.240.0.0`이니 둘째 덩어리가 `1111 0000` → **뒤 4칸이 자유**
> → `0001 0000`(16) ~ `0001 1111`(31) → 그래서 **172.16 ~ 172.31**입니다.

### `0.0.0.0/0`이 헷갈리는 이유

이건 **IP 주소가 아니라 "모든 IP"라는 조건**입니다.

```
0.0.0.0/0 → igw
```

이걸 말로 풀면: **"목적지가 어디든 상관없으면, 정문으로 보내라"**

그래서 이걸 **디폴트 경로**라고 불러요. 위 조건에 안 걸린 나머지를 다 잡는 그물입니다.

### 같은 표기, 다른 의미

쓰이는 자리에 따라 뜻이 달라집니다. 이게 헷갈림의 진짜 원인이에요.

| 어디에 쓰였나 | `0.0.0.0/0`의 뜻 |
|---|---|
| 라우팅 테이블 | **목적지**가 어디든 |
| 보안 그룹 인바운드 | **출발지**가 어디든 = 전 세계 아무나 |

보안 그룹에 `SSH(22), 0.0.0.0/0`이 있으면 **전 세계 누구나 접속 가능**이라는 뜻이라 위험합니다. 내 IP만 열려면 `내IP주소/32`로 씁니다.

## 2. 사설 IP와 공인 IP

> **한 줄 요약**
> 공인 IP는 **전국에서 유일한 주소**, 사설 IP는 **건물 안에서만 통하는 호수**.

### 비유 ★ 이 비유를 계속 씁니다

**아파트**로 생각하면 전부 풀립니다.

| 아파트 | AWS |
|---|---|
| 도로명 주소 "행복로 25" | **공인 IP** (전국에서 유일) |
| "301호" | **사설 IP** (아파트마다 다 있음) |
| 단지 정문 경비실 | **IGW** |

택배 기사는 "행복로 25"까지만 압니다. 정문에 도착하면 경비실이 "아, 이건 301호 거네" 하고 전달해줘요.

**택배 상자에 '301호'라고만 써서 부치면 절대 도착 못 합니다.** 301호는 전국 아파트마다 다 있으니까요.

### 자세히

사설 IP는 전 세계가 **"인터넷에서 쓰지 말자"고 약속한** 주소들입니다.

| 대역 | 실제 범위 | 어디서 쓰나 |
|---|---|---|
| `10.0.0.0/8` | 10.0.0.0 ~ **10.255**.255.255 | 회사, 클라우드 |
| `172.16.0.0/12` | 172.16.0.0 ~ **172.31**.255.255 | AWS 기본 VPC, 도커 |
| `192.168.0.0/16` | 192.168.0.0 ~ **192.168.255**.255 | 집 공유기 |

> ⚠️ `/12`가 제일 헷갈립니다. `172.16.0.0/12`는 **172.16만**이 아니라 **172.16 ~ 172.31 전체**예요.
>
> `/12` = 앞 12칸 고정 = 첫 덩어리(8칸) + **둘째 덩어리의 절반(4칸)**
> ```
> 16을 2진수로:  0001 0000
>                ^^^^ 고정   ^^^^ 자유(0~15)
> → 16 ~ 31
> ```
> 참고로 `172.16.0.0 ~ 172.16.15.255`는 **`/20`** 입니다.

### 핵심 원칙

> **인터넷에는 사설 IP가 절대 안 나타납니다.**

EC2는 **퍼블릭이든 프라이빗이든 항상 사설 IP만** 가집니다. 직접 확인해볼 수 있어요.

```bash
ip addr
# 172.31.1.10 만 나옴. 공인 IP는 어디에도 없음
```

**EC2는 자기 공인 IP를 모릅니다.** 301호 사람이 자기 집 도로명 주소를 모르는 것과 같아요. 그건 경비실(IGW)이 관리하는 정보니까요.

# Part 2. VPC — 나만의 네트워크

## 3. VPC와 서브넷

> **한 줄 요약**
> VPC는 **아파트 단지**, 서브넷은 그 안의 **동(棟)**.

### 비유

```
VPC (아파트 단지)  10.0.0.0/16
 ├─ 서브넷 (1동)   10.0.1.0/24
 ├─ 서브넷 (2동)   10.0.2.0/24
 └─ 서브넷 (3동)   10.0.11.0/24
```

단지 전체 주소 범위를 정하고, 그 안에서 동별로 나눠 갖는 구조예요.

### 자세히

**규칙 1. 서브넷 하나는 AZ 하나에만 속합니다.**
동 하나가 두 곳에 걸쳐 있을 수 없는 것과 같아요. 그래서 서버를 안전하게 운영하려면 같은 역할의 동을 여러 곳에 만들어야 합니다.

**규칙 2. IP 5개는 AWS가 미리 가져갑니다.**

`10.0.1.0/24` 서브넷이라면:

| 주소 | 상태 |
|---|---|
| 10.0.1.0 | ✗ 네트워크 주소 |
| 10.0.1.1 ~ 10.0.1.3 | ✗ **AWS 예약** (라우터, DNS, 예비) |
| 10.0.1.4 ~ 10.0.1.254 | **✓ 사용 가능 (251개)** |
| 10.0.1.255 | ✗ 브로드캐스트 |

**AWS에서 첫 IP는 `.1`이 아니라 `.4`부터**입니다. 일반 네트워크와 다른 점이에요.

> ⚠️ **중요: 이건 서브넷마다 생깁니다**
>
> `172.16.0.0/12` 같은 큰 대역은 **서브넷이 아니라 "이 범위는 사설용"이라는 구획 지정**이에요.
> 그래서 "전체 범위에서 양 끝 2개만 빼면 된다"가 **아닙니다.**
>
> 아파트로 치면, `/12`는 "이 지역은 주거지역"이라는 도시계획이고
> **관리사무소·경비실은 단지(서브넷)마다 하나씩** 생기는 겁니다.
>
> `172.16.0.0/12`를 `/24`로 쪼개면 서브넷이 4,096개 →
> AWS에서 못 쓰는 주소는 4,096 × 5 = **20,480개**

**규칙 3. 서브넷끼리 주소가 겹치면 안 됩니다.**

### 서브넷은 몇 개까지 만들 수 있나?

**CIDR만 봐서는 알 수 없습니다.** 내가 어떻게 쪼개느냐에 달렸어요.

`/12`는 **땅 크기**만 알려줄 뿐입니다. "100만 평이야"라고 하면, 몇 동을 지을지는 내 마음이죠.

같은 크기로 나눈다면:

| 어떤 크기로? | 몇 개 나오나 |
|---|---|
| `/12`를 `/16`씩 | 16개 |
| `/12`를 `/24`씩 | **4,096개** |
| `/16`을 `/24`씩 | 256개 |

계산: **2의 (뒷숫자 − 앞숫자) 제곱**
`/12 → /24` = 2^(24−12) = 2^12 = 4,096

**꼭 똑같이 안 나눠도 됩니다.** 겹치지만 않으면 크기가 달라도 돼요.

### ⚠️ 실제로는 3단계입니다

`/12`에서 바로 서브넷을 만드는 게 아니에요.

```
① 172.16.0.0/12   ← 전 세계 약속 (RFC1918)
                     "이 범위는 사설용으로 쓰세요"
        ↓ 이 안에서 고름
② 172.16.0.0/16   ← 내 VPC (단지)
        ↓ 이 안에서 쪼갬
③ 172.16.1.0/24   ← 서브넷 (동)
   172.16.2.0/24
```

**AWS에서 VPC는 `/16` ~ `/28`만 만들 수 있습니다.** `/12`짜리 VPC는 아예 못 만들어요.

### 실무에선 이렇게

VPC가 `10.0.0.0/16`이면 `/24` 서브넷을 256개까지 만들 수 있지만, 실제로는 **4~6개만** 만듭니다.

```
10.0.1.0/24    퍼블릭 (AZ-a)
10.0.2.0/24    퍼블릭 (AZ-c)
10.0.11.0/24   프라이빗 (AZ-a)
10.0.12.0/24   프라이빗 (AZ-c)
(나머지 250개 공간은 비워둠)
```

**남는 건 나중에 확장할 여유분**으로 놔둡니다.

### 기본으로 주어지는 172.31

AWS 계정을 만들면 `172.31.0.0/16` VPC가 자동으로 생깁니다.

왜 하필 172.31이냐면, **사람들이 잘 안 쓰는 구석 번호**라서예요. 나중에 회사 네트워크와 연결할 때 주소가 겹치면 연결 자체가 안 되거든요. 그래서 일부러 구석에 배치한 겁니다.

## 4. 퍼블릭 서브넷과 프라이빗 서브넷

> **한 줄 요약**
> 주소 대역이 다른 게 아니다. **정문으로 나가는 길이 있으면 퍼블릭, 없으면 프라이빗.**

### 비유

같은 아파트 단지 안의 동인데,

- **퍼블릭 동** = 정문으로 통하는 길이 있음
- **프라이빗 동** = 그 길이 없음 (단지 안에서만 돌아다님)

건물 자체는 똑같아요. **길이 있느냐 없느냐의 차이**입니다.

### 자세히

퍼블릭 서브넷에서 인터넷을 쓰려면 **두 가지가 다 있어야** 합니다.

| 필요한 것 | 없으면 |
|---|---|
| ① 정문으로 가는 길 (`0.0.0.0/0 → igw`) | 나갈 방법이 없음 |
| ② 공인 IP | 경비실에 내 이름이 없어서 택배가 못 옴 |

**공인 IP 없이 퍼블릭 서브넷에 EC2를 만들면 인터넷이 완전히 끊깁니다.** 길이 있어도 소용없어요.

> 💡 프라이빗 서브넷에 길을 뚫고 공인 IP를 주면 그 순간 퍼블릭이 됩니다.
> **퍼블릭/프라이빗은 타고난 성질이 아니라 설정의 결과예요.**

## 5. 라우팅 테이블

> **한 줄 요약**
> **단지 안에 세워진 이정표.** 나가는 짐을 어디로 보낼지 알려준다.

### 비유

단지 안 갈림길에 이정표가 서 있어요.

```
← 우리 단지 주소면 (10.0.x.x)  : 단지 안으로
← 그 외 전부 (0.0.0.0/0)       : 정문으로
```

택배 기사가 이 표를 보고 방향을 정합니다.

### 실제 표는 어떻게 생겼나 ★

**개별 IP는 절대 안 적힙니다. 범위(CIDR)만 적혀요.**
그리고 **인바운드용/아웃바운드용이 따로 없습니다.** 표는 하나뿐이고 방향 무관하게 같은 표를 봅니다.

**퍼블릭 서브넷의 표**

| 대상 (Destination) | 대상 (Target) |
|---|---|
| `10.0.0.0/16` | `local` |
| `0.0.0.0/0` | `igw-0abc123` |

**프라이빗 서브넷의 표**

| 대상 (Destination) | 대상 (Target) |
|---|---|
| `10.0.0.0/16` | `local` |
| `0.0.0.0/0` | `nat-0def456` |

**딱 2줄입니다.** 다른 건 두 번째 줄뿐이에요.

> ⚠️ 한국어 콘솔은 두 열 이름이 **둘 다 "대상"** 이라 헷갈립니다.
> 왼쪽 = **목적지 범위**, 오른쪽 = **보낼 곳**

**매칭되는 과정** (EC2가 `10.0.1.10`일 때)

들어올 때:
```
정문 통과 후 목적지 = 10.0.1.10

1줄: 10.0.1.10이 10.0.0.0/16 안에 있나?
     → 앞 두 자리 "10.0" 같음 → ✓ 매칭

결과: local   (2줄은 볼 필요도 없음)
```

나갈 때:
```
목적지 = 142.250.196.100 (구글)

1줄: 10.0.0.0/16 안에 있나? → ✗
2줄: 0.0.0.0/0 안에 있나?   → ✓ (모든 IP 포함)

결과: igw
```

**줄이 더 늘어나는 경우**

| 대상 (Destination) | 대상 (Target) | 뜻 |
|---|---|---|
| `10.0.0.0/16` | `local` | 우리 단지 |
| `172.16.0.0/16` | `pcx-0aaa` | 옆 단지 (피어링) |
| `pl-6ca54005` | `vpce-0bbb` | S3 (VPC Endpoint) |
| `0.0.0.0/0` | `nat-0def456` | 나머지 전부 |

**구체적인 것이 위, `0.0.0.0/0`은 항상 맨 마지막 그물**입니다.

**퍼블릭과 프라이빗 이정표 비교**

| | 나갈 때 | 들어올 때 |
|---|---|---|
| **퍼블릭 동** | `0.0.0.0/0 → igw` | `local` |
| **프라이빗 동** | `0.0.0.0/0 → nat` | `local` |

**다른 건 "나갈 때 어디를 거치냐"뿐입니다.** 들어오는 짐은 이미 단지 안 주소라 둘 다 `local`에 걸려요.

> 💡 프라이빗 동은 인터넷에서 들어올 일이 **아예 없습니다.** NAT Gateway는 밖에서 먼저 못 들어오니까요(→ 8장).
> 그럼 요청은 어떻게 받나? **단지 안에서 옵니다.**
> `사용자 → 정문 → ALB(퍼블릭 동) → Spring Boot(프라이빗 동)`
> 마지막 구간은 사설 IP끼리라 `local`만 쓰고 정문도 NAT도 안 거칩니다.

### 이정표는 왜 서브넷 소속일까? ★

"패킷이 이정표를 보고 움직이는데, 왜 주인이 서브넷이지?"

**둘 다 맞는 얘기인데 서로 다릅니다.**

| | 답 |
|---|---|
| 이정표를 **보고 움직이는** 건? | **패킷** |
| 이정표가 **세워져 있는 곳**은? | **서브넷** |

도로 표지판을 보고 움직이는 건 자동차지만, 표지판은 **그 갈림길에 속해** 있죠. 갈림길마다 내용이 다르고요.

**왜 동마다 따로 있어야 하나?** 같은 목적지인데 답이 달라야 하기 때문입니다.

목적지가 구글(`8.8.8.8`)인 패킷:

| 어느 동에서 출발? | 어디로 |
|---|---|
| 퍼블릭 동 | **정문(IGW)으로** |
| 프라이빗 동 | **대표전화(NAT GW)로** |

목적지는 똑같은데 답이 다릅니다. 그러니 **"어느 동에서 출발했는지"** 를 알아야 결정할 수 있어요.

> 💡 만약 단지에 이정표가 하나뿐이라면 모든 동이 같은 규칙을 따르게 되고,
> **퍼블릭/프라이빗 구분 자체가 불가능해집니다.** (→ 4장)

### 이정표 읽는 법 ★

각 줄을 **문장으로 풀어서** 읽으면 헷갈리지 않아요. 기준은 항상 **짐의 목적지**입니다.

| 줄 | 문장으로 읽으면 |
|---|---|
| `172.31.0.0/16 → local` | "목적지가 **우리 단지 주소**면 단지 안으로" |
| `0.0.0.0/0 → igw` | "목적지가 **그 외 아무데나**면 정문으로 내보내라" |

그래서 이렇게 나뉩니다.

| 줄 | 언제 쓰이나 |
|---|---|
| `172.31.0.0/16 → local` | **들어오는 짐** (+ 단지 안 이동) |
| `0.0.0.0/0 → igw` | **나가는 짐** |

**들어오는 짐은 "정문으로" 줄에 절대 안 걸립니다.** 정문에서 이미 주소가 단지 안 주소로 바뀌었거든요.

```
정문 도착:  받는 사람 = 행복로 25  (공인)
정문 통과:  받는 사람 = 301호      (사설)  ← 여기서 바뀜
   ↓
이정표:    "301호? 우리 단지네" → 단지 안으로
```

> ⚠️ 그렇다고 "정문으로" 줄이 인바운드와 무관한 건 아닙니다.
> **답장은 나가는 짐이라 이 줄을 씁니다.** 지우면 접속 자체가 안 돼요. (→ 12장)

### 헷갈리는 것 3가지

**① "두 줄 중에 뭔지 판별하는 거야?"**

아닙니다. 그냥 **이정표에 적힌 목록 전체**예요. 짐 하나당 **한 줄만 골라집니다.**

**② "인터넷이 이 이정표를 보는 거야?"**

아닙니다. **우리 단지 안에서만 쓰는 표**예요. 바깥 세상은 이런 게 있는지도 모릅니다.

**③ "이정표에서 정해지면 그 다음이 검문소야?"**

아닙니다. 이정표는 **방향만** 알려줍니다. 검문소(NACL, 보안 그룹)는 가는 길에 있는 관문일 뿐이에요.

```
이정표: "단지 안으로 가라"
   ↓
동 입구 검문소 (NACL)
   ↓
집 현관 도어락 (보안 그룹)
   ↓
도착
```

### 위치와 개수

| | 개수 |
|---|---|
| 서브넷 하나가 보는 이정표 | **딱 1개** |
| 이정표 하나를 여러 서브넷이 공유 | **가능** |

역할이 같은 동끼리는 이정표를 같이 씁니다. 퍼블릭 동 두 개는 어차피 "정문으로"가 똑같으니 하나면 충분해요.

> ⚠️ **자주 하는 실수**
> 기본 이정표에 "정문으로" 길을 넣어두면, **나중에 만드는 모든 동이 자동으로 퍼블릭이 됩니다.**
> 기본 이정표는 "단지 안으로"만 남겨두세요.

## 6. IGW (인터넷 게이트웨이)

> **한 줄 요약**
> **단지 정문 + 경비실.** 나가는 길이 되어주고, 주소를 바꿔준다.

### 비유

정문 경비실이 하는 일이 딱 두 가지예요.

1. **문** — 나가고 들어오는 통로
2. **주소 변환** — "행복로 25" ↔ "301호" 바꿔치기

### 자세히

| 역할 | 설명 |
|---|---|
| ① 나가는 길 | 이정표에서 "정문으로"의 그 정문 |
| ② 주소 변환 (NAT) | 공인 IP ↔ 사설 IP |

**"IGW = 주소 변환기"는 반만 맞습니다.** 문 역할도 하니까요.

증거: IPv6에는 주소 변환이 아예 없는데도 IGW는 필요합니다. 그때는 **문 역할만** 해요.

### 개수

**VPC 하나에 IGW 하나.** 정문이 하나뿐인 단지라고 보면 됩니다.

모든 동이 같은 정문을 씁니다. 프라이빗 동도 물리적으로는 정문에 갈 수 있어요. **다만 이정표에 그 길이 안 적혀 있어서 안 갈 뿐**입니다.

# Part 3. NAT — 주소 바꿔치기

## 7. NAT이 하는 일

> **한 줄 요약**
> **나갈 때는 보내는 사람 주소를, 들어올 때는 받는 사람 주소를** 바꾼다.

### 비유

택배 송장을 생각해보세요.

**밖으로 나갈 때** — 보내는 사람 칸을 고침
```
보내는 사람: 301호        →  보내는 사람: 행복로 25
받는 사람: 부산 어딘가         받는 사람: 부산 어딘가  (그대로!)
```

왜? "301호"라고 쓰면 답장이 못 오니까요.

**들어올 때** — 받는 사람 칸을 고침
```
받는 사람: 행복로 25      →  받는 사람: 301호
```

### 핵심 표

| 방향 | 바뀌는 칸 |
|---|---|
| **나갈 때** | **보내는 사람** (사설 → 공인) |
| **들어올 때** | **받는 사람** (공인 → 사설) |

**목적지는 나갈 때 절대 안 바뀝니다.** 이걸 헷갈리는 사람이 많아요.

### 확인해보기

```bash
curl ifconfig.me
# 3.3.3.3  ← EC2 안엔 없는 주소인데 외부는 이걸로 봄
```

### 왜 "Static(고정)" NAT인가

**공인 IP를 붙이는 순간 짝이 미리 정해지기 때문**입니다.

경비실 명부에 "행복로 25 = 301호"라고 **미리 적혀 있는** 거예요. 택배가 한 번도 안 왔어도 명부엔 이미 있습니다.

이게 왜 중요하냐면, **밖에서 먼저 찾아와도 어디로 안내할지 알 수 있기 때문**이에요. 이따 나올 NAT Gateway와의 결정적 차이입니다.

## 8. NAT Gateway

> **한 줄 요약**
> **회사 대표전화.** 여러 명이 하나의 번호로 밖에 전화할 수 있지만, 밖에서 특정인에게 바로 걸 수는 없다.

### 비유

회사 대표번호 `02-1234-5678`이 있어요.

- 직원 여러 명이 **밖으로 전화** → 상대방에겐 전부 대표번호로 보임 ✓
- 밖에서 **김대리에게 직접 전화** → 불가능 ✗ (누구인지 알 방법이 없음)

프라이빗 서브넷 EC2가 `apt update` 같은 걸 할 때 이걸 씁니다.

### IGW와 뭐가 다른가

| | **IGW** | **NAT Gateway** |
|---|---|---|
| 비유 | 아파트 경비실 (1:1 명부) | 회사 대표전화 (여럿이 공유) |
| 밖에서 먼저 들어오기 | **가능** | **불가능** |
| 왜? | 명부에 미리 적혀 있어서 | 나갈 때만 기록이 생겨서 |
| 위치 | 단지 정문 | **퍼블릭 서브넷 안** |
| 요금 | 무료 | **유료** |

> 💡 "NAT Gateway는 나가는 것만 된다"는 **규칙이 아니라 원리상 불가능**한 겁니다.
> 밖에서 먼저 오면 누구에게 줘야 할지 알 수가 없거든요.

### 중요한 순서

NAT Gateway도 결국 정문을 거쳐야 나갑니다.

```
프라이빗 EC2 → NAT Gateway → IGW → 인터넷
```

### 📖 용어: Ingress / Egress

| 단어 | 뜻 | 우리가 쓴 말 |
|---|---|---|
| **Ingress** | 들어옴 | 인바운드 |
| **Egress** | 나감 | 아웃바운드 |

- **in**(안으로) + gress(가다)
- **e**(밖으로) + gress(가다)

**Static Egress NAT** = "나갈 때 항상 같은 공인 IP로 바뀌는 NAT"

```
서버 A (10.0.1.5)  ┐
서버 B (10.0.1.6)  ├→ 나갈 때 전부 → 3.3.3.3 (항상 고정)
서버 C (10.0.1.7)  ┘
```

**왜 중요하냐면**, 외부 회사가 이렇게 요구할 때가 있어요.

> "우리 API를 쓰려면 당신 서버 IP를 알려주세요. 그 IP만 허용할게요."

서버 재시작마다 IP가 바뀌면 이걸 못 하죠. 그래서 **NAT Gateway에 고정 IP(EIP)를 붙여** 항상 같은 주소로 나가게 만듭니다. 결제사나 본인인증 API를 붙일 때 실제로 마주칩니다.

> 💡 **Egress-Only Internet Gateway** — IPv6 전용. **나가기만 되고 들어오지는 못하는** 정문입니다.
> IPv6엔 NAT이 없어서 NAT Gateway 대신 이걸 씁니다.

### 💰 아껴쓰기

S3나 DynamoDB를 쓸 때는 **VPC Endpoint**를 쓰면 인터넷을 안 거쳐도 되고 **무료**입니다.
다만 카카오 로그인 같은 외부 API는 NAT Gateway가 필요해요.

# Part 4. 보안

## 9. 패킷과 세션

> **한 줄 요약**
> **패킷은 편지 한 통, 세션은 주고받은 대화 전체.**

### 비유

친구에게 편지를 보내고 답장을 받았어요.

- **편지 한 통 한 통** = 패킷 (가는 편지, 오는 편지)
- **주고받은 대화 전체** = 세션

**"내가 먼저 편지를 보낸 대화"** 라고 하면, 그 안엔 **내 편지도 있고 친구 답장도 있죠.**

### 그래서 헷갈립니다

**"인바운드 SSH"** = 외부에서 **먼저 시작한** 대화라는 뜻이에요.
그 안에는 들어오는 패킷도 있고 **나가는 패킷(응답)도 있습니다.**

SSH 접속 하나를 펼치면 이래요.

| 순서 | 내용 | 방향 |
|---|---|---|
| 1 | "안녕하세요?" | **들어옴** |
| 2 | "네 안녕하세요" | **나감** |
| 3 | "접속할게요" | 들어옴 |
| 4~ | 대화 계속 | 왔다갔다 |

이 전부가 **"인바운드 세션 1개"** 입니다. 1번이 밖에서 왔다는 이유 하나로요.

### 왜 이걸 알아야 하나

AWS 구성 요소마다 **보는 단위가 다르기 때문**입니다.

| | 뭘 보나 | 결과 |
|---|---|---|
| **보안 그룹** | **세션(대화 전체)** | 들어오는 것만 열면 답장은 자동으로 나감 |
| **NACL** | **패킷 한 통** | 답장도 따로 열어줘야 함 |
| **이정표** | **패킷 한 통** | 답장도 다시 길을 찾음 |

## 10. Security Group과 NACL

> **한 줄 요약**
> **보안 그룹은 얼굴을 기억하는 경비원, NACL은 매번 새로 검사하는 검문소.**

### 비유

**보안 그룹 = 우리 집 현관 경비원**
"아까 들어온 손님이네" 하고 기억해요. 나갈 때 다시 안 물어봅니다.

**NACL = 동 입구 검문소**
기억을 전혀 못 해요. 들어올 때 검사하고, 나갈 때 **또 검사**합니다.

### 비교

| | **보안 그룹** | **NACL** |
|---|---|---|
| 어디에 | 집 현관 (서버 하나하나) | 동 입구 (서브넷 전체) |
| 기억력 | **있음** (Stateful) | **없음** (Stateless) |
| 답장 | 자동 통과 | **따로 열어야 함** |
| 규칙 | 허용만 | 허용 + 차단 |

### ⚠️ 여기서 다들 한 번은 당합니다

NACL에서 SSH를 열려고 이렇게 씁니다.

```
들어올 때: 22번 허용  ✓
나갈 때:   22번 허용  ✗ ← 틀림!
```

**답장은 22번으로 안 나가거든요.** 답장은 상대방이 쓰던 임시 번호(5만번대)로 갑니다.

```
나갈 때: 1024~65535 허용  ✓ 이게 맞음
```

보안 그룹은 이런 고민이 없어요. **기억하고 있으니까요.** 이게 Stateful과 Stateless의 실제 차이입니다.

### 실전 설정

```
22번  ← 내 IP만        (SSH는 나만 쓰니까)
443번 ← 전 세계        (사용자가 써야 하니까)
```

### 소스에 IP 대신 보안 그룹 쓰기 ★

**"이 IP에서 오면 허용"** 대신 **"이 그룹 소속이면 허용"** 이라고 적는 방법입니다.

| 방식 | 도어락에 뭐라고 등록? |
|---|---|
| **IP로 지정** | "**301호 사람**만 들어와" |
| **SG로 지정** | "**관리사무소 직원증** 있는 사람만 들어와" |

방 번호로 등록하면 그 사람이 이사 가면 끝이지만, **직원증으로 등록하면 담당자가 바뀌어도 그대로 통합니다.**

```
프라이빗 EC2의 보안 그룹 (인바운드)

22번   ← sg-bastion    (배스천을 단 서버면 허용)
8080번 ← sg-alb        (ALB를 단 놈이면 허용)
```

**왜 훨씬 나은가?**

① **IP가 바뀌어도 안 깨짐** — 배스천을 재시작하면 사설 IP가 바뀔 수 있는데, IP로 적었으면 그때마다 규칙을 고쳐야 합니다.

② **서버가 늘어나도 규칙은 한 줄** — Auto Scaling으로 2대 → 10대가 되면?

| | 규칙 몇 줄? |
|---|---|
| IP로 지정 | **10줄** (늘어날 때마다 추가) |
| SG로 지정 | **1줄** (끝) |

새로 뜨는 서버가 자동으로 그 SG를 달고 나오니 **아무것도 안 해도 됩니다.**

**주의할 점**

- **방향이 있습니다.** `A의 인바운드 ← sg-B`는 "B → A"만 허용. 반대는 따로 열어야 함
- **같은 VPC 안에서만** 됩니다 (VPC 피어링 시 예외)

# Part 5. 전체 흐름

## 11. 들어올 때 (인바운드)

> **한 줄 요약**
> 정문에서 주소를 바꾸고, 이정표는 "단지 안으로"를 고른다.

```
① 내 노트북에서 출발
   받는 사람: 3.3.3.3 (공인)

② 인터넷 통과
   공인 IP만 보임

③ 정문(IGW) 도착 → 주소 변환
   받는 사람: 172.31.1.10 (사설)   ← 여기서 처음 사설 IP 등장

④ 이정표 확인
   "172.31로 시작하네 → 단지 안으로"

⑤ 동 입구 검문소 (NACL)

⑥ 집 현관 경비원 (보안 그룹)
   "22번 손님이시군요"

⑦ 도착
```

### 여기서 IGW는

**주소 변환만 합니다.** 길 안내는 이정표의 "단지 안으로" 줄이 했어요.

**"정문으로 가라"는 줄은 이 짐에겐 절대 안 걸립니다.** 정문에서 이미 단지 안 주소로 바꿔놨으니까요.

## 12. 나갈 때 (아웃바운드)

> **한 줄 요약**
> 이정표가 "정문으로"를 고르고, 정문에서 보내는 사람 주소를 바꾼다.

```
① EC2가 구글에 요청
   보내는 사람: 172.31.1.10
   받는 사람: 구글

② 이정표 확인
   "172.31로 시작 안 하네 → 정문으로"

③ 정문(IGW) → 주소 변환
   보내는 사람: 3.3.3.3   ← 바뀜
   받는 사람: 구글        ← 그대로

④ 인터넷으로
```

### 여기서 IGW는

**길 안내 + 주소 변환 둘 다** 합니다. 오히려 나갈 때가 IGW를 제대로 쓰는 쪽이에요.

### ★ 가장 헷갈리는 지점

> **"인바운드니까 정문으로 가는 길은 필요 없는 거 아냐?"**
> → **틀렸습니다. 답장이 나가야 하니까요.**

들어오는 것만 되고 나가는 길이 없으면, 손님은 들어왔는데 **인사를 못 해서 대화가 시작조차 안 됩니다.**

실제로 "정문으로" 줄을 지우고 SSH를 하면 `Connection timed out`이 뜹니다. 요청은 도착했는데 **답장이 못 나가서** 그래요.

### 정리

| | 길 안내 | 주소 변환 |
|---|---|---|
| **들어올 때** | ✗ | ✓ (받는 사람) |
| **나갈 때** | ✓ | ✓ (보내는 사람) |

**한 번의 대화에서 둘 다 쓰입니다.**

# Part 6. 접속 방법

## 13. Bastion Host

> **한 줄 요약**
> **관리사무소를 거쳐서 안쪽 동에 들어가는 것.**

### 비유

프라이빗 동은 정문에서 바로 못 갑니다. 그래서 이렇게 가요.

```
개발자 → 정문 → 관리사무소(퍼블릭 동) → 프라이빗 동
                    ↑ 배스천
```

### 자주 하는 오해

| 오해 | 사실 |
|---|---|
| 배스천은 프라이빗 서브넷에 둔다 | **퍼블릭에 둡니다.** 자기가 인터넷에 닿아야 하니까 |
| 프라이빗이라서 SSH가 필요하다 | SSH는 원래 쉘 접속 수단. **한 번 더 거칠 뿐** |
| 인바운드는 다 배스천을 거친다 | 배스천은 **관리자 전용**. 사용자는 ALB로 갑니다 |

### 두 갈래 길

```
사용자  → 정문 → ALB       → Spring Boot 서버   (443번)
개발자  → 정문 → 배스천     → 같은 서버          (22번)
```

### 요즘은 안 씁니다

**SSM Session Manager**를 쓰면 배스천이 아예 필요 없어요.
22번 포트를 하나도 안 열고도 접속됩니다. 관리할 서버 한 대와 키 파일이 줄어들어요.

# Part 7. 가상화

## 14. 가상화란?

> **한 줄 요약**
> **큰 집 하나를 칸막이로 나눠서 여러 세대에 세놓는 것.**

### 비유

100평짜리 집이 하나 있어요. 혼자 살면 대부분 빈 공간이죠.

칸막이를 세워서 20평씩 다섯 세대로 나눕니다. 세입자들은 **각자 자기 집이라고 생각하고** 삽니다. 옆집이 있는지도 몰라요.

### 왜 필요했나

옛날엔 서버 한 대에 서비스 하나만 올렸어요. 그래서 **CPU를 5~15%밖에 못 썼습니다.** 나머지는 그냥 놀았죠.

가상화는 이걸 **"물리적으로 나누지 말고 칸막이로 나누자"** 로 풀었습니다.

| 문제 | 해결 |
|---|---|
| 서버가 놀고 있음 | 한 대에 여러 개 올림 |
| 서로 충돌함 | 칸막이로 완전 분리 |
| 새 서버 받는 데 몇 주 | 몇 분이면 생성 |

EC2를 클릭 몇 번으로 만들 수 있는 게 전부 이 덕분이에요.

## 15. Host와 Guest

> **한 줄 요약**
> **Host는 집주인, Guest는 세입자.** 세입자는 자기가 세입자인 줄 모른다.

### 비유

| | Host (집주인) | Guest (세입자) |
|---|---|---|
| 집 | **소유함** | 빌려 씀 |
| 공간 | 자기 마음대로 | **주인이 정해준 만큼만** |
| 옆집 | 다 알고 있음 | **있는지도 모름** |

### 마지막 줄이 핵심입니다

**EC2는 자기가 세입자인 줄 모릅니다.**

```bash
lscpu     # "CPU 2개" ← 실제 물리 서버는 128개일 수도
free -h   # "메모리 2GB" ← 실제로는 1TB짜리 장비
```

앞에서 EC2가 자기 공인 IP를 모른다고 했죠. **똑같은 구조예요. 보여준 만큼만 진실로 믿습니다.**

### 용어 정리

"Host"가 세 가지 뜻으로 쓰여서 헷갈립니다.

| 말 | 뜻 |
|---|---|
| **Host Machine** | 물리 서버 (쇳덩이) |
| **Host OS** | 하드웨어를 직접 쓰는 OS (소프트웨어) |
| **Guest OS** | VM 안에서 도는 OS |

**"물리 서버 = Host, VM = Guest"는 맞습니다.**

## 16. 하이퍼바이저

> **한 줄 요약**
> **건물 관리인.** 세입자들에게 공간과 전기를 나눠준다.

### 이름의 유래

옛날엔 OS를 **supervisor(감독자)** 라고 불렀어요. 프로그램들을 감독하니까요.

그럼 그 감독자들을 **또 감독하는 것**은?
→ **hyper(위) + visor = hypervisor**

### 그래서 "OS의 OS"

| | 누굴 관리? | 뭘 나눠줌? |
|---|---|---|
| **OS** | 프로그램들 | CPU 시간, 메모리 |
| **하이퍼바이저** | **OS들** | vCPU, 메모리 |

OS가 프로그램에게 하는 일을, 하이퍼바이저는 **OS에게** 합니다. **한 층 위**인 거예요.

### 중요: 하이퍼바이저는 소프트웨어입니다

물리 서버가 아니에요. 물리 서버에 **설치하는 프로그램**입니다.

## 17. Type 1과 Type 2 ★

### 먼저: 뭘 나눈 건가?

**하이퍼바이저를 두 종류로 나눈 것**입니다.

원래 이름이 **"Type 1 하이퍼바이저"**, **"Type 2 하이퍼바이저"** 인데, 말할 때 뒷부분을 생략해서 헷갈립니다.

```
운전면허            하이퍼바이저
 ├ 1종               ├ Type 1
 └ 2종               └ Type 2
```

"1종"만 말하면 뭔지 모르는 것처럼, "Type 1"도 앞에 **하이퍼바이저**를 붙여야 이해됩니다.

```
가상화 (기술 전체)
 └ 하이퍼바이저 (가상화를 실제로 수행하는 소프트웨어)
    ├ Type 1 ← 하드웨어에 바로 설치
    └ Type 2 ← OS 위에 설치
```

| 질문 | 답 |
|---|---|
| 뭘 나눈 건가? | **하이퍼바이저** |
| 무슨 기준으로? | **어디에 설치되는가** |
| 결과 | Type 1(하드웨어 위) / Type 2(OS 위) |

> **한 줄 요약**
> **하이퍼바이저 밑에 윈도우 같은 평범한 OS가 있으면 Type 2, 없으면 Type 1.**

### 비유

| | 비유 |
|---|---|
| **Type 2** | **내가 사는 집의 방 한 칸을 세놓기** |
| **Type 1** | **처음부터 원룸 임대 전용 건물 짓기** |

Type 2는 원래 내가 살려고 산 집(윈도우)이 있고, 세놓기는 부업이에요.
Type 1은 주인이 거기 안 삽니다. **세놓는 게 유일한 목적**이에요.

### 그림

```
Type 2:  하드웨어 → 윈도우 → VirtualBox → VM     (4칸)

Type 1:  하드웨어 → 하이퍼바이저 → VM            (3칸)
                    ↑ 윈도우 자리가 없음
```

**"Host OS가 없다"는 건 저 한 칸이 없다는 뜻**이에요. 하드웨어를 아무도 관리 안 한다는 게 아닙니다.

### 확인하는 법 ★

**"하이퍼바이저를 지우면 뭐가 남을까?"**

| | 지운 후 | 판정 |
|---|---|---|
| **Type 2** | 윈도우가 멀쩡히 남음 | Host OS 있음 |
| **Type 1** | **아무것도 안 남음** (부팅도 안 됨) | Host OS 없음 |

VirtualBox를 지워도 윈도우는 잘 돌아가죠. 하지만 **ESXi를 지우면 그 서버는 빈 쇳덩이**가 됩니다.

### 또 다른 확인법

**"그걸로 다른 일을 할 수 있나?"**

- Type 2의 윈도우 → 게임도 하고, 유튜브도 보고, VM도 돌림
- Type 1의 하이퍼바이저 → **VM 돌리는 것 말고 아무것도 못 함**

### 비교표

| | **Type 1** | **Type 2** |
|---|---|---|
| 다른 이름 | 베어메탈 | **호스티드** ("얹혀 있는") |
| 밑에 있는 것 | 하드웨어 | **OS** |
| 하이퍼바이저는 | 그 자체로 시스템 | **응용 프로그램 하나** |
| 속도 | **빠름** (층이 적음) | 느림 |
| 예시 | Xen, KVM, ESXi, Hyper-V | VirtualBox, VMware Workstation |
| 어디에 | **클라우드, 데이터센터** | **내 노트북 실습** |

**AWS EC2는 Type 1입니다.**

### 🔍 심화 (나중에 봐도 됨)

**Q. Type 1 하이퍼바이저도 OS 아닌가요?**

기능은 비슷합니다. CPU 스케줄러도 있고 메모리 관리자도 있어요. **미니 OS**라고 봐도 됩니다.

다만 **VM 돌리는 기능만 남기고 나머지를 다 뺐어요.** 그래서 "Host OS"라고 분류하지 않습니다.

**Q. KVM은요?**

KVM은 리눅스 커널의 일부입니다. 그래서 애매해요.

- 리눅스 위에서 도니까 Type 2?
- 커널 자체가 하이퍼바이저가 되니까 Type 1?

**보통 Type 1로 봅니다.** VirtualBox처럼 "프로그램 하나"가 아니라 **커널이 변신하는 것**이거든요.

## 18. 실제 예시 — t3.small

> **한 줄 요약**
> **평소엔 20%만 쓰고, 필요할 때 잠깐 몰아 쓰는 세입자.**

### 스펙

| | |
|---|---|
| vCPU | 2 (= 물리 코어 약 1개) |
| 메모리 | 2 GiB |
| 하이퍼바이저 | **Nitro** (Type 1) |

### 어떻게 생겼나

```
┌──────────────────────────────────┐
│ t3.small │ 남의 것 │ 남의 것 │ ... │ ← 세입자 수십 명
├──────────────────────────────────┤
│      Nitro 하이퍼바이저            │ ← 관리인
├──────────────────────────────────┤
│      물리 서버 (수십 코어)          │ ← 건물
└──────────────────────────────────┘
```

### CPU 크레딧 — 이게 제일 중요합니다

t3는 **평소에 20%만** 쓸 수 있어요. 대신 안 쓴 만큼 **크레딧으로 저금**됩니다.

```
100% ┤     ╭──╮      ← 저금 꺼내 쓰기
     │     │  │
 20% ┼─────╯  ╰────  ← 평소 (저금 쌓임)
     └──────────────
```

**문제:** 저금이 떨어져도 계속 쓸 수 있는데, **그때부터 돈이 나갑니다.** 이게 기본 설정이라 모르고 요금 폭탄을 맞는 경우가 많아요.

### 세입자가 눈치챌 수 있는 유일한 단서

```bash
top
# %Cpu(s): ... 5.4 st
#                 ↑ steal time
```

**"관리인이 내 시간을 다른 세입자에게 준 시간"** 이에요. 이 숫자가 계속 높으면 크레딧이 떨어졌거나 건물이 붐빈다는 뜻입니다.

### 용도별 추천

| 용도 | 좋을까? |
|---|---|
| Bastion Host | ◎ 평소 놀아서 크레딧 잘 쌓임 |
| 개발 서버 | ○ |
| Spring Boot 운영 | △ 2GB는 좀 빠듯 |
| CI 빌드 서버 | ✗ **크레딧 폭식. 요금 나감** |

## 19. 데이터 센터와 엣지 로케이션

> **한 줄 요약**
> **데이터 센터는 본사 창고, 엣지 로케이션은 동네 편의점.**

### 비유

- **본사 창고(데이터 센터)** — 물건을 만들고 보관하는 곳
- **동네 편의점(엣지 로케이션)** — 잘 팔리는 것만 갖다놓은 곳

편의점에선 물건을 **만들지 못합니다.** 창고에서 가져온 것만 팔아요.

### 비교

| | **데이터 센터** | **엣지 로케이션** |
|---|---|---|
| 역할 | **원본 만들고 보관** | **사본 갖다놓고 전달** |
| EC2, RDS | ✓ | **✗** |
| 개수 | 리전 30여 개 | **400곳 이상** |
| 고르는 법 | 내가 지정 | **자동으로 가까운 곳** |

### 흐름

```
사용자
  ↓
동네 편의점 (엣지)
  ├─ 있으면 → 바로 줌 (빠름!)
  └─ 없으면 ↓
본사 창고 (리전)
```

**편의점에 있으면 창고까지 안 갑니다.** 그래서 빠른 거예요.

### 헷갈리는 것들

| | EC2 띄우기 |
|---|---|
| **엣지 로케이션** | **✗** (캐시 전용) |
| **Local Zone** | ✓ (작은 데이터센터) |
| **Outposts** | ✓ (우리 회사에 AWS 장비 설치) |

> ⚠️ 시험에 자주 나옵니다: **"엣지 로케이션에서 EC2를 실행할 수 있나?" → 불가능**

## 20. 스토리지 — EBS, EFS, S3

> **한 줄 요약**
> **EBS는 USB 외장하드, EFS는 공유 폴더, S3는 온라인 창고.**

### 비유

| | 비유 | 특징 |
|---|---|---|
| **EBS** | **USB 외장하드** | 한 번에 **한 대**에만 꽂힘 |
| **EFS** | **공유 폴더(NAS)** | **여러 대**가 동시에 씀 |
| **S3** | **온라인 창고** | 파일을 올리고 내려받음 |

### 비교

| | **EBS** | **EFS** | **S3** |
|---|---|---|---|
| 동시 연결 | **1대** | 여러 대 | 해당 없음 |
| OS 설치(부팅) | **✓ 가능** | ✗ | ✗ |
| 쓰는 법 | 디스크처럼 | 폴더처럼 | API로 |
| 용도 | 서버 디스크 | 여러 서버가 공유할 파일 | 이미지, 백업, 정적 파일 |

### "단일 인스턴스 부팅 볼륨"이란?

EBS를 설명하는 말인데, 두 단어를 쪼개면 됩니다.

| 말 | 뜻 |
|---|---|
| **부팅 볼륨** | **OS가 들어있는 디스크.** 없으면 켜지지도 않음 |
| **단일 인스턴스** | **한 번에 EC2 한 대에만** 붙음 |

EC2를 만들면 **루트(부팅) 볼륨은 무조건 하나 생깁니다.**

```bash
lsblk
# nvme0n1  8G   ← 루트(부팅) 볼륨. OS가 여기 있음
# nvme1n1  20G  ← 나중에 추가로 붙인 데이터용 EBS
```

### ⚠️ 주의할 점

**① 이름이 `/dev/sda`가 아니라 `nvme`로 잡힙니다**

요즘 EC2(Nitro)는 EBS를 NVMe 장치로 보여줘요. 콘솔에서 `/dev/sdf`로 지정해도 실제로는 `nvme1n1`이 됩니다.

그래서 `/etc/fstab`에 장치 이름을 적으면 **재부팅 후 깨질 수 있어요.** UUID로 적으세요.

```
UUID=abcd-1234  /data  ext4  defaults,nofail  0 2
```

**② EBS는 AZ를 벗어날 수 없습니다**

USB를 다른 건물로 못 들고 가는 것과 같아요. 다른 AZ에서 쓰려면 스냅샷을 떠서 복사해야 합니다.

**③ 인스턴스를 종료하면 루트 볼륨은 기본적으로 같이 삭제됩니다**

데이터를 지키려면 별도 EBS를 붙이거나, 삭제 옵션을 꺼두세요.

## 21. ICMP

> **한 줄 요약**
> **"여보세요? 들려요?"** 하고 확인하는 용도. 포트 번호가 없다.

### 비유

전화 연결 상태를 확인하는 것과 비슷해요. 내용을 주고받는 게 아니라 **"연결됐나?"만 확인**합니다.

### 자주 쓰는 것

| 이름 | 쓰임 |
|---|---|
| ping | "살아있어?" → "응" |
| traceroute | 어떤 길로 가는지 추적 |

### AWS에서 주의할 점

**① 22번, 443번 다 열었는데 ping이 안 돼요**

정상입니다. **ICMP는 포트가 없어서** 그 규칙들과 무관해요. 보안 그룹에서 `All ICMP`를 따로 추가해야 합니다.

**② ping 안 되면 서버가 죽은 건가요?**

아닙니다. 일부러 막아둔 곳이 많아요. 실제 확인은 이렇게 합니다.

```bash
curl -I https://내주소.com
nc -zv 3.3.3.3 443
```

## 22. 전체 요약 카드

### 아파트 비유 전체 대응표

| 아파트 | AWS |
|---|---|
| 아파트 단지 | **VPC** |
| 동(棟) | **서브넷** |
| 집 (301호) | **EC2** |
| 301호라는 번호 | **사설 IP** |
| 도로명 주소 | **공인 IP** |
| 정문 + 경비실 | **IGW** |
| 단지 안 이정표 | **라우팅 테이블** |
| 동 입구 검문소 | **NACL** |
| 집 현관 경비원 | **보안 그룹** |
| 관리사무소 | **Bastion** |
| 회사 대표전화 | **NAT Gateway** |
| 건물 관리인 | **하이퍼바이저** |
| 세입자 | **Guest (VM)** |
| USB 외장하드 | **EBS** |
| 공유 폴더 | **EFS** |
| 온라인 창고 | **S3** |

### 꼭 기억할 10가지

1. **인터넷엔 사설 IP가 안 나타난다.** IGW를 지나야 등장한다
2. **퍼블릭/프라이빗은 타고난 게 아니라 이정표가 정한다**
3. **라우팅 테이블은 우리 단지 안에서만 쓰는 표**다
4. **나갈 때는 보내는 사람, 들어올 때는 받는 사람** 주소가 바뀐다
5. **인바운드 대화에도 나가는 길이 필요하다** (답장 때문에)
6. **보안 그룹은 기억하고, NACL은 기억 못 한다**
7. **NAT Gateway는 밖에서 먼저 못 들어온다** (원리상 불가능)
8. **Type 1은 밑에 OS가 없고, Type 2는 있다**
9. **Guest는 자기가 Guest인 줄 모른다**
10. **엣지 로케이션에선 EC2를 못 띄운다**

## 23. 실수 체크리스트

### 개념 오해

| 이렇게 생각했다면 | 실제로는 |
|---|---|
| 퍼블릭 서브넷은 공인 IP를 쓴다 | 전부 사설 IP. 차이는 이정표 |
| 인터넷이 라우팅 테이블을 본다 | 우리 단지 전용 표 |
| `0.0.0.0/0`은 특정 IP다 | "모든 IP"라는 조건 |
| IGW는 주소 변환기다 | 문 역할도 한다 |
| 나갈 땐 NAT을 안 한다 | 보내는 사람 주소를 바꾼다 |
| 하이퍼바이저는 물리 서버다 | 소프트웨어다 |
| Type 1엔 관리자가 없다 | 하이퍼바이저가 그 역할을 겸한다 |
| 엣지 로케이션은 작은 데이터센터다 | EC2를 못 띄우는 캐시 전용 |

### 설정 실수

- [ ] 기본 이정표에 "정문으로"를 넣어 새 동이 다 퍼블릭이 됨
- [ ] NACL 나가는 쪽에 임시 번호(1024-65535)를 안 열어 답장이 막힘
- [ ] 공인 IP 없이 퍼블릭 서브넷에 EC2 생성 → 완전 단절
- [ ] 보안 그룹 SSH를 전 세계에 열어둠
- [ ] 서브넷을 `/28`로 너무 잘게 쪼개 쓸 IP가 11개뿐
- [ ] t3에 빌드 서버를 올려 요금 폭탄
