# 3Tier 아키텍처

> 한 줄 요약
> **역할이 다른 세 덩어리로 나누고, 그 경계를 네트워크로 갈라놓는 구조.**

## 세 계층

| 계층 | 하는 일 | 예 |
|---|---|---|
| **프레젠테이션** | 요청을 받는 맨 앞. 화면을 내려주거나 뒤로 넘김 | CDN, 로드밸런서, Ingress, Nginx |
| **애플리케이션** | 실제 로직을 처리하고 결과를 만듦 | WAS, API 서버 |
| **데이터** | 결과를 보관 | RDB, 오브젝트 스토리지 |

## 왜 나누는가 — 세 가지

**① 부족한 곳만 늘릴 수 있다.**
요청이 몰려 처리가 밀리면 **애플리케이션 계층만 늘리면 된다.** 셋이 한 덩어리면 DB까지 같이 복제해야 하는 상황이 생긴다.

**② 보안 경계가 생긴다.** — 인프라 관점에서 가장 중요하다.
데이터 계층을 외부에서 아예 만질 수 없게 만들 수 있다. 앞단이 뚫려도 **뒤로 가려면 한 겹을 더 넘어야** 한다.

**③ 장애가 번지는 범위가 줄어든다.**
한 계층이 죽어도 나머지가 통째로 무너지지는 않는다.

## 코드 구조로만 나눈 것은 3Tier가 아니다

패키지를 controller / service / repository로 나눠도, **같은 서버 같은 네트워크에 다 있으면 보안 경계가 생기지 않는다.** 네트워크로 갈라야 계층 분리다.

```
퍼블릭 서브넷    : 로드밸런서 (외부에서 접근 가능)
프라이빗 서브넷  : 애플리케이션 서버 (외부에서 직접 접근 불가)
프라이빗 서브넷  : DB (애플리케이션 계층에서만 접근 가능)
```

밖에서 애플리케이션 서버로 바로 들어올 방법이 없고, **반드시 앞단을 거쳐야 한다.** 대신 안에서 밖으로 나갈 때는 NAT을 통해서만 나간다 — **들어오는 길과 나가는 길을 따로 만드는 것**이다.

## 단점

- **거쳐 가는 지점이 늘어난 만큼 지연이 늘어난다.**
- **앞 계층이 뒤 계층을 기다리는 동안 자원(스레드)을 붙잡는다.** 계층이 많을수록 그런 대기가 겹칠 지점도 늘어난다.
- **계층마다 이중화가 필요해 관리 대상이 늘어난다.**

그렇다고 계층을 줄이면 **보안 경계가 사라지는 대가가 훨씬 크다.** 다만 **상태가 없고 모든 요청에 공통으로 걸리는 일**(인증, 압축, 정적 파일 전달)은 앞단으로 올려도 계층 분리가 깨지지 않는다. 계층 분리는 지키되 **어떤 일을 어느 계층에 둘지는 다시 볼 수 있다.**

## 온프레미스에서는

원리는 같고 **경계를 만드는 수단이 다르다.** 클라우드는 서브넷과 보안 그룹으로 나누지만, 온프레미스는 **VLAN, 방화벽 정책, 물리적 네트워크 분리**로 같은 일을 한다.
차이는 **경계를 바꾸는 비용**이다. 클라우드는 설정 한 줄이지만 온프레미스는 장비 설정이 필요해서, **처음에 잘 나눠 두는 것이 훨씬 중요하다.**
