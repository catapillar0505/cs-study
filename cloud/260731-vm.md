## 하이퍼바이저란?

물리 하드웨어 위에서 **여러 개의 가상 머신(VM)을 만들고 관리하는 소프트웨어 계층**입니다. 정식 명칭은 **VMM(Virtual Machine Monitor)**.

핵심 역할은 CPU, 메모리, 디스크, 네트워크를 쪼개서 각 VM에게 "이게 네 전용 하드웨어야"라고 속이는 것입니다. 각 VM은 자기가 물리 서버 위에서 도는 줄 알고 **각자 독립된 커널**을 부팅합니다.

이름의 유래도 재밌습니다. OS를 supervisor(감독자)라고 부르던 시절, 그 위에 있는 놈이라 **hyper**visor입니다.

## Type 1 vs Type 2

```
[Type 1 - 베어메탈]              [Type 2 - 호스티드]

┌─────┬─────┬─────┐            ┌─────┬─────┐
│ VM  │ VM  │ VM  │            │ VM  │ VM  │
├─────┴─────┴─────┤            ├─────┴─────┤
│   하이퍼바이저   │            │ 하이퍼바이저│  ← 그냥 앱
├─────────────────┤            ├───────────┴──┬──────┐
│    하드웨어      │            │   호스트 OS   │ 크롬 │
└─────────────────┘            ├──────────────┴──────┤
                               │      하드웨어        │
                               └─────────────────────┘
```

| | Type 1 (Bare-metal) | Type 2 (Hosted) |
|---|---|---|
| 위치 | 하드웨어 위에 직접 | 호스트 OS 위에 앱으로 |
| 성능 | 높음 (계층 하나 적음) | 낮음 |
| 용도 | 서버, 데이터센터 | 개발자 로컬 테스트 |
| 예시 | VMware ESXi, Xen, Hyper-V, Proxmox | VirtualBox, VMware Workstation, Parallels |

## KVM은 애매합니다 (면접 단골)

**KVM(Kernel-based Virtual Machine)** 은 리눅스 **커널 모듈**입니다. `modprobe kvm_intel` 하는 순간 리눅스 커널 자체가 하이퍼바이저로 변신합니다.

- 리눅스라는 범용 OS 위에서 돈다 → Type 2처럼 보임
- 근데 그 리눅스 커널이 곧 하이퍼바이저다 → 실질적으로 Type 1

RedHat 공식 입장은 **Type 1**입니다. 스케줄링·메모리 관리를 커널이 직접 하니까요. 시험 문제로 나오면 Type 1로 답하고, 애매하다는 점을 덧붙이면 됩니다.

KVM은 CPU/메모리 가상화만 담당하고, 디스크·NIC 같은 장치 에뮬레이션은 **QEMU**가 맡습니다. 그래서 항상 `qemu-kvm` 세트로 다닙니다. 관리 API는 **libvirt**(`virsh` 명령어)입니다.

## 하드웨어 지원이 핵심

x86은 원래 가상화가 안 되는 구조였습니다. 커널이 ring 0에서 도는데 하이퍼바이저가 그 자리를 차지해야 하니 충돌하죠. 초기엔 소프트웨어로 명령어를 실시간 번역(binary translation)해서 우회했고, 그래서 느렸습니다.

2005년 **Intel VT-x / AMD-V**가 나오면서 해결됐습니다. 흔히 **ring -1**이라 부르는 하이퍼바이저 전용 특권 레벨을 만들어, 게스트 커널이 ring 0에 그대로 앉을 수 있게 했습니다.

| 기술 | 대상 | 역할 |
|---|---|---|
| VT-x / AMD-V | CPU | 하이퍼바이저 전용 특권 모드 |
| EPT / NPT | 메모리 | 2단계 주소 변환을 하드웨어로 |
| VT-d / AMD-Vi (IOMMU) | I/O | 물리 장치를 VM에 직접 할당 (GPU 패스스루) |
| SR-IOV | NIC | 물리 NIC 하나를 여러 가상 NIC으로 |

BIOS에서 이거 꺼놓고 "VirtualBox 64비트 옵션이 안 보여요" 하는 게 흔한 삽질입니다. 리눅스에서 확인은:

```bash
grep -E 'vmx|svm' /proc/cpuinfo   # vmx=Intel, svm=AMD
lsmod | grep kvm
```

## 전가상화 vs 반가상화

**전가상화(Full)**: 게스트 OS를 수정하지 않음. 하이퍼바이저가 하드웨어를 완벽히 흉내. 편하지만 에뮬레이션 오버헤드가 큽니다.

**반가상화(Para)**: 게스트가 "나 가상 머신인 거 안다"는 전제로 하이퍼바이저에게 직접 요청(hypercall). Xen이 대표적이었고, 지금은 **virtio** 드라이버 형태로 널리 쓰입니다. 디스크·네트워크만 반가상화하는 하이브리드가 사실상 표준입니다.

VM 만들 때 디스크를 `virtio` 대신 `IDE`로 잡으면 성능이 몇 배 차이 납니다. 실무에서 자주 보는 실수입니다.

## 컨테이너와의 차이

| | 하이퍼바이저(VM) | 컨테이너 |
|---|---|---|
| 커널 | VM마다 별도 커널 | **호스트 커널 공유** |
| 격리 수준 | 하드웨어 수준 (강함) | 커널 기능 수준 (namespace, cgroups) |
| 부팅 시간 | 수십 초 | 1초 미만 |
| 오버헤드 | GB 단위 | MB 단위 |
| 이종 OS | 리눅스 위에 윈도우 가능 | 불가 (커널이 같아야 함) |

컨테이너는 사실 가상화가 아니라 **격리된 프로세스**입니다. `ps`로 보면 호스트에서 그냥 프로세스로 보입니다. 그래서 컨테이너 탈출 취약점이 곧 호스트 장악으로 이어지고, 멀티테넌트 환경에선 이게 문제가 됩니다.

그래서 요즘은 둘을 섞습니다. **AWS Firecracker**(Lambda·Fargate가 사용)나 **Kata Containers**는 컨테이너를 초경량 VM(microVM) 안에 넣어 컨테이너의 속도와 VM의 격리를 동시에 노립니다. 부팅 125ms 수준입니다.

## 클라우드에서

EC2 인스턴스는 결국 하이퍼바이저 위의 VM입니다. AWS는 오랫동안 **Xen**을 쓰다가 2017년부터 **Nitro**(KVM 기반 + 전용 하드웨어 카드)로 넘어갔습니다. 네트워크·스토리지 처리를 별도 칩으로 오프로드해서 하이퍼바이저 오버헤드를 거의 없앤 구조입니다.

베어메탈 인스턴스(`c5.metal`)는 하이퍼바이저 없이 물리 서버를 통째로 주는 상품이고, 그 위에 직접 ESXi 같은 걸 올릴 수 있습니다.

---

OS 운영 직무 면접이라면 **Type 1/2 구분**, **KVM이 커널 모듈이라는 점**, **VM과 컨테이너의 커널 공유 여부** 이 세 가지가 실제로 자주 나옵니다. 특히 마지막 건 "왜 도커가 VM보다 가벼운가"로 변형돼서 물어봅니다.
