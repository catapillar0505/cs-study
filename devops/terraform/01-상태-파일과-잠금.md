# Terraform 상태 파일과 잠금

> 한 줄 요약
> **코드가 진실이 아니라 상태 파일이 진실이다.**

## 상태 파일이 하는 일

상태 파일(`terraform.tfstate`)은 **실제 인프라가 지금 어떤 모습인지**를 기록해 둔 파일이다. Terraform은 **코드와 이 파일을 비교해서** 무엇을 만들고 바꾸고 지울지 정한다.

```
코드(원하는 상태)  ↔  상태 파일(현재 상태)  →  차이만큼 실행
```

## 로컬에 두면 생기는 문제

**① 팀원마다 다른 상태 파일을 갖게 된다.** 서로 다른 현실을 보고 작업하는 셈이다.
**② 잃어버리면 Terraform이 자기가 만든 것을 못 알아본다.** 이미 존재하는 리소스를 또 만들려고 한다.

그래서 **공유 스토리지(S3, GCS 등)에 두고 모두가 같은 파일을 보게** 한다.

## 잠금이 필요한 이유

두 사람이 동시에 `apply`하면 **각자 읽은 상태를 기준으로 판단하고 각자 덮어쓴다.** 그러면 상태 파일과 실제가 어긋난다. 작업 중에는 잠가서 **한 번에 한 명만** 실행하게 만든다.

```hcl
terraform {
  backend "s3" {
    bucket         = "my-tfstate"
    key            = "prod/terraform.tfstate"
    region         = "ap-northeast-2"
    dynamodb_table = "terraform-lock"   # 잠금
    encrypt        = true
  }
}
```

> 상태 파일에는 리소스 속성이 평문으로 들어간다. **암호화와 접근 제어가 필요하고, git에 올리면 안 된다.**

## drift — 코드 밖에서 바뀐 것

콘솔에서 수동으로 고치면 실제와 상태 파일이 어긋난다(drift). 다음 `apply` 때 Terraform은 **코드 기준으로 되돌리려 하고**, 그 과정에서 리소스를 지우려 들 수도 있다.

- `terraform plan`을 **적용 전에 반드시 읽는다** — 특히 `destroy`가 섞여 있는지
- 같은 대상을 바꾸는 경로를 **하나로 유지한다** (콘솔 수정 금지)
- 이미 존재하는 리소스는 `import`로 상태에 편입시킨다
