# PART 0. 브라우저 기초

React를 이해하려면 "실제 DOM 조작이 왜 비싼가"부터 알아야 한다.

## 0-1. 렌더링 파이프라인

```
HTML  →  DOM 트리
CSS   →  CSSOM 트리
          ↓
      Render Tree (화면에 그려질 노드만)
          ↓
      Layout (Reflow)   각 노드의 위치·크기 계산
          ↓
      Paint (Repaint)   픽셀 채우기
          ↓
      Composite         레이어 합성
```

**비용 순서: Layout > Paint > Composite**

| 바꾸는 속성 | 발생하는 단계 |
|---|---|
| `width`, `top` 등 기하 속성 | Layout → Paint → Composite |
| `background-color` 등 | Paint → Composite |
| `transform`, `opacity` | Composite만 |

## 0-2. DOM은 JavaScript 객체가 아니다

브라우저는 두 엔진이 붙어 있는 구조다.

| | 담당 |
|---|---|
| **V8** | JavaScript 실행 |
| **Blink** | HTML 파싱, DOM 트리, 레이아웃, 페인트 |

DOM 노드의 실제 데이터는 **Blink 쪽 C++ 객체**에 있다. JS 힙에는 없다.

```js
const el = document.getElementById('box');
// el 은 JS 객체지만, 내부에 C++ 객체를 가리키는 포인터만 들고 있음
el.className = 'active';
// → V8이 setter 호출 → 바인딩 코드 → C++ Element::setAttribute() 실행
```

이 중간의 자동 생성된 접착 코드를 **바인딩(WebIDL bindings)**이라 한다. Java의 JNI와 비슷한 구조.

> **주의**: "DOM이 느린 건 JS 객체가 아니라서"는 절반만 맞다. 현대 엔진은 바인딩을 크게 최적화했고, 경계를 넘는 오버헤드 자체는 작다. 진짜 비용은 **그 호출이 유발하는 레이아웃 무효화**다.

## 0-3. 리플로우 전파 — 계산의 "범위" 문제

노드 하나의 크기가 바뀌면 형제·자손·조상의 레이아웃까지 다시 계산될 수 있다. DOM 조작 1회 = 연산 1회가 아니다.

## 0-4. 강제 동기 레이아웃 — 계산의 "횟수" 문제

전파와는 **다른 축의 문제**다.

브라우저는 DOM을 건드릴 때마다 즉시 계산하지 않고, **dirty 플래그만 찍고 프레임 끝까지 미룬다.**

```js
el.style.width  = '100px';   // dirty 표시만
el.style.height = '200px';   // dirty 표시만
// → 프레임 끝에서 레이아웃 계산 1회
```

JPA의 쓰기 지연 저장소(write-behind store)와 같은 발상.

그런데 **레이아웃 결과값을 읽으면** 브라우저는 정확한 값을 주기 위해 밀린 계산을 즉시 실행한다.

```js
el.style.width = '100px';        // dirty
const h = el.offsetHeight;       // ← 강제 동기 레이아웃 발생
```

JPA에서 JPQL 쿼리가 강제 flush를 유발하는 것과 동일한 패턴.

### Layout Thrashing

```js
// 나쁨: 쓰기와 읽기를 번갈아 → 레이아웃 N회
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';
}

// 좋음: 읽기 몰아치고 → 쓰기 몰아치기 → 레이아웃 1~2회
const widths = items.map(el => el.offsetWidth);
items.forEach((el, i) => { el.style.width = widths[i] + 10 + 'px'; });
```

**강제 레이아웃 유발 읽기**: `offsetTop/Left/Width/Height`, `clientTop/Left/Width/Height`, `scrollTop/Left/Width/Height`, `getBoundingClientRect()`, `getComputedStyle()`, `focus()`

## 0-5. 세 개념의 층위 정리

| 개념 | 무엇에 대한 문제인가 |
|---|---|
| **바인딩 경계** | DOM은 남의 집(C++) 객체다 — 구조적 배경 |
| **리플로우 전파** | 계산의 **범위** — 얼마나 넓게 퍼지나 |
| **강제 동기 레이아웃** | 계산의 **횟수** — 몇 번 일어나나 |

React가 실제로 해결해주는 건 주로 세 번째다.

# PART 1. JavaScript 기초

React의 거의 모든 함정이 이 두 개념에서 나온다.

## 1-1. 원시 타입 vs 참조 타입

**원시 타입** (숫자, 문자열, boolean) — 상자에 값이 직접 들어있다.

```js
let a = 5;
let b = a;    // 값을 복사
b = 10;
console.log(a);  // 5 ← a는 그대로
```

**참조 타입** (객체, 배열, 함수) — 상자에 **주소**가 들어있다. 실제 데이터는 다른 곳에 있다.

```js
let a = [1, 2, 3];
let b = a;       // 주소를 복사 (데이터 복사 아님)
b.push(4);
console.log(a);  // [1, 2, 3, 4] ← a도 바뀜
```

`a`와 `b`는 **같은 배열을 가리키는 두 개의 이름표**다.

### `===`는 주소를 비교한다

```js
const x = [1, 2, 3];
const y = [1, 2, 3];
x === y;   // false ← 내용은 같지만 다른 상자

const z = x;
x === z;   // true ← 같은 상자
```

**함수도 참조 타입이다.**

```js
const A = () => console.log('안녕');
const B = () => console.log('안녕');
A === B;   // false
```

### 왜 얕은 비교인가

깊은 비교는 트리 전체를 순회해야 하고, 매 렌더마다 해야 한다. 참조 비교는 O(1)이다. React는 **비교를 O(1)로 만드는 대신 불변성 유지 책임을 개발자에게 넘긴** 트레이드오프를 택했다.

### 원본 변경 vs 새것 반환

| 원본을 바꾸는 메서드 | 새것을 반환하는 메서드 |
|---|---|
| `push` `pop` `shift` `unshift` | `map` `filter` `slice` `concat` |
| `splice` `sort` `reverse` | 전개 연산자 `...` |

> `sort`와 `reverse`는 반환값이 있어 안전해 보이지만 **원본을 변경**한다. 사고가 가장 잦은 지점.

### 전개 연산자

```js
const 옛것 = ['공', '인형'];
const 새것 = [...옛것, '블록'];
// 새것 = ['공', '인형', '블록']
// 옛것 = ['공', '인형']  ← 원본 그대로
```

`...items`는 **"쪽지가 가리키는 상자를 열어 내용물을 하나씩 꺼내라"**는 동작이다. 꺼낸 것들을 어디에 놓을지는 바깥의 `[ ]`가 정한다. `items` 자체는 처음부터 끝까지 쪽지(참조)다.

```js
items                    // 쪽지를 그대로 다룸
items.push('곰')         // 쪽지 보고 찾아가서, 그 상자에 넣음
[...items, '곰']         // 쪽지 보고 찾아가서 꺼내온 뒤, 새 상자에 담음
```

## 1-2. 클로저

함수 안에서 함수를 만들면, 바깥 변수를 **붙잡고 나간다.**

```js
function makeCounter(start) {
  return function() { console.log(start); };
}

const a = makeCounter(1);
const b = makeCounter(2);
a();  // 1
b();  // 2
```

`a`는 `start = 1`을, `b`는 `start = 2`를 붙잡았다. **한 번 붙잡힌 값은 나중에 바뀌지 않는다. 사진처럼 박제된다.**

## 1-3. 표현식 vs 문

| 표현식 (값으로 평가됨) | 문 (값이 아님) |
|---|---|
| `1 + 2` → `3` | `if (x) {...}` |
| `a ? b : c` | `for (...) {...}` |
| `arr.map(fn)` | `switch (...) {...}` |
| `cond && <div/>` | `const x = 1;` |
| `fn()` | `return ...;` |

**판별법**: `const x = (여기에 넣어보기);`가 성립하면 표현식이다.

# PART 2. React의 3형제 — Component, Element, DOM Element

## 2-1. Component = 함수 그 자체

```jsx
function 인사() {
  return <div>안녕</div>;
}
```

그냥 함수다. **정의만 해서는 아무 일도 일어나지 않는다.**

## 2-2. Element = "그 함수를 쓰겠다"고 적은 객체

```jsx
<인사 />
```

**이건 함수 실행이 아니다.**

```jsx
인사()      // 함수 실행
<인사 />    // 실행 아님. "이걸 쓸 거야"라고 적어둔 것
```

변환되면:

```js
{
  type: 인사,        // 어떤 함수를 쓸지만 적혀있음
  key: null,
  ref: null,
  props: {}
}
```

`<인사 />`와 이 객체는 **같은 것**이다. 전자는 우리가 쓰는 JSX 문법이고, 후자는 Babel이 변환한 실제 모습이다. `0xFF`와 `255`의 관계와 같다.

```jsx
const 주문서 = <인사 />;
console.log(주문서);   // { type: 인사, props: {} }
// 함수는 아직 실행 안 됨
```

### 소문자 태그와 대문자 컴포넌트

| 쓴 것 | `type`에 들어가는 것 | 의미 |
|---|---|---|
| `<div />` | `'div'` (문자열) | 브라우저 기본 태그 |
| `<인사 />` | `인사` (함수) | 내가 만든 컴포넌트 |

그래서 컴포넌트 이름은 **대문자로 시작**해야 한다. 소문자면 React가 문자열로 착각한다.

## 2-3. DOM Element = 화면의 실제 태그

```
Component  →  Element  →  [ Fiber ]  →  DOM Element
   틀          주문서       장부           붕어빵
```

- **Component**: 붕어빵 틀 (레시피)
- **Element**: 붕어빵 주문서 ("팥 붕어빵 하나")
- **Fiber**: 장부 — 상태(`useState` 값), effect 목록, 이전 Element 참조 보관
- **DOM Element**: 실제 붕어빵 (화면에 있는 것)

**Element는 불변(immutable)이고 가볍다.** 만들어진 뒤 절대 수정되지 않고, 상태가 바뀌면 새로 만들어진다. DOM Element는 가변(mutable)이고 무겁다.

주문서를 만드는 건 공짜에 가깝고, 붕어빵을 굽는 게 비싸다. **가상 DOM이 성립하는 이유가 정확히 이 비용 차이다.**

## 2-4. Fiber — 상태가 사는 곳

Element는 매번 버려지고 새로 만들어지는데, `useState(0)`으로 만든 값은 유지되어야 한다. 그 값이 사는 곳이 Fiber다.

> **주문서는 매번 새로 쓰지만, 단골 손님의 적립 카드는 그대로다.**

type이 바뀌면 React가 Fiber를 폐기하고 새로 만들기 때문에 상태가 날아간다. `key`가 하는 일도 "이 주문서가 어느 단골 것인지" 식별해 Fiber를 올바르게 이어붙이는 것이다.

## 2-5. `element`는 다의어다

| 용어 | 실체 | 소속 |
|---|---|---|
| **DOM Element** | `HTMLDivElement` 인스턴스 (C++ 객체) | 실제 DOM |
| **React Element** | `{ type, props, key, ref }` JS 객체 | 가상 DOM |
| **Fiber Node** | React 내부 작업 단위 | React 내부 |

DOM에서 `element`라 부르는 이유: DOM 트리 노드에는 Element(태그), Text, Comment 등 여러 종류가 있고, **Node가 상위 개념이고 Element는 그중 "태그"인 것**이다. 그래서 `getNodeById`가 아니라 `getElementById`다.

## 2-6. `document.*`는 언제나 실제 DOM

```jsx
createRoot(document.getElementById('root')).render(<App />);
//         └─ 실제 DOM 노드
```

가상 DOM은 React 내부 자료구조라 전역 API로 접근할 방법이 없다. React 앱에서 `document.getElementById`를 직접 쓰면 가상 DOM과 실제 DOM 상태가 어긋난다. 필요하면 `ref`를 쓴다.

# PART 3. JSX

## 3-1. JSX는 문법 설탕이다

```jsx
<div className="box" onClick={handleClick}>Hello {name}</div>
```

```js
React.createElement(
  'div',
  { className: 'box', onClick: handleClick },
  'Hello ', name
);
```

여기서 나오는 결론:

- JSX 태그 = **함수 호출**
- 태그 속성 = **함수에 넘기는 객체의 프로퍼티**
- `{}` 안의 내용 = **함수의 인자로 평가되는 값**

## 3-2. "JSX 안/밖"은 파일이 아니라 문법 모드

`.jsx` 파일 전체가 JSX인 게 아니다. 파서가 두 모드를 오간다.

```jsx
function App() {              // JS 모드
  const name = 'jina';        // JS 모드 (if, for 다 됨)
  if (loading) return null;   // JS 모드

  return (
    <div>                     {/* JSX 모드 진입 */}
      hello                   {/* JSX 모드: 텍스트 */}
      {name.toUpperCase()}    {/* 다시 JS 모드 */}
    </div>
  );
}
```

| 전환 | 트리거 |
|---|---|
| JS → JSX | `<` 태그 시작 |
| JSX → JS | `{` 열림 |

무한 중첩 가능하다.

## 3-3. `{`의 세 가지 정체

**기호만 보고 판단하면 안 된다.**

| 코드 | `{`의 정체 | 문 사용 |
|---|---|---|
| `<div>{name}</div>` | JSX 표현식 슬롯 | ✗ 표현식만 |
| `<div style={{color:'red'}}>` | 바깥=슬롯, 안쪽=객체 리터럴 | — |
| `{arr.map(x => { ... })}` | 바깥=슬롯, 안쪽=**함수 블록** | ✓ 가능 |

```jsx
{items.map(item => {          // ← 이 { 는 함수 본문 블록
  if (item.hidden) return null;    // 문 사용 가능!
  const label = item.text.trim();  // 변수 선언 가능!
  return <li>{label}</li>;
})}
```

정확한 규칙: **"JSX 표현식 슬롯 자체에는 표현식만 온다."** 그 표현식이 함수 호출이면, 함수 본문 안에서는 문을 자유롭게 쓸 수 있다.

## 3-4. 단일 루트 요소

```jsx
// ✗ 컴파일 불가
return (
  <h1>제목</h1>
  <p>본문</p>
);
```

변환하면 `return createElement(...) createElement(...)` — JS 함수의 `return`은 하나의 값만 반환한다. JSX가 까다로운 게 아니라 JS 기본 제약이다.

**단, 반환 가능한 것은 더 많다** (React 16+):

```jsx
return [<li key="a">A</li>, <li key="b">B</li>];  // 배열 (key 필수)
return null;      // 아무것도 안 그림
return '문자열';
return 42;
```

정확히는 **"하나의 값을 반환해야 한다."**

## 3-5. Fragment

```jsx
return (
  <>
    <h1>제목</h1>
    <p>본문</p>
  </>
);
```

실제 DOM 노드를 만들지 않는다. 불필요한 `div`는 지저분한 정도가 아니라 레이아웃을 깨뜨린다 — 부모가 `flex`면 flex item이 뭉치고, `<table>` 안에 `div`가 들어가면 HTML이 무효가 된다.

**단축 문법은 `key`를 줄 수 없다.**

```jsx
{items.map(item => (
  <React.Fragment key={item.id}>
    <dt>{item.term}</dt>
    <dd>{item.desc}</dd>
  </React.Fragment>
))}
```

## 3-6. 속성명 camelCase

두 가지 이유가 겹친다.

1. `class`, `for`는 JS 예약어 → DOM Property 이름을 따름 (`element.className`, `label.htmlFor`)
2. 변환 결과가 JS 객체이므로 JS 관례를 따름

**JSX는 HTML 속성이 아니라 DOM 프로퍼티 이름을 따른다.**

### 예외

```jsx
<div data-testid="btn" aria-label="닫기" />   // 하이픈 유지
<div style={{ backgroundColor: 'red' }} />    // 객체 + camelCase
<circle strokeWidth="2" />                    // SVG도 camelCase
```

`style`의 중괄호가 두 겹인 건 바깥이 JSX 슬롯, 안쪽이 객체 리터럴이라서.

## 3-7. 조건부 렌더링

`{}` 안은 `createElement`의 인자 자리라 **표현식만** 온다. `if`/`for`/`switch`는 불가.

```jsx
// ① 삼항 연산자 — 둘 중 하나
{isLoggedIn ? <Dashboard /> : <LoginForm />}

// ② && — 조건일 때만
{hasError && <ErrorMessage />}

// ③ map — 반복
{items.map(item => <Item key={item.id} {...item} />)}

// ④ JSX 밖으로 빼기 (분기 3개 이상이면 이게 가장 깔끔)
let content;
if (status === 'loading') content = <Spinner />;
else if (status === 'error') content = <Error />;
else content = <List />;
return <div>{content}</div>;

// ⑤ IIFE — 함수 호출은 표현식이므로 가능하나 가독성 나쁨
{(() => { if (a) return <A />; return <B />; })()}
```

### `&&` 패턴의 `0` 함정

```jsx
{items.length && <List />}      // ✗ 0이면 화면에 "0"이 찍힘
{items.length > 0 && <List />}  // ✓
{!!items.length && <List />}    // ✓
```

`{}` 안의 값이 `null`, `undefined`, `false`, `true`면 렌더링되지 않지만, **`0`은 falsy여도 렌더링된다.**

## 3-8. 기타 JSX 규칙

| 규칙 | 이유 |
|---|---|
| 컴포넌트는 대문자 시작 | 소문자는 문자열 type으로 컴파일됨 |
| 자체 닫는 태그 필수 (`<img />`) | XML 문법이라 모든 태그가 닫혀야 함 |
| 주석은 `{/* ... */}` | `{}`로 JS 모드 진입 후 JS 주석 |
| `return (` 괄호로 감싸기 | 자동 세미콜론 삽입(ASI) 방지 |
| `onClick={handleClick}` (참조 전달) | `handleClick()`은 렌더 중 즉시 실행됨 |

# PART 4. 가상 DOM과 렌더링 흐름

## 4-1. 왜 가상 DOM인가

명령형(imperative) 방식은 상태와 DOM의 동기화를 개발자가 책임진다.

```js
if (isLoggedIn) {
  loginBtn.style.display = 'none';
  userMenu.classList.add('visible');
  userMenu.querySelector('.name').textContent = user.name;
}
```

상태가 늘어날수록 "이 상태에서 저 상태로 갈 때 DOM을 어떻게 바꿔야 하는가"의 경우의 수가 폭발한다.

React는 **선언형(declarative)**으로 뒤집는다.

> **UI = f(state)** — 개발자는 "현재 상태에서 화면이 어떤 모습이어야 하는가"만 기술하고, **전이(transition)** 계산은 React가 맡는다.

매번 전체를 새로 그릴 수는 없으므로 중간 계층으로 가상 DOM을 둔다.

## 4-2. 가상 DOM의 실체

**평범한 JavaScript 객체 트리**다. 실제 DOM 노드가 갖는 계산된 스타일, 레이아웃 정보, 이벤트 시스템 등이 없고, 렌더 결과를 기술하는 최소 정보만 담는다.

**실제 DOM을 복제해서 만드는 게 아니다.** 컴포넌트 함수를 실행한 결과로 처음부터 새로 만든다. 실제 DOM을 읽으면 강제 동기 레이아웃이 발생하기 때문.

## 4-3. Render 단계와 Commit 단계

```
1. 컴포넌트 함수 실행 (렌더)     ┐
2. 새 Element 트리 생성          │ Render 단계
3. 이전 트리와 diff              ┘ (메모리 안, 중단 가능)
      ↓
4. 실제 DOM에 커밋               ┐ Commit 단계
5. useLayoutEffect 실행          ┘ (동기, 중단 불가)
      ↓
6. 브라우저 리플로우/리페인트
      ↓
7. useEffect 실행
```

**Render 단계는 전부 메모리에서만 일어난다.** 화면은 아직 안 바뀐다. 실제 DOM이 건드려지는 건 커밋 단계뿐.

## 4-4. 용어 정리

React가 말하는 **"렌더링"은 브라우저의 페인팅이 아니라 "컴포넌트 함수를 실행해서 Element 트리를 만드는 것"**이다.

### 리렌더 ≠ DOM 갱신

컴포넌트 함수가 100번 재실행되어도, diff 결과 차이가 없으면 실제 DOM은 한 번도 안 바뀐다.

### 리렌더와 리플로우는 대응 관계가 아니라 선후 관계

거울처럼 마주 보는 한 쌍이 아니라 **직렬로 이어진 사슬의 서로 다른 구간**이다.

| 상황 | 리렌더 | 리플로우/리페인트 |
|---|---|---|
| `setState(5)`인데 이미 값이 5 | 발생(또는 bailout) | **없음** |
| 부모 리렌더 → 자식도 리렌더, 출력 동일 | 발생 | **없음** |
| CSS `:hover`로 배경색 변경 | **없음** | 리페인트만 |
| 창 크기 조절, 웹폰트 로딩 완료 | **없음** | 리플로우 발생 |
| CSS `transform` 애니메이션 | **없음** | 합성만 |
| 스크롤, 비제어 input 타이핑 | **없음** | 발생 |
| `setState`로 `background-color`만 변경 | 발생 | **리페인트만** |

리플로우/리페인트는 DOM 변경 외에도 뷰포트 변경, 폰트 로드, CSS 상태 변화, 스크롤로도 트리거된다. **"실제 DOM에서만 나오는 개념"보다 "브라우저 렌더링 엔진의 개념"이 정확하다.**

### 굳이 대응쌍을 찾는다면

| 축 | React 쪽 | 브라우저 쪽 |
|---|---|---|
| 뭘 바꿀지 계산 | 리렌더 + diff | 스타일 계산 + 리플로우 |
| 실제로 반영 | 커밋 | 리페인트 + 합성 |
| 비용 절감 수단 | `React.memo`, `useMemo`, `key` | `transform`/`opacity`, 읽기·쓰기 분리 |

**"계산과 반영을 분리한다"는 설계 철학이 양쪽에서 반복되는 것**이지 1:1 매핑은 아니다.

## 4-5. 배칭(Batching)

```js
setCount(c => c + 1);
setName('jina');
setOpen(true);
```

각각 즉시 커밋되면 렌더-커밋 사이클이 3번, 리플로우도 여러 번. React는 이걸 **하나의 사이클로 묶는다.**

**React 18부터 Automatic Batching** — 이전에는 React 이벤트 핸들러 안에서만 배칭됐지만, 이제 `setTimeout`, `Promise.then`, 네이티브 이벤트 핸들러 안에서도 자동으로 묶인다.

## 4-6. 가상 DOM은 메모리를 더 쓴다

가상 DOM을 쓰면 메모리에 **실제 DOM 트리 + 가상 DOM 트리**가 동시에 존재한다. 게다가 Fiber는 **더블 버퍼링**을 써서 `current` 트리와 `workInProgress` 트리 두 벌을 유지한다.

> **가상 DOM은 메모리(공간)를 더 써서 DOM 조작 횟수(시간)를 아끼는 기법이다.**

Redis 캐시로 DB 조회를 줄이는 것과 같은 구조의 트레이드오프.

## 4-7. 흔한 오해

| 오해 | 사실 |
|---|---|
| 가상 DOM은 항상 빠르다 | ✗ 최적화된 수동 DOM 조작이 더 빠르다. diff 연산도 공짜가 아니다 |
| 가상 DOM은 React만의 기술 | ✗ Vue 2/3, Preact도 사용. Svelte/Solid는 컴파일 타임 처리로 아예 안 씀 |
| 리렌더되면 DOM이 바뀐다 | ✗ 함수 재실행일 뿐 |
| `React.memo`는 diff를 줄인다 | △ **Render 단계 실행 자체**를 건너뛰게 함 |
| 가상 DOM이 브라우저 렌더링을 대체 | ✗ 최종적으로 반드시 실제 DOM을 거친다 |

# PART 5. Reconciliation과 key

## 5-1. 재조정 알고리즘

두 트리의 최소 차이를 구하는 일반 알고리즘은 O(n³). React는 **두 가지 휴리스틱**으로 O(n)까지 낮춘다.

### 휴리스틱 1 — 타입이 다르면 비교하지 않고 통째로 교체

```jsx
<div><Counter /></div>   →   <span><Counter /></span>
```

하위를 비교조차 하지 않고 서브트리 전체를 파괴하고 새로 만든다. `Counter`의 상태도 함께 날아간다.

같은 타입이면 속성만 비교해 바뀐 attribute만 갱신한다.

```jsx
<button className="on">저장</button> → <button className="off">저장</button>
// DOM 노드는 재사용, button.className = 'off' 한 줄만 실행
```

### 휴리스틱 2 — 형제 노드는 `key`로 식별

## 5-2. key가 없을 때 무슨 일이 일어나는가

```
이전:  0번째=빨래   1번째=설거지
새것:  0번째=청소   1번째=빨래     2번째=설거지
```

React는 **순서대로 짝을 지어 비교**한다.

```
0번째: 빨래 → 청소     "글자가 바뀌었네" → 수정
1번째: 설거지 → 빨래   "글자가 바뀌었네" → 수정
2번째: (없음) → 설거지 "새로 생겼네"     → 추가
```

**세 개를 다 건드린다.** 실제로는 하나만 추가하면 되는데도.

## 5-3. key = 이름표

```jsx
{할일들.map(할일 => <li key={할일.id}>{할일.내용}</li>)}
```

```
이전:  [id=1 빨래]  [id=2 설거지]
새것:  [id=3 청소]  [id=1 빨래]  [id=2 설거지]

id=1 : 이전에도 있었고 내용도 같음 → 그대로 둠 ✓
id=2 : 이전에도 있었고 내용도 같음 → 그대로 둠 ✓
id=3 : 처음 보는 이름표            → 새로 만듦
```

**하나만 만들고 끝.**

## 5-4. 형제끼리만 고유하면 된다

```jsx
<ul><li key="1">사과</li><li key="2">바나나</li></ul>
<ul><li key="1">축구</li><li key="2">농구</li></ul>   {/* 겹쳐도 OK */}
```

"1반의 3번"과 "2반의 3번"은 서로 상관없는 것과 같다.

## 5-5. index를 key로 쓰면 안 되는 이유

```
추가 전:  key=0 빨래     key=1 설거지
추가 후:  key=0 청소     key=1 빨래      key=2 설거지
```

'빨래'의 이름표가 0에서 1로 **밀려버렸다.** 이름표를 안 붙였을 때와 똑같은 결과가 된다.

### 진짜 무서운 건 상태 꼬임

```jsx
{할일들.map((할일, index) => (
  <li key={index}>
    <input type="checkbox" />
    {할일.내용}
  </li>
))}
```

'설거지'만 체크한 상태에서 맨 앞에 '청소'를 추가하면:

```
□ 청소
☑ 빨래      ← 체크가 빨래로 옮겨감!
□ 설거지    ← 체크가 풀림!
```

React가 `key=1`에 체크 상태를 저장해뒀는데, 그 자리에 이제 '빨래'가 앉아있기 때문. **상태는 Fiber에 저장되고, React는 `key`를 보고 어느 Fiber에 이어붙일지 결정한다.**

### index를 써도 되는 경우

- 목록 순서가 절대 안 바뀌고
- 항목 추가/삭제가 없고
- 각 항목이 자기만의 상태를 안 가질 때

## 5-6. key는 props가 아니다

```js
{
  type: 할일카드,
  key: 1,                        // ← 독립된 자리
  ref: null,
  props: { 내용: '빨래' }         // ← props는 여기
}
```

React가 컴포넌트를 실행할 때:

```js
const 결과 = element.type(element.props);
//                        ^^^^^^^^^^^^^^ props만 넘김
```

**Element가 컴포넌트로 전달되는 게 아니다.** React가 Element를 열어서 `props` 칸만 꺼내 인자로 넘긴다.

| 칸 | 용도 | 누가 씀 |
|---|---|---|
| `type` | 어떤 함수를 실행할지 | React |
| `key` | 어느 Fiber에 이어붙일지 | React |
| `ref` | 실제 DOM 노드를 어디에 담을지 | React |
| `props` | 화면 그릴 때 쓸 데이터 | **컴포넌트** |

```jsx
function 할일카드(props) {
  console.log(props.key);    // undefined
}
```

필요하면 다른 이름으로 한 번 더 넘긴다.

```jsx
<할일카드 key={할일.id} id={할일.id} 내용="빨래" />
```

# PART 6. Hooks 공통 구조

모든 훅은 같은 구조다.

```
창고(Fiber)
 ├── 0번 칸: useState가 쓰는 자리
 ├── 1번 칸: useEffect가 쓰는 자리
 └── 2번 칸: useCallback이 쓰는 자리
```

**창고(Fiber)는 하나, 창구(훅)는 여러 개.** 각 훅이 자기 칸을 하나씩 차지한다.

| 훅 | 창고에 보관하는 것 | 변경 시 React에 알림 |
|---|---|---|
| `useState` | 값 | ✓ |
| `useCallback` | 함수 | — |
| `useMemo` | 계산 결과 | — |
| `useRef` | `{ current: ... }` 객체 | ✗ |
| `useEffect` | 이전 의존성 배열 + cleanup | — |

## 6-1. 칸은 호출 순서로 정해진다

```jsx
const [a, setA] = useState(0);              // 0번 칸
const b = useCallback(() => {}, []);        // 1번 칸
useEffect(() => {}, []);                    // 2번 칸
```

**변수 이름과 무관하다.** 첫 번째로 호출됐기 때문에 0번 칸이다.

## 6-2. 그래서 훅의 규칙

```jsx
if (isLoggedIn) {
  const [name, setName] = useState('');  // ✗ 순서가 흔들림
}
```

조건문·반복문 안에서 훅을 호출하면 렌더마다 순서가 달라져 **남의 칸을 읽게 된다.**

## 6-3. 훅을 직접 만들어본다면

```js
const 저장소 = [];
let 순서 = 0;

function useState(초기값) {
  const 내칸 = 순서++;
  if (저장소[내칸] === undefined) {
    저장소[내칸] = 초기값;        // 첫 실행에만 초기값 사용
  }
  const setter = (새값) => {
    저장소[내칸] = 새값;
    리렌더예약();
  };
  return [저장소[내칸], setter];
}
```

# PART 7. useState

## 7-1. 상태는 어디에 사는가

```jsx
function Counter() {
  const [count, setCount] = useState(0);   // 매 렌더마다 이 줄이 다시 실행됨
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

`count`는 지역 상수인데 왜 유지되는가? **상태가 컴포넌트 함수가 아니라 Fiber에 저장되기 때문이다.**

**`useState`는 저장소가 아니라 함수다.**

```
저장소(Fiber)  ─── useState가 꺼내옴 ──▶  count
      ▲
      └────── setCount가 값을 넣음
```

| | 언제 | 무슨 일 |
|---|---|---|
| `useState` | 화면 그릴 때마다 | 보관함에서 **꺼냄** (읽기) |
| `setCount` | 사건 발생 시 | 보관함에 **넣음** + 리렌더 예약 (쓰기) |

**서로를 부르지 않는다.** 각자 Fiber를 상대할 뿐.

## 7-2. 초기값은 첫 렌더에만 쓰인다

```
1회차: useState(0) → Fiber 0번 칸 비어있음 → 0을 넣고 0 반환
클릭 : setCount(1) → Fiber 0번 칸 = 1, 리렌더 예약
2회차: useState(0) → Fiber 0번 칸에 1이 있음 → 인자 0은 무시하고 1 반환
```

## 7-3. 배열을 반환하는 이유

```jsx
const [count, setCount] = useState(0);
const [name, setName] = useState('');
```

배열 구조 분해는 **위치 기반**이라 이름이 자유롭다. 객체였다면 매번 별칭이 필요하다.

## 7-4. 왜 setter로 통보해야 하는가

**React는 변수를 감시하지 않는다.** Vue 2의 `defineProperty`나 Vue 3의 Proxy 같은 메커니즘이 없다.

> Vue는 **감시(reactive)**, React는 **통보(explicit)**.

`setCount`는 값만 바꾸는 게 아니라 **"값 변경 + Fiber를 dirty로 표시 + 리렌더 예약"**의 통합 함수다.

## 7-5. 스냅샷 — 3번 호출해도 1이 되는 이유

```jsx
function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}
// 결과: 1 (3이 아님)
```

이 `handleClick`은 첫 렌더에서 만들어졌고 `count = 0`을 **클로저로 박제**했다.

```js
setCount(0 + 1);   // setCount(1)
setCount(0 + 1);   // setCount(1)
setCount(0 + 1);   // setCount(1)
```

**`count`는 중간에 절대 안 바뀐다. 바꿀 수가 없다. 이미 박제된 값이다.**

### 리렌더 = 모든 지역 변수와 함수가 새로 만들어짐

```
1회차: count = 0, handleClick = function() { setCount(0 + 1) }
2회차: count = 1, handleClick = function() { setCount(1 + 1) }  ← 완전히 새 함수
```

첫 렌더의 `count`와 두 번째 렌더의 `count`는 이름만 같은 남남이다.

## 7-6. 함수형 업데이트

```jsx
setCount(prev => prev + 1);   // 0 → 1
setCount(prev => prev + 1);   // 1 → 2
setCount(prev => prev + 1);   // 2 → 3
```

React는 setState 호출을 **업데이트 큐**에 쌓아두고, 함수를 넣으면 순서대로 실행하며 앞 결과를 뒤 함수의 인자로 넘긴다.

```js
큐 = [ fn1, fn2, fn3 ]
let 결과 = 0;
for (const fn of 큐) { 결과 = fn(결과); }
// 0 → 1 → 2 → 3
```

| | 이전 값의 출처 |
|---|---|
| `setCount(count + 1)` | 클로저에 박제된 값 → **과거의 사진** |
| `setCount(prev => prev + 1)` | React가 넘겨주는 최신값 → **실시간 중계** |

### 필수인 상황

```jsx
// ① 비동기 콜백 — 오래된 클로저
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);        // ✗ 영원히 0 + 1 = 1
    setCount(prev => prev + 1); // ✓
  }, 1000);
  return () => clearInterval(id);
}, []);   // count는 첫 렌더의 0에 영원히 고정

// ② 의존성 배열에서 state 제거 → 함수 참조 고정
const increment = useCallback(() => {
  setCount(prev => prev + 1);
}, []);
```

## 7-7. 불변성

### React의 변경 감지

```js
if (Object.is(이전상태, 새상태)) {
  return;  // 같으면 리렌더 건너뜀 (bailout)
}
```

**`===` 참조 비교 한 번이다. 안을 들여다보지 않는다.**

### 그래서 push가 실패한다

```jsx
items.push(4);       // 상자 안에 물건을 넣음 (주소는 그대로)
setItems(items);     // 같은 주소를 건네줌
// → Object.is(이전, 새것) === true → "안 바뀌었네" → 리렌더 안 함
```

이사를 안 가고 집 안 가구만 바꾼 상황. 우편물은 주소만 보고 배달되니 아무도 눈치채지 못한다.

### 불변 패턴

```jsx
// 배열
setItems(prev => [...prev, item]);                          // 추가
setItems(prev => prev.filter(i => i.id !== id));            // 삭제
setItems(prev => prev.map(i => i.id === id ? {...i, done: true} : i));  // 수정
setItems(prev => [...prev].sort());                         // 정렬 (복사 후!)

// 객체
setUser(prev => ({ ...prev, name: 'jina' }));

// 중첩 — 바뀌는 경로를 전부 새로 만들어야 함
setState(prev => ({
  ...prev,
  profile: { ...prev.profile, address: { ...prev.profile.address, city: '서울' } }
}));
```

### 얕은 복사의 함정

```jsx
const copy = { ...user };
copy.address.city = '부산';   // ✗ 원본 user.address도 바뀜
```

바뀌지 않은 부분의 참조를 공유하는 건 **의도된 최적화**다. 중첩이 깊으면 Immer(`useImmer`) 사용을 고려한다.

## 7-8. 실전 형태

```jsx
setItems(prev => [...prev, newItem]);
//        ^^^^   ^^^^^^^^^^^^^^^^^^
//   최신값 받기      새 배열 만들기
```

두 함정(스냅샷 / 참조 비교)을 동시에 피하는 형태. 습관으로 만들면 좋다.

## 7-9. 전체 사이클

```
   타이핑 / 클릭
        ↓
     setState  ─── 옛값과 같음? ──▶ 끝 (리렌더 없음)
        ↓ 다름
   Fiber에 저장 + 리렌더 예약
        ↓
   컴포넌트 함수 재실행
        ↓
   useState ── Fiber에서 새 값 꺼냄
        ↓
   새 Element 생성
        ↓
   diff (옛 Element vs 새 Element)
        ↓
   실제 DOM 수정 (커밋)
        ↓
      화면
```

### 비교는 두 번 나온다

| | 언제 | 무엇을 비교 | 목적 |
|---|---|---|---|
| **1차** | `setState` 호출 시 | Fiber의 옛값 vs 새값 | 리렌더를 할지 말지 |
| **2차** | 리렌더 후 | 옛 Element vs 새 Element (diff) | DOM을 어디까지 고칠지 |

1차에서 걸러지면 2차는 아예 안 일어난다.

# PART 8. useEffect

## 8-1. 왜 필요한가

```jsx
function Profile({ userId }) {
  const [user, setUser] = useState(null);
  fetch(`/api/users/${userId}`).then(r => r.json()).then(setUser);  // ✗
  return <div>{user?.name}</div>;
}
```

무한 루프다. 그리고 컴포넌트 함수는 **언제 몇 번 실행될지 모른다.**

> **컴포넌트 함수는 순수해야 한다** — 같은 props/state면 항상 같은 결과를 반환하고, 바깥 세상에 영향을 주지 않아야 한다.

**"바깥 세상에 영향을 주는 일"이 사이드 이펙트**이고, 이걸 안전한 타이밍에 실행해주는 장치가 `useEffect`다.

| 순수한 일 (렌더 중 OK) | 사이드 이펙트 (useEffect로) |
|---|---|
| 계산하기 | 서버 요청 |
| JSX 반환 | 타이머 (`setInterval`) |
| props/state 읽기 | 이벤트 리스너 등록 |
| | `localStorage` 읽고 쓰기 |
| | `document.title` 변경 |
| | WebSocket 연결 |

## 8-2. 의존성 배열

```jsx
useEffect(실행할함수, 의존성배열);
```

두 번째 자리의 배열이 **"이 값들이 바뀔 때만 실행해줘"**라는 목록이다. **의존(依存)** = 이 코드가 무엇에 기대고 있는가.

### 세 가지 형태

| 코드 | React가 받은 것 | 판단 |
|---|---|---|
| `useEffect(fn, [count])` | 칸 1개짜리 배열 | 그 칸 비교 → 다르면 실행 |
| `useEffect(fn, [])` | **빈 배열** | 비교할 칸 없음 → **차이 없음** → 첫 번만 |
| `useEffect(fn)` | **배열 없음(`undefined`)** | 비교 불가 → **무조건 실행** |

### 왜 배열이 없으면 매번 실행되나

**"비교 결과" 때문이 아니라, 비교 단계로 가지 않는 별도의 경로이기 때문이다.**

```js
if (의존성배열 === undefined) {
  실행한다;                          // ← 별도 분기
} else if (이전배열과_하나라도_다르면) {
  실행한다;
} else {
  건너뛴다;
}
```

`undefined`와 `[]`는 완전히 다른 값이다. 빈 상자를 준 것과 상자 자체를 안 준 것의 차이.

설계 의도: 개발자가 배열을 깜빡 빠뜨렸을 때 코드가 **조용히 아무것도 안 하면** 버그를 못 찾는다. 차라리 자주 실행돼서 눈에 띄는 게 낫다.

### 왜 빈 배열은 "같음"인가

React가 비교하는 건 **배열끼리가 아니라 배열 안의 값들끼리**다.

```
[count]:  이전 [3] vs 지금 [7]  → 0번째 칸 다름 → 실행
[]     :  이전 [ ] vs 지금 [ ]  → 비교할 칸 없음 → 실행 안 함
```

`[] === []`는 `false`지만, React는 배열을 `===`로 비교하지 않는다. **상자는 안 보고 내용물만 본다.**

### 실행 예시

```jsx
useEffect(() => { console.log('A'); });          // 배열 없음
useEffect(() => { console.log('B'); }, []);      // 빈 배열
useEffect(() => { console.log('C'); }, [count]); // count
```

```
처음 렌더:          A B C
count 변경:         A C        (B는 빈 배열이라 안 함)
name만 변경:        A          (C도 안 함, count가 안 바뀜)
```

### 참조 비교 함정

```jsx
function Chat({ options }) {   // options = { room: 'general' }
  useEffect(() => { connect(options); }, [options]);   // ✗ 매번 실행
}
```

부모가 리렌더될 때마다 새 객체가 만들어져 참조가 달라진다.

```jsx
useEffect(() => { connect(options.room); }, [options.room]);   // ✓ 문자열
```

**원시 타입을 의존성에 넣는 게 안전하다.** 객체/함수를 넣어야 하면 `useMemo`/`useCallback`으로 참조를 고정한다.

## 8-3. cleanup 함수

```jsx
useEffect(() => {
  const id = setInterval(() => console.log('tick'), 1000);
  return () => clearInterval(id);   // ← cleanup
}, []);
```

### 호출 시점 두 가지

```
① 컴포넌트가 사라질 때 (언마운트)
② 다음 effect가 실행되기 직전
```

`roomId`가 'A' → 'B'로 바뀌면:

```
1. disconnect('A')   ← 이전 effect의 cleanup 먼저
2. connect('B')      ← 새 effect
```

**항상 정리 후 실행.** cleanup이 이전 값을 아는 건 **클로저로 박제**되었기 때문.

### 대표 케이스

```jsx
// 타이머
return () => clearInterval(id);

// 이벤트 리스너
useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener('resize', onResize);
  return () => window.removeEventListener('resize', onResize);
}, []);

// race condition 방지
useEffect(() => {
  let 유효 = true;
  fetch(url).then(r => r.json()).then(data => {
    if (유효) setData(data);     // 이미 바뀐 뒤면 무시
  });
  return () => { 유효 = false; };
}, [url]);
```

## 8-4. 실행 타이밍

```
1. 컴포넌트 함수 실행 (렌더)
2. 가상 DOM diff
3. 실제 DOM에 커밋
4. useLayoutEffect 실행      ← 동기, 화면에 그려지기 전
5. 브라우저 리플로우/리페인트  ← 사용자가 화면을 봄
6. useEffect 실행             ← 비동기, 화면에 그려진 후
```

**`useEffect`는 화면에 그려진 후 비동기로 실행된다.** 무거운 작업이 화면 표시를 막지 않게 하기 위해서.

### 그래서 반짝임이 생긴다

```jsx
useEffect(() => {
  const rect = ref.current.getBoundingClientRect();
  setTop(rect.top - 50);
}, []);
```

```
1. top = 0 으로 그려짐
2. 화면에 표시됨          ← 사용자가 잘못된 위치를 봄
3. useEffect 실행 → setTop
4. 다시 그려짐 → 올바른 위치
```

### useLayoutEffect

```jsx
useLayoutEffect(() => {
  const rect = ref.current.getBoundingClientRect();
  setTop(rect.top - 50);
}, []);
```

```
1. top = 0 으로 커밋 (아직 화면 안 나감)
2. useLayoutEffect 실행 → setTop → 즉시 다시 렌더+커밋
3. 화면에 표시됨          ← 처음부터 올바른 위치
```

| | 실행 시점 | 화면을 막는가 |
|---|---|---|
| `useEffect` | 페인트 **후**, 비동기 | 안 막음 |
| `useLayoutEffect` | 페인트 **전**, 동기 | 막음 |

**기본은 `useEffect`.** "측정 후 즉시 보정해야 하는 경우"에만 `useLayoutEffect`를 쓴다 (툴팁/드롭다운 위치, 스크롤 복원).

## 8-5. StrictMode 이중 실행

개발 모드 StrictMode에서 effect가 **두 번 실행된다.** React 18부터 의도적으로 그렇게 만들었다. "cleanup을 제대로 짰나" 검사하는 장치. 실서비스 빌드에서는 한 번만 실행된다.

## 8-6. useState vs useEffect

| | `useState` | `useEffect` |
|---|---|---|
| **목적** | 값 기억하기 | 일 시키기 |
| **넣는 것** | 초기값 | 함수 (+ 의존성 배열) |
| **받는 것** | `[값, 바꾸는함수]` | 없음 |
| **실행 시점** | 화면 그리는 중 | 화면 다 그린 후 |
| **다루는 것** | 명사 | 동사 |

가장 흔한 조합:

```jsx
const [데이터, set데이터] = useState(null);     // 담을 그릇
useEffect(() => {                              // 채우러 다녀오기
  서버요청().then(set데이터);
}, []);
```

# PART 9. useRef

## 9-1. current 칸이 있는 상자

```jsx
const ref = useRef(0);
console.log(ref);   // { current: 0 }
```

컴포넌트가 살아있는 동안 **계속 같은 객체**다. 리렌더돼도 새로 안 만들어진다.

## 9-2. 가변(Mutable)

```jsx
ref.current = 5;    // 그냥 바꿈. 정상.
```

`useState`와 정반대다.

```jsx
count = 5;          // ✗
setCount(5);        // ✓ 함수로만
```

## 9-3. DOM 다루기

```jsx
const inputRef = useRef(null);
<input ref={inputRef} />

inputRef.current.focus();                      // 포커스
inputRef.current.getBoundingClientRect();      // 크기 측정
inputRef.current.scrollTo({ top: 0 });         // 스크롤
```

React가 커밋할 때 실제 DOM 노드를 `current`에 넣어준다. `document.getElementById` 대신 쓰는 방법.

## 9-4. 리렌더를 유발하지 않는다

```jsx
const ref = useRef(0);
<button onClick={() => { ref.current++; }}>{ref.current}</button>
// 값은 바뀌지만 화면은 0에서 안 바뀜
```

`ref.current = 5`는 **평범한 JS 객체 프로퍼티 대입**이다. React에게 아무 신호도 안 보낸다.

## 9-5. 화면과 무관한 값 붙잡기

```jsx
const 타이머id = useRef(null);
const 시작 = () => { 타이머id.current = setInterval(...); };
const 정지 = () => { clearInterval(타이머id.current); };
```

**`useRef`는 DOM 참조 전용이 아니다.** "값이 바뀌어도 리렌더를 일으키지 않는 저장소"로도 쓴다.

| | 리렌더 유발 | 용도 |
|---|---|---|
| `useState` | ✓ | 화면에 **보여야 하는** 값 |
| `useRef` | ✗ | 화면과 **무관한** 값 |

판별법: **"이 값이 바뀌면 화면이 바뀌어야 하나?"**

## 9-6. 의존성 배열에 넣을 수 없다

```jsx
useEffect(() => { ... }, [ref.current]);   // ✗ 작동 안 함
useEffect(() => { ... }, [ref]);           // ✗ 이것도 안 됨
```

**이유 ①**: `.current`를 바꿔도 리렌더가 안 일어난다 → 의존성 비교 시점 자체가 오지 않는다.

**이유 ②**: `ref` 객체 자체는 **항상 같은 참조**다. `current`만 바뀌지 상자는 안 바뀐다 → `Object.is`가 항상 `true`.

**감지가 필요하면 애초에 `useState`를 써야 한다.** 두 훅의 용도가 정반대라서 `useRef`를 의존성에 넣는 발상 자체가 모순이다.

# PART 10. 성능 최적화 3종

## 10-1. 전제 — 부모가 리렌더되면 자식도 리렌더된다

```jsx
function 부모() {
  const [count, setCount] = useState(0);
  return <>
    <button onClick={() => setCount(count + 1)}>{count}</button>
    <자식 />        {/* count와 무관한데도 다시 실행됨 */}
  </>;
}
```

**리렌더 = 함수 재실행**이므로 `<자식 />` 줄도 다시 실행된다. React는 "자식이 바뀔 필요가 있나?"를 판단하지 않는다.

대부분 괜찮다 — 결과가 같으면 diff에서 걸러진다. 하지만 자식이 무겁거나 개수가 많으면 낭비다.

## 10-2. React.memo — 문지기

```jsx
const 자식 = React.memo(function 자식({ 이름 }) { ... });
```

규칙은 하나: **"아까 받은 props랑 똑같으면 안 들여보낸다."**

```js
Object.is(이전props.이름, 새props.이름)
// 전부 같으면 → 함수를 아예 안 부름
```

### 고차 컴포넌트(HOC)란

> 컴포넌트를 받아서, 기능을 덧붙인 새 컴포넌트를 돌려주는 함수

포장지를 한 겹 씌우는 것. 안쪽은 그대로고 바깥에 문지기를 추가한 것이다.

## 10-3. 문지기만으로는 안 되는 이유

```jsx
function 부모() {
  const 클릭 = () => console.log('안녕');   // 매 렌더마다 새 함수
  return <자식 onClick={클릭} />;
}
```

```
1번째 렌더: 함수 A 만듦 → 자식에게 A 전달
2번째 렌더: 함수 B 만듦 → 자식에게 B 전달   (내용은 같지만 다른 물건)
3번째 렌더: 함수 C 만듦 → 자식에게 C 전달

문지기: A와 B는 다름 → 통과
        B와 C는 다름 → 통과
```

**문지기가 일을 못한 게 아니다. 규칙대로 정확히 판단했다.** 매번 진짜로 다른 물건이 왔기 때문.

똑같이 생긴 열쇠 두 개 — 모양은 같지만 물리적으로 별개다. 문지기는 "모양이 같나"가 아니라 "아까 그 물건인가"를 본다.

## 10-4. useCallback — 창고에서 꺼내주기

```jsx
const 클릭 = useCallback(() => console.log('안녕'), []);
```

```
1번째 렌더: 함수 A 만들어 창고에 넣음 → A 전달
2번째 렌더: 창고에서 A 꺼냄 → A 전달
3번째 렌더: 창고에서 A 꺼냄 → A 전달

문지기: 아까 그 A네 → 차단 ✓
```

### 창고는 Fiber, useCallback은 창구

**`useCallback`을 쓴다고 함수 생성이 막히는 게 아니다.**

```jsx
useCallback(() => console.log('안녕'), []);
//          ^^^^^^^^^^^^^^^^^^^^^^^^^ 이 함수는 매 렌더마다 새로 만들어짐
```

`useCallback`이 그걸 받아서 **"창고에 있는 옛것을 대신 돌려주는" 것**이다. 새로 만든 건 버려진다. 만드는 걸 막는 게 아니라 **결과를 바꿔치기**한다.

### 의존성이 필요한 경우

```jsx
const 삭제 = useCallback(() => { 서버에요청(userId); }, [userId]);
```

`userId`를 붙잡고 있는데 그게 바뀌었는데도 옛 함수를 쓰면 **옛날 값으로 요청**을 보낸다.

## 10-5. useMemo — 계산 결과 저장

```jsx
const 필터결과 = useMemo(() => {
  return 항목들.filter(x => x.이름.includes(검색어));
}, [항목들, 검색어]);
```

### 두 가지 용도

**① 무거운 계산 아끼기**

```jsx
const 결과 = useMemo(() => 백만개_정렬(데이터), [데이터]);
```

**② 참조 고정하기** (실은 이 용도가 더 많다)

```jsx
// ✗ 매번 새 객체 → memo 무력화
<자식 설정={{ 색: '빨강' }} />

// ✓
const 설정 = useMemo(() => ({ 색: '빨강' }), []);
<자식 설정={설정} />
```

### 셋의 관계

```jsx
useCallback(fn, deps)  ===  useMemo(() => fn, deps)
```

**`useCallback`은 `useMemo`의 함수 전용 버전**이다.

## 10-6. 세트로 써야 작동한다

| 위치 | 도구 | 역할 |
|---|---|---|
| 부모 | `useCallback` / `useMemo` | **참조를 고정**해서 props가 안 바뀌게 |
| 자식 | `React.memo` | 바뀐 게 없으면 **실행 안 함** |

```jsx
// ✗ 문지기만  → 매번 다른 물건이라 통과. 효과 없음
// ✗ 창고만    → 확인할 사람이 없어 그냥 통과. 효과 없음
// ✓ 둘 다     → 같은 물건 + 확인 → 차단
```

**부모가 재료를 안 바꿔야, 자식이 문을 닫을 수 있다.**

## 10-7. 남발하면 안 되는 이유

**비용 ① 비교 연산**

```jsx
const 합 = useMemo(() => a + b, [a, b]);
```

덧셈보다 의존성 배열 만들기 + `Object.is` 비교가 더 비싸다.

**비용 ② 메모리** — 저장값과 이전 의존성 배열을 계속 들고 있어야 한다.

**비용 ③ 자주 바뀌면 무용지물** — 매번 다시 계산하는데 저장·비교 비용만 추가된다.

**비용 ④ 코드 복잡도** — 의존성을 빠뜨리면 오래된 값을 붙잡는 버그가 생긴다.

> **원칙: 먼저 측정하고, 문제가 확인된 곳에만 적용한다.** React DevTools Profiler로 확인 후 적용. "혹시 몰라서" 붙이는 건 대부분 손해.

## 10-8. 최적화 도구와 층위

| 층 | 도구 | 아끼는 것 |
|---|---|---|
| Component 호출 | `React.memo` | 함수 실행 자체 |
| Element 생성 | `useMemo`, `useCallback` | 참조 동일성 유지 → 위 memo가 작동하게 함 |
| Fiber 매칭 | `key` | 불필요한 폐기/재생성 |
| DOM 조작 | (React가 자동으로) | 실제 DOM 호출 횟수 |

# PART 11. Context API

## 11-1. Props Drilling 문제

```jsx
function 앱() {
  const 사용자 = { 이름: '지나' };
  return <레이아웃 사용자={사용자} />;
}
function 레이아웃({ 사용자 }) { return <사이드바 사용자={사용자} />; }  // 안 쓰는데 넘김
function 사이드바({ 사용자 }) { return <프로필 사용자={사용자} />; }    // 여기도
function 프로필({ 사용자 }) { return <div>{사용자.이름}</div>; }        // 드디어 사용
```

중간 컴포넌트가 배달원이 된다. 데이터 하나 추가하려면 경로의 모든 컴포넌트를 수정해야 한다.

## 11-2. Context = 방송

```
Props Drilling:  손 → 손 → 손 → 손 (한 칸씩)
Context:         방송국 → 듣고 싶은 사람이 직접 수신
```

```jsx
// ① 채널 개설
const 사용자Context = React.createContext(null);

// ② 방송
<사용자Context.Provider value={사용자}>
  <레이아웃 />      {/* props 안 넘김 */}
</사용자Context.Provider>

// ③ 수신
function 프로필() {
  const 사용자 = useContext(사용자Context);
  return <div>{사용자.이름}</div>;
}
```

범위는 **Provider 안쪽뿐**이다. 바깥은 못 듣는다. `createContext(null)`의 `null`은 Provider가 없을 때 나오는 기본값.

## 11-3. React.memo가 통하지 않는다

```jsx
const 프로필 = React.memo(function 프로필() {
  const 사용자 = useContext(사용자Context);   // ← 정문을 안 거침!
  return <div>{사용자.이름}</div>;
});
```

```
      부모
       │
   [props] ──▶ 🚪 문지기(React.memo) ──▶ 자식
                                          ▲
   [Context] ─────────────────────────────┘
                문지기를 안 거침
```

`React.memo`는 **정문에서 props만 검사**한다. Context는 props로 들어오지 않고 컴포넌트 안에서 직접 꺼내온다.

React는 별도 통로로 처리한다.

```
value 바뀜 → 구독 중인 컴포넌트 목록 확인 → 전부 강제 리렌더
             (React.memo 무시, props 비교 안 함)
```

**논리적으로도 당연하다.** 구독했다는 건 "바뀌면 알려달라"는 뜻이고, 안 알려주면 화면에 옛 값이 남는 버그가 된다.

## 11-4. Provider value에 useMemo를 쓰는 이유

```jsx
<사용자Context.Provider value={{ 사용자, set사용자 }}>
//                            ^^^^^^^^^^^^^^^^^^^^^ 매 렌더마다 새 객체
```

내용이 하나도 안 바뀌어도 참조가 달라져 **구독자 전원이 리렌더**된다.

```jsx
const value = useMemo(() => ({ 사용자, set사용자 }), [사용자]);
<사용자Context.Provider value={value}>
```

> `set사용자`는 의존성에 안 넣어도 된다. React가 setState 함수의 참조를 항상 고정해준다.

**원시 타입(문자열, 숫자)을 value로 주면 필요 없다.** 값 자체를 비교하므로 참조 문제가 없다.

## 11-5. Context를 여러 개로 쪼개는 이유

```jsx
<앱Context.Provider value={{ 사용자, 테마, 알림, 장바구니 }}>
```

**넷 중 하나만 바뀌어도 구독자 전원이 리렌더**된다. Context는 "value가 바뀌었나"만 보지 "어느 것이 바뀌었나"는 구분하지 못한다.

```jsx
<사용자Context.Provider value={사용자}>
  <테마Context.Provider value={테마}>
    <장바구니Context.Provider value={장바구니}>
```

### 특히 중요한 분리 — 값과 함수

```jsx
<상태Context.Provider value={할일목록}>        {/* 자주 바뀜 */}
  <함수Context.Provider value={{ 추가, 삭제 }}>  {/* 안 바뀜 */}
```

"할 일 추가 버튼"은 `추가` 함수만 필요하지 목록은 필요 없다. 묶여있으면 목록이 바뀔 때마다 버튼까지 리렌더된다.

## 11-6. Context vs Redux vs Zustand

| | Context | Redux | Zustand |
|---|---|---|---|
| 정체 | React 내장 **전달 통로** | 상태관리 라이브러리 | 상태관리 라이브러리 |
| 설치 | 불필요 | 필요 | 필요 |
| 코드량 | 적음 | 많음 (action, reducer) | 적음 |
| **부분 구독** | ✗ | ✓ | ✓ |
| 개발 도구 | 없음 | 강력 (타임머신 디버깅) | 있음 |

### 핵심 차이 — 부분 구독

```jsx
// Context: 일부만 골라 듣기 불가
const { 사용자, 테마 } = useContext(앱Context);
// 사용자만 쓰는데도 테마가 바뀌면 리렌더

// Zustand: 가능
const 사용자 = useStore(state => state.사용자);
// 사용자가 바뀔 때만 리렌더
```

### 선택 기준

**Context로 충분**
- 값이 거의 안 바뀜 (테마, 언어, 로그인 사용자)
- 앱 규모가 작음
- Props Drilling만 해결하면 됨

**라이브러리 필요**
- 값이 자주 바뀌고 구독자가 많음
- 상태가 복잡하게 얽힘
- 변경 추적이 필요함
- 서버 데이터 캐싱까지 필요 (이건 TanStack Query 영역)

> **Context는 전달 도구지 상태 관리 도구가 아니다.** 담을 수는 있지만 최적화 기능이 없다.

# PART 12. 폼 — 제어 vs 비제어

## 12-1. 전제 — input은 원래 스스로 값을 기억한다

```html
<input type="text" />
```

아무 코드 없이도 타이핑하면 값이 보인다. **브라우저가 실제 DOM 노드 안에 값을 담아두기 때문.**

```js
document.querySelector('input').value;   // '빨래'
```

## 12-2. 기억 장치가 두 개다

```
① 브라우저의 input 안 (.value)
② React의 Fiber (useState)
```

**값을 어디에 둘 것인가?** 이 선택이 제어/비제어를 가른다.

| | 값이 사는 곳 | 이름 |
|---|---|---|
| input이 알아서 관리 | 브라우저 (DOM) | **비제어** |
| React가 관리 | Fiber | **제어** |

"제어(control)" = "React가 통제한다".

## 12-3. 비제어 컴포넌트

```jsx
function 폼() {
  const 입력창ref = useRef(null);
  const 제출 = () => { console.log(입력창ref.current.value); };
  return <>
    <input ref={입력창ref} />
    <button onClick={제출}>제출</button>
  </>;
}
```

```
타이핑 → 브라우저가 알아서 화면 갱신 (React는 모름, 리렌더 없음)
제출 클릭 → 그제서야 .value 꺼내옴
```

## 12-4. 제어 컴포넌트

```jsx
function 폼() {
  const [값, set값] = useState('');
  return <input value={값} onChange={e => set값(e.target.value)} />;
}
```

```
타이핑 → onChange → set값 → Fiber 저장 → 리렌더 → value 갱신 → 화면
   ↑                                                          │
   └──────────────────────────────────────────────────────────┘
```

### 중요: 사용자가 타이핑해도 input은 저절로 안 바뀐다

`value={값}`을 쓰는 순간 input은 **React가 시키는 것만 보여주는 화면**이 된다.

```jsx
<input value={값} />   {/* onChange 없음 → 아예 입력 안 됨 */}
```

자물쇠를 채우고 열쇠를 안 준 상태. `onChange`가 그 열쇠다.

## 12-5. 제어 방식의 이점

```jsx
// 실시간 검사
onChange={e => {
  set값(e.target.value);
  set에러(e.target.value.includes('@') ? '' : '이메일 형식이 아닙니다');
}}

// 입력 제한 — 문자를 쳐도 화면에 나타나지도 않음
onChange={e => set값(e.target.value.replace(/[^0-9]/g, ''))}

// 다른 요소와 연동
<button disabled={값.length < 5}>제출</button>
```

## 12-6. 비교표

| | 제어 컴포넌트 | 비제어 컴포넌트 |
|---|---|---|
| 값이 사는 곳 | React (Fiber) | DOM (input 안) |
| 쓰는 훅 | `useState` | `useRef` |
| 필수 속성 | `value` + `onChange` | `ref` |
| 타이핑할 때 | 매번 리렌더 | 리렌더 없음 |
| 실시간 검사 | 쉬움 ✓ | 어려움 |
| 코드량 | 많음 | 적음 |

## 12-7. 실무에서는

**비제어를 쓰는 경우**

1. **값이 제출 때만 필요할 때** — 검색창 등
2. **파일 업로드** — `<input type="file">`은 보안상 `value` 설정이 금지되어 **제어 불가**
3. **필드가 아주 많을 때** — 30개 필드가 매 글자마다 리렌더되면 버벅임

**현실적으로는 폼 라이브러리를 쓴다.** React Hook Form이 실무 표준에 가까운데, 내부적으로 비제어 방식(ref)을 쓰면서 유효성 검사를 지원한다. **비제어의 성능 + 제어의 편의.**

```jsx
const { register, handleSubmit } = useForm();
<input {...register('이메일')} />   // 내부에서 ref를 붙임
```

| 상황 | 선택 |
|---|---|
| 실시간 검사·입력 제한·연동 | **제어** |
| 파일 업로드 | **비제어** (강제) |
| 값이 제출 때만 필요 | 비제어 OK |
| 필드 많고 버벅임 | React Hook Form |
| 그 외 대부분 | **제어** (기본값) |

# PART 13. 시험 문제 요약

## Q1. 가상 DOM — 정답 4번

> "가상 DOM을 쓰면 항상 모든 상황에서 물리적으로 메모리를 덜 사용한다" (✗)

**근거**: 가상 DOM은 메모리를 **추가로** 쓴다. 실제 DOM + 가상 DOM 트리(그것도 Fiber 더블 버퍼링으로 두 벌). 목적은 메모리 절약이 아니라 **DOM 조작 횟수 최소화**다.

**시험 팁**: "항상", "모든 상황에서", "반드시" 같은 절대 수식어는 오답 신호.

## Q2. JSX — 정답 4번

> "`if`문이나 `for`문을 중괄호 `{}` 안에 직접 작성할 수 있다" (✗)

**근거**: `{}` 안은 `createElement`의 **인자 자리**라 값으로 평가되는 **표현식**만 온다. `if`/`for`는 **문(statement)**이라 불가.

**대안**: 삼항 연산자, `&&`, `map()`, JSX 밖에서 분기 후 변수로 넘기기.

## Q3. useState — 정답 5번

> "`state.push(item)` 후 `setState(state)`를 호출하면 React가 변경을 정상 감지한다" (✗)

**근거**: React는 `Object.is` **참조 비교**로 감지한다. `push`는 주소를 바꾸지 않으므로 "안 바뀜"으로 판정된다. 전개 연산자로 **새 객체/배열**을 만들어야 한다.

## Q4. useEffect — 정답 5번

> "`useEffect`는 렌더링되기 직전(동기)에 실행되므로 화면 반짝임을 완전히 방지한다" (✗)

**근거**: `useEffect`는 브라우저가 **화면을 그린 후 비동기**로 실행된다. 반짝임을 막으려면 페인트 전 동기 실행되는 `useLayoutEffect`가 필요하다.

## Q5. key — 정답 4번

> "자식 컴포넌트 내부에서 `props.key`로 접근할 수 있다" (✗)

**근거**: `key`는 Element 객체에서 `props`와 **별도의 자리**에 저장되는 React 전용 값이다. React는 `element.type(element.props)`로 props만 넘긴다. 필요하면 `id={...}`로 한 번 더 넘겨야 한다.

## Q6. 제어/비제어 — 정답 4번

> "비제어 컴포넌트에서는 `useRef`를 사용하여 submit 시점에 DOM에서 직접 값을 추출한다" (✓)

나머지는 제어/비제어 설명을 **서로 바꿔치기한 함정**이다.

| 선지 | 실제로는 |
|---|---|
| 1 (제어 = DOM이 관리) | 비제어의 설명 |
| 2 (비제어 = useState) | 제어의 설명 |
| 3 (제어 = useRef) | 비제어의 설명 |
| 5 (실시간 검사는 비제어가 유리) | 정반대 |

## Q7. 성능 최적화 — 정답 5번

> "사용하면 할수록 무조건 성능이 좋아지므로 모든 곳에 적용하는 것이 바람직하다" (✗)

**근거**: 메모이제이션은 **비교 연산 + 메모리 유지 비용**이 든다. 가벼운 계산이나 자주 바뀌는 값에 남발하면 이점보다 비용이 커진다. 측정 후 선별 적용해야 한다.

## Q8. Context — 정답 5번

> "`React.memo`로 감싼 하위 컴포넌트는 Context 값 변화를 무시하고 리렌더링되지 않는다" (✗)

**근거**: Context 값은 **props 경로를 우회하는 별도의 구독 통로**로 전달된다. `React.memo`는 props만 검사하므로 막을 수 없고, 구독 중인 컴포넌트는 **무조건 리렌더**된다.

## Q9. useRef — 정답 5번

> "`useEffect`의 의존성 배열에 ref를 추가하면 변경 시점마다 감지할 수 있다" (✗)

**근거 ①**: `.current` 변경은 리렌더를 유발하지 않아 **의존성 비교 시점 자체가 오지 않는다.**
**근거 ②**: `ref` 객체는 **항상 같은 참조**라 `Object.is`가 항상 `true`다.

감지가 필요하면 `useState`를 써야 한다. 두 훅의 용도가 정반대다.

# 핵심 관통 개념

전체를 관통하는 개념은 **참조 비교(`Object.is`)** 하나다.

| 어디서 | 무엇을 비교 | 틀리면 생기는 일 |
|---|---|---|
| `setState` | 옛 상태 vs 새 상태 | `push` 후 리렌더 안 됨 |
| `useEffect` 의존성 | 이전 배열 vs 새 배열 | 객체를 넣으면 매번 실행 |
| `React.memo` | 이전 props vs 새 props | 함수 props로 무력화 |
| `useMemo`/`useCallback` | 이전 의존성 vs 새 의존성 | 참조 고정 실패 |
| Context `value` | 이전 value vs 새 value | 객체 리터럴로 전원 리렌더 |

그리고 React의 두 가지 대원칙:

1. **React는 감시하지 않는다. 통보받는다.** — 값이 바뀌었다고 알려줘야만 안다.
2. **리렌더 = 함수 재실행.** — 모든 지역 변수와 함수가 새로 만들어진다. 그래서 클로저로 값이 박제되고, 참조가 매번 달라진다.

이 둘에서 거의 모든 함정이 파생된다.
